# DressCode internals

How DressCode works: the facts an agent or a contributor needs before touching the engine, a rule or the configuration. The catalog of rules is not here; it is generated from the rules themselves.

## Layers

- `phpsyntax/phpsyntax` (namespace `PhpSyntax`, a repository of its own): lexer, parser, tree, printer, navigation, mutation. Its internals are documented there; what a rule of DressCode uses from it is below.
- `DressCode` (`src/`): engine, rules API, rules, configuration, CLI. Rules use only the public API of `PhpSyntax`; whatever a built-in rule needs from it is public API for plugins too.

The public, semver-stable surface of `DressCode` is `Config` with `Profile`, `Override` and `Extension`, `Rule` with `NodeRule` and `GapRule`, `ConfigurableRule`, `Claim`, `Space`, `Line`, `Gap` and `Style`, `RuleInfo`, `RuleContext`, `Preset`, `PresetInfo`, `Presets\*`, `Violation`, the enums `Stage` and `Severity`, the exceptions of `exceptions.php` and `Testing\exceptions.php`, `Reporter` with `FileResult`, `RunResult` and `Reporters\*`, `Runner`, `Console\Application` with `Console\UsageException`, `Config\Loader`, `Config\ResolvedConfig` and `Config\ResolvedRule`, `Analyses\*`, `Rules\*` and `Testing\RuleTester`. `Engine\*`, `Interop\*` and the rest of `Config\*` and `Console\*` are `@internal`, as are `Helpers`, `Rules\NodeHelpers`, `Rules\BlankLines`, `Rules\Namespaces\NameReferences`, `Rules\Classes\ClassReplacement`, `Analyses\Registry`, `Analyses\PhpSymbolsData`, `Analyses\PhpSignaturesData` and `Testing\GapSurvey`; the constructors of `Gap` and `RuleContext` and the methods marked `@internal` (`RuleContext::reportGap()`, `hasReports()`, `takeReports()`, `Profile::toSymbolKey()`) are the engine's alone.

## The tree a rule works with

Printing the tree reproduces the input byte for byte, so a rule changes what it means to change: formatting rules change trivia, structural rules change nodes.

- Whitespace, comments and open tags are `Trivia` attached to tokens. **Trailing trivia** of a token is everything after it up to and including the first end of line, **leading trivia** of the next token is everything else (blank lines, indentation, comments on their own lines, doc comments). An `OpenTag` trivia (`<?php` with its mandatory whitespace) is always leading trivia of the following token; the final `EndOfFile` token has only leading trivia.
- `<?php` is not a token. `?>` is a token of kind `CloseTag` that keeps the newline PHP swallows after it, and the parser sees it as `;`; after a terminated statement it forms an `EmptyStatementNode`. `<?=` is a token of kind `OpenTagWithEcho` seen as `echo`. `Token::isSemicolon()` and `isOpenTagWithEcho()` cover these cases.
- Whitespace that PHP counts as part of a token stays in its text: inline HTML, `T_ENCAPSED_AND_WHITESPACE`, heredoc delimiters (the closing one keeps its indentation), casts like `( int )`. A BOM or a hashbang line is inline HTML, as PHP sees it. A single-line comment never contains its newline, but it does contain trailing spaces before it.
- Trivia inside string interpolation (`"{$a /* c */ }"`) carry `inInterpolation = true`; the token helpers refuse to change them because that whitespace is part of the string value.
- Slots are named by role (`ifKeyword`, `openParen`, `semicolon`, `condition`, `body`), paired delimiters are always `open*`/`close*`, lists are plural. A slot says what stands in it rather than what the class suggests, so the left of an assignment is `target` and not a variable, and what a `switch` and a `match` compare against is `subject` and not a condition. Every token of the source has a slot or a place in a list, so the order and number of children are not part of the API, only the slot names. Whoever names a slot instead of reaching for it writes the name as a string (`'openParen'`, `'statements:item'`), which is what a gap rule declares its claims with.
- The body of a control structure is a `StatementNode`, not necessarily a block; `else if` is an `ElseNode` whose body is an `IfNode`. The alternative syntax uses the same classes with `colon`, `statements`, `endKeyword` and `semicolon` slots instead of `body`. Class-like declarations implement `ClassLikeNode`, because an anonymous class is not a statement.
- A new node comes from `Parser::parseExpression()`, `parseStatement()`, `parseType()` or `parseName()`, which return it detached, with empty trivia on its edges and without original positions, or, where it is put together from nodes already at hand, from the `of()` factory of its class (`FunctionCallNode`, `MethodCallNode`, `StaticMethodCallNode`, `NewNode`, `ArgumentListNode`, `ParenthesizedNode`), so that a rule does not parse a template with a `0` in it to hunt the placeholder down afterwards; a constructor is public but its parameters follow the slots of the grammar, which a minor release may add to, so a call spells them as named arguments.

## Analyses

An analysis is information derived from a file, and any class the engine can build is one: `NameResolver` (namespace, imports, resolution of class, function and constant names with the runtime fallback of unqualified functions and constants to the global namespace, `isGlobalFunctionCall()`, and the way back: `getShortName()` gives the shortest way to write a fully qualified name where a node stands, through an alias, a prefix import or the namespace, and `isAliasFree()` says whether a name is still free there, which is what a rule adding an import asks), `Scope` (enclosing function-like construct and class, availability of `$this`, captured variables) and, in `DressCode`, `PhpDoc` (doc comments as phpstan/phpdoc-parser trees printed back with the original formatting) and `PhpSymbols` (what PHP declares: its functions with the version each is deprecated since, its classes, interfaces and enums in their declared case, its constants and the functions PHP 8.4 calls without a frame with their parameters, over PHP 8.0 to 8.5 and the extensions shipped with it, from the generated `PhpSymbolsData`; a PECL extension is not PHP and is not there).

Analyses are lazy and computed once per file. `Analyses\Registry`, reached through `RuleContext::getAnalysis()`, one for every combination of overrides, with the factories the `analyses` of the configuration and of its extensions give (given the `FileNode` and the path of the file), creates them on demand, with the `FileNode` when the constructor takes one, and throws them away as soon as `FileNode::$revision` changes, so any mutation invalidates every analysis of the file. An analysis implementing `Analyses\PassAnalysis` is the exception: computed at the beginning of a pass and kept over the mutations in it, because computing it anew after every mutation would cost more than the staleness, and dropped when `PassRunner` begins the next pass (`Registry::beginPass()`); a node inserted during the pass has no answer in it, and a rule asking for one asks with `?->`. `Analyses\Types` is one: the types of the code from the PHPStan of the project, the `phpstan/phpstan` in its vendor, which `RunnerFactory` wires when the configuration says `types: phpstan` and which is otherwise not there at all. The analysis prints the tree, has PHPStan's `currentPhpVersionRichParser` parse the text (`defaultAnalysisParser` routes a string to the simple parser, which drops the bodies of functions), runs `NodeScopeResolver::processNodes()` and maps every expression of PHPStan to the tree by its offsets (`TokenIndex::findNode()`, whose parity with php-parser PhpSyntax tests), so the map holds on the identity of the nodes and survives the mutations of the pass; only what PHPStan marks `@api` is used, through `Analyses\PhpStan`, which builds the container once per process from the `phpstan.neon` of the project. Starting it registers the Composer loader inside the phar, after which `Composer\InstalledVersions` answers with the packages, the versions and the root of the phar as well; `RunnerFactory` therefore reads the raw data of the project's own loader for the identity of a result and for the files no package holds. A rule asks questions (`findCallee()`, the member an access or a call reaches, decided by the class that declares it and not by the text, so that `$form::FILLED`, `MyForm::FILLED` and `self::FILLED` are one `Callee`; `getDeprecation()`, what its declaration says; `findOverridden()`, the member of a parent class or of an interface a method declaration overrides, for which the analysis maps the method declarations of PHPStan to the tree the same way it maps the expressions; `hasParentSignature()`, whether the parent class declares the method as the declaration does, so that no caller tells them apart; `findClassName()`, the declared spelling of a class the project, its packages or PHP declare, or null), and `getType()` answers in the words of PHPStan for what the questions do not cover, which binds the rule to PHPStan and is for the exception. PHPStan reads the declarations of a file from the disk, so the path the analysis gets must be a file holding them: the file of the run, or in `RuleTester` a file the text is written to, named by it. The path of a run is relative to the root, while PHPStan resolves a relative path against the working directory, which is another; `Analyses\PhpStan` therefore makes it absolute against the root before handing it over.

## Mutation from a rule

### Writing the tree

- A node or token belongs to exactly one tree: inserting one that already has a parent throws; `clone` gives a deep copy without a parent.
- A slot is written by assignment (`$node->condition = $expression`, `replaceChild()`, or `setSlot()` given the name of the slot), which adopts the value, releases the current one and tells the index. Lists mutate through `append()`, `insert()`, `removeItem()`, `replaceChild()`; `SeparatedNodeList::insert()` derives a missing separator from the existing ones (or `", "` in a one-line list) and gives the item the indentation of its neighbor in a multi-line list, `removeItem()` takes the separator after the item, or before the last one.
- `Node::remove()` removes a list item: a node alone on its lines takes the lines with it, otherwise the whitespace around stays; comments inside, each with the line ending after it, go to the next token, the previous token, or away, as the `CommentPolicy` says. `Node::replaceWith()` keeps the trivia around the old node around the new one by joining them with the new node's own edge trivia; a replacement cloned from nearby source still carries its original leading trivia, so that an `OpenTag` gets doubled; `Node::withoutEdgeTrivia()` is the copy without them, which is what a rule takes of whatever it writes into another place.
- What a rule reads is a property (`value`, `base`, `quote`, `label`, `indentation`, `kind`, `parts`, `role`, `text`), and it writes one where the write takes a single value with a single consequence: a slot, and `NameNode::$text`, whose hook tokenizes the name anew. It writes through a method where the write takes more values or two things change together (`StringNode::setValue($value, ?$quote)`, the delimiter deciding how the value is written), and for a token always, because `?->` cannot stand on the left of an assignment: `Token::setText()`, `setLeadingTrivia()`, `setTrailingTrivia()`, and `Node::setEdgeTrivia()` for the outer edges of a node, where the first or the last token may be missing.
- What has no hook the language guards: the text and the trivia of a token are `private(set)`, the items of a list `protected(set)`, `parent` is written by `attachTo()`. Such a property takes no indirect modification from outside, and neither does the hooked `leadingTrivia` or `trailingTrivia` of a node, so `end($token->trailingTrivia)`, which takes its argument by reference, needs a copy.
- Every mutation increments `FileNode::$revision`, which the engine reads to detect mutations; it is a version of the tree, not a count, because a compound mutation raises it several times. `Token::$originalLine` and `$originalOffset` never change and are the source of positions in reports; `getLine()` and `getColumn()` follow mutations.

### Comments and doc comments

- A single trivia (typically a comment) is removed by `Token::removeTrivia()`, which tidies the whitespace around it: one alone on its line takes the line with it, an inline one takes an adjacent space; `Token::replaceTrivia()` swaps one in place.
- A rule that must not destroy a comment asks `Token::hasComment()` (in the trivia of the token), `Token::hasCommentUpTo()` (anywhere between the texts of two tokens) or `Node::hasComment()` (inside the node, its outer edges excluded); `Token::getComments()` and `Node::getComments()` give what those count, and a `Trivia` says of itself whether it `isDocComment()`, `isLineComment()` or `isMultiLine()` and hands over its text without the delimiters as `getCommentText()`.
- A doc comment is read with `Node::getDocComment()` (above the node, or after the previous token) and, after editing through `Analyses\PhpDoc`, written back with `Node::replaceDocComment()` or dropped with `Node::removeDocComment()`. The tree is the phpstan/phpdoc-parser AST itself, which is therefore part of the public API (its major version is ours), and it is edited the way its format-preserving printer expects: replace `children` or return a new node from a visitor, never mutate a list such as `UnionTypeNode::$types` in place (it prints wrongly); a text node whose text changed loses its ` * ` line prefixes, so rewrite whole lines; a tree with nothing but blank text (`PhpDoc::isEmpty()`) is removed, not printed, or it prints `/**  */`. `NativeType` (annotation to native type) is the shared helper above the AST and `PhpDoc::findTemplates()` names the template types in scope, which a native type cannot use; there is no tag-editing layer of DressCode's own.

### What the rules share

- `Node::matches()` compares two nodes by their token texts and `ExpressionNode::isRepeatableRead()` tells whether reading an expression again is free of side effects; together they answer "does this assignment repeat its target". `ExpressionNode::isDereferenced()` tells whether the parent accesses a member or element of the expression, which is what decides whether parentheses around it can go.
- `Rules\NodeHelpers` holds the questions and constructions several rules need: whether an expression is a boolean by its form and its negation as a detached node, whether a block ends by leaving, the constructs that reach a variable by a name they do not spell out, the reason a global call is uncertain, the spelling of another global function in its place, whether a call is one PHP optimizes, adding an import, splitting a declaration of several items, and removing a member so that one gap stays of the two around it. A rule asks them rather than reimplementing them, and two of them carry what the name does not say: `negate()` flips an equality but never an ordering, which NAN makes false both ways, and a rule reasoning about the variables of a scope must respect `findDynamicVariableAccesses()` (`$$name`, `compact()`, `extract()`, `get_defined_vars()`, `eval`, `include`).
- Whether an expression a rule writes into a place needs parentheses there is not the rule's to decide: `ExpressionNode::replaceWithExpression()` puts it in and keeps the parentheses `ParenthesizedNode::isRedundant()` does not call needless, by the precedence of both sides and by what follows the place, and `ParenthesizedNode::of()` writes the ones a rule wants for the reader alone (`explicit-operator-precedence`). A rule with a list of operators of its own for that is a rule with an answer of its own.
- A rule that writes a call or a node of its own clones the arguments and the operands it keeps, and a clone brings the trivia of its edges along: the trailing trivia of the closing parenthesis belongs to what follows the call, which `replaceWith()` keeps on the node it replaces, so the clone must lose it or the space or the line ending comes twice. A fixture ending every call with a semicolon never shows it.
- `dresscode/replaced-functions` and `dresscode/replaced-classes` are tools the project fills with what it wants written instead, not policies with a list of their own, so their fix is not risky: what changes is what the project asked for, and only a call in a namespace that may reach a function of that namespace, where the code decides the target, is. A call is rewritten only where the replacement takes every argument of it, compared by the type at the position and by the name of a named argument (`Parameter::canReplace()`, not the name at the position, which `substr()` and `mb_substr()` spell differently for the same thing), no parameter the replacement needs is left out and the target version declares it; any other call is reported with `fixable: false`. Where either function is not PHP's own its parameters are unknown and the map is taken at its word. The rewrite of a class, its imports among the references, is `Rules\Classes\ClassReplacement`.
- A rule adding code writes it in the shape the other rules ask for, so that they find nothing to add. `NodeHelpers::addImport()` writes an import in the shape `dresscode/import-notation` gives its kind, asked through `RuleContext::findRule()`, which hands a rule another rule as configured for the file, or where that rule gives none the way the scope writes its imports, and puts it where the default order of ordered-imports does.
- `Rules\BlankLines` holds the schema of a count of blank lines in the options of a rule: a number, a range `[min, max]` (a `tuple`, with `null` for an open end) or `keep` to leave the place alone; the count is what a rule claims as the `blank` of a `Gap`, and the engine moves a count outside the range to its nearest bound.

### Names of global functions and constants

- `dresscode/name-notation` and `dresscode/name-fallback` split the writing of names by the transition, so that they never pull at one token: name-notation moves a qualified name between the import and the leading backslash and is never risky, name-fallback moves a global function or constant between bare and qualified, risky unless the resolution of names is certain. name-fallback writes a qualified name in the shape name-notation gives it (`findShape()`), and name-notation leaves a name name-fallback writes bare (`isWrittenBare()`) and adds no import a bare name would be taken over by; what both read of a namespace is `Rules\Namespaces\NameReferences`.
- The keys of name-fallback go from the general to the particular and the most particular that answers decides: `functions` and `constants` speak of every global function and constant, `optimizedFunctions` of a function PHP optimizes where a call of it is optimized with its arguments (`NodeHelpers::isOptimizedCall()`), and `optimizedConstants` of a constant of PHP where the compiler computes with it, which takes only `qualified` or `keep`. The compiler optimizes a call or puts a constant in place only for a name it knows to be global while compiling: qualified, imported, or in a file without a namespace.
- `dresscode/optimized-call-notation` writes a call PHP optimizes in the form the optimization takes: a named argument of a function PHP 8.4 calls without a frame positionally where it stands at the position of its parameter (`PhpSymbols::findFramelessParameters()`), and an unpacked argument is reported with no fix. The rules that write calls in the form PHP optimizes are the preset `dresscode/optimizations`, which no standard composes.

### Whitespace and indentation

- Horizontal whitespace between two tokens on a line is the trailing trivia of the first one, never the leading trivia of the second (a rule joining two lines writes the space there, or the next rule reading the gap sees none), and it is read and written through `Token::getTrailingSpace()` and `setTrailingSpace()`, which answer `null` and refuse where no such whitespace is there to write. `Token::is()` given a text never matches the content of a string, only operators and punctuation. `Token::getLineWidth()` measures a line visually, tabs by the tab width of the style.
- The style a rule gets from `RuleContext::getStyle()` and `Gap::$style` is `DressCode\Style`: the indentation, the line ending, the tab width and `lineLength`, the widest line that passes (null for none), which every rule that breaks or reports a long line reads instead of a threshold of its own. What PhpSyntax measures and writes whitespace with (`Indentation`, `Token::getLineWidth()`, `getVisualColumn()`) takes `PhpSyntax\Style`, which has no line length, and gets it from `toPhpSyntax()`.
- `Token::removeTrailingWhitespace()` also trims the end of a `//` or `#` comment, because the tokenizer counts the spaces before the line break as part of the comment text; a rule that calls it therefore changes a comment.
- Indentation is changed through `Indentation` and `Token::getLineIndentation()`; `Token::setIndentation()` alone moves one line and leaves the rest of the statement where it was. `Indentation::opensLine()` says whether the line ending above a token is trivia, which is the only case its indentation is whitespace a rule may write: `Token::startsLine()` also answers yes after inline HTML, a heredoc body or a close tag, and there the leading whitespace is text.

The indentation of every line is decided by one rule, `dresscode/indentation`, and it is a function of the tree alone: a line-opening token belongs to the lowest ancestor it does not begin (`Indentation::findOwner()`), the slot it stands in has a `LayoutRole` (`LayoutData`, which the syntax layer generates for every slot), and the line is placed by that role at a level counted from the level the rule gave the line the ancestor begins on, never read from the text. A line no rule governs (the first token of a file, the code after inline HTML, an operator the options leave alone) is a fact the lines below count from.

The rules that break a construct over lines (`braces-position`, `multi-line-call`, `multi-line-signature`, `multi-line-condition`, `multi-line-array`, `multi-line-chain`, `multi-line-ternary`, `single-statement-per-line`, `single-member-per-line`, `attribute-position`) are claims on the line breaks, and where the lines then stand is not their business; the engine gives an opened line the conventional indentation (`Indentation::infer()`), so that the shape is acceptable even when no rule about indentation runs. A rule that reads the indentation of a line to place another one reintroduces what this design removed: a wrong line that carries its neighbours with it and is a fixpoint afterwards.

Code between pieces of inline HTML (a template with `<?php if ($a) { ?>` around markup) begins on lines the markup opens, and what those lines have is text the rule counts from as it is: such a file is not laid out by the tree, and PER exempts templates as well.

### Gaps

The gap between two tokens (the whitespace when they share a line, the line break, the blank lines when there is one) is decided by claims rather than by procedures. A `GapRule` declares, per node class (or `*`) and slot (`'body'`, or `'statements:item'` for every item of a list, `'arguments:separator'` for its separators), the `Claim` it makes before and after the value of the slot: `space`, `line`, `blank`, `blankBelowComment`, each null when not claimed. The factories `Claim::single()`, `Claim::nextLine()`, `Claim::blank(1)` are the claims on one component, shared instances, and a rule with an option builds its claim once in `configure()`. Where the claim depends on the code (`?:`, `.` against the other operators, a keyword followed by `;`, the kind of the statement above) it is a closure given the `Gap`: the token at its edge, the value or item the claim was made for and its index in the list, the `Style`.

A claim of `*` applies to every class that has the slot, so it is right only where the slot means the same thing in all of them (the `openBrace` of a block is not the one of `$o->{$m}`, the `body` of a statement is not the one of a `match` arm), and elsewhere it names the classes. A claim must also be right on its own: the stricter claim wins only among the rules that are on, and a fixture runs its rule alone, so a claim right only thanks to another rule passes its fixture and breaks under a preset.

A claim that depends on the shape of the text (a list already broken, a line too long) must give every gap of the construct the same answer whatever the engine did to the gaps before it: the closure decides once per pass, from the shape the construct has when its first gap is reached (`Gap::once()`, which the engine remembers by rule and node until the pass ends, unlike `RuleContext::$storage`, which lives for the file), and a list counts as broken once any item or its closing delimiter begins a line, so that a decision to break it holds for the rest of the list.

`Engine\Gaps\Resolver` applies every gap rule along the traversal of the formatting stage: entering a node hands the claims to the first and last tokens of its slot values and to each item of a list, and reaching a token decides the gap before it component by component. The claim of a class goes before one of `*`, an inner slot before an ancestor's, the stricter space before the looser (`return;`), and of blank lines the count both sides allow or the narrower of two counts that exclude each other. When the two sides disagree about the line, `Line::Next` wins over `Line::Same`. What was decided goes to a `Gaps\Sink`: `Gaps\Fixer` reports under the name of the rule whose claim won and fixes, `Testing\GapSurvey` records what the rules govern for the whitespace fuzz; the messages of all three components are composed by `Gaps\Messages`.

Blank lines are counted above the comment that stands on lines of its own above a token, because the comment goes with the code below it, except above a token that closes a construct (`LayoutRole::Closes`) or the file, where the comment belongs to what is above and the blank lines below it are what is counted. The blank lines between the last comment in the gap and the token are a component of their own, `blankBelowComment`, which the rule about declarations claims for a doc comment, so that no rule reaches into the trivia of a token for them.

The open tag is trivia too, and the gap it stands in is decided like any other where the tag opens the code of the file (after nothing or a hashbang): a `Line::Next` there means the tag ends its line, which `blank-lines` claims; inside markup the tag's line is the template's and no rule breaks it.

A claim of no whitespace is a claim of a single space between two tokens the lexer would read as something else once they touch (`Lexer::canAdjoin()`): `- -$a` is not `--$a`, whatever a rule says about the space after an operator.

A required line break goes in first and the blank lines wait for the next pass, and a doc comment standing in front of the token on its line goes below with it, because it documents the token. A forbidden line break is taken out only when nothing but whitespace stands in the gap; where a comment stands there the claim is reported and left unfixed, and the settled round reports it again, so it is among what the fix leaves.

Two plain claims on the same component of the same side of the same slot are a `ConfigurationException` when the rules are put together, so a gap has one owner; closures may share a slot because each abstains where the other decides, a plain claim shares it only with a plain claim on other components. Put together is also where a claim is checked against the slots the tree has (`LayoutData::Roles`, the same table the resolver hands the claims out by): a claim on a slot no node has, or `:item` and `:separator` on a slot holding no such list, is a `ConfigurationException`, because a slot renamed in the tree would otherwise leave the rule claiming gaps that never reach it, and neither a type nor a fixture would say a word.

Two closures deciding one component on one side of one slot at the same gap are refused there, so rules whose closures share a slot abstain by a predicate they both read, not by two that happen to agree: `binary-operator-spacing` leaves the line around a boolean operator chaining a condition to `multi-line-condition`, both asking `NodeHelpers::findConditionStatement()`. Where no predicate can say which rule decides, a rule claims the break from the other side of the gap: `ternary-operator-spacing` claims the break in front of `?` and `:` after the operand before them, because the claim before the operator is `multi-line-ternary`'s.

A gap rule is made of claims alone: `GapRule` and `NodeRule` are the two shapes of `Rule`, a class is one or the other, and a rule that also has to change tokens is two rules (`attribute-spacing` and `useless-attribute-parentheses`). A gap nobody claims is left alone: the whitespace fuzz runs with every spacing rule on and exact to find such gaps.

### Traversal

`Node::getChildren()` is the children in source order, empty slots left out, and the only way to the children: a node is not iterable, except the lists (`NodeList`, `SeparatedNodeList`) over their items and `ModifiersNode` over its tokens, so that there is one way and it is an array, which the printer, the index and the traverser read directly. `Node::find()` takes a node class, optionally narrowed by a predicate, and gives the descendants it accepts as a snapshot safe to iterate while mutating; `Node::findFirst()` stops at the first one. The `Traverser` walks in pre-order; it does not descend into a node a callback replaced, skips siblings detached meanwhile and leaves inserted ones for the next walk.

## Rules and the engine

### Identity

A rule is one instance per run and stateless across files; per-file state lives in `RuleContext::$storage`. Its identity is the `#[RuleInfo]` name (`vendor/slug`); `RuleRegistry` maps names and classes and refuses a name owned by two classes. What a rule of another tool means here is not part of that identity: it lives in `DressCode\Interop`, where a translation carries the options too.

### Report before mutation

Every mutation must follow a `RuleContext::report()` that returned `true`. `PassRunner` pairs the two through `FileNode::$revision`: a callback that raised the revision without a report ("silent mutation") or after a report that returned `false` (silenced by a `dresscode:ignore` comment) breaks the contract; `strict` mode (RuleTester, `--strict-rules`) throws, otherwise it is a warning of the file. A denied report, by a comment or because the run refuses a risky fix, is judged by the window between it and the next report of the same rule, not by the whole callback, because a callback that reports many times may be denied one occurrence and allowed the next. Along the gap traversal the revision covers every rule of the stage, so the silent-mutation check is left out there: the whitespace of a gap is written by the engine and always after a report of its own.

What a fix leaves is not read from the reports at all: a rule may report every occurrence first and write its fixes afterwards, the whitespace of a gap is written for the whole traversal, and a rule may rewrite what another one reported, so no window of revisions says which report a mutation was for. `FileResult::$remaining` is what the rules report over the settled text instead, see below.

### Risk and consent

Risk is a property of the occurrence, not of the rule: `report(risky: true)` says that fixing this one may change what the code does, the violation is recorded either way, and `false` comes back until the run is allowed to make such a fix (the configuration names the rule in `fixRisky`, or `--fix-risky` on the command line allows every such fix). The rule then leaves the code alone, and the violation says `risky` and `refused` and stays among what the fix leaves, so the summary can offer the refused ones. Until it is fixed or in the baseline it is an error like any other, and a `dresscode:ignore` comment silences it like any other.

An occurrence the rule has no fix for is reported with `fixable: false`, which is never risky, never lets the rule mutate and is therefore never offered to the consent (`strict-call` on an explicit `false`, `type-hint-required` on a parameter with neither a type nor an annotation), and `RuleTester` fails a `// risky` fixture in which a risky violation remains, so a forgotten `fixable: false` is a failing test rather than a false offer.

**A risky fix may change what the code does; it may never write code that does not compile.** What only a file the run does not have could decide is therefore not risky but undecidable, and there the rule says nothing at all, because the consent of `fixRisky` cannot be asked for it: `readonly-class-for-readonly-members` marks a final class alone, since the children of any other would have to turn readonly with it, and `readonly-for-unwritten-property` a private property or any property of a final class, since a child may redeclare a protected one. Both are a fatal error in another file, not a change of behaviour in this one.

An unqualified call of a global function in a namespace is a risky occurrence wherever `NameResolver::getUnqualifiedResolution()` says `UnqualifiedResolution::Uncertain`, which `nameResolution: certain` of the project takes away, and the rule that rewrites it gives the reason after its message (`NodeHelpers::findUncertainty()`); a name the rule writes anew follows the name it replaces, or `NameResolver::getShortName()` where there is none.

A rule whose every fix may change what the code does, because the code cannot tell it a safe occurrence, says so once with `risky` in its `#[RuleInfo]` and `RuleContext` makes every report of it risky: `strict-call` adds `$strict = true`, which changes what a loose comparison found, and `static-closure` cannot see a later `bindTo()`. Turning such a rule on, by name or by a preset, is not consent to the change: the project gives it by naming the rule in `fixRisky`, for the whole tree or in an override for a part of it, which a preset cannot (the resolver refuses it), and `--fix-risky` gives it to every rule for one run. A hook therefore needs no switch of its own: it fixes what the project accepted and reports the rest. The reference marks a rule with such a fix from the attribute, or, for a rule risky per occurrence, from a fixture whose header says `// risky`, so no hand-kept list can go stale.

### Severity

Every violation is an error until the configuration softens it: the `warnings` of a profile name the rules whose violations only warn, `PassRunner` stamps the severity when it makes the violation, and `RunResult::getExitCode()` counts the errors and syntax errors alone, with `--max-warnings` as the only threshold the warnings can cross. `keep` on a rule says what `false` says.

### Passes

A pass is one pre-order traversal per stage (`Structure`, `Formatting`, `Cleanup`); node rules are dispatched by `instanceof` on the node class, in configuration order within a stage, `enter()` and `leave()` apart and only for the rules that override them, and the gap rules ride along the traversal of the formatting stage. When a rule replaces or removes the node it was given, the rest of the chain for that node is skipped. Passes repeat until one changes nothing; the printed text of every mutating pass is hashed and a repeated state is a cycle, reported at once with the rules that mutated and a diff of the two states. Rules must therefore be idempotent and must not depend on the pass number, which the context does not expose.

### Positions and derived violations

Violations carry positions from the original file (`Token::$originalLine`, the nearest original token before a synthetic one; `Trivia::$originalLine` when the report names a trivia, so that whitespace and comment problems land on their own line for suppression and baselines).

A violation that the fix of another violation brought about is **derived** from it: `Violation::$derivedFrom` names the fingerprint of the first violation of the chain, so that a report is true about the file on disk or says which violation made it true. The fixer remembers, per token, the violation it opened or closed the line before that token for, and a report about the gap before such a token (its blank lines, which wait for the next pass, the whitespace of a joined line, the indentation the engine inferred for an opened one) follows from it. A rule that places a line by what another line was given says so with `report(follows: $token)`, the token opening that line, and the report follows from whatever opened, closed or moved that line; `dresscode/indentation` names the line its construct begins on, so a block indented consistently wrong is one violation and the lines placed by it follow it, and a condition written again carries its continuation lines with it. A rule that reports the shape of the line a token stands on says `report(byLine: true)` instead, which asks the same of that line but claims nothing about its whitespace, so nothing is placed by such a report: the comma `dresscode/trailing-comma` asks for is there because the closing bracket takes a line of its own, so it follows whatever put the bracket there.

Nothing else is derived: not a report on a tree another rule has changed, by that alone, and not even one on a token a fix wrote anew, which is often the user's code rebuilt (a group import expanded into statements, a gap moved in front of an inserted modifier), and a rule adding code writes it instead in the shape the other rules ask for; not a report about a comment, which is the user's whatever line it stands on, and not the sibling claims of one decision, each about a break the user did not write. Those are not derived but one: the claims whose closure decided something about a construct through `Gap::once()`, a decision other than null, false or an empty array, are about its shape, so every gap of that construct is reported in the pass as a single violation, placed at its first report, silenced by a comment on that line and known to the baseline under one fingerprint (`Fingerprints::placeConstruct()`), and a rule of a shape is reported once per construct, which is what counting the places it decides needs.

A derived violation is a violation like any other, in the JSON, in the baseline, under `dresscode:ignore` and in the exit code, because `fix` changes what `check` reports and the derived ones are changed too; only the console folds them under their ancestor.

`RuleContext` keeps the reports of a callback as `Engine\Report`, with the gap and the line a report is about, and `PassRunner::account()` turns them into violations. The fingerprint (rule, message, normalized line content, occurrence within the pass) is made by `Engine\Fingerprints` at the moment of the report, so that the position is the one the reported code still had; repeated reports of one violation across passes collapse on it.

### Baseline

A `Baseline` (per file and fingerprint, written by `check --generate-baseline` into the file the key `baseline` names, or into `dresscode-baseline.*` beside the configuration, which the user then has to name for it to apply) is asked at `report()` beside the `dresscode:ignore` comment, and it is no suppression: a violation the baseline knows is not recorded, but `report()` does not deny it, so a rule that can fix it by now fixes it and the entry turns stale; outside the baseline **`fix` changes exactly what `check` reports**.

A baseline is the way to enforce a rule the code does not meet yet, and it holds only what a fix leaves: `check --generate-baseline` writes nothing while a fix would still change a file or a file fails or does not parse, and refuses `--fix-risky`, so its entries are the violations the rules have no fix for and the risky fixes the project does not accept; a style the rules can fix is reached by a fix, not recorded. A later round of `FileProcessor` computes the fingerprints from its own text, so a known violation on a line another fix rewrote is not recognized there: it is recorded in `remaining`, which is what the next check reports.

Its format follows the extension of its file, so it is written in whichever of the two the configuration is written in and there is no third format, and any other extension is refused instead of guessed at, whether the file exists yet or not. The fingerprints a file silenced travel back in `FileResult::$baselined`, because a worker has a baseline of its own; the run marks them used, counts them for the summary and warns about stale entries: the unmatched entries of the files it processed and, in a run narrowed by `only`, of the rules that ran there, because an entry of a file outside the scope or of a rule narrowed away is not stale, only not asked about. The identity of the result cache holds the baseline for the same reason, a file clean under one baseline is not clean under another, and a cached content keeps the fingerprints the baseline silenced in it, so that a run served by the cache counts and marks what a processing run would.

### Suppression

Suppression is read once from the original comments before any mutation: `dresscode:ignore [names]` on a line silences that line, on its own line the nearest node starting on the next line, `disable`/`enable` a range, `ignore-file` everything. The forms of PHP_CodeSniffer (`phpcs:ignore`, `phpcs:disable`, `phpcs:enable` and the `@phpcsSuppress` annotation) name the rules of another tool, which `Interop\Translator` translates, one name possibly standing for several rules; `dresscode migrate-suppressions` rewrites them to the dresscode form with the canonical names and lists the names no rule covers.

### Processing a file

`FileProcessor` is a pure function of path and text: parse, passes, print, and the same again over the printed text until it settles, at most five rounds: a text the rounds come back to, or one still changing in the fifth, is a `ConvergenceException` and fails the file like a cycle of passes, because only a broken rule gets there. A mutated tree is not the tree the parser would build from the printed text, so a rule can miss what another one has just written; the text is what has to settle, not the tree.

The violations reported are those of the first round, whose positions belong to the file as it was. What the last round reports is `FileResult::$remaining`, positioned in the fixed text: the last round is a full check of the text a fix writes, the baseline included, so it says exactly what the next check of that text reports, and the exit code of a fix, the result cache and every listing of what a fix left read it, while a check says how many a fix would leave. A text that no longer parses is a failure of the fixer rather than a syntax error of the file. What a run reports therefore depends on which other rules are on: a rule that fixes a shape first takes away the report of a rule that would have met it later. A syntax error is a result, not an exception, and the `Style` follows the prevailing line ending of the file unless the configuration fixes one.

### Running

`Runner::findFiles()` finds the files (patterns with a slash are anchored to the root, without one they match a segment at any depth, both also match directories on the way; a file named on the command line is taken as it is, and only `--skip-excluded`, which a hook or an editor naming every file it touches passes, lets the excluded paths leave it out like a found one) and `Runner::run()` takes that list, reads and writes the files and hands results to a `Reporter`. The caller expands the paths so that it knows the scope before the run starts. A path named on the command line is relative to the working directory, and `Runner::narrowPaths()` narrows a named directory that holds some of the configured `paths` to those, so that `fix .` in the root never reaches beyond them, while a path outside them is taken as named.

The format is the whole contract of the output, never a switch modifying another one: `console` unless `--format` says otherwise, `github` when `GITHUB_ACTIONS` says the run is a step of a workflow, `json` and `checkstyle` for tools, and `bare` for a hook, which prints the violations left to the user and a `rewritten` note for every file the fixer touched, so a clean run prints nothing while a silent rewrite never happens; the php-fixer plugin of `nette/claude-code` is such a hook, and it passes `--skip-excluded` with it. The header naming the configuration file and the scope belongs to `Console\Application` and is written, together with the warning that Xdebug makes the run many times slower, only for the console and github formats; the progress bar only for the console format on a terminal, where it is a status of the very console the report goes to, so that writing the report erases it. A fix run lists every file it touched exactly once, with a `rewritten` note and under it what the fixed text still violates; which violation a fix removed cannot be told from the text, so the verdict counts what was found and what remains, and `--diff` shows what changed.

A rule exception or a cycle fails that one file (nothing is written, the run goes on, exit code 2), and so does a file whose text on the disk is no longer the one processed when the fix is about to write it, so that what an editor saved meanwhile is never overwritten; a syntax error is exit code 1 like a violation.

A `ResultCache` (one JSON file per project root in `cacheDir` or the system temp) remembers every content that came out clean under the effective configuration: rules with options, style, PHP version, the version each package of the project stands for with the reference of the source it came from (`ProjectPackages::getIdentity()`, the packages of the project and never those of the running process, which are the tool's own wherever it is not installed in the project), the modification times of the files of the rule, preset and analysis classes no package of the process holds, which a rule of the project itself changes under the same version, and the text of the configuration file, hashed by `RunnerFactory::hashConfiguration()`. That text is all that describes a rule or an analysis a closure builds, so such a closure must build from nothing but what the text says, and a run with a closure and no file is not cached. A content is remembered by its path together with its text, because an override or a rule reading the path gives the same text in two files two verdicts; `Runner::run()` skips such a file with a `cached` result and, after a fix whose text has nothing remaining, remembers the written content too, unless there is a baseline, whose entries no run has yet held against the fixed lines. `--no-cache` disables it; `processFile()` (stdin) never uses it.

With `--jobs` above 1 (by default the processor count, capped at one worker per four files, because a worker costs about that much to start; an explicit `--jobs` is taken as given) the files not served by the cache go to a `WorkerPool`. Worker processes are started with the same command line plus a hidden `--worker <address>` and connect to a TCP server on the loopback, the only channel `stream_select()` handles on Windows before PHP 8.5, which fixed it for pipes; once 8.5 is the minimum, the pipes of `proc_open` can replace the server. A worker receives one path at a time and answers with the `FileResult` as a line of JSON (`toArray()`/`fromArray()`). The parent reads the connections without blocking and puts a line together from its parts, because waiting for the rest of one would stop it from hearing the other workers and from noticing a stuck one; it takes an answer only about the path it gave that worker, and a worker spending longer than the timeout of the pool on one file fails the run, since a rule has most likely looped. The listening socket is closed as soon as the last worker is in, because on Windows closing it later costs every run a wait.

A worker only processes and, when fixing, writes; the parent keeps the cache and the baseline, reads a file again when it hands it out, reports every file in the order of the input as soon as the files before it are done and keeps its result without the code and the output (`FileResult::withoutTexts()`), so that only the files in progress and those waiting for an earlier one are held as text, and turns a worker that dies or exits with an error into a failure of the run.

## Configuration

### The file

A configuration is written as `dresscode.neon` or `dresscode.php`, and the two are the same thing said twice: every key of the NEON is a named argument of the constructor of `Config`, so `NeonReader` is a schema that accepts no key it does not know, the evaluation of entities and a spread into the constructor, and a test asserts that the two files of the fixture build an equal `Config`.

The shape is shared: `Profile` holds what decides how a file is processed (`presets`, `rules`, `indent`, `eol`, `lineLength`, `php`, `namespaces`, `nameResolution`, `fixRisky`, `warnings`), a preset is a profile under a name, an `Override` is a profile with the `paths` it applies to, and `Config` is the profile of the whole project with the scope of a run (`paths`, `excludePaths`, `fileExtensions`, `skipWhen`, `baseline`, `cacheDir`), its `overrides`, what it brings in (`extensions`, `analyses`) and the versions of its packages the code is written for (`packages`), which only the project can say, so that neither a preset nor an override has the key. They are readonly values checked when they are constructed: a value one of them refuses is an `InvalidArgumentException`, which `NeonReader` and `Loader` turn into a `ConfigurationException` naming the file and the resolver into one naming the preset.

What the PHP notation passes as an object or a callable (an extension, `skipWhen`, the factory of a rule or of an analysis) the NEON writes as an entity: `Class(args)` is a new object, `Class::method(args)` what the static method returns, `Class::method(...)` the method itself, and in a chain `Class(args)::method(args)` a link calls the method on what the link before it gave. An entity is evaluated when the file is read, except the one of a rule: a rule is built anew for every combination of overrides, so its entity is a recipe evaluated at every build, and only the class or method it starts from is looked up when the file is read, so that a misspelled one is still an error of the file. The schema keeps only the keys the file gave, so that an absent key keeps the default of the constructor.

`Loader::find()` walks upwards and takes, in each directory, the local file before the `.dist` template; the two formats side by side are an ambiguity it refuses rather than resolves. A configuration file is the only thing laid over a project, and `--config` names it (its format follows its extension); a wrapper binary that wants a configuration to apply in a project without one hands `Console\Application` a `defaultConfig`, which the loader uses when it finds no file, and the workers get it because they are started with the same script. The command line is no key of a file: `--preset` and `--rule` are a `Profile` laid over everything the file says, and `--only`, `--fix-risky` and `--strict-rules` are parameters of `RunnerFactory::createRunner()`.

### Extensions

`extensions` names classes. A rule or a preset there is made known by its name, and an `Extension` is what a package brings to a project: its `getConfig()` is a `Config` that may set nothing but `extensions`, `analyses`, `excludePaths` and `skipWhen`, which `RunnerFactory` refuses otherwise. It lies below the project, the extensions it names below it and every class once: the excluded paths add up, a file any of them skips is skipped, and an analysis of the same class the project gives wins. How the code is written is no business of an extension; that is a preset, which the project names, so the standard of a project is always read in its own file.

### The profiles of the packages

A package installed with the project speaks without being named: `Config\PackageProfiles` reads `vendor/composer/installed.json` of the nearest `composer.json`, the root package included, and takes from every package what its `composer.json` says under `extra.dresscode`: `extension`, a class loaded as if `extensions` named it, and `upgrading`, one file or several, `upgrading.neon` by convention, or `upgrading/<library>.neon` in a package that carries the files of several libraries. Such a file says what the versions of a library retired and what to write instead: `package` names the package whose versions the sections are of (the carrier itself, or the library a package of rules carries the file for), and every section `since <version>` holds rules with the options that version brought, the renames it made as the maps of `replaced-classes` and `replaced-members`. The sections the version the project stands on reaches are merged in the order of their versions whatever order the file writes them in (newest first, as a guide to upgrading is written), a later one having the last word on an entry, every one where any version does, none for a package the project does not have, and the versions of the sections left out stay with the profile (`PackageProfile::$unreached`); the key is spelled `since 3.10` because NEON reads a bare `3.10` as the number 3.1. A value is handed over as NEON reads it, so what it reads as an entity (`isFilled()`) is for the schema of the rule to take. A member is spelled the way PHP reads it, `Class::name` for a constant or a method, `Class::name()` for a method where a constant of that name exists too, `Class::$name` for a property, and the replacement is the name alone for the same class, `Class::name` for another, or `\function` for the global function a method becomes. What a version took back, a later section withdraws with the value `keep` in place of the replacement, and so does any layer of the project; the entry never reaches the rule (`Rules\Classes\MemberMaps`, the schema such maps share, which also takes a value NEON reads as an entity, `isMethod(POST)`, and reads its arguments the way NEON gives them: a placeholder, a number, `Class::NAME` and a nested call as written, any other string as a string, quoted or not; what that cannot say is a string holding the whole code).

Such a file sets options and nothing else: a section holding a bare value instead of a map of options is an error naming the file, because no package may turn a rule on. `PresetResolver` lays what the packages say under every layer and hears it only of a rule some layer of the project turns on; a rule they name that this DressCode does not know is a warning, because the package may be newer than the tool. Turning a rule off drops what the layers below said but not what the packages say (`ResolvedRule::$packageLayers`), so a rule a preset turns off and the project turns on again keeps the data. The result cache needs nothing new: the options a rule ends up with are in its identity, and so are the versions of the installed packages.

### Presets

A preset is a `Profile` under a name (`Preset::getProfile()`), whose `presets` are the ones it builds on; it may carry the style it needs, and it may not make a decision of the project, `php`, `nameResolution`, `fixRisky` or `warnings`, which the resolver refuses. A rule or preset is named either by class or by name, and a name without a vendor is the built-in one, so `per` and `dresscode/per` are the same preset.

The built-in presets are the four standards and two presets of their own kind. A standard carries a style and says how the code looks: `dresscode/psr12`, `dresscode/per` on top of it, `dresscode/nette` on `per` with `dresscode/nette-style` (its layout and the style of tabs) and the groups of hygiene it asks for, and `dresscode/symfony` on `per` with `dresscode/symfony-configurator`. `dresscode/nette-style` carries rules of layout together with the style of tabs and exists for `nette` alone; `symfony-configurator` has no rules at all, only what a framework declares into its namespaces. What a project wants beyond the looks of its code is not a preset but a group. `dresscode/psr12` and `dresscode/per` follow their specifications section by section and add no style of their own, so a rule whose fixed behaviour contradicts a specification gets an option rather than a preset-side workaround. Without a configuration file the `dresscode/per` preset applies.

### Groups

`groups` of a profile names what the project wants beyond the looks of its code, `cleanup` or `types`, and every registered rule whose `#[RuleInfo]` carries that group runs with the options it defaults to. The names are the cases of `Group` and nothing else: a name outside them is refused with the list, and no package can invent one, which is what keeps them few. A rule of an extension carrying a group therefore joins what the project already asks for, without a name of its own to be learnt.

A group lies under the rules of its own profile, so the project keeps the last word over what its groups turn on, and it names no rule: a rule of a group that cannot run here is left out in silence, as one a preset named is, never as an error. `--group` on the command line is a profile over everything else, as `--preset` is, `--only` takes the name of a group as it takes the name of a preset, and `dresscode config` prints the groups the resolution came to next to the presets.

### Resolving the layers

`PresetResolver::resolve()` lays the profiles that decide for a file one over another: the configuration, the overrides the file matches in the order they are written, and the command line, each above the presets it names with their parents, parents first and every preset once, where it is named first. A later layer has the last word on a value (`indent`, `eol`, `lineLength`, `php`, `nameResolution`), adds to a list (`namespaces`, `fixRisky`, `warnings`) and merges the options it gives a rule with those of the layers below; the order of the rules is that of their first mention. Every mention of a rule is a layer, and the resolver turns the layers into a `ResolvedConfig`: what each rule ends up with, the layers that said it, the style, the target version of PHP, and for a rule that does not run the reason it does not. The run builds its instances from that one result, the result cache keys on it and whoever prints the configuration reads it, so none of them can say something the others do not.

**A map of options merges with the layer below it key by key; a list and a scalar replace it, and a list also replaces its default.** Turning a rule off drops what was said before it, so a map written after that starts from the defaults of the schema again. A preset that writes `true` over a parent that set options therefore keeps them, and a preset that wants something else says so. The merging is `Processor::processMultiple()` over the schema of the rule, which knows a map from a tuple; the policy that a list replaces is one line in the resolver, the `Helpers::PreventMerging` marker every `merge()` of `nette/schema` honours.

A rule that is one decision says so with `RuleInfo::$decision`, the option a bare value written for the rule fills (`dresscode/yoda: forbidden`), which the resolver turns into that one-key layer before the layers meet, so the long and the short notation resolve to the same thing; a rule that declares none refuses a bare value and says which options it has.

`keep` is the only word for "leave this alone" and it means the same at every level: on a rule it drops the rule from the run, in an option it takes that one place out of what the rule governs, so `null`, `false` and a turned-off rule never stand side by side for the one idea. The schema of such an option names `keep` among its values, the reference therefore shows it, and the rule turns it into whatever its own code calls "nothing to claim" in `configure()`.

An option whose value is one of an enumeration may also take a list of them, and that list is a tolerance, not a set: every shape in it passes, and what is in none of them is written in the first. The rule turns the list into the shapes that pass and the target once, in `configure()`, decides per unit which it is (`Gap::once()` for a gap rule) and then claims the target alone; a rule that held one claim per tolerated shape would claim the same gap twice. What the predicate of a shape measures and how far the claims reach must be the same set of nodes, or the rule reports what it cannot fix, or fixes what it did not report.

What the schema warns about the options it completed, through `Context::addWarning()` in a `transform()` (that they leave the rule nothing to do), or what `nette/schema` warns itself (a deprecated option), reaches the user as `Rule <name>: <message>`, once however many overrides are resolved, so a message is a sentence of its own, and the resolver knows no rule by name.

An override (`overrides` in NEON, `Override` in PHP) is a profile for a part of the tree, with every key a profile has: its `paths` go through the same matcher as the excluded paths, anchored to the root of the configuration. A file's configuration is therefore the combination of overrides it matches. `RunnerFactory::createRunner()` builds one processor per combination, with an `Analyses\Registry` of its own because an override may add to what the namespaces declare, and `Config\FileProcessors` keeps them, because a rule carries the options it was configured with and must never be reconfigured under a file already being processed; the identity of a cached result carries the path, which decides that combination, because the same text is clean under one and not under another. A part of the tree where a rule must not run is an override that turns it off, so a later override may turn it on again. Every override is resolved on its own when the run is built, not when a file of it comes, so a name no rule or preset owns and an option no rule takes are an error naming the override rather than a line that does nothing until such a file comes.

The style is the last one a layer says, else a tab, the majority line ending of each file and no line length (`false` in a layer says none over a length below it); `platform` is answered by the resolver, so what reaches the engine and the result cache is a line ending or `majority`. The excluded paths only ever add up, the default list, those of the extensions and those of the configuration, so no layer can bring back what another left out.

`only` (`--only`, a parameter of the run and no key of a file) narrows a run to the rules it names, a preset standing for every rule it and its parents mention, and it is one more reason of that resolution, applied to what the rest came to after `--preset` and `--rule`: it takes a rule away and never enables one, a name that lets nothing in is an error rather than a run that checks nothing, the result cache keys on the rules that run, and the workers get it on their command line. `fix --only` fixes that one rule and leaves the rest, so the next full `fix` changes more, which is the point and not a failure to converge.

### What the commands print

`dresscode explain <rule>` says what one rule is for, the options it has under this configuration with the layer that set each, and the examples chosen for it; an example is a fixture named `showcase*.code` in the directory of the rule, so the suite runs it against the rule itself and one that stopped being true cannot survive, and a rule that only reports has no "becomes". Without a rule it explains every rule that runs, and with `--output` it writes the same as a Markdown document: what the configuration is composed of and every rule with the options it runs with and its example, grouped by area, which says of itself that what no rule covers is not in it. `dresscode config` prints that resolution, `--file` narrowed to what the run uses for one file and `--json` as data: every option a layer named with the layer that named it and what it overrode, of a rule with risky fixes whether the project accepts them (`ResolvedRule::$fixRisky`, which is also what the run allows, and a name there whose rule runs nowhere, not even in an override, is a warning of every run), and every rule that does not run with the reason (turned off, too new for the target, nowhere mentioned, narrowed to other rules).

### The target version of PHP

The version of PHP the rules target is a property of the checked project, never of the run: `RunnerFactory::resolvePhpVersion()` takes it from the key `php` of the configuration, else from `require.php` of the nearest `composer.json` at or above the root (the lower bound of its constraint as `composer/semver` parses it, cut to major.minor; a constraint without a lower bound, `<8.4` or `*`, leaves the version to the default rather than to a guess), else from `Config::DefaultPhpVersion`, and an override may give its files another one. Whichever it is, a version older than `Config::MinPhpVersion` is raised to it by the resolver with a warning, because no rule asks whether the target has what PHP 8.0 already has, so a fix may write such syntax. Nothing else raises it, a package backfilling a newer construct least of all: a rule writes what the version the project moves to gives its code, while such a package exists so that the project need not move, and taking it for an answer would turn the target from a version into a list of what happens to be in the vendor directory.

It travels as a plain string compared with `version_compare()`, never with the string operators, under which 8.9 outranks 8.10. NEON reads a bare number as a version whose minor is a single digit, which every PHP ever released has had, so `8` and `8.0` both mean 8.0. The running interpreter is never the answer, so that the same file gets the same verdict from any directory under any PHP; only `Lexer` asks about the runtime, to emulate the tokens its own build does not know.

What PHP itself declares is the same kind of question, and a rule asks `Analyses\PhpSymbols` about it rather than `function_exists()` or reflection, which would answer with the extensions and the version of the machine: the catalog holds every version from 8.0 on, so what depends on the version, since when a function is deprecated and which versions declare it at all, is compared with the target. The parameters of those functions are a catalog of their own, `Analyses\PhpSignatures`, because they are two thirds the size of the rest and the command line compiles what it loads on every run, so only a rule that asks about them pays for it; it answers with `Parameter`, whose `canReplace()` says whether an argument written for one parameter may stand at another, and it knows nothing of the extensions its source cannot see, where a rule then has no answer rather than a wrong one. A rule whose construct exists only from some version on says so with `requires: ['php' => '>=8.4']` in its `#[RuleInfo]`, named as the `require` of `composer.json` names it, which is metadata and never a directory, so that a rule lives with its topic and the reference can index the catalogue by the version a rule needs, and `PresetResolver` leaves it out below that version: silently when it came from a preset, with a warning when the configuration asked for it by name. A rule that needs the version more finely than "run me or not" asks `RuleContext::getPhpVersion()` instead, and never about anything PHP 8.0 already had. A package in `requires` is the same question asked of `Config\ProjectPackages`, which answers from the `composer.json` of the project and the `installed.json` beside it, never from the Composer of the running process: for a package the project requires itself the version is the lowest its constraint allows, because code written for a newer one breaks wherever the constraint lets an older one in, for a package that only comes with another it is the installed one, the alias of a development branch standing for the newest of its line, and any version does for the project itself and for a branch without an alias. The `packages` of the configuration (`nette/forms: '3.3'`) say the version of an installed package outright and come before all of that (`ProjectPackages::withTargets()`), so that code is fixed for a version while the one before it is still installed and its members still have a declaration to read; the version is quoted, because NEON reads a bare `3.10` as the number 3.1. The resolver leaves a rule whose package the project does not have, or has below the version, out as it does a rule too new for the target, and the sections `since` of a package's deprecations are cut by the same answer. A rule that makes no sense without the types of the code says so with `requiresTypes`, and the resolver leaves it out where the configuration sets no `types` (a decision of the project, which a preset may not make): silently when a preset named it, so that a preset may name it whatever the project has, and as a `ConfigurationException` when the configuration or the command line named it, because the project then asked for what it cannot get and a run without the rule would lie. There is no third way: the registry builds `Analyses\Types` only where the configuration asked for the types, so a rule cannot ask for them and take `null`. A rule that would only do better with them does without and says in its docblock what it then cannot see (`useless-set-accessible` reads the one assignment of a variable instead of its type).

### The namespaces of the project

What the namespaces of the project declare is a property of the project too, and no file shows it: an unqualified function or constant in a namespace reaches the namespaced one PHP knows at run time before it falls back to the global one. `namespaces: {functions, constants}` lists such symbols as the items of a use statement write them (`App\Utils\{format, parse}`, parsed by `Parser` when the profile is constructed), and every layer adds to the lists; `nameResolution: certain` says the lists are all there is, which the configuration or an override says and a preset cannot, knowing a framework and not the project. An override may say `uncertain` for a part of the tree whose declarations nothing outside it reaches, such as the helpers of the tests, so that no fix there rests on the lists and nothing there is guarded.

`PresetResolver` puts both into `ResolvedConfig`, so they are in the identity of the result cache and in `dresscode config` with the layer that named each symbol, and `Analyses\Registry` builds `NameResolver` with them as `NamespacedSymbols`, which is also the analysis a rule asks for the lists themselves.

A certain resolution rests on lists that must stay complete, so the key turns on their guard, `no-unlisted-namespaced-declaration`, as a layer of its own below the rules of the same profile, which may turn it off, and a file whose resolution ends up uncertain has no guard; a declaration the lists do not name is decidable in its file, a declaration inside a condition and a `define()` with its name written as a string among them (`NodeHelpers::findNamespacedDeclarations()`), and the lists can then go stale only through a path left out of the run or a package of the same namespace. What a framework declares for the files a project writes into its namespace is carried by a preset with no rules, `dresscode/symfony-configurator`, which `dresscode/symfony` composes and any other standard may.

### init

`dresscode init` writes `dresscode.neon` from how the code is already written, and it has no measuring code of its own: `Config\Survey` runs the rule of each value over a sample of the scope, and what the rule reports is what disagrees with that value.

The scope is what the `autoload` and `autoload-dev` of the nearest `composer.json` name, which is the one place a project says where its code is (`psr-4`, `psr-0` and `classmap`, read by the same code that reads the target version from that file; a `files` entry is a single file and no scope), together with the conventional directories the root has beside it for what an autoload cannot name, the entry points and the test suites (`Proposal::Paths`, where a name with `*` is a pattern of the root); a path lying inside another one is already in the scope and drops out, and `.` is the scope when neither source says anything.

The sample is every k-th of the sorted files, so that the same tree always gives the same one, at most `Sample::MaxFiles` files **and** `Sample::MaxBytes` bytes, because the cost of measuring is bytes and not files; a file over `Sample::MaxFileSize` never enters it and neither does one whose head says a generator wrote it, which is the reason reported when both hold, and the directories of `Proposal::GeneratedDirs` are left out on top of the default exclusions and written into the file when the tree has them.

A decision that is a property of the file (the indentation) is counted by files; one every place makes anew is counted by places, which needs a rule that reports each place once under every value: `string-quotes` reports every plain string written the other way, and `multi-line-condition` a condition once, because the gaps of a construct decided through `Gap::once()` are one violation; a run with every value allowed counts the places in none of them. A file the rule fails in under any of the values is left out of the decision for all of them, because it would agree with the value it failed under, and the measurement says how many were. A value at least `Measurement::Threshold` of the places agree with is written with its share; below that the file writes the tolerance where the option takes one and the values together reach it, else `keep` or a comment, never a bare value, and never `fixRisky`.

The standard is not measured: the file gets the one given with `--preset`, `per` without it, and a comment naming the others. What each standard would cost is measured instead, a consequence and not a likeness: the files of the sample its first fix would change (`Proposal::countChangedByStandard()`, the same dry run over the same decisions with that standard alone). Without `--preset` all four are told, the cheapest first; with one, only that one. The prices stay out of the file, where a price of a standard that was not written defends no line and would go stale with the first fix.

What the namespaces declare is not a decision and not sampled: every file of the scope naming a namespace or `define` is parsed, because a declaration a sample left out would be taken as global with nothing to report it, and `nameResolution: certain` is written only when all of them parse, the first that does not being named instead, and the preset of a framework is proposed where the lock file or the installed packages have its package (`Proposal::FrameworkPresets`). What the file says is read back and resolved before it is written and must be what was measured (`Proposal::checkResolution()`), and a configuration that exists is never overwritten (the proposal goes to the output and the exit code is 2).

## Writing a rule

### Messages

A violation message describes the code, never the reader: no imperative (`Use…`, `Add…`, `Remove…`), because a rule that only reports has nothing to command. It takes one of three shapes, and which one is decided by the rule, not by taste: the required state as a noun phrase where the rule wants one short thing in one place (`A single space after a comma`), `<subject> must <requirement>` where that needs a sentence (`The opening brace must be on its own line`), and the defect where the thing is wrong in itself or the rule guards several places at once (`Function foo() is deprecated`, `Wrong whitespace in a type declaration`).

A family shares one pattern: every `-spacing` rule says `No whitespace <where>`, `A single space <where>` or `At least one space <where>` with the token the claim is on as `<where>` (`before the closing parenthesis`, `after the return keyword`), composed by the engine, every `-indentation` rule `Wrong indentation of <what>`, every claim on a line break `A line break <where>` or `No line break <where>` with the bracket at the edge of the gap or the node the claim was made for as `<where>`, and the reason after a comma when the claim follows from a measure or a property of the code (`Claim::$because`: `A line break before the parameter, the line is 135 characters long`), every `-blank-lines` rule the measured `Expected <count> <place>, <found> found` composed by the engine from the node or token the claim was made for (`before the method`, `after the opening brace`), every `useless-` rule `Useless <what>` with the reason after a comma.

The subject is the thing at the reported position, with a definite article, and an operator or a call in that role carries its kind (`The <> operator must be written !=`, `The is_null() call must be…`); `written X` names a literal replacement, `written as X` a form. A spelling the message shows, the one to type and the one found when it holds a space, goes in single quotes (`must be written 'Exception'`, `The keyword 'YIELD FROM'`, `must start with '//', not '#'`), because a bare token at the end of a sentence has no visible end; what carries its own delimiter stays bare: a call the message only names (`is_null()`), an expression built from the code at hand (`$obj::class`), and a word that is not a spelling (`camelCase`, `the short syntax`). Names and measured values belong in the message, the rule name and the standard do not. In prose a `/** */` block is a `doc comment` and a tag in it an `annotation`, whatever the rule name calls them; `whitespace` is what a rule forbids, `a single space` what it requires.

### Options

An option is named after the place or the shape it governs, and the bare name is that: `emptyBodies`, `onObjects`, `leadingLinks`, `betweenMembers`. The prefix `allow` is reserved for the permission of an exception the rule would otherwise report (`allowNested`, `allowMultiline`), so it never stands in front of a choice of shape. One idea carries one name across the catalogue, whichever rule has it: `ignorePatterns` is the list of regular expressions whose match is never reported, wherever a rule takes one.

An option carries a `description()` only where its name, type and default do not say everything: a hidden scope (`classes` also covers interfaces, traits and enums), a hidden condition (`afterClassBrace` does not apply when the first member is a method), an inclusive threshold (`minDigitsBeforeDecimalPoint`), a value whose meaning is not its name (`nextLineAfterReturnType`); a description that restates the name is noise. Its form follows `RuleInfo::$description`: English, one sentence, capitalized, no trailing period. A count says where it applies ("Before the first member, unless…"), a boolean states what holds when true ("A class name referenced in a doc comment counts as used"), a choice names its values and what they do ("atLeastSingle keeps…, single collapses…"). Another rule is referred to by its full name (`afterOpeningTag of dresscode/blank-lines`). The text is checked against the code, not against the docblock of the rule.

### Testing

`Testing\RuleTester` runs a rule over `*.code` fixtures (`.expected` output beside them, `.violations` as `line: message`, options in a `// {"json"}` comment, a run that allows risky fixes in a `// risky` one, the targeted version in a `// php 8.4` one, the widest line in a `// lineLength 80` one (120 without it) and what the namespaces declare outside the fixture in `// namespacedFunctions`, `// namespacedConstants` and `// nameResolution certain`, all in the comments that open the fixture; without a version the rule is tested at the version of PHP it requires, else at `Config::DefaultPhpVersion`, never at the version of the interpreter running the tests) and checks the contract: parent invariant, idempotence over the output, comments preserved unless `modifiesComments`, `dresscode:ignore-file` honored, no silent mutation.

What no fixture catches, the runs over the corpus do: the whitespace fuzz damages the whitespace of a fixed file and requires the fixer to come back to it, and `name-meaning.phpt` runs the rules that write names and imports over the corpus and requires every name outside the imports to resolve to what it resolved to before, because an import moved into a statement writing its items differently, or dropped while something still uses it, leaves code that parses and round-trips and says nothing else.

## Interop: the rules of other tools

- `Interop` is the only place that knows the names of PHP CS Fixer and PHP_CodeSniffer. Two tables, one per
  configuration format: `PhpCsFixer` holds the fixers (friendsofphp, the custom fixers of kubawerlos) and
  `PhpCodeSniffer` the sniffs (the standards shipped with phpcs, slevomat); the names a tool built on DressCode
  had in its own earlier versions are that tool's to translate. The two name spaces do not overlap, a fixer is snake_case and a sniff is
  `Standard.Category.Name`, so `Translator` searches one merged table and a mixed configuration translates too.
  The tables are given to its constructor, the two built-in ones when none are; `RuleRegistry` holds the
  instance the run uses.
- A translation is a rule name, or a closure of the foreign options building the rules with theirs; it may
  produce several rules, and it warns about what it could not carry over instead of dropping it in silence.
  Every closure reads its options through `??`, which is what lets the test call each of them with none and
  validate the result against the schema of the target rule: a translation naming a rule that does not exist,
  or giving it an option it does not take, fails there.
- Enabling one rule from two foreign ones merges their options: a list becomes the union, a map merges key by
  key, a boolean is true when either says so, anything else is the value written last. Rules of one DressCode
  rule split across several foreign ones (`blank-lines`, `trailing-comma`, `type-hint-required`) depend on it.
- The tables also answer the reverse question, which rules a foreign name stands for, and that is what makes
  `phpcs:ignore <foreign name>` work and what the reference and `dresscode rules` print as "covers". A foreign
  name is not a valid key in the configuration: `dresscode import` translates a whole configuration file once,
  options included, and `resolveRule()` says so when it meets one.
