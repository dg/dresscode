# DressCode internals

How DressCode works: the facts an agent or a contributor needs before touching the engine, a rule or the configuration. The catalog of rules is not here; it is generated from the rules themselves.

## Layers

- `phpsyntax/phpsyntax` (namespace `PhpSyntax`, a repository of its own): lexer, parser, tree, printer, navigation, mutation. Its internals are documented there; what a rule of DressCode uses from it is below.
- `DressCode` (`src/`): engine, rules API, rules, configuration, CLI. Rules use only the public API of `PhpSyntax`; whatever a built-in rule needs from it is public API for plugins too. The public, semver-stable surface of `DressCode` is `Config` with `Override` and `Extension`, `Rule` with `NodeRule` and `GapRule`, `ConfigurableRule`, `Claim`, `Space`, `Line` and `Gap`, `RuleInfo`, `RuleContext`, `Preset`, `PresetInfo`, `Profile`, `Violation`, `Reporter` with `FileResult` and `RunResult`, `Runner`, `Console\Application`, `Config\Loader`, `Analyses\*`, `Rules\*` and `Testing\RuleTester`; `Engine\*` and the rest of `Config\*` are `@internal`, as are `Rules\NodeHelpers`, `Rules\BlankLines` and `Analyses\Registry`.

## The tree a rule works with

Printing the tree reproduces the input byte for byte, so a rule changes what it means to change: formatting rules change trivia, structural rules change nodes.

- Whitespace, comments and open tags are `Trivia` attached to tokens. **Trailing trivia** of a token is everything after it up to and including the first end of line, **leading trivia** of the next token is everything else (blank lines, indentation, comments on their own lines, doc comments). An `OpenTag` trivia (`<?php` with its mandatory whitespace) is always leading trivia of the following token; the final `EndOfFile` token has only leading trivia.
- `<?php` is not a token. `?>` is a token of kind `CloseTag` that keeps the newline PHP swallows after it, and the parser sees it as `;`; after a terminated statement it forms an `EmptyStatementNode`. `<?=` is a token of kind `OpenTagWithEcho` seen as `echo`. `Token::isSemicolon()` and `isOpenTagWithEcho()` cover these cases.
- Whitespace that PHP counts as part of a token stays in its text: inline HTML, `T_ENCAPSED_AND_WHITESPACE`, heredoc delimiters (the closing one keeps its indentation), casts like `( int )`. A BOM or a hashbang line is inline HTML, as PHP sees it. A single-line comment never contains its newline, but it does contain trailing spaces before it.
- Trivia inside string interpolation (`"{$a /* c */ }"`) carry `inInterpolation = true`; the token helpers refuse to change them because that whitespace is part of the string value.
- Slots are named by role (`ifKeyword`, `openParen`, `semicolon`, `condition`, `body`), paired delimiters are always `open*`/`close*`, lists are plural. A slot says what stands in it rather than what the class suggests, so the left of an assignment is `target` and not a variable, and what a `switch` and a `match` compare against is `subject` and not a condition. Every token of the source has a slot or a place in a list, so the order and number of children are not part of the API, only the slot names. Whoever names a slot instead of reaching for it writes the name as a string (`'openParen'`, `'statements:item'`), which is what a gap rule declares its claims with.
- The body of a control structure is a `StatementNode`, not necessarily a block; `else if` is an `ElseNode` whose body is an `IfNode`. The alternative syntax uses the same classes with `colon`, `statements`, `endKeyword` and `semicolon` slots instead of `body`. Class-like declarations implement `ClassLikeNode`, because an anonymous class is not a statement.
- A new node comes from `Parser::parseExpression()`, `parseStatement()`, `parseType()` or `parseName()`, which return it detached, with empty trivia on its edges and without original positions, or, where it is put together from nodes already at hand, from the `of()` factory of its class (`FunctionCallNode`, `MethodCallNode`, `StaticMethodCallNode`, `NewNode`, `ArgumentListNode`, `ParenthesizedNode`), so that a rule does not parse a template with a `0` in it to hunt the placeholder down afterwards; a constructor is public but its parameters follow the slots of the grammar, which a minor release may add to, so a call spells them as named arguments.

## Analyses

An analysis is information derived from a file, and any class the engine can build is one: `NameResolver` (namespace, imports, resolution of class, function and constant names with the runtime fallback of unqualified functions and constants to the global namespace, `isGlobalFunctionCall()`, and the way back: `getShortName()` gives the shortest way to write a fully qualified name where a node stands, through an alias, a prefix import or the namespace, and `isAliasFree()` says whether a name is still free there, which is what a rule adding an import asks), `Scope` (enclosing function-like construct and class, availability of `$this`, captured variables) and, in `DressCode`, `PhpDoc` (doc comments as phpstan/phpdoc-parser trees printed back with the original formatting) and `PhpSymbols` (what PHP declares: its functions with the version each is deprecated since, its classes, interfaces and enums in their declared case, its constants and the functions PHP 8.4 calls without a frame with their parameters, over PHP 8.0 to 8.5 and the extensions shipped with it, from the generated `PhpSymbolsData`; a PECL extension is not PHP and is not there). Analyses are lazy and computed once per file; `Analyses\Registry` (internal, reached through `RuleContext::getAnalysis()`, one for every combination of overrides, with the factories the `analyses` of the configuration and of its extensions give) creates them on demand, with the `FileNode` when the constructor takes one, and throws them away as soon as `FileNode::$revision` changes, so any mutation invalidates every analysis of the file.

## Mutation from a rule

- A node or token belongs to exactly one tree: inserting one that already has a parent throws; `clone` gives a deep copy without a parent.
- A slot is written by assignment (`$node->condition = $expression`, `replaceChild()`, or `setSlot()` given the name of the slot), which adopts the value, releases the current one and tells the index. Lists mutate through `append()`, `insert()`, `removeItem()`, `replaceChild()`; `SeparatedNodeList::insert()` derives a missing separator from the existing ones (or `", "` in a one-line list) and gives the item the indentation of its neighbor in a multi-line list, `removeItem()` takes the separator after the item, or before the last one.
- `Node::remove()` removes a list item: a node alone on its lines takes the lines with it, otherwise the whitespace around stays; comments inside, each with the line ending after it, go to the next token, the previous token, or away, as the `CommentPolicy` says. `Node::replaceWith()` keeps the trivia around the old node around the new one by joining them with the new node's own edge trivia; a replacement cloned from nearby source still carries its original leading trivia, so that an `OpenTag` gets doubled; `Node::withoutEdgeTrivia()` is the copy without them, which is what a rule takes of whatever it writes into another place.
- What a rule reads is a property (`value`, `base`, `quote`, `label`, `indentation`, `kind`, `parts`, `role`, `text`), and it writes one where the write takes a single value with a single consequence: a slot, and `NameNode::$text`, whose hook tokenizes the name anew. It writes through a method where the write takes more values or two things change together (`StringNode::setValue($value, ?$quote)`, the delimiter deciding how the value is written), and for a token always, because `?->` cannot stand on the left of an assignment: `Token::setText()`, `setLeadingTrivia()`, `setTrailingTrivia()`, and `Node::setEdgeTrivia()` for the outer edges of a node, where the first or the last token may be missing. What has no hook the language guards: the text and the trivia of a token are `private(set)`, the items of a list `protected(set)`, `parent` is written by `attachTo()`. A hooked property takes no indirect change, so `end($token->trailingTrivia)` needs a copy.
- Every mutation increments `FileNode::$revision`, which the engine reads to detect mutations; it is a version of the tree, not a count, because a compound mutation raises it several times. `Token::$originalLine` and `$originalOffset` never change and are the source of positions in reports; `getLine()` and `getColumn()` follow mutations.
- A single trivia (typically a comment) is removed by `Token::removeTrivia()`, which tidies the whitespace around it: one alone on its line takes the line with it, an inline one takes an adjacent space; `Token::replaceTrivia()` swaps one in place. A doc comment is read with `Node::getDocComment()` (above the node, or after the previous token) and, after editing through `Analyses\PhpDoc`, written back with `Node::replaceDocComment()` or dropped with `Node::removeDocComment()`. The tree is the phpstan/phpdoc-parser AST itself, which is therefore part of the public API (its major version is ours), and it is edited the way its format-preserving printer expects: replace `children` or return a new node from a visitor, never mutate a list such as `UnionTypeNode::$types` in place (it prints wrongly); a text node whose text changed loses its ` * ` line prefixes, so rewrite whole lines; a tree with nothing but blank text (`PhpDoc::isEmpty()`) is removed, not printed, or it prints `/**  */`. `NativeType` (annotation to native type) is the shared helper above the AST and `PhpDoc::findTemplates()` names the template types in scope, which a native type cannot use; there is no tag-editing layer of DressCode's own. `Rules\Whitespace\BlankLines` holds the schema of a count of blank lines in the options of a rule: a number, a range `[min, max]` (a `tuple`, with `null` for an open end) or `null` to leave the place alone; the count is what a rule claims as the `blank` of a `Gap`, and the engine moves a count outside the range to its nearest bound.
- Comment queries for rules that must not destroy a comment: `Token::hasComment()` (in the trivia of the token), `Token::hasCommentUpTo()` (anywhere between the texts of two tokens) and `Node::hasComment()` (inside the node, its outer edges excluded); `Token::getComments()` and `Node::getComments()` give what those count, and a `Trivia` says of itself whether it `isDocComment()`, `isLineComment()` or `isMultiLine()` and hands over its text without the delimiters as `getCommentText()`. `Node::matches()` compares two nodes by their token texts, `ExpressionNode::isRepeatableRead()` tells whether reading an expression again is free of side effects; together they answer "does this assignment repeat its target". `NodeHelpers::isBoolean()` tells whether an expression is a boolean by its form, `NodeHelpers::negate()` builds its negation as a detached node, flipping an equality but never an ordering, which NAN makes false both ways, `NodeHelpers::endsWithExit()` whether a block ends by leaving (return, break, continue, goto, throw, exit), `NodeHelpers::findDynamicVariableAccesses()` the constructs inside a node that may reach a variable by a name they do not spell out (`$$name`, `compact()`, `extract()`, `get_defined_vars()`, `eval`, `include`), which a rule reasoning about the variables of a scope must respect, `NodeHelpers::findUncertainty()` the reason a call taken as a call of a global function may call a namespaced one, which makes a rewrite of it risky, `NodeHelpers::spellGlobalFunction()` how another global function is written in place of such a name, bare only where the bare name is no less certain than the replaced one, `NodeHelpers::canAddImport()` and `addImport()` an import written in the shape `dresscode/import-notation` gives its kind, asked through `RuleContext::findRule()`, which hands a rule another rule as configured for the file, or where that rule gives none the way the scope writes its imports, into a statement of its kind listing several names or as a statement of its own, where the default order of ordered-imports puts it, so that the rules of the shape and the order of imports find nothing to add, and `NodeHelpers::splitItems()` turns a declaration of several items into one per item; `ExpressionNode::isDereferenced()` tells whether the parent accesses a member or element of the expression, which is what decides whether parentheses around it can go.
- `dresscode/name-notation` and `dresscode/name-fallback` split the writing of names by the transition, so that they never pull at one token: name-notation moves a qualified name between the import and the leading backslash and is never risky, name-fallback moves a global function or constant between bare and qualified, risky unless the resolution of names is certain. name-fallback writes a qualified name in the shape name-notation gives it (`findShape()`), and name-notation leaves a name name-fallback writes bare (`isWrittenBare()`) and adds no import a bare name would be taken over by; what both read of a namespace is `Rules\Namespaces\NameReferences`.
- Horizontal whitespace between two tokens on a line is the trailing trivia of the first one, never the leading trivia of the second (a rule joining two lines writes the space there, or the next rule reading the gap sees none), and it is read and written through `Token::getTrailingSpace()` and `setTrailingSpace()`, which return or refuse `null` when a line ending, a comment or string content is in the way, or when the first token ends its line by its own text (a close tag, a heredoc start); `Token::is()` given a text never matches the content of a string, only operators and punctuation. `Token::getLineWidth()` measures the line of a token visually (tabs by the tab width of the style), which is how rules about line length decide. `Token::removeTrailingWhitespace()` also trims the end of a `//` or `#` comment, because the tokenizer counts the spaces before the line break as part of the comment text; a rule that calls it therefore changes a comment.
- Indentation is changed through `Indentation` (`set()` a line and the comments above it, `normalize()` into the characters of the style) and `Token::getLineIndentation()`; `Token::setIndentation()` alone moves one line and leaves the rest of the statement where it was. `Indentation::findOwner()` and `findRole()` tell which construct a line-opening token continues and in what role, and `Indentation::infer()` gives the indentation such a line conventionally has, counted from the line its construct begins on: what the engine gives a line it has just opened for a required break, before the rule about indentation places it. `Indentation::opensLine()` says whether the line ending above a token is trivia, which is the only case its indentation is whitespace a rule may write: `Token::startsLine()` also answers yes after inline HTML, a heredoc body or a close tag, and there the leading whitespace is text.
- The indentation of every line is decided by one rule, `dresscode/indentation`, and it is a function of the tree alone: a line-opening token belongs to the lowest ancestor it does not begin, the slot it stands in has a `LayoutRole` (`LayoutData`, which the syntax layer generates for every slot), and the line is placed by that role at a level counted from the level the rule gave the line the ancestor begins on, never read from the text. A line no rule governs (the first token of a file, the code after inline HTML, an operator the options leave alone) is a fact the lines below count from. The rules that break a construct over lines (`braces-position`, `multi-line-call`, `multi-line-signature`, `multi-line-condition`, `multi-line-array`, `multi-line-chain`, `multi-line-ternary`, `single-statement-per-line`, `single-member-per-line`, `attribute-position`) are claims on the line breaks, and where the lines then stand is not their business; the engine gives an opened line the conventional indentation so that the shape is acceptable even when no rule about indentation runs. A claim that depends on the shape of the text (a list already broken, a line too long) must give every gap of the construct the same answer whatever the engine did to the gaps before it: the closure decides once per pass, from the shape the construct has when its first gap is reached (`Gap::once()`, which the engine remembers by rule and node until the pass ends, unlike `RuleContext::$storage`, which lives for the file), and a list counts as broken once any item or its closing delimiter begins a line, so that a decision to break it holds for the rest of the list. A rule that reads the indentation of a line to place another one reintroduces what this design removed: a wrong line that carries its neighbours with it and is a fixpoint afterwards. Code between pieces of inline HTML (a template with `<?php if ($a) { ?>` around markup) begins on lines the markup opens, and what those lines have is text the rule counts from as it is: such a file is not laid out by the tree, and PER exempts templates as well.
- The gap between two tokens (the whitespace when they share a line, the line break, the blank lines when there is one) is decided the same way, by claims rather than by procedures: a `GapRule` declares, per node class (or `*`) and slot (`'body'`, or `'statements:item'` for every item of a list, `'arguments:separator'` for its separators), the `Claim` it makes before and after the value of the slot (`space`, `line`, `blank`, `blankBelowComment`, each null when not claimed; the factories `Claim::single()`, `Claim::nextLine()`, `Claim::blank(1)` are the claims on one component, shared instances, and a rule with an option builds its claim once in `configure()`), a closure given the `Gap` (the token at its edge, the value or item the claim was made for and its index in the list, the `Style`) where that depends on the code (`?:`, `.` against the other operators, a keyword followed by `;`, the kind of the statement above), and `Engine\Gaps\Resolver` applies every such rule along the traversal of the formatting stage: entering a node hands the claims to the first and last tokens of its slot values and to each item of a list, reaching a token decides the gap before it component by component, the claim of a class before one of `*`, an inner slot before an ancestor's, the stricter space before the looser (`return;`), the blank lines both sides allow or the narrower of two counts that exclude each other, and hands what it decided to a `Gaps\Sink`: `Gaps\Fixer` reports under the name of the rule whose claim won and fixes; the messages of all three components are composed by `Gaps\Messages`. Blank lines are counted above the comment that stands on lines of its own above a token, because the comment goes with the code below it, except above a token that closes a construct (`LayoutRole::Closes`) or the file, where the comment belongs to what is above and the blank lines below it are what is counted; the blank lines between the last comment in the gap and the token are a component of their own, `blankBelowComment`, which the rule about declarations claims for a doc comment, so that no rule reaches into the trivia of a token for them. The open tag is trivia too, and the gap it stands in is decided like any other where the tag opens the code of the file (after nothing or a hashbang): a `Line::Next` there means the tag ends its line, which `blank-lines` claims; inside markup the tag's line is the template's and no rule breaks it. When the two sides disagree about the line, `Line::Next` wins over `Line::Same`. A required line break goes in first and the blank lines wait for the next pass, and a doc comment standing in front of the token on its line goes below with it, because it documents the token; a forbidden one is taken out only when nothing but whitespace stands in the gap, and where a comment stands there the claim is reported and left unfixed, and the settled round reports it again, so it is among what the fix leaves. Two plain claims on the same component of the same side of the same slot are a `ConfigurationException` when the rules are put together, so a gap has one owner; closures may share a slot because each abstains where the other decides, a plain claim shares it only with a plain claim on other components. Put together is also where a claim is checked against the slots the tree has (`LayoutData::Roles`, the same table the resolver hands the claims out by): a claim on a slot no node has, or `:item` and `:separator` on a slot holding no such list, is a `ConfigurationException`, because a slot renamed in the tree would otherwise leave the rule claiming gaps that never reach it, and neither a type nor a fixture would say a word. A gap rule is made of claims alone: `GapRule` and `NodeRule` are the two shapes of `Rule`, a class is one or the other, and a rule that also has to change tokens is two rules (`attribute-spacing` and `useless-attribute-parentheses`). A gap nobody claims is left alone.
- `Node::getChildren()` is the children in source order, empty slots left out, and the only way to the children: a node is not iterable, so that there is one way and it is an array, which the printer, the index and the traverser read directly. `Node::find()` takes a node class or a predicate and gives the descendants it accepts as a snapshot safe to iterate while mutating, `Node::findFirst()` stops at the first one; the `Traverser` walks in pre-order with `traverse($root, $enter, $leave)`, a callback steering it with `DontTraverseChildren` or `StopTraversal`, and it does not descend into a replaced node, skips siblings detached meanwhile and leaves inserted ones for the next walk.

## Rules and the engine

- A rule is one instance per run and stateless across files; per-file state lives in `RuleContext::$storage`. Its identity is the `#[RuleInfo]` name (`vendor/slug`); `RuleRegistry` maps names and classes and refuses a name owned by two classes.
- Every mutation must follow a `RuleContext::report()` that returned `true`. `PassRunner` pairs the two through `FileNode::$revision`: a callback that raised the revision without a report ("silent mutation") or after a report that returned `false` (silenced by a `dresscode:ignore` comment) breaks the contract; `strict` mode (RuleTester, `--strict-rules`) throws, otherwise it is a warning of the file. A denied report, by a comment or because the run refuses a risky fix, is judged by the window between it and the next report of the same rule, not by the whole callback, because a callback that reports many times may be denied one occurrence and allowed the next. What a fix leaves is not read from the reports at all: a rule may report every occurrence first and write its fixes afterwards, the whitespace of a gap is written for the whole traversal, and a rule may rewrite what another one reported, so no window of revisions says which report a mutation was for; `FileResult::$remaining` is what the rules report over the settled text instead, see below. Risk is a property of the occurrence, not of the rule: `report(risky: true)` says that fixing this one may change what the code does, the violation is recorded either way, and `false` comes back until the run is allowed to make such a fix (the configuration names the rule in `fixRisky`, or `--fix-risky` on the command line allows every such fix). The rule then leaves the code alone, and the violation says `risky` and `refused` and stays among what the fix leaves, so the summary can offer the refused ones; an occurrence the rule has no fix for is reported with `fixable: false`, which is never risky, never lets the rule mutate and is therefore never offered to the consent (`strict-call` on an explicit `false`, `type-hint-required` on a parameter with neither a type nor an annotation), and `RuleTester` fails a `// risky` fixture in which a risky violation remains, so a forgotten `fixable: false` is a failing test rather than a false offer; until it is fixed it is an error like any other, and a `dresscode:ignore` comment silences it like any other. An unqualified call of a global function in a namespace is such an occurrence wherever `NameResolver::getUnqualifiedResolution()` says `UnqualifiedResolution::Uncertain`, which `nameResolution: certain` of the project takes away, and the rule that rewrites it gives the reason after its message; a name the rule writes anew follows the name it replaces, or `NameResolver::getShortName()` where there is none. A rule whose every fix may change what the code does, because the code cannot tell it a safe occurrence, says so once with `risky` in its `#[RuleInfo]` and `RuleContext` makes every report of it risky: `strict-call` adds `$strict = true`, which changes what a loose comparison found, and `static-closure` cannot see a later `bindTo()`. Turning such a rule on, by name or by a preset, is not consent to the change: the project gives it by naming the rule in `fixRisky`, for the whole tree or in an override for a part of it, which a preset cannot (the resolver refuses it), and `--fix-risky` gives it to every rule for one run. A hook therefore needs no switch of its own: it fixes what the project accepted and reports the rest. Along the gap traversal the revision covers every rule of the stage, so the silent-mutation check is left out there: the whitespace of a gap is written by the engine and always after a report of its own.
- Every violation is an error until the configuration softens it: the `warnings` of a profile name the rules whose violations only warn, `PassRunner` stamps the severity when it makes the violation, and `RunResult::getExitCode()` counts the errors and syntax errors alone, with `--max-warnings` as the only threshold the warnings can cross. `keep` on a rule says what `false` says.
- A pass is one pre-order traversal per stage (`Structure`, `Formatting`, `Cleanup`); node rules are dispatched by `instanceof` on the node class, in configuration order within a stage, `enter()` and `leave()` apart and only for the rules that override them, and the gap rules ride along the traversal of the formatting stage. When a rule replaces or removes the node it was given, the rest of the chain for that node is skipped. Passes repeat until one changes nothing; the printed text of every mutating pass is hashed and a repeated state is a cycle, reported at once with the rules that mutated and a diff of the two states. Rules must therefore be idempotent and must not depend on the pass number, which the context does not expose.
- Violations carry positions from the original file (`Token::$originalLine`, the nearest original token before a synthetic one; `Trivia::$originalLine` when the report names a trivia, so that whitespace and comment problems land on their own line for suppression and baselines). A violation about whitespace that the fix of another violation brought about is **derived** from it: `Violation::$derivedFrom` names the fingerprint of the first violation of the chain, so that a report is true about the file on disk or says which violation made it true. The fixer remembers, per token, the violation it opened or closed the line before that token for, and a report about the gap before such a token (its blank lines, which wait for the next pass, the whitespace of a joined line, the indentation the engine inferred for an opened one) follows from it. A rule that places a line by what another line was given says so with `report(follows: $token)`, the token opening that line, and the report follows from whatever opened, closed or moved that line; `dresscode/indentation` names the line its construct begins on, so a block indented consistently wrong is one violation and the lines placed by it follow it, and a condition written again carries its continuation lines with it. Nothing else is derived: not a report on a tree another rule has changed, by that alone, and not even one on a token a fix wrote anew, which is often the user's code rebuilt (a group import expanded into statements, a gap moved in front of an inserted modifier), and a rule adding code writes it instead in the shape the other rules ask for (`NodeHelpers::addImport()`); not a report about a comment, which is the user's whatever line it stands on, and not the sibling claims of one decision, each about a break the user did not write. Those are not derived but one: the claims whose closure decided about a construct through `Gap::once()` are about its shape, so every gap of that construct is reported in the pass as a single violation, placed at its first report, silenced by a comment on that line and counted under one fingerprint (`Fingerprints::placeConstruct()`), and a rule of a shape is reported once per construct, which is what counting the places it decides needs. A derived violation is a violation like any other, in the JSON, under `dresscode:ignore` and in the exit code, because `fix` changes what `check` reports and the derived ones are changed too; only the console folds them under their ancestor. `RuleContext` keeps the reports of a callback as `Engine\Report`, with the gap and the line a report is about, and `PassRunner::account()` turns them into violations. The fingerprint (rule, message, normalized line content, occurrence within the pass) is made by `Engine\Fingerprints` at the moment of the report, so that the position is the one the reported code still had; repeated reports of one violation across passes collapse on it. **`fix` changes exactly what `check` reports**.
- Suppression is read once from the original comments before any mutation: `dresscode:ignore [names]` on a line silences that line, on its own line the nearest node starting on the next line, `disable`/`enable` a range, `ignore-file` everything.
- `FileProcessor` is a pure function of path and text: parse, passes, print, and the same again over the printed text until it settles, at most five rounds: a text the rounds come back to, or one still changing in the fifth, is a `ConvergenceException` and fails the file like a cycle of passes, because only a broken rule gets there. A mutated tree is not the tree the parser would build from the printed text, so a rule can miss what another one has just written; the text is what has to settle, not the tree. The violations reported are those of the first round, whose positions belong to the file as it was. What the last round reports is `FileResult::$remaining`, positioned in the fixed text: the last round is a full check of the text a fix writes, so it says exactly what the next check of that text reports, and the exit code of a fix and every listing of what a fix left read it, while a check says how many a fix would leave. A text that no longer parses is a failure of the fixer rather than a syntax error of the file. What a run reports therefore depends on which other rules are on: a rule that fixes a shape first takes away the report of a rule that would have met it later. A syntax error is a result, not an exception, and the `Style` follows the prevailing line ending of the file unless the configuration fixes one. `Runner::findFiles()` finds the files (patterns with a slash are anchored to the root, without one they match a segment at any depth, both also match directories on the way; a file named on the command line is taken as it is, and only `--skip-excluded`, which a hook or an editor naming every file it touches passes, lets the excluded paths leave it out like a found one) and `Runner::run()` takes that list, reads and writes the files and hands results to a `Reporter`. The caller expands the paths so that it knows the scope before the run starts; the header naming the configuration file and the scope belongs to `Console\Application`, which writes it only for the console and github formats, and so does the progress bar, drawn only for the console format on a terminal, and the warning in red that Xdebug is loaded, which makes a run many times slower and is detected only when the output is the process's own. A fix run lists every file it touched exactly once, with a `rewritten` note and under it what the fixed text still violates; which violation a fix removed cannot be told from the text, so the verdict counts what was found and what remains, and `--diff` shows what changed. The format is the whole contract of the output, never a switch modifying another one: `console` unless `--format` says otherwise, `github` when `GITHUB_ACTIONS` says the run is a step of a workflow, and `bare` for a hook, which prints the violations left to the user and a `rewritten` note for every file the fixer touched, so a clean run prints nothing while a silent rewrite never happens; the php-fixer plugin of `nette/claude-code` is such a hook, and it passes `--skip-excluded` with it. A rule exception or a cycle fails that one file (nothing is written, the run goes on, exit code 2), and so does a file whose text on the disk is no longer the one processed when the fix is about to write it, so that what an editor saved meanwhile is never overwritten; a syntax error is exit code 1 like a violation.
- A configuration is written as `dresscode.neon` or `dresscode.php`, and the two are the same thing said twice: every key of the NEON is a named argument of the constructor of `Config`, so `NeonReader` is a schema that accepts no key it does not know, the evaluation of entities and a spread into the constructor, and a test asserts that the two files of the fixture build an equal `Config`. The shape is shared: `Profile` holds what decides how a file is processed (`presets`, `rules`, `indent`, `eol`, `php`, `namespaces`, `nameResolution`, `fixRisky`, `warnings`), a preset is a profile under a name, an `Override` is a profile with the `paths` it applies to, and `Config` is the profile of the whole project with the scope of a run (`paths`, `excludePaths`, `fileExtensions`, `skipWhen`), its `overrides` and what it brings in (`extensions`, `analyses`). They are readonly values checked when they are constructed: a value one of them refuses is an `InvalidArgumentException`, which `NeonReader` and `Loader` turn into a `ConfigurationException` naming the file and the resolver into one naming the preset. What the PHP notation passes as an object or a callable (an extension, `skipWhen`, the factory of a rule or of an analysis) the NEON writes as an entity: `Class(args)` is a new object, `Class::method(args)` what the static method returns, `Class::method(...)` the method itself, and in a chain `Class(args)::method(args)` a link calls the method on what the link before it gave. An entity is evaluated when the file is read, except the one of a rule: a rule is built anew for every combination of overrides, so its entity is a recipe evaluated at every build, and only the class or method it starts from is looked up when the file is read, so that a misspelled one is still an error of the file. The schema keeps only the keys the file gave, so that an absent key keeps the default of the constructor. `Loader::find()` walks upwards and takes, in each directory, the local file before the `.dist` template; the two formats side by side are an ambiguity it refuses rather than resolves. A configuration file is the only thing laid over a project, and `--config` names it (its format follows its extension); a wrapper binary that wants a configuration to apply in a project without one hands `Console\Application` a `defaultConfig`, which the loader uses when it finds no file. The command line is no key of a file: `--preset` and `--rule` are a `Profile` laid over everything the file says, and `--only`, `--fix-risky` and `--strict-rules` are parameters of `RunnerFactory::createRunner()`.
- `extensions` names classes. A rule or a preset there is made known by its name, and an `Extension` is what a package brings to a project: its `getConfig()` is a `Config` that may set nothing but `extensions`, `analyses`, `excludePaths` and `skipWhen`, which `RunnerFactory` refuses otherwise. It lies below the project, the extensions it names below it and every class once: the excluded paths add up, a file any of them skips is skipped, and an analysis of the same class the project gives wins. How the code is written is no business of an extension; that is a preset, which the project names, so the standard of a project is always read in its own file.
- `PresetResolver::resolve()` lays the profiles that decide for a file one over another: the configuration, the overrides the file matches in the order they are written, and the command line, each above the presets it names with their parents, parents first and every preset once, where it is named first. A later layer has the last word on a value (`indent`, `eol`, `php`, `nameResolution`), adds to a list (`namespaces`, `fixRisky`, `warnings`) and merges the options it gives a rule with those of the layers below; the order of the rules is that of their first mention. Every mention of a rule is a layer, and the resolver turns the layers into a `ResolvedConfig`: what each rule ends up with, the layers that said it, the style, the target version of PHP, and for a rule that does not run the reason it does not. The run builds its instances from that one result. **A map of options merges with the layer below it key by key; a list and a scalar replace it, and a list also replaces its default.** Turning a rule off drops what was said before it, so a map written after that starts from the defaults of the schema again. A rule that is one decision says so with `RuleInfo::$decision`, the option a bare value written for the rule fills (`dresscode/yoda: forbidden`), which the resolver turns into that one-key layer before the layers meet, so the long and the short notation resolve to the same thing; a rule that declares none refuses a bare value and says which options it has. `keep` is the only word for "leave this alone" and it means the same at every level: on a rule it drops the rule from the run, in an option it takes that one place out of what the rule governs, so `null`, `false` and a turned-off rule never stand side by side for the one idea. The schema of such an option names `keep` among its values, the reference therefore shows it, and the rule turns it into whatever its own code calls "nothing to claim" in `configure()`. An option whose value is one of an enumeration may also take a list of them, and that list is a tolerance, not a set: every shape in it passes, and what is in none of them is written in the first. The rule turns the list into the shapes that pass and the target once, in `configure()`, decides per unit which it is (`Gap::once()` for a gap rule) and then claims the target alone; a rule that held one claim per tolerated shape would claim the same gap twice. What the predicate of a shape measures and how far the claims reach must be the same set of nodes, or the rule reports what it cannot fix, or fixes what it did not report. The merging is `Processor::processMultiple()` over the schema of the rule, which knows a map from a tuple; the policy that a list replaces is one line in the resolver, the `Helpers::PreventMerging` marker every `merge()` of `nette/schema` honours. What the schema warns about the options it completed, through `Context::addWarning()` in a `transform()` (that they leave the rule nothing to do), or what `nette/schema` warns itself (a deprecated option), reaches the user as `Rule <name>: <message>`, once however many overrides are resolved, so a message is a sentence of its own, and the resolver knows no rule by name. A preset that writes `true` over a parent that set options therefore keeps them, and a preset that wants something else says so. An override (`overrides` in NEON, `Override` in PHP) is a profile for a part of the tree, with every key a profile has: its `paths` go through the same matcher as the excluded paths, anchored to the root of the configuration. A file's configuration is therefore the combination of overrides it matches; `Config\FileProcessors` builds one processor per combination, with an `Analyses\Registry` of its own because an override may add to what the namespaces declare, and keeps it, because a rule carries the options it was configured with and must never be reconfigured under a file already being processed. Of a rule with risky fixes the resolution says whether the project accepts them (`ResolvedRule::$fixRisky`, which is also what the run allows), and a name in `fixRisky` whose rule runs nowhere, not even in an override, is a warning of every run. `only` (`--only`, a parameter of the run and no key of a file) narrows a run to the rules it names, a preset standing for every rule it and its parents mention, and it is one more reason of that resolution, applied to what the rest came to after `--preset` and `--rule`: it takes a rule away and never enables one, and a name that lets nothing in is an error rather than a run that checks nothing. `fix --only` fixes that one rule and leaves the rest, so the next full `fix` changes more, which is the point and not a failure to converge. A rule or preset is named either by class or by name, and a name without a vendor is the built-in one, so `per` and `dresscode/per` are the same preset. Without a configuration file the `dresscode/per` preset applies; `dresscode/psr12` and `dresscode/per` (its child) follow their specifications section by section and add no style of their own, so a rule whose fixed behaviour contradicts a specification gets an option rather than a preset-side workaround. A preset is a `Profile` under a name (`Preset::getProfile()`), whose `presets` are the ones it builds on; it may carry the style it needs, and it may not make a decision of the project, `php`, `nameResolution`, `fixRisky` or `warnings`, which the resolver refuses. The style is the last one a layer says, else a tab and the majority line ending of each file; `platform` is answered by the resolver, so what reaches the engine and the result cache is a line ending or `majority`. The excluded paths only ever add up, the default list, those of the extensions and those of the configuration, so no layer can bring back what another left out. A part of the tree where a rule must not run is an override that turns it off, so a later override may turn it on again. Every override is resolved on its own when the run is built, not when a file of it comes, so a name no rule or preset owns and an option no rule takes are an error naming the override rather than a line that does nothing until such a file comes.
- The version of PHP the rules target is a property of the checked project, never of the run: `RunnerFactory::resolvePhpVersion()` takes it from the key `php` of the configuration, else from `require.php` of the nearest `composer.json` at or above the root (the lower bound of its constraint as `composer/semver` parses it, cut to major.minor; a constraint without a lower bound, `<8.4` or `*`, leaves the version to the default rather than to a guess), else from `Config::DefaultPhpVersion`, and an override may give its files another one. Whichever it is, a version older than `Config::MinPhpVersion` is raised to it by the resolver with a warning, because no rule asks whether the target has what PHP 8.0 already has, so a fix may write such syntax. It travels as a plain string compared with `version_compare()`, never with the string operators, under which 8.9 outranks 8.10. NEON takes it with quotes or without them: a number is read as a version whose minor is a single digit, which every PHP ever released has had (5 reached 5.6, 7 reached 7.4, 8 is at 8.5), so `8` and `8.0` both mean 8.0. The running interpreter is never the answer, so that the same file gets the same verdict from any directory under any PHP; only `Lexer` asks about the runtime, to emulate the tokens its own build does not know. What PHP itself declares is the same kind of question, and a rule asks `Analyses\PhpSymbols` about it rather than `function_exists()` or reflection, which would answer with the extensions and the version of the machine: the catalog holds every version from 8.0 on, so what depends on the version, since when a function is deprecated, is compared with the target. A rule whose construct exists only from some version on says so with `requires: ['php' => '>=8.4']` in its `#[RuleInfo]`, named as the `require` of `composer.json` names it, and `PresetResolver` leaves it out below that version: silently when it came from a preset, with a warning when the configuration asked for it by name. A rule that needs the version more finely than "run me or not" asks `RuleContext::getPhpVersion()` instead, and never about anything PHP 8.0 already had.
- What the namespaces of the project declare is a property of the project too, and no file shows it: an unqualified function or constant in a namespace reaches the namespaced one PHP knows at run time before it falls back to the global one. `namespaces: {functions, constants}` lists such symbols as the items of a use statement write them (`App\Utils\{format, parse}`, parsed by `Parser` when the profile is constructed), and every layer adds to the lists; `nameResolution: certain` says the lists are all there is, which the configuration or an override says and a preset cannot, knowing a framework and not the project. An override may say `uncertain` for a part of the tree whose declarations nothing outside it reaches, such as the helpers of the tests, so that no fix there rests on the lists and nothing there is guarded. `PresetResolver` puts both into `ResolvedConfig`, with the layer that named each symbol, and `Analyses\Registry` builds `NameResolver` with them as `NamespacedSymbols`, which is also the analysis a rule asks for the lists themselves. A certain resolution rests on lists that must stay complete, so the key turns on their guard, `no-unlisted-namespaced-declaration`, as a layer of its own below the rules of the same profile, which may turn it off, and a file whose resolution ends up uncertain has no guard; a declaration the lists do not name is decidable in its file, a declaration inside a condition and a `define()` with its name written as a string among them (`NodeHelpers::findNamespacedDeclarations()`), and the lists can then go stale only through a path left out of the run or a package of the same namespace.
- A violation message describes the code, never the reader: no imperative (`Use…`, `Add…`, `Remove…`), because a rule that only reports has nothing to command. It takes one of three shapes, and which one is decided by the rule, not by taste: the required state as a noun phrase where the rule wants one short thing in one place (`A single space after a comma`), `<subject> must <requirement>` where that needs a sentence (`The opening brace must be on its own line`), and the defect where the thing is wrong in itself or the rule guards several places at once (`Function foo() is deprecated`, `Wrong whitespace in a type declaration`). A family shares one pattern: every `-spacing` rule says `No whitespace <where>`, `A single space <where>` or `At least one space <where>` with the token the claim is on as `<where>` (`before the closing parenthesis`, `after the return keyword`), composed by the engine, every `-indentation` rule `Wrong indentation of <what>`, every claim on a line break `A line break <where>` or `No line break <where>` with the bracket at the edge of the gap or the node the claim was made for as `<where>`, and the reason after a comma when the claim follows from a measure or a property of the code (`Claim::$because`: `A line break before the parameter, the line is 135 characters long`), every `-blank-lines` rule the measured `Expected <count> <place>, <found> found` composed by the engine from the node or token the claim was made for (`before the method`, `after the opening brace`), every `useless-` rule `Useless <what>` with the reason after a comma. The subject is the thing at the reported position, with a definite article, and an operator or a call in that role carries its kind (`The <> operator must be written !=`, `The is_null() call must be…`); `written X` names a literal replacement, `written as X` a form. A spelling the message shows — the one to type, and the one found when it holds a space — goes in single quotes (`must be written 'Exception'`, `The keyword 'YIELD FROM'`, `must start with '//', not '#'`), because a bare token at the end of a sentence has no visible end; what carries its own delimiter stays bare: a call the message only names (`is_null()`), an expression built from the code at hand (`$obj::class`), and a word that is not a spelling (`camelCase`, `the short syntax`). Names and measured values belong in the message, the rule name and the standard do not. In prose a `/** */` block is a `doc comment` and a tag in it an `annotation`, whatever the rule name calls them; `whitespace` is what a rule forbids, `a single space` what it requires.
- An option is named after the place or the shape it governs, and the bare name is that: `emptyBodies`, `onObjects`, `groupPerLine`, `betweenMembers`. The prefix `allow` is reserved for the permission of an exception the rule would otherwise report (`allowNested`, `allowMultiline`, `allowFullyQualifiedGlobalNames`), so it never stands in front of a choice of shape. One idea carries one name across the catalogue, whichever rule has it: `ignorePatterns` is the list of regular expressions whose match is never reported, wherever a rule takes one.
- An option carries a `description()` only where its name, type and default do not say everything: a hidden scope (`classes` also covers interfaces, traits and enums), a hidden condition (`afterOpeningBrace` does not apply when the first member is a method), an inclusive threshold, a value whose meaning is not its name (`nextLineAfterReturnType`); a description that restates the name is noise. Its form follows `RuleInfo::$description`: English, one sentence, capitalized, no trailing period. A count says where it applies ("Before the first member, unless…"), a boolean states what holds when true ("A class name referenced in a doc comment counts as used"), a choice names its values and what they do ("atLeastSingle keeps…, single collapses…"). Another rule is referred to by its full name (`beforeFirst of dresscode/blank-lines`). The text is checked against the code, not against the docblock of the rule.
- `Testing\RuleTester` runs a rule over `*.code` fixtures (`.expected` output beside them, `.violations` as `line: message`, options in a `// {"json"}` comment, a run that allows risky fixes in a `// risky` one, the targeted version in a `// php 8.4` one and what the namespaces declare outside the fixture in `// namespacedFunctions`, `// namespacedConstants` and `// nameResolution certain`, all in the comments that open the fixture; without a version the rule is tested at the version of PHP it requires, else at `Config::DefaultPhpVersion`, never at the version of the interpreter running the tests) and checks the contract: parent invariant, idempotence over the output, comments preserved unless `modifiesComments`, `dresscode:ignore-file` honored, no silent mutation. What no fixture catches, the runs over the corpus do: `name-meaning.phpt` runs the rules that write names and imports over the corpus and requires every name outside the imports to resolve to what it resolved to before, because an import moved into a statement writing its items differently, or dropped while something still uses it, leaves code that parses and round-trips and says nothing else.
