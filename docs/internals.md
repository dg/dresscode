# DressCode internals

How the syntax layer works: the facts an agent or a contributor needs before touching the lexer, the grammar, the nodes or the mutation API. Catalogs of nodes and rules are not here; they are generated from `grammar/nodes.php` and from the rules themselves.

## Layers

- `PhpSyntax` (`src/PhpSyntax/`): lexer, parser, tree, printer, navigation, mutation. It has no dependencies and never imports `DressCode\`, Nette, php-parser or anything from `vendor/`; a PHPStan rule (`LayerBoundaryRule`) enforces it.
- `DressCode` (`src/DressCode/`): engine, rules API, rules, configuration, CLI. Rules use only the public API of `PhpSyntax`; whatever a built-in rule needs from it is public API for plugins too.

## Tokens and trivia

The lexer (`PhpSyntax\Lexer\Lexer`) turns `PhpToken::tokenize()` output into significant tokens; whitespace, comments and open tags become `Trivia` attached to tokens:

- **Trailing trivia** of a token is everything after it up to and including the first end of line. **Leading trivia** of the next token is everything else (blank lines, indentation, comments on their own lines, doc comments). Whitespace is split into `Whitespace` runs and single `EndOfLine` pieces (`"\n"`, `"\r\n"` or a lone `"\r"`), so the leading trivia of a token starting a line looks like `[..., EndOfLine, Whitespace]`.
- Exceptions: an `OpenTag` trivia (`<?php` with its mandatory whitespace) is always leading trivia of the following token, and everything after it too; the final `EndOfFile` token has only leading trivia, never trailing; a token whose text ends with a newline (`CloseTag`, a heredoc start) ends its line the same way an `EndOfLine` does.
- `<?php` is not a token. `?>` is a token of kind `CloseTag` that keeps the newline PHP swallows after it, and the parser sees it as `;`; after a terminated statement it forms an `EmptyStatementNode`. `<?=` is a token of kind `OpenTagWithEcho` seen as `echo`. `Token::isSemicolon()` and `isOpenTagWithEcho()` cover these cases.
- Whitespace that PHP counts as part of a token stays in its text: inline HTML, `T_ENCAPSED_AND_WHITESPACE`, heredoc delimiters (the closing one keeps its indentation), casts like `( int )`.
- Trivia inside string interpolation (`"{$a /* c */ }"`) carry `inInterpolation = true`; the token helpers refuse to change them because that whitespace is part of the string value.
- A BOM or a hashbang line is inline HTML, as PHP sees it. A single-line comment never contains its newline, but it does contain trailing spaces before it.
- Token ids differ between PHP builds; `TokenKind::HostConstants` maps them by constant name. Syntax of PHP 8.4 and 8.5 on an older runtime is emulated by rewriting the raw token stream (`Lexer\Emulators`).

## Round trip

`Printer::print(parse($code)) === $code` byte for byte for any input PHP accepts, including BOM, hashbang, CR/CRLF, close tags, inline HTML and `__halt_compiler()` data. It is the invariant every change to the lexer, the grammar, the nodes or the printer must keep; the tests run it over the committed corpus (`tests/PhpSyntax/Parser/corpus/`) and, with `DRESSCODE_CORPUS` set, over an external tree. Formatting rules change trivia, structural rules change nodes; the printer is a concatenation and has no logic of its own.

## Parser and generated files

The parser is an LALR(1) driver over tables generated by phpyacc from `grammar/php.y`, a fork of the nikic/php-parser grammar with the PHP 7 branch and the error-recovery productions removed. Productions are never changed, only their semantic actions. `composer build` regenerates `src/PhpSyntax/Parser/ParserData.php`, `src/PhpSyntax/TokenKind.php` and the node classes in `src/PhpSyntax/Nodes/**` from `grammar/php.y` and `grammar/nodes.php`; the output is committed and CI checks that it is up to date. Every generated file says so with `@generated` in its header, which is how the node generator tells its own stale output from the handwritten classes it leaves alone, and how the check of this project leaves generated code out (`tools/SkipGenerated`); handwritten classes therefore live in `Nodes/` next to the generated ones without any path having to name them.

- Every grammar alternative with two or more symbols must have an action that uses every symbol, otherwise tokens would drop out of the tree; the build fails on such an alternative. A single symbol passes through, an empty alternative yields `null`.
- Actions may put plain arrays of slot values on the value stack (tails of alternative syntax, optional pairs such as `: type`); they are spread into the node constructor and never leave the parser.
- After parsing, statements following `namespace A;` are nested into that `NamespaceNode`, so every namespace has its statements as children; only `__halt_compiler()` stays outside.
- The data after `__halt_compiler();` is a token in `HaltCompilerNode::$data`.
- `Parser::parseExpression()`, `parseStatement()`, `parseType()` and `parseName()` parse a fragment inside a helper file and return the node detached, with empty trivia on its edges and without original positions. Plugins build new nodes this way; node constructors are `@internal`.

## Tree

- Every node class ends with `Node`; slots are named by role (`ifKeyword`, `openParen`, `semicolon`, `cond`, `body`), paired delimiters are always `open*`/`close*`. Every token of the source has a slot or a place in a list, so the order and number of children are not part of the API, only the slot names.
- Lists: `NodeList<T>` (statements, members, attribute groups) and `SeparatedNodeList<T>` (parameters, arguments, items, imports) with separator tokens between items and an optional trailing separator; `EmptyArrayItemNode` stands for nothing between two commas of a destructuring list. `ModifiersNode` holds modifier tokens in source order.
- The body of a control structure is a `StatementNode`, not necessarily a block; `else if` is an `ElseNode` whose body is an `IfNode`. The alternative syntax uses the same classes with `colon`, `stmts`, `endKeyword` and `semicolon` slots instead of `body`.
- Scalars keep their raw text (`IntegerNode::$token->text` is `0x1F`). Operators are one `BinaryNode`, `UnaryNode`, `PostfixNode`, `AssignNode` or `CastNode` with the operator token; names are one `NameNode` with a token of any kind, including keywords the grammar accepts as names; `NameNode::getRole()` tells from its place in the tree whether it stands for a class, a function, a constant or a namespace.
- Class-like declarations (`ClassNode`, `InterfaceNode`, `TraitNode`, `EnumNode`, `AnonymousClassNode`) implement the `ClassLikeNode` interface, because an anonymous class is not a statement.

## Analyses

An analysis is information derived from a file, and any class the engine can build is one: `NameResolver` (namespace, imports, resolution of class, function and constant names with the runtime fallback of unqualified functions and constants to the global namespace, `isGlobalFunctionCall()`), `Scope` (enclosing function-like construct and class, availability of `$this`, captured variables) and, in `DressCode`, `PhpDoc` (doc comments as phpstan/phpdoc-parser trees printed back with the original formatting). Analyses are lazy and computed once per file; `AnalysisRegistry` creates them on demand, with the `FileNode` when the constructor takes one, and throws them away as soon as `FileNode::$revision` changes, so any mutation invalidates every analysis of the file.

## Parents, mutation and the index

- A node or token belongs to exactly one tree: `$parent` is set by the parser and by the mutation API, and inserting a node that already has a parent throws; `clone` gives a deep copy without a parent.
- Slots are public but written only through the generated setters (`setCond()`, `replaceChild()`), which move parents and keep the index up to date; `TreeWriteRule` forbids direct writes outside the tree implementation. Lists mutate through `append()`, `insert()`, `removeItem()`, `replaceChild()`; `SeparatedNodeList::insert()` derives a missing separator from the existing ones (or `", "` in a one-line list) and gives the item the indentation of its neighbor in a multi-line list, `removeItem()` takes the separator after the item, or before the last one.
- `Node::remove()` removes a list item: a node alone on its lines takes the lines with it, otherwise the whitespace around stays; comments inside, each with the line ending after it, go to the next token, the previous token, or away, as the `CommentPolicy` says. `Node::replaceWith()` keeps the trivia around the old node around the new one by joining them with the new node's own edge trivia; a replacement cloned from nearby source still carries its original leading trivia, so clear the clone's edges first or an `OpenTag` gets doubled.
- The text and trivia of a token are written only through `setText()`, `setLeadingTrivia()` and `setTrailingTrivia()`, the same way slots are written through the setters of nodes; `TreeWriteRule` enforces both outside the tree implementation; the lexer and the parser go through the setters too, on tokens that are not in a file yet, which costs nothing. The setters are what keeps the index right: `FileNode` owns the `TokenIndex` (order, previous/next token, offset, line, column, visual column) built lazily and kept up to date rather than rebuilt. A structural change reports the children it adopted and released and, once complete, `structureChanged()`, and the index moves their tokens; a token setter reports `tokenChanged()` with the line endings the token gained or lost, and the lines before the token stay as they are; only offsets and columns are recomputed from scratch. The numbering and the lines of the tokens after a change are brought up to date lazily, as far as the queries reach, so the cost of a mutation followed by a query nearby is proportional to the distance, not to the file. A tree changed behind the back of the index is a `LogicException` at the next mutation, not a slow path. Every mutation increments `FileNode::$revision`, which the engine reads to detect mutations. A token carries its index and the index that numbered it (`Token::$index`, `Token::$indexedBy`, both `@internal`), which is how navigation finds the file without walking the parents; the shortcut is verified against the index before use, so a token moved to another tree falls back to the parents. Navigation from a detached subtree returns `null`.
- `Token::$originalLine` and `$originalOffset` never change and are the source of positions in reports; `getLine()` and `getColumn()` follow mutations.
- A single trivia (typically a comment) is removed by `Token::removeTrivia()`, which tidies the whitespace around it: one alone on its line takes the line with it, an inline one takes an adjacent space; `Token::replaceTrivia()` swaps one in place. A doc comment is read with `Node::getDocComment()` (above the node, or after the previous token) and, after editing through `Analyses\PhpDoc`, written back with `Node::replaceDocComment()` or dropped with `Node::removeDocComment()`. The tree is the phpstan/phpdoc-parser AST itself, which is therefore part of the public API (its major version is ours), and it is edited the way its format-preserving printer expects: replace `children` or return a new node from a visitor, never mutate a list such as `UnionTypeNode::$types` in place (it prints wrongly); a text node whose text changed loses its ` * ` line prefixes, so rewrite whole lines; a tree with nothing but blank text (`PhpDoc::isEmpty()`) is removed, not printed, or it prints `/**  */`. `NativeType` (annotation to native type) is the shared helper above the AST and `PhpDoc::findTemplates()` names the template types in scope, which a native type cannot use; there is no tag-editing layer of DressCode's own.
- Comment queries for rules that must not destroy a comment: `Token::hasComment()` (in the trivia of the token), `Token::hasCommentUpTo()` (anywhere between the texts of two tokens) and `Node::hasComment()` (inside the node, its outer edges excluded). `Node::matches()` compares two nodes by their token texts, `Node::isRepeatableRead()` tells whether reading an expression again is free of side effects; together they answer "does this assignment repeat its target". `NodeHelpers::isBoolean()` tells whether an expression is a boolean by its form, `NodeHelpers::negate()` builds its negation as a detached node; `ExpressionNode::isDereferenced()` tells whether the parent accesses a member or element of the expression, which is what decides whether parentheses around it can go.
- Horizontal whitespace between two tokens on a line is read and written through `Token::getTrailingSpace()` and `setTrailingSpace()`, which return or refuse `null` when a line ending, a comment or string content is in the way; `Token::is()` given a text never matches the content of a string, only operators and punctuation. `Token::getLineWidth()` measures the line of a token visually (tabs by the tab width of the style), which is how rules about line length decide.
- Indentation is changed through `Indentation` (`set()` a line and the comments above it, `shift()` the lines continuing a node by the same visual distance, `normalize()` into the characters of the style) and `Token::getLineIndentation()`; `Token::setIndentation()` alone moves one line and leaves the rest of the statement where it was.
- `Node::getChildren()` is the generated list of the children in source order, empty slots left out, and the only way to the children: a node is not iterable, so that there is one way and it is an array, which the printer, the index, the traverser and `attach()` read directly. `Node::getDescendants()` is a snapshot safe to iterate while mutating; the `Traverser` walks in pre-order, does not descend into a replaced node, skips siblings detached meanwhile and leaves inserted ones for the next walk.

## Rules and the engine

- A rule is one instance per run and stateless across files; per-file state lives in `RuleContext::getStorage()`. Its identity is the `#[RuleInfo]` name (`vendor/slug`); `RuleRegistry` maps names, aliases and classes and refuses a name owned by two classes.
- Every mutation must follow a `RuleContext::report()` that returned `true`. `PassRunner` pairs the two through `FileNode::$revision`: a callback that raised the revision without a report ("silent mutation") or after a report that returned `false` (suppressed by a `dresscode:ignore` comment) breaks the contract; `strict` mode (RuleTester, `--strict`) throws, otherwise it is a warning of the file.
- A pass is one pre-order traversal per stage (`Structure`, `Formatting`, `Cleanup`); rules are dispatched by `instanceof` on the node class, in configuration order within a stage, `enter()` and `leave()` apart and only for the rules that override them. When a rule replaces or removes the node it was given, the rest of the chain for that node is skipped. Passes repeat until one changes nothing; the printed text of every mutating pass is hashed and a repeated state is a cycle, reported at once with the rules that mutated and a diff of the two states. Rules must therefore be idempotent and must not depend on the pass number, which the context does not expose.
- Violations carry positions from the original file (`Token::$originalLine`, the nearest original token before a synthetic one; `Trivia::$originalLine` when the report names a trivia, so that whitespace and comment problems land on their own line for suppression and baselines); a violation reported on a tree already changed by another rule is `followUp`. `fixable` means the rule mutated after the report. The fingerprint (rule, message, normalized line content, occurrence) is stable across runs for baselines; repeated reports of one violation across passes collapse on it. A `Baseline` (JSON, per file and fingerprint, written by `check --generate-baseline` into the file named by `Config::baseline()`) silences the violations it knows in `Engine::processFile()`; the run counts the matched ones for the summary and warns about stale entries.
- Suppression is read once from the original comments before any mutation: `dresscode:ignore [names]` on a line silences that line, on its own line the nearest node starting on the next line, `disable`/`enable` a range, `ignore-file` everything; `phpcs:*` forms work through rule aliases.
- `FileProcessor` is a pure function of path and text: parse, passes, print, and the same again over the printed text until it settles, at most five rounds and a warning of the file when it does not. A mutated tree is not the tree the parser would build from the printed text, so a rule can miss what another one has just written; the text is what has to settle, not the tree. The violations reported are those of the first round, whose positions belong to the file as it was, and a text that no longer parses is a failure of the fixer rather than a syntax error of the file. What a run reports therefore depends on which other rules are on: a rule that fixes a shape first takes away the report of a rule that would have met it later. A syntax error is a result, not an exception, and the `Style` follows the prevailing line ending of the file unless the configuration fixes one. `Engine` finds the files (patterns with a slash are anchored to the root, without one they match a segment at any depth, both also match directories on the way), reads and writes them and hands results to a `Reporter`. A rule exception or a cycle fails that one file (nothing is written, the run goes on, exit code 2); a syntax error is exit code 1 like a violation. A `ResultCache` (one JSON file per project root in `cacheDir()` or the system temp) remembers the hash of every content that came out clean under the effective configuration (rules with options, style, PHP version, versions and git references of all installed packages, hashed by `EngineFactory::hashConfiguration()`); `Engine::run()` skips such a file with a `cached` result and, after a fix that left nothing unfixed, remembers the written content too. `--no-cache` disables it; `processFile()` (stdin) never uses it.
- Configuration composes presets parents first; a later mention overrides the whole entry (options are never deep-merged, a list option replaces its default) and the order of rules is that of the first mention. Options are validated by the rule's `nette/schema` and passed to `configure()` as an array. Without a configuration file the `dresscode/per` preset applies; `dresscode/psr12` and `dresscode/per` (its child) follow their specifications section by section and add no style of their own, so a rule whose fixed behaviour contradicts a specification gets an option rather than a preset-side workaround. A preset may carry the style it needs (`PresetInfo` `indent` and `eol`): the configuration's `style()` wins, then the last preset declaring one, then a tab and the prevailing line ending of each file.
- A violation message describes the code, never the reader: no imperative (`Use…`, `Add…`, `Remove…`), because a rule that only reports has nothing to command. It takes one of three shapes, and which one is decided by the rule, not by taste: the required state as a noun phrase where the rule wants one short thing in one place (`A single space after a comma`), `<subject> must <requirement>` where that needs a sentence (`The opening brace must be on its own line`), and the defect where the thing is wrong in itself or the rule guards several places at once (`Function foo() is deprecated`, `Wrong whitespace in a type declaration`). A family shares one pattern: every `-spacing` rule says `No whitespace <where>` or `A single space <where>`, every `-indentation` rule `Wrong indentation of <what>`, every `-blank-lines` rule the measured `Expected <count> <place>, <found> found` of `BlankLines::describe()`, every `useless-` rule `Useless <what>` with the reason after a comma. The subject is the thing at the reported position, with a definite article, and an operator or a call in that role carries its kind (`The <> operator must be written !=`, `The is_null() call must be…`); `written X` names a literal replacement, `written as X` a form. A spelling the message shows — the one to type, and the one found when it holds a space — goes in single quotes (`must be written 'Exception'`, `The keyword 'YIELD FROM'`, `must start with '//', not '#'`), because a bare token at the end of a sentence has no visible end; what carries its own delimiter stays bare: a call the message only names (`is_null()`), an expression built from the code at hand (`$obj::class`), and a word that is not a spelling (`camelCase`, `the short syntax`). Names and measured values belong in the message, the rule name and the standard do not. In prose a `/** */` block is a `doc comment` and a tag in it an `annotation`, whatever the rule name calls them; `whitespace` is what a rule forbids, `a single space` what it requires.
- An option carries a `description()` only where its name, type and default do not say everything: a hidden scope (`classes` also covers interfaces, traits and enums), a hidden condition (`afterOpeningBrace` does not apply when the first member is a method), an inclusive threshold, a value whose meaning is not its name (`nextLineAfterReturnType`); a description that restates the name is noise. Its form follows `RuleInfo::$description`: English, one sentence, capitalized, no trailing period. A count says where it applies ("Before the first member, unless…"), a boolean states what holds when true ("A class name referenced in a doc comment counts as used"), a choice names its values and what they do ("atLeastSingle keeps…, single collapses…"). Another rule is referred to by its full name (`beforeFirst of dresscode/function-spacing`). The text is checked against the code, not against the docblock of the rule.
- `Testing\RuleTester` runs a rule over `*.code` fixtures (`.expected` output beside them, `.violations` as `line: message`, options in a `// {"json"}` comment on the first lines) and checks the contract: parent invariant, idempotence over the output, comments preserved unless `modifiesComments`, `dresscode:ignore-file` honored, no silent mutation.
