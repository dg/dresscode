# DressCode internals

How DressCode works: the facts an agent or a contributor needs before touching the engine, a rule or the configuration. The catalog of rules is not here; it is generated from the rules themselves.

## Layers

- `phpsyntax/phpsyntax` (namespace `PhpSyntax`, a repository of its own): lexer, parser, tree, printer, navigation, mutation. Its internals are documented there; what a rule of DressCode uses from it is below.
- `DressCode` (`src/`): engine, rules API, rules, configuration, CLI. Rules use only the public API of `PhpSyntax`; whatever a built-in rule needs from it is public API for plugins too. The public, semver-stable surface of `DressCode` is `Config` with `Override` and `Extension`, `Rule` with `NodeRule` and `GapRule`, `ConfigurableRule`, `Claim`, `Space`, `Line` and `Gap`, `RuleInfo`, `RuleContext`, `Preset`, `PresetInfo`, `Profile`, `Violation`, `Reporter` with `FileResult` and `RunResult`, `Runner`, `Console\Application`, `Config\Loader`, `Analyses\*`, `Rules\*` and `Testing\RuleTester`; `Engine\*` and the rest of `Config\*` are `@internal`, as is `Analyses\Registry`.

## The tree a rule works with

Printing the tree reproduces the input byte for byte, so a rule changes what it means to change: formatting rules change trivia, structural rules change nodes.

- Whitespace, comments and open tags are `Trivia` attached to tokens. **Trailing trivia** of a token is everything after it up to and including the first end of line, **leading trivia** of the next token is everything else (blank lines, indentation, comments on their own lines, doc comments). An `OpenTag` trivia (`<?php` with its mandatory whitespace) is always leading trivia of the following token; the final `EndOfFile` token has only leading trivia.
- `<?php` is not a token. `?>` is a token of kind `CloseTag` that keeps the newline PHP swallows after it, and the parser sees it as `;`; after a terminated statement it forms an `EmptyStatementNode`. `<?=` is a token of kind `OpenTagWithEcho` seen as `echo`. `Token::isSemicolon()` and `isOpenTagWithEcho()` cover these cases.
- Whitespace that PHP counts as part of a token stays in its text: inline HTML, `T_ENCAPSED_AND_WHITESPACE`, heredoc delimiters (the closing one keeps its indentation), casts like `( int )`. A BOM or a hashbang line is inline HTML, as PHP sees it. A single-line comment never contains its newline, but it does contain trailing spaces before it.
- Trivia inside string interpolation (`"{$a /* c */ }"`) carry `inInterpolation = true`; the token helpers refuse to change them because that whitespace is part of the string value.
- Slots are named by role (`ifKeyword`, `openParen`, `semicolon`, `condition`, `body`), paired delimiters are always `open*`/`close*`, lists are plural. A slot says what stands in it rather than what the class suggests, so the left of an assignment is `target` and not a variable, and what a `switch` and a `match` compare against is `subject` and not a condition. Every token of the source has a slot or a place in a list, so the order and number of children are not part of the API, only the slot names. Whoever names a slot instead of reaching for it writes the name as a string (`'openParen'`, `'statements:item'`), which is what a gap rule declares its claims with.
- The body of a control structure is a `StatementNode`, not necessarily a block; `else if` is an `ElseNode` whose body is an `IfNode`. The alternative syntax uses the same classes with `colon`, `statements`, `endKeyword` and `semicolon` slots instead of `body`. Class-like declarations implement `ClassLikeNode`, because an anonymous class is not a statement.
- A new node comes from `Parser::parseExpression()`, `parseStatement()`, `parseType()` or `parseName()`, which return it detached, with empty trivia on its edges and without original positions; a constructor is public but its parameters follow the slots of the grammar, which a minor release may add to, so a call spells them as named arguments.

## Analyses

An analysis is information derived from a file, and any class the engine can build is one: `NameResolver` (namespace, imports, resolution of class, function and constant names with the runtime fallback of unqualified functions and constants to the global namespace, `isGlobalFunctionCall()`, and the way back: `getShortName()` gives the shortest way to write a fully qualified name where a node stands, through an alias, a prefix import or the namespace, and `isAliasFree()` says whether a name is still free there, which is what a rule adding an import asks) and `Scope` (enclosing function-like construct and class, availability of `$this`, captured variables). Analyses are lazy and computed once per file; `Analyses\Registry` (internal, reached through `RuleContext::getAnalysis()`, one for every combination of overrides, with the factories the `analyses` of the configuration and of its extensions give) creates them on demand, with the `FileNode` when the constructor takes one, and throws them away as soon as `FileNode::$revision` changes, so any mutation invalidates every analysis of the file.

## Mutation from a rule

- A node or token belongs to exactly one tree: inserting one that already has a parent throws; `clone` gives a deep copy without a parent.
- A slot is written by assignment (`$node->condition = $expression`, `replaceChild()`, or `setSlot()` given the name of the slot), which adopts the value, releases the current one and tells the index. Lists mutate through `append()`, `insert()`, `removeItem()`, `replaceChild()`; `SeparatedNodeList::insert()` derives a missing separator from the existing ones (or `", "` in a one-line list) and gives the item the indentation of its neighbor in a multi-line list, `removeItem()` takes the separator after the item, or before the last one.
- `Node::remove()` removes a list item: a node alone on its lines takes the lines with it, otherwise the whitespace around stays; comments inside, each with the line ending after it, go to the next token, the previous token, or away, as the `CommentPolicy` says. `Node::replaceWith()` keeps the trivia around the old node around the new one by joining them with the new node's own edge trivia; a replacement cloned from nearby source still carries its original leading trivia, so clear the clone's edges first or an `OpenTag` gets doubled.
- What a rule reads is a property (`value`, `base`, `quote`, `label`, `indentation`, `kind`, `parts`, `role`, `text`), and it writes one where the write takes a single value with a single consequence: a slot, and `NameNode::$text`, whose hook tokenizes the name anew. It writes through a method where the write takes more values or two things change together (`StringNode::setValue($value, ?$quote)`, the delimiter deciding how the value is written), and for a token always, because `?->` cannot stand on the left of an assignment: `Token::setText()`, `setLeadingTrivia()`, `setTrailingTrivia()`, and `Node::setEdgeTrivia()` for the outer edges of a node, where the first or the last token may be missing. What has no hook the language guards: the text and the trivia of a token are `private(set)`, the items of a list `protected(set)`, `parent` is written by `attachTo()`. A hooked property takes no indirect change, so `end($token->trailingTrivia)` needs a copy.
- Every mutation increments `FileNode::$revision`, which the engine reads to detect mutations; it is a version of the tree, not a count, because a compound mutation raises it several times. `Token::$originalLine` and `$originalOffset` never change and are the source of positions in reports; `getLine()` and `getColumn()` follow mutations.
- A single trivia (typically a comment) is removed by `Token::removeTrivia()`, which tidies the whitespace around it: one alone on its line takes the line with it, an inline one takes an adjacent space; `Token::replaceTrivia()` swaps one in place. A doc comment is read with `Node::getDocComment()` (above the node, or after the previous token), written back with `Node::replaceDocComment()` or dropped with `Node::removeDocComment()`.
- Comment queries for rules that must not destroy a comment: `Token::hasComment()` (in the trivia of the token), `Token::hasCommentUpTo()` (anywhere between the texts of two tokens) and `Node::hasComment()` (inside the node, its outer edges excluded); `Token::getComments()` and `Node::getComments()` give what those count, and a `Trivia` says of itself whether it `isDocComment()`, `isLineComment()` or `isMultiLine()` and hands over its text without the delimiters as `getCommentText()`. `Node::matches()` compares two nodes by their token texts, `ExpressionNode::isRepeatableRead()` tells whether reading an expression again is free of side effects; together they answer "does this assignment repeat its target". `ExpressionNode::isDereferenced()` tells whether the parent accesses a member or element of the expression, which is what decides whether parentheses around it can go.
- Horizontal whitespace between two tokens on a line is the trailing trivia of the first one, never the leading trivia of the second (a rule joining two lines writes the space there, or the next rule reading the gap sees none), and it is read and written through `Token::getTrailingSpace()` and `setTrailingSpace()`, which return or refuse `null` when a line ending, a comment or string content is in the way, or when the first token ends its line by its own text (a close tag, a heredoc start); `Token::is()` given a text never matches the content of a string, only operators and punctuation. `Token::getLineWidth()` measures the line of a token visually (tabs by the tab width of the style), which is how rules about line length decide. `Token::removeTrailingWhitespace()` also trims the end of a `//` or `#` comment, because the tokenizer counts the spaces before the line break as part of the comment text; a rule that calls it therefore changes a comment.
- Indentation is changed through `Indentation` (`set()` a line and the comments above it, `normalize()` into the characters of the style) and `Token::getLineIndentation()`; `Token::setIndentation()` alone moves one line and leaves the rest of the statement where it was. `Indentation::findOwner()` and `findRole()` tell which construct a line-opening token continues and in what role, and `Indentation::infer()` gives the indentation such a line conventionally has, counted from the line its construct begins on: what the engine gives a line it has just opened for a required break, before the rule about indentation places it. `Indentation::opensLine()` says whether the line ending above a token is trivia, which is the only case its indentation is whitespace a rule may write: `Token::startsLine()` also answers yes after inline HTML, a heredoc body or a close tag, and there the leading whitespace is text.
- `Node::getChildren()` is the children in source order, empty slots left out, and the only way to the children: a node is not iterable, so that there is one way and it is an array, which the printer, the index and the traverser read directly. `Node::find()` takes a node class or a predicate and gives the descendants it accepts as a snapshot safe to iterate while mutating, `Node::findFirst()` stops at the first one; the `Traverser` walks in pre-order with `traverse($root, $enter, $leave)`, a callback steering it with `DontTraverseChildren` or `StopTraversal`, and it does not descend into a replaced node, skips siblings detached meanwhile and leaves inserted ones for the next walk.

## Rules and the engine

- A rule is one instance per run and stateless across files; per-file state lives in `RuleContext::$storage`. Its identity is the `#[RuleInfo]` name (`vendor/slug`); `RuleRegistry` maps names and classes and refuses a name owned by two classes.
- Every mutation must follow a `RuleContext::report()` that returned `true`. `PassRunner` pairs the two through `FileNode::$revision`: a callback that raised the revision without a report ("silent mutation") or after a report that returned `false` (silenced by a `dresscode:ignore` comment) breaks the contract; `strict` mode (RuleTester, `--strict-rules`) throws, otherwise it is a warning of the file. A denied report, by a comment or because the run refuses a risky fix, is judged by the window between it and the next report of the same rule, not by the whole callback, because a callback that reports many times may be denied one occurrence and allowed the next. What a fix leaves is not read from the reports at all: a rule may report every occurrence first and write its fixes afterwards, the whitespace of a gap is written for the whole traversal, and a rule may rewrite what another one reported, so no window of revisions says which report a mutation was for; `FileResult::$remaining` is what the rules report over the settled text instead, see below. Risk is a property of the occurrence, not of the rule: `report(risky: true)` says that fixing this one may change what the code does, the violation is recorded either way, and `false` comes back until the run is allowed to make such a fix (the configuration names the rule in `fixRisky`, or `--fix-risky` on the command line allows every such fix). The rule then leaves the code alone, and the violation says `risky` and `refused` and stays among what the fix leaves, so the summary can offer the refused ones; an occurrence the rule has no fix for is reported with `fixable: false`, which is never risky, never lets the rule mutate and is therefore never offered to the consent (`strict-call` on an explicit `false`), and `RuleTester` fails a `// risky` fixture in which a risky violation remains, so a forgotten `fixable: false` is a failing test rather than a false offer; until it is fixed it is an error like any other, and a `dresscode:ignore` comment silences it like any other. A rule whose every fix may change what the code does, because the code cannot tell it a safe occurrence, says so once with `risky` in its `#[RuleInfo]` and `RuleContext` makes every report of it risky: `strict-call` adds `$strict = true`, which changes what a loose comparison found, and `static-closure` cannot see a later `bindTo()`. Turning such a rule on, by name or by a preset, is not consent to the change: the project gives it by naming the rule in `fixRisky`, for the whole tree or in an override for a part of it, which a preset cannot (the resolver refuses it), and `--fix-risky` gives it to every rule for one run. A hook therefore needs no switch of its own: it fixes what the project accepted and reports the rest. Along the gap traversal the revision covers every rule of the stage, so the silent-mutation check is left out there: the whitespace of a gap is written by the engine and always after a report of its own.
- Every violation is an error until the configuration softens it: the `warnings` of a profile name the rules whose violations only warn, `PassRunner` stamps the severity when it makes the violation, and `RunResult::getExitCode()` counts the errors and syntax errors alone, with `--max-warnings` as the only threshold the warnings can cross. `keep` on a rule says what `false` says.
- A pass is one pre-order traversal per stage (`Structure`, `Formatting`, `Cleanup`); node rules are dispatched by `instanceof` on the node class, in configuration order within a stage, `enter()` and `leave()` apart and only for the rules that override them, and the gap rules ride along the traversal of the formatting stage. When a rule replaces or removes the node it was given, the rest of the chain for that node is skipped. Passes repeat until one changes nothing; the printed text of every mutating pass is hashed and a repeated state is a cycle, reported at once with the rules that mutated and a diff of the two states. Rules must therefore be idempotent and must not depend on the pass number, which the context does not expose.
- Violations carry positions from the original file (`Token::$originalLine`, the nearest original token before a synthetic one; `Trivia::$originalLine` when the report names a trivia, so that whitespace and comment problems land on their own line for suppression and baselines). A violation about whitespace that the fix of another violation brought about is **derived** from it: `Violation::$derivedFrom` names the fingerprint of the first violation of the chain, so that a report is true about the file on disk or says which violation made it true. The fixer remembers, per token, the violation it opened or closed the line before that token for, and a report about the gap before such a token (its blank lines, which wait for the next pass, the whitespace of a joined line, the indentation the engine inferred for an opened one) follows from it. A rule that places a line by what another line was given says so with `report(follows: $token)`, the token opening that line, and the report follows from whatever opened, closed or moved that line. Nothing else is derived: not a report on a tree another rule has changed, by that alone, and not even one on a token a fix wrote anew, which is often the user's code rebuilt (a group import expanded into statements, a gap moved in front of an inserted modifier), and a rule adding code writes it instead in the shape the other rules ask for; not a report about a comment, which is the user's whatever line it stands on, and not the sibling claims of one decision, each about a break the user did not write. Those are not derived but one: the claims whose closure decided about a construct through `Gap::once()` are about its shape, so every gap of that construct is reported in the pass as a single violation, placed at its first report, silenced by a comment on that line and counted under one fingerprint (`Fingerprints::placeConstruct()`), and a rule of a shape is reported once per construct, which is what counting the places it decides needs. A derived violation is a violation like any other, in the JSON, under `dresscode:ignore` and in the exit code, because `fix` changes what `check` reports and the derived ones are changed too; only the console folds them under their ancestor. `RuleContext` keeps the reports of a callback as `Engine\Report`, with the gap and the line a report is about, and `PassRunner::account()` turns them into violations. The fingerprint (rule, message, normalized line content, occurrence within the pass) is made by `Engine\Fingerprints` at the moment of the report, so that the position is the one the reported code still had; repeated reports of one violation across passes collapse on it. **`fix` changes exactly what `check` reports**.
- Suppression is read once from the original comments before any mutation: `dresscode:ignore [names]` on a line silences that line, on its own line the nearest node starting on the next line, `disable`/`enable` a range, `ignore-file` everything.
- `FileProcessor` is a pure function of path and text: parse, passes, print, and the same again over the printed text until it settles, at most five rounds: a text the rounds come back to, or one still changing in the fifth, is a `ConvergenceException` and fails the file like a cycle of passes, because only a broken rule gets there. A mutated tree is not the tree the parser would build from the printed text, so a rule can miss what another one has just written; the text is what has to settle, not the tree. The violations reported are those of the first round, whose positions belong to the file as it was. What the last round reports is `FileResult::$remaining`, positioned in the fixed text: the last round is a full check of the text a fix writes, so it says exactly what the next check of that text reports, and the exit code of a fix and every listing of what a fix left read it, while a check says how many a fix would leave. A text that no longer parses is a failure of the fixer rather than a syntax error of the file. What a run reports therefore depends on which other rules are on: a rule that fixes a shape first takes away the report of a rule that would have met it later. A syntax error is a result, not an exception, and the `Style` follows the prevailing line ending of the file unless the configuration fixes one. `Runner::findFiles()` finds the files (patterns with a slash are anchored to the root, without one they match a segment at any depth, both also match directories on the way; a file named on the command line is taken as it is, and only `--skip-excluded`, which a hook or an editor naming every file it touches passes, lets the excluded paths leave it out like a found one) and `Runner::run()` takes that list, reads and writes the files and hands results to a `Reporter`. The caller expands the paths so that it knows the scope before the run starts; the header naming the configuration file and the scope belongs to `Console\Application`, which writes it only for the console and github formats, and so does the progress bar, drawn only for the console format on a terminal, and the warning in red that Xdebug is loaded, which makes a run many times slower and is detected only when the output is the process's own. A fix run lists every file it touched exactly once, with a `rewritten` note and under it what the fixed text still violates; which violation a fix removed cannot be told from the text, so the verdict counts what was found and what remains, and `--diff` shows what changed. The format is the whole contract of the output, never a switch modifying another one: `console` unless `--format` says otherwise, `github` when `GITHUB_ACTIONS` says the run is a step of a workflow, and `bare` for a hook, which prints the violations left to the user and a `rewritten` note for every file the fixer touched, so a clean run prints nothing while a silent rewrite never happens; the php-fixer plugin of `nette/claude-code` is such a hook, and it passes `--skip-excluded` with it. A rule exception or a cycle fails that one file (nothing is written, the run goes on, exit code 2), and so does a file whose text on the disk is no longer the one processed when the fix is about to write it, so that what an editor saved meanwhile is never overwritten; a syntax error is exit code 1 like a violation.
- A configuration is written as `dresscode.neon` or `dresscode.php`, and the two are the same thing said twice: every key of the NEON is a named argument of the constructor of `Config`, so `NeonReader` is a schema that accepts no key it does not know, the evaluation of entities and a spread into the constructor, and a test asserts that the two files of the fixture build an equal `Config`. The shape is shared: `Profile` holds what decides how a file is processed (`presets`, `rules`, `indent`, `eol`, `php`, `namespaces`, `nameResolution`, `fixRisky`, `warnings`), a preset is a profile under a name, an `Override` is a profile with the `paths` it applies to, and `Config` is the profile of the whole project with the scope of a run (`paths`, `excludePaths`, `fileExtensions`, `skipWhen`), its `overrides` and what it brings in (`extensions`, `analyses`). They are readonly values checked when they are constructed: a value one of them refuses is an `InvalidArgumentException`, which `NeonReader` and `Loader` turn into a `ConfigurationException` naming the file and the resolver into one naming the preset. What the PHP notation passes as an object or a callable (an extension, `skipWhen`, the factory of a rule or of an analysis) the NEON writes as an entity: `Class(args)` is a new object, `Class::method(args)` what the static method returns, `Class::method(...)` the method itself, and in a chain `Class(args)::method(args)` a link calls the method on what the link before it gave. An entity is evaluated when the file is read, except the one of a rule: a rule is built anew for every combination of overrides, so its entity is a recipe evaluated at every build, and only the class or method it starts from is looked up when the file is read, so that a misspelled one is still an error of the file. The schema keeps only the keys the file gave, so that an absent key keeps the default of the constructor. `Loader::find()` walks upwards and takes, in each directory, the local file before the `.dist` template; the two formats side by side are an ambiguity it refuses rather than resolves. A configuration file is the only thing laid over a project, and `--config` names it (its format follows its extension); a wrapper binary that wants a configuration to apply in a project without one hands `Console\Application` a `defaultConfig`, which the loader uses when it finds no file. The command line is no key of a file: `--preset` and `--rule` are a `Profile` laid over everything the file says, and `--only`, `--fix-risky` and `--strict-rules` are parameters of `RunnerFactory::createRunner()`.
- `extensions` names classes. A rule or a preset there is made known by its name, and an `Extension` is what a package brings to a project: its `getConfig()` is a `Config` that may set nothing but `extensions`, `analyses`, `excludePaths` and `skipWhen`, which `RunnerFactory` refuses otherwise. It lies below the project, the extensions it names below it and every class once: the excluded paths add up, a file any of them skips is skipped, and an analysis of the same class the project gives wins. How the code is written is no business of an extension; that is a preset, which the project names, so the standard of a project is always read in its own file.
- `PresetResolver::resolve()` lays the profiles that decide for a file one over another: the configuration, the overrides the file matches in the order they are written, and the command line, each above the presets it names with their parents, parents first and every preset once, where it is named first. A later layer has the last word on a value (`indent`, `eol`, `php`, `nameResolution`), adds to a list (`namespaces`, `fixRisky`, `warnings`) and merges the options it gives a rule with those of the layers below; the order of the rules is that of their first mention. Every mention of a rule is a layer, and the resolver turns the layers into a `ResolvedConfig`: what each rule ends up with, the layers that said it, the style, the target version of PHP, and for a rule that does not run the reason it does not. The run builds its instances from that one result. **A map of options merges with the layer below it key by key; a list and a scalar replace it, and a list also replaces its default.** Turning a rule off drops what was said before it, so a map written after that starts from the defaults of the schema again. A rule that is one decision says so with `RuleInfo::$decision`, the option a bare value written for the rule fills, which the resolver turns into that one-key layer before the layers meet, so the long and the short notation resolve to the same thing; a rule that declares none refuses a bare value and says which options it has. `keep` is the only word for "leave this alone" and it means the same at every level: on a rule it drops the rule from the run, in an option it takes that one place out of what the rule governs, so `null`, `false` and a turned-off rule never stand side by side for the one idea. The schema of such an option names `keep` among its values, the reference therefore shows it, and the rule turns it into whatever its own code calls "nothing to claim" in `configure()`. An option whose value is one of an enumeration may also take a list of them, and that list is a tolerance, not a set: every shape in it passes, and what is in none of them is written in the first. The rule turns the list into the shapes that pass and the target once, in `configure()`, decides per unit which it is (`Gap::once()` for a gap rule) and then claims the target alone; a rule that held one claim per tolerated shape would claim the same gap twice. What the predicate of a shape measures and how far the claims reach must be the same set of nodes, or the rule reports what it cannot fix, or fixes what it did not report. The merging is `Processor::processMultiple()` over the schema of the rule, which knows a map from a tuple; the policy that a list replaces is one line in the resolver, the `Helpers::PreventMerging` marker every `merge()` of `nette/schema` honours. What the schema warns about the options it completed, through `Context::addWarning()` in a `transform()` (that they leave the rule nothing to do), or what `nette/schema` warns itself (a deprecated option), reaches the user as `Rule <name>: <message>`, once however many overrides are resolved, so a message is a sentence of its own, and the resolver knows no rule by name. A preset that writes `true` over a parent that set options therefore keeps them, and a preset that wants something else says so. An override (`overrides` in NEON, `Override` in PHP) is a profile for a part of the tree, with every key a profile has: its `paths` go through the same matcher as the excluded paths, anchored to the root of the configuration. A file's configuration is therefore the combination of overrides it matches; `Config\FileProcessors` builds one processor per combination, with an `Analyses\Registry` of its own because an override may add to what the namespaces declare, and keeps it, because a rule carries the options it was configured with and must never be reconfigured under a file already being processed. Of a rule with risky fixes the resolution says whether the project accepts them (`ResolvedRule::$fixRisky`, which is also what the run allows), and a name in `fixRisky` whose rule runs nowhere, not even in an override, is a warning of every run. `only` (`--only`, a parameter of the run and no key of a file) narrows a run to the rules it names, a preset standing for every rule it and its parents mention, and it is one more reason of that resolution, applied to what the rest came to after `--preset` and `--rule`: it takes a rule away and never enables one, and a name that lets nothing in is an error rather than a run that checks nothing. `fix --only` fixes that one rule and leaves the rest, so the next full `fix` changes more, which is the point and not a failure to converge. A rule or preset is named either by class or by name, and a name without a vendor is the built-in one. The style is the last one a layer says, else a tab and the majority line ending of each file; `platform` is answered by the resolver, so what reaches the engine and the result cache is a line ending or `majority`. The excluded paths only ever add up, the default list, those of the extensions and those of the configuration, so no layer can bring back what another left out. A part of the tree where a rule must not run is an override that turns it off, so a later override may turn it on again. Every override is resolved on its own when the run is built, not when a file of it comes, so a name no rule or preset owns and an option no rule takes are an error naming the override rather than a line that does nothing until such a file comes.
- The version of PHP the rules target is a property of the checked project, never of the run: `RunnerFactory::resolvePhpVersion()` takes it from the key `php` of the configuration, else from `require.php` of the nearest `composer.json` at or above the root (the lowest version its constraint allows, read only from a shape that says it, `^V`, `~V`, `>=V` with or without an upper bound and `V - V` and alternatives of them; any other constraint leaves the version to the default rather than to a guess), else from `Config::DefaultPhpVersion`, and an override may give its files another one. Whichever it is, a version older than `Config::MinPhpVersion` is raised to it by the resolver with a warning, because no rule asks whether the target has what PHP 8.0 already has, so a fix may write such syntax. It travels as a plain string compared with `version_compare()`, never with the string operators, under which 8.9 outranks 8.10. NEON takes it with quotes or without them: a number is read as a version whose minor is a single digit, which every PHP ever released has had (5 reached 5.6, 7 reached 7.4, 8 is at 8.5), so `8` and `8.0` both mean 8.0. The running interpreter is never the answer, so that the same file gets the same verdict from any directory under any PHP; only `Lexer` asks about the runtime, to emulate the tokens its own build does not know. A rule whose construct exists only from some version on says so with `minPhpVersion` in its `#[RuleInfo]`, and `PresetResolver` leaves it out below that version: silently when it came from a preset, with a warning when the configuration asked for it by name. A rule that needs the version more finely than "run me or not" asks `RuleContext::getPhpVersion()` instead, and never about anything PHP 8.0 already had.
- What the namespaces of the project declare is a property of the project too, and no file shows it: an unqualified function or constant in a namespace reaches the namespaced one PHP knows at run time before it falls back to the global one. `namespaces: {functions, constants}` lists such symbols as the items of a use statement write them (`App\Utils\{format, parse}`, parsed by `Parser` when the profile is constructed), and every layer adds to the lists; `nameResolution: certain` says the lists are all there is, which the configuration or an override says and a preset cannot, knowing a framework and not the project. An override may say `uncertain` for a part of the tree whose declarations nothing outside it reaches, such as the helpers of the tests, so that no fix there rests on the lists and nothing there is guarded. `PresetResolver` puts both into `ResolvedConfig`, with the layer that named each symbol, and `Analyses\Registry` builds `NameResolver` with them as `NamespacedSymbols`, which is also the analysis a rule asks for the lists themselves.
- `Testing\RuleTester` runs a rule over `*.code` fixtures (`.expected` output beside them, `.violations` as `line: message`, options in a `// {"json"}` comment, a run that allows risky fixes in a `// risky` one, the targeted version in a `// php 8.4` one and what the namespaces declare outside the fixture in `// namespacedFunctions`, `// namespacedConstants` and `// nameResolution certain`, all in the comments that open the fixture; without a version the rule is tested at its `minPhpVersion`, else at `Config::DefaultPhpVersion`, never at the version of the interpreter running the tests) and checks the contract: parent invariant, idempotence over the output, comments preserved unless `modifiesComments`, `dresscode:ignore-file` honored, no silent mutation.
