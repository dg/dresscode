# DressCode internals

How DressCode works: the facts an agent or a contributor needs before touching the engine, a rule or the configuration.

## Layers

- `phpsyntax/phpsyntax` (namespace `PhpSyntax`, a repository of its own): lexer, parser, tree, printer, navigation, mutation. Its internals are documented there; what a rule of DressCode uses from it is below.
- `DressCode` (`src/`): engine, rules API, configuration, CLI. Rules use only the public API of `PhpSyntax`; whatever a rule of the core needs from it is public API for plugins too.

The public, semver-stable surface of `DressCode` is what the first list names, and the second names what is `@internal`. Every class of `src/` is in one of them, the more specific name deciding (a class before a namespace, a longer namespace before a shorter one). An item names its classes, namespaces or files first, the explanation follows a colon.

Public:

- `Config`, `Profile`, `Override`, `Plugin`, `PluginManifest`: the configuration
- `Decision`, `Domain`, `Domains\*`, `Value`, `Values`, `Config\Layer`, `Config\LayerKind`, `Config\Catalogue`: the decisions a rule declares, the values they take, the values decided for a file with the layer that said each, and the catalogue of them all
- `Rule`, `NodeRule`, `GapRule`, `RuleInfo`, `RuleContext`, `Claim`, `Space`, `Line`, `Gap`, `Style`, `ImportStyle`, `Violation`: the API of a rule
- `Stage`, `Severity`, `Tristate`, `Risk`: the enums
- `exceptions.php`, `Testing\exceptions.php`: the exceptions
- `FileResult`: the result of a file
- `Console\Application`, `Console\UsageException`: a program embedding a run goes through them
- `Analyses\*`, `Rules\*`: the analyses and the rules
- `Testing\RuleTester`: the tester

Internal:

- `Engine\*`, `Config\*`, `Console\*`: the engine, the configuration and the console
- `Reporter`, `Reporters\*`: the formats of the output, whose contract is the output itself, and the interface they implement next to them; they print the `Engine\RunResult` of a run
- `Analyses\Registry`: the machinery of the analyses

Of the public classes, the constructors of `Gap` and `RuleContext` and the methods marked `@internal` (`Value::__construct()`, `Value::keep()`, `Values::__construct()`, `reportGap()`, `hasReports()`, `takeReports()`, `Config::MinPhpVersion`, `FileResult::markWritten()`) are the engine's alone. For a rule the name and the namespace of its class are public, so that a configuration can name it by class, while its methods are not. A rule never asks another one: what two rules share is a decision of a tree, which a rule that only reads it names in `RuleInfo::$reads` and reads from its values, the style of the run (`Style`, its imports among it), or an analysis of the file (`Analyses\IndentationPlan`).

## The tree a rule works with

Printing the tree reproduces the input byte for byte, so a rule changes what it means to change: formatting rules change trivia, structural rules change nodes.

- Whitespace, comments and open tags are `Trivia` attached to tokens. **Trailing trivia** of a token is everything after it up to and including the first end of line, **leading trivia** of the next token is everything else (blank lines, indentation, comments on their own lines, doc comments). An `OpenTag` trivia (`<?php` with its mandatory whitespace) is always leading trivia of the following token; the final `EndOfFile` token has only leading trivia.
- `<?php` is not a token. `?>` is a token of kind `CloseTag` that keeps the newline PHP swallows after it, and the parser sees it as `;`; after a terminated statement it forms an `EmptyStatementNode`. `<?=` is a token of kind `OpenTagWithEcho` seen as `echo`. A rule tells them by their kind, `$semicolon->is(Token::CloseTag)`.
- Whitespace that PHP counts as part of a token stays in its text: inline HTML, `T_ENCAPSED_AND_WHITESPACE`, heredoc delimiters (the closing one keeps its indentation), casts like `( int )`. A BOM or a hashbang line is inline HTML, as PHP sees it. A single-line comment never contains its newline, but it does contain trailing spaces before it.
- Trivia inside string interpolation (`"{$a /* c */ }"`) carry `inInterpolation = true`; the token helpers refuse to change them because that whitespace is part of the string value.
- Slots are named by role (`ifKeyword`, `openParen`, `semicolon`, `condition`, `body`), paired delimiters are always `open*`/`close*`, lists are plural. A slot says what stands in it rather than what the class suggests, so the left of an assignment is `target` and not a variable, and what a `switch` and a `match` compare against is `subject` and not a condition. Every token of the source has a slot or a place in a list, so the order and number of children are not part of the API, only the slot names. Whoever names a slot instead of reaching for it writes the name as a string (`'openParen'`, `'statements:item'`), which is what a gap rule declares its claims with.
- The body of a control structure is a `StatementNode`, not necessarily a block; `else if` is an `ElseNode` whose body is an `IfNode`. The alternative syntax uses the same classes with `colon`, `statements`, `endKeyword` and `semicolon` slots instead of `body`. Class-like declarations implement `ClassLikeNode`, because an anonymous class is not a statement.
- A new node comes from `Builder`: `expression()`, `statement()`, `type()`, `name()` and `fragment()` (a node of the class given) parse a piece of code and return it detached, with empty trivia on its edges and without original positions. Where it is put together from nodes already at hand, the template names them as placeholders (`$builder->expression('count($x) > 0', x: $array)`), each put in by `replaceWithExpression()`, and what data decide (a name from a variable, an operator as a string, a varying number of arguments) is a method of the builder (`call()`, `methodCall()`, `staticMethodCall()`, `new()`, `arguments()`, the fetches, `binary()`, `unary()`, `cast()`, `ternary()`, `assign()`, `parenthesize()`, `value()` for a literal), so that a rule neither glues code from the text of nodes nor hunts a placeholder down afterwards. A name, an identifier and a string literal are also made from their text or value (`NameNode::fromText()`, `IdentifierNode::fromText()`, `StringNode::fromValue()`), a `Token` and a `Trivia` by `Token::fromText()` and `Trivia::fromText()`, which give the kind PHP gives the text. A node constructor is `@internal`, its parameters following the slots of a grammar the next version of PHP may extend.

## Analyses

An analysis is information derived from a file, and any class the engine can build is one: `NameResolver` (namespace, imports, resolution of class, function and constant names with the runtime fallback of unqualified functions and constants to the global namespace, `isGlobalFunctionCall()`, and the way back: `shortenName()` gives the shortest way to write a fully qualified name where a node stands, through an alias, a prefix import or the namespace, and `isAliasFree()` says whether a name is still free there, which is what a rule adding an import asks) and `Scope` (availability of `$this`; the enclosing function-like construct and class are `findAncestor(FunctionLikeNode::class)` and `findAncestor(ClassLikeNode::class)` of the node, no analysis).

Analyses are lazy and computed once per file. `Analyses\Registry`, reached through `RuleContext::getAnalysis()`, one for every combination of overrides, with the factories the `analyses` of the configuration and of its plugins give (given the `FileNode` and the path of the file), creates them on demand, with the `FileNode` when the constructor takes one, and throws them away as soon as `FileNode::$revision` changes, so any mutation invalidates every analysis of the file, and all of them once the passes over the file are over (`Registry::endFile()`). A rule names in `RuleInfo::$analyses` every analysis it asks for, through `RuleContext`, through `Gap` or through a helper it calls, and a strict run refuses one it does not name, so that what a rule depends on stands in its attribute.

## Mutation from a rule

### Writing the tree

- A node or token belongs to exactly one tree: inserting one that already has a parent throws; `clone` gives a deep copy without a parent.
- A slot is written by assignment (`$node->condition = $expression`, or `replaceChild()`), which adopts the value, releases the current one and tells the index. Lists mutate through `append()`, `insert()` and its `insertAfter()` and `insertBefore()` an item already there, `removeItem()`, `replaceChild()`; `SeparatedNodeList::insert()` derives a missing separator from the existing ones (or `", "` in a one-line list) and gives the item the indentation of its neighbor in a multi-line list, `removeItem()` takes the separator after the item, or before the last one. `Node::getNextSibling()` and `getPreviousSibling()` are the neighboring items of the list, null at its ends. `BlockNode::unwrap()` moves the statements of a block standing among statements into its place and removes the braces, their comments going before the first statement and after the last one; the statements keep their indentation, which `Indentation::shift()` moves a level up.
- `Node::remove()` removes a list item: a node alone on its lines takes the lines with it, otherwise the whitespace around stays; the comments it owns (inside it, on its line, its doc comment and those right above it), each with the line ending after it, go to the next token, the previous token, or out of the tree with the node, as the `CommentPolicy` says, so that no rule loses a comment by removing a node; a comment above it set apart by a blank line, the header of a section, stays where it is. The doc comment of a removed declaration therefore lands above the next one, and a rule removing a declaration that may carry one refuses it or takes it out with `CommentPolicy::StayWithNode` under `modifiesComments`. The blank lines around the node stay, both gaps joined into one; `remove(mergeBlankLines: true)` leaves the narrower of the two instead, so that removing a member leaves the spacing of the class as it was. `Node::replaceWith()` keeps the trivia around the old node around the new one by joining them with the new node's own edge trivia; a replacement cloned from nearby source still carries its original leading trivia, so that an `OpenTag` gets doubled. A node standing in the tree that a rule hands to the builder comes in as a copy without the trivia on its edges, as many times as it is given; one written into another place by assignment or `replaceWith()` is taken with `Node::withoutEdgeTrivia()`, the copy without them, never with `clone`.
- What a rule reads is a property (`value`, `base`, `quote`, `label`, `indentation`, `kind`, `parts`, `role`, `text`), and it writes one where the write takes a single value with a single consequence: a slot, and `NameNode::$text`, whose hook tokenizes the name anew. It writes through a method where the write takes more values or two things change together (`StringNode::setValue($value, ?$quote)`, the delimiter deciding how the value is written), and for a token always, because `?->` cannot stand on the left of an assignment: `Token::setText()`, `setLeadingTrivia()`, `setTrailingTrivia()`, and `Node::setEdgeTrivia()` for the outer edges of a node, where the first or the last token may be missing.
- What has no hook the language guards: the text and the trivia of a token are `private(set)`, the items of a list its own storage, written by its methods alone, and `parent` is written by the nodes when they adopt or release a child. Such a property takes no indirect modification from outside, and neither does the hooked `leadingTrivia` or `trailingTrivia` of a node, so `end($token->trailingTrivia)`, which takes its argument by reference, needs a copy.
- Every mutation increments `FileNode::$revision`, which the engine reads to detect mutations; it is a version of the tree, not a count, because a compound mutation raises it several times. `Token::$line` and `$pos`, inherited from `PhpToken`, never change and are the source of positions in reports; `getCurrentLine()`, `getCurrentColumn()` and `getCurrentOffset()` follow mutations.

### Comments and doc comments

- A single trivia (typically a comment) is removed by `Token::removeTrivia()`, which tidies the whitespace around it: one alone on its line takes the line with it, an inline one takes an adjacent space; `Token::replaceTrivia()` swaps one in place.
- A rule that must not destroy a comment asks `Token::hasComment()` (in the trivia of the token), `Token::hasCommentUpTo()` (anywhere between the texts of two tokens) or `Node::hasInnerComment()` (inside the node, its outer edges excluded, walking the whole subtree, so it is asked of a candidate only), and by place `hasLeadingComment()` and `hasTrailingComment()` of a node (on its outer edges) and of a token (on either side of its text, which `hasComment()` asks of both at once); `Token::getComments()`, `Node::getInnerComments()` and the `getLeadingComments()` and `getTrailingComments()` of both give what those count, and a `Trivia` says of itself whether it `isComment()`, `isLineComment()` or `isMultiLineComment()`, a doc comment being `is(Trivia::DocComment)`, and hands over its text without the delimiters as `getCommentText()`.
- A doc comment is read with `Node::getDocComment()` (above the node, or after the previous token).

### What the rules share

- `Node::matches()` compares two nodes by their token texts and `ExpressionNode::isRepeatableRead()` tells whether reading an expression again is free of side effects; together they answer "does this assignment repeat its target". `ExpressionNode::isDereferenced()` tells whether the parent accesses a member or element of the expression, which is what decides whether parentheses around it can go.
- Whether an expression may be written in place of another, in a string where its interpolation may not take it or braces would read as `${`, is asked of the tree: `ExpressionNode::checkReplaceWithExpression()` throws what `replaceWithExpression()` would, and a rule reports the reason with the occurrence it leaves.
- Whether an expression a rule writes into a place needs parentheses there is not the rule's to decide: `ExpressionNode::replaceWithExpression()` puts it in and keeps the parentheses `ParenthesizedNode::isRedundant()` does not call needless, by the precedence of both sides and by what follows the place, and `Builder::parenthesize()` writes the ones a rule wants for the reader alone. A rule with a list of operators of its own for that is a rule with an answer of its own.
- A rule that writes a call or a node of its own gives the builder the arguments and the operands it keeps as they stand, and the builder copies them without the trivia of their edges: the trailing trivia of the closing parenthesis belongs to what follows the call, which `replaceWith()` keeps on the node it replaces, so a copy that brought it along would write the space or the line ending twice. A rule that writes such a node into a slot itself takes it with `withoutEdgeTrivia()` for the same reason. A fixture ending every call with a semicolon never shows it.
- PHP binds a function or a class declared at the top level of a file or of a namespace before the code runs, and one inside a function, a loop or a branch only when the code reaches it. A rule that moves statements out of a branch therefore keeps a branch declaring one where it stands at the top level, because the move would bind the declaration whatever the condition says.
- A rule adding code writes it in the shape the other rules ask for, so that they find nothing to add.

### Whitespace and indentation

- Horizontal whitespace between two tokens on a line is the trailing trivia of the first one, never the leading trivia of the second (a rule joining two lines writes the space there, or the next rule reading the gap sees none), and it is read and written through `Token::getTrailingSpace()` and `setTrailingSpace()`, which answer `null` and refuse where no such whitespace is there to write. `Token::is()` given a text never matches the content of a string, only operators and punctuation. `Indentation::measureLineWidth()` measures a line visually, tabs by the tab width of the style.
- The style a rule gets from `RuleContext::$style` and `Gap::$style` is `DressCode\Style`: the indentation, the line ending, the tab width and `maxLineLength`, the widest line that passes (null for none), which every rule that breaks or reports a long line reads instead of a threshold of its own, and `$imports`, the `ImportStyle` an import a rule adds is written in (each kind separate or combined, whether a group use stays, null for a kind the file decides). What PhpSyntax measures and writes whitespace with (`Indentation`, `Indentation::measureLineWidth()`, `Token::getVisualColumn()`) takes `PhpSyntax\Style`, which has no line length, and gets it from `toPhpSyntax()`.
- `Token::removeTrailingWhitespace()` also trims the end of a `//` or `#` comment, because the tokenizer counts the spaces before the line break as part of the comment text; a rule that calls it therefore changes a comment. Where the line goes on it takes the space before the next token as well, joining the two, so it is for a token that ends its line.
- Indentation is changed through `Indentation` and `Token::getLineIndentation()`; `Token::setIndentation()` alone moves one line and leaves the rest of the statement where it was. `Indentation::opensLine()` says whether the line ending above a token is trivia, which is the only case its indentation is whitespace a rule may write: `Token::startsLine()` also answers yes after inline HTML, a heredoc body or a close tag, and there the leading whitespace is text.

The rules that break a construct over lines are claims on the line breaks, and where the lines then stand is not their business; the engine gives an opened line the conventional indentation (`Indentation::infer()`), so that the shape is acceptable even when no rule about indentation runs.

### Gaps

The gap between two tokens (the whitespace when they share a line, the line break, the blank lines when there is one) is decided by claims rather than by procedures. A `GapRule` declares, per node class (or `*`) and slot (`'body'`, or `'statements:item'` for every item of a list, `'arguments:separator'` for its separators), the `Claim` it makes before and after the value of the slot: `space`, `line`, `blankLines`, `blankLinesBelowComment`, each null when not claimed. The factories `Claim::singleSpace()`, `Claim::nextLine()`, `Claim::blankLines(1)` are the claims on one component, shared instances, and a rule with an option builds its claim once in `configure()`. Where the claim depends on the code (`?:`, `.` against the other operators, a keyword followed by `;`, the kind of the statement above) it is a closure given the `Gap`: the token at its edge, the value or item the claim was made for and its index in the list, the `Style`.

A claim of `*` applies to every class that has the slot, so it is right only where the slot means the same thing in all of them (the `openBrace` of a block is not the one of `$o->{$m}`, the `body` of a statement is not the one of a `match` arm), and elsewhere it names the classes. A claim must also be right on its own: the stricter claim wins only among the rules that are on, and a fixture runs its rule alone, so a claim right only thanks to another rule passes its fixture and breaks under a preset.

A claim that depends on the shape of the text (a list already broken, a line too long) must give every gap of the construct the same answer whatever the engine did to the gaps before it: the closure decides once per pass, from the shape the construct has when its first gap is reached (`Gap::once()`, which the engine remembers by rule and node until the pass ends), and a list counts as broken once any item or its closing delimiter begins a line, so that a decision to break it holds for the rest of the list.

`Engine\Gaps\Resolver` applies every gap rule along the traversal of the formatting stage: entering a node hands the claims to the first and last tokens of its slot values and to each item of a list, and reaching a token decides the gap before it component by component. The claim of a class goes before one of `*`, an inner slot before an ancestor's, the stricter space before the looser (`return;`), and of blank lines the count both sides allow or the narrower of two counts that exclude each other. When the two sides disagree about the line, `Line::Next` wins over `Line::Same`. What was decided goes to a `Gaps\Sink`: `Gaps\Fixer` reports under the decision of the claim that won and fixes; the messages of all three components are composed by `Gaps\Messages`. The claims are checked and indexed by class and slot once for a configuration, by `Gaps\Claims`, which `Engine\RulePlan` holds together with the node rules of each stage, the classes each of them is dispatched to and the gate of the reports of every rule; `FileProcessor` makes the plan when it is made itself and the runner of every file reads it, keeping only what belongs to the file and the pass, and `Runner::run()` makes the processor of every file it will process before the first one, so that rules the configuration does not fit are a mistake of the configuration (exit code 3), never a failure inside a file.

Blank lines are counted above the comment that stands on lines of its own above a token, because the comment goes with the code below it, except above a token that closes a construct (`LayoutRole::Closer`) or the file, where the comment belongs to what is above and the blank lines below it are what is counted. The blank lines between the last comment in the gap and the token are a component of their own, `blankLinesBelowComment`, so that no rule reaches into the trivia of a token for them.

The open tag is trivia too, and the gap it stands in is decided like any other where the tag opens the code of the file (after nothing or a hashbang): a `Line::Next` there means the tag ends its line; inside markup the tag's line is the template's and no rule breaks it. A gap inside a string (an interpolation, a heredoc, backticks) or next to a close tag, inline HTML or the data after `__halt_compiler()` is printed text, and the resolver decides nothing there whatever is claimed.

A claim of no whitespace is a claim of a single space between two tokens the lexer would read as something else once they touch (`Lexer::canAdjoin()`): `- -$a` is not `--$a`, whatever a rule says about the space after an operator.

A required line break goes in first and the blank lines wait for the next pass, and a doc comment standing in front of the token on its line goes below with it, because it documents the token. A forbidden line break is taken out only when nothing but whitespace stands in the gap; where a comment stands there the claim is reported and left unfixed, and the settled round reports it again, so it is among what the fix leaves.

Two plain claims on the same component of the same side of the same slot are a `ConfigurationException` when the rules are put together, so a gap has one owner; closures may share a slot because each abstains where the other decides, a plain claim shares it only with a plain claim on other components. Put together is also where a claim is checked against the slots the tree has (`LayoutData::Roles`, the same table the resolver hands the claims out by): a claim on a slot no node has, `:item` and `:separator` on a slot holding no such list, or `*` for the slot anywhere but in `*.*:item` and `*.*:separator`, the items and separators of every list, is a `ConfigurationException`, because a slot renamed in the tree would otherwise leave the rule claiming gaps that never reach it, and neither a type nor a fixture would say a word.

Two closures deciding one component on one side of one slot at the same gap are refused there, so rules whose closures share a slot abstain by a predicate they both read, not by two that happen to agree, and where no predicate can say which rule decides, a rule claims the break from the other side of the gap. An empty pair of braces has one gap and not two, and it belongs to the closing brace, so a claim after the opening one abstains there; the braces of a `BlockNode` are claimed through the block, whose parent says whether it is a body.

A gap rule is made of claims alone: `GapRule` and `NodeRule` are the two shapes of `Rule`, a class is one or the other, and a rule that also has to change tokens is two rules. `RulePlan` refuses with a `ConfigurationException` what would never run: a rule of neither shape, a gap rule whose `RuleInfo` names another stage than `Formatting`, where the engine settles every claim, and a visited class that is no class of a node or a token, nor an interface. A gap nobody claims is left alone.

### Traversal

`Node::getChildren()` is the children in source order, empty slots left out, and the only way to the children: a node is not iterable, except a list (`NodeList`, plain or separated), which is read as a collection of its items, and `ModifiersNode` over its tokens, so that there is one way and it is an array, which the printer, the index and the traverser read directly. `Node::find()` takes a node class, optionally narrowed by a predicate, and gives the descendants it accepts as a snapshot safe to iterate while mutating; `Node::findFirst()` stops at the first one. The `Traverser` walks in pre-order; it does not descend into a node a callback replaced, skips siblings detached meanwhile and leaves inserted ones for the next walk.

## Rules and the engine

### Identity

A rule is one instance per run and stateless across files. It has no name: what a user writes, reads in a report, silences and accepts is a decision, and the rule is known by its class, in the profile, in a fixture and in the message of a broken contract. Every rule declares or names a decision at least, and one that has none is a mistake of the configuration, refused by the catalogue and by the plan. It reports an occurrence under the path of the decision it violates (the `decision` of `report()`, `Claim::$decision`), which only a rule of one requirement leaves out; a report under a decision the rule does not declare or under a parameter is a broken contract, and one under a requirement that is `keep` or narrowed away records nothing and returns false. What decides it is the `Engine\Gate` of the rule, which the plan holds for every rule, made from the values of the run (`ResolvedConfig::getGates()`) or open, every requirement reported, for a rule run without a resolution. `PluginRegistry` keeps the classes in the order of their registration and the presets by name.

### Report before mutation

Every mutation must follow a `RuleContext::report()` that returned `true`. `PassLoop` pairs the two through `FileNode::$revision`: a callback that raised the revision without a report ("silent mutation") or after a report that returned `false` (silenced by a `dresscode:ignore` comment) breaks the contract; `strict` mode (RuleTester, `--strict-rules`) throws, otherwise it is a warning of the file. A denied report, by a comment or because the run refuses a risky fix, is judged by the window between it and the next report of the same rule, not by the whole callback, because a callback that reports many times may be denied one occurrence and allowed the next. Along the gap traversal the revision covers every rule of the stage, so the silent-mutation check is left out there: the whitespace of a gap is written by the engine and always after a report of its own.

What a fix leaves is not read from the reports at all: a rule may report every occurrence first and write its fixes afterwards, the whitespace of a gap is written for the whole traversal, and a rule may rewrite what another one reported, so no window of revisions says which report a mutation was for. `FileResult::$remaining` is what the rules report over the settled text instead, see below.

### Risk and consent

Risk is a property of the occurrence, not of the rule: `report(risk: Risk::TypeUnknown)` says that fixing this one may change what the code does, and names what would decide that it does not: the type of a value (`TypeUnknown`), whether an unqualified name reaches a function of the namespace (`NameUncertain`), or a human (`BehaviorChanges`), where changing what the code does is the point of the fix or depends on code the run does not see. `because` says what may go wrong at this occurrence where the risk alone does not say it; it stands beside the message and never in it, the message being part of the fingerprint and bound to stay the same whether the run can decide the risk or not. The violation is recorded either way, and `false` comes back until the run is allowed to make such a fix (the configuration names the decision in `fixRisky`, or `--fix-risky` on the command line allows every such fix). The rule then leaves the code alone, and the violation says `risk` and `refused` and stays among what the fix leaves. A `dresscode:ignore` comment silences it like any other violation.

An occurrence the rule has no fix for is reported with `fixable: false`, which is never risky, never lets the rule mutate and is therefore never offered to the consent, and a pass that changed nothing while a rule reported an occurrence without it, neither refused as risky nor a gap the engine fixes, is a broken contract (`PassLoop::checkUnfixed()`), so a forgotten `fixable: false` is a failing fixture rather than a false offer.

A comment inside the code a rule would rewrite silences the rule, which then neither fixes nor reports: the comment says the code is written so for a reason, and the rewrite would lose it or carry it where it no longer says that. A rule that reports such an occurrence anyway reports it with `fixable: false`, best with the reason after the message (`, but a comment stands among its arguments`), and says so in its docblock, where silence needs no word.

**A risky fix may change what the code does; it may never write code that does not compile.** What only a file the project need not know of could decide is therefore not risky but undecidable, and there the rule says nothing at all, because the consent of `fixRisky` cannot be asked for it: a fatal error in another file, not a change of behaviour in this one. A class marked `@internal` is where the project does know: only its own package may extend it, so the project giving the consent is the one place such a child may live, and a fix that such a child decides is risky rather than silent.

The behaviour a fix keeps is that of working code. A fix that only spares an error or a warning the original code would raise past the point where it knows its answer, its evaluation cut short, is not risky.

An unqualified call of a global function in a namespace is a risky occurrence wherever `NameResolver::getUnqualifiedResolution()` says `UnqualifiedResolution::Uncertain`, which `nameResolution: certain` of the project takes away, and the rule that rewrites it reports it with `Risk::NameUncertain`; a name the rule writes anew follows the name it replaces, or `NameResolver::shortenName()` where there is none.

A rule whose every fix may change what the code does says so at every report, the risk having no other channel. Writing such a decision, in the project or by a preset, is not consent to the change: the project gives it by naming the decision in `fixRisky`, for the whole tree or in an override for a part of it, which a preset cannot (the resolver refuses it), and `--fix-risky` gives it to every decision for one run; a name of `fixRisky` is read as `only` reads one, a decision, a section or a structure for every decision under it, a preset for every decision it writes. A hook therefore needs no switch of its own: it fixes what the project accepted and reports the rest.

### Severity

Every violation is an error until the configuration softens it: the `warnOnly` of a profile names the decisions whose violations only warn, as `fixRisky` names them, `PassLoop` stamps the severity when it makes the violation, and `RunResult::getExitCode()` counts the errors and syntax errors alone, with `--max-warnings` as the only threshold the warnings can cross.

### Passes

A pass is one pre-order traversal per stage (`Structure`, `Formatting`, `Finishing`); node rules are dispatched by `instanceof` on the node class, in configuration order within a stage, `enter()` and `leave()` apart and only for the rules that override them, and the gap rules ride along the traversal of the formatting stage. When a rule replaces or removes the node it was given, the rest of the chain for that node is skipped. Passes repeat until one changes nothing; the printed text of every mutating pass is hashed and a repeated state is a cycle, reported at once with the rules that mutated and a diff of the two states. Rules must therefore be idempotent and must not depend on the pass number, which the context does not expose.

### Positions and derived violations

Violations carry positions from the original file (`Token::$line`; for a synthetic token the first original one after it within its statement or member, which is what a fix moved or left in place of the code it replaced, so that a report of a later pass on a rewritten call lands on the line of the call, and failing that the nearest original token before it; `Trivia::$line` when the report names a trivia, so that whitespace and comment problems land on their own line for suppression).

A violation that the fix of another violation brought about is **derived** from it: `Violation::$derivedFrom` names the fingerprint of the first violation of the chain, so that a report is true about the file on disk or says which violation made it true. The fixer remembers, per token, the violation it opened or closed the line before that token for, and a report about the gap before such a token (its blank lines, which wait for the next pass, the whitespace of a joined line, the indentation the engine inferred for an opened one) follows from it. A rule that places a line by what another line was given says so with `report(follows: $token)`, the token opening that line, and the report follows from whatever opened, closed or moved that line. A rule that reports the shape of the line a token stands on says `report(byLine: true)` instead, which asks the same of that line but claims nothing about its whitespace, so nothing is placed by such a report.

Nothing else is derived: not a report on a tree another rule has changed, by that alone, and not even one on a token a fix wrote anew, which is often the user's code rebuilt, and a rule adding code writes it instead in the shape the other rules ask for; not a report about a comment, which is the user's whatever line it stands on, and not the sibling claims of one decision, each about a break the user did not write. Those are not derived but one: the claims whose closure decided something about a construct through `Gap::once()`, a decision other than null, false or an empty array, are about its shape, so every gap of that construct is reported in the pass as a single violation, placed at its first report, silenced by a comment on that line and given one fingerprint (`Fingerprints::createFor()`, placed by `placeConstruct()`), and a rule of a shape is reported once per construct, which is what counting the places it decides needs.

A derived violation is a violation like any other, in the JSON, under `dresscode:ignore` and in the exit code, because `fix` changes what `check` reports and the derived ones are changed too; only the console format folds them under an ancestor of the same state (error, warning, or a risky fix the run did not make), a `Then also` line with its message and rule, and the bare one folds nothing.

`RuleContext` keeps the reports of a callback as `Engine\Report`, with the gap and the line a report is about, and `PassLoop::account()` turns them into violations. The fingerprint (rule, normalized line content, and the place of the violation among those of the rule on that line, in the order they first come while the file is processed) is made by `Engine\Fingerprints` at the moment of the report, so that the position is the one the reported code still had; repeated reports of one violation across passes collapse on it. The message tells the violations of a rule on a line apart and is not part of the fingerprint, so that a message worded otherwise by a newer version keeps the fingerprint; two violations of one rule on one line are told apart by their order alone, and once the first is fixed, the second takes its fingerprint.

### Suppression

Suppression is read once from the original comments before any mutation: `dresscode:ignore [paths]` on a line silences that line, a section or a structure standing for every decision under it, on its own line the nearest node starting on the next line, `disable`/`enable` a range, `ignoreFile` everything; what follows ` -- ` says why, as in ESLint and phpcs, and names no rule. A name no decision stands for is a warning of the run.

### Processing a file

`FileProcessor` is a pure function of path and text: parse, passes, print. What a run decides about the reports, the same for every file of one configuration (`warnOnly`, `fixRisky`, `--strict-rules`), reaches it, the passes and the `RuleContext` of every rule as one `Engine\ReportPolicy`, which `RunnerFactory` builds from the configuration and the options of the run. A mutated tree is not the tree the parser would build from the printed text, so a rule can miss what another one has just written; a strict run (`--strict-rules`) therefore does the same again over the printed text until it settles, at most five rounds: a text the rounds come back to, or one still changing in the fifth, is a `ConvergenceException` and fails the file like a cycle of passes, because only a broken rule gets there. Any other run takes the last pass of the tree, which changed nothing, for the round over the printed text, which spares a pass of every fixed file and keeps only its parse, so that a broken rule never writes code PHP refuses: what that pass reported, identified by the lines of the printed text as a run over it identifies it (`PassLoop::collectRemaining()`: the line of a token where it stands now, of a trivia counted back from its token, the fingerprints counted again in the order of the pass, the violations it follows from found again), is what that round reports. `RuleTester` holds the two equal on every fixture; the price is that a rule missing in the tree what the text shows is seen only by a strict run.

The violations reported are those of the first round, whose positions belong to the file as it was. What the last round reports, or the last pass standing for it, is `FileResult::$remaining`, positioned in the fixed text: it is a full check of the text a fix writes, so it says exactly what the next check of that text reports, and the exit code of a fix and every listing of what a fix left read it, while a check says how many a fix would leave. A text that no longer parses is a failure of the fixer rather than a syntax error of the file. What a run reports therefore depends on which other rules are on: a rule that fixes a shape first takes away the report of a rule that would have met it later. A syntax error is a result, not an exception, and the `Style` follows the prevailing line ending of the file unless the configuration fixes one.

### Running

`Runner::findFiles()` finds the files (patterns with a slash are anchored to the root, without one they match a segment at any depth, both also match directories on the way, and `**/` is no directory or any number of them, as in gitignore, a pattern that is no valid glob being refused when the configuration is read; a file named on the command line is taken as it is, and only `--skip-excluded`, which a hook or an editor naming every file it touches passes, lets the excluded paths leave it out like a found one) and `Runner::run()` takes that list, reads and writes the files and hands results to a `Reporter`. The caller expands the paths so that it knows the scope before the run starts. A path named on the command line is relative to the working directory, and `Runner::narrowPaths()` narrows a named directory that holds some of the configured `paths` to those, so that `fix .` in the root never reaches beyond them, while a path outside them is taken as named.

The format is the whole contract of the output, never a switch modifying another one: `console` unless `--format` says otherwise, `github` when `GITHUB_ACTIONS` says the run is a step of a workflow, `json` and `checkstyle` for tools (the JSON document says its `version`, the `mode` and the `root` of the run, its keys are camelCase and the values from the code stand as they are, the `severity` of a violation being `error` or `warning` and its `risk` `typeUnknown`, `nameUncertain` or `behaviorChanges`, the backing values of `Severity` and `Risk`, a change of its shape being a new version), and `bare` for a hook, which prints the violations left to the user and a `rewritten` note for every file the fixer touched, so a clean run prints nothing while a silent rewrite never happens. The header naming the configuration file and the scope belongs to `Console\Application` and is written, together with the warning that Xdebug makes the run many times slower, only for the console and github formats; the progress bar only for the console format on a terminal, where it is a status of the very console the report goes to, so that writing the report erases it. A fix run lists every file it touched exactly once, with a `rewritten` note and under it what the fixed text still violates; which violation a fix removed cannot be told from the text, so the verdict counts what was found and what remains, and `--diff` shows what changed.

A rule exception or a cycle fails that one file (nothing is written, the run goes on, exit code 2, also for a runtime error of the tool), and so does a file that cannot be read or written, and a file whose text on the disk is no longer the one processed when the fix is about to write it, so that what an editor saved meanwhile is never overwritten; a syntax error is exit code 1 like a violation, while a mistake of the command line or of the configuration, and a program run without a command, is exit code 3, which is no result of a run at all. The fix writes a file through a temporary one renamed over it, so that an interrupted run never leaves it cut short, and in place where no temporary file can be made beside it or renamed over it (a directory that is not writable, a file mounted on its own, on Windows a file another process holds).

A process working through files keeps the cycle collector of PHP off and collects between two files once the memory has doubled since what the last collection left, never above three quarters of `memory_limit` (`Engine\CycleCollector`). The collector PHP runs by itself scans again and again what stays alive, the tree being processed above all, and frees little.

The run keeps of the result of a file what it needs without the code and the output (`Engine\FileSummary`), so that only the file in progress is held as text.

## Configuration

### The file

A configuration says how the code of a project is written, decision by decision, and what surrounds that: the facts of the project, the scope of a run and how a run treats what it finds. It is written as `dresscode.neon` or `dresscode.php`, and the two are the same thing said twice: every key of the NEON is a named argument of the constructor of `Config`, the sections of the decisions together under `decisions`, so `NeonReader` is a schema of the reserved keys that accepts none it does not know, the evaluation of entities and a spread into the constructor.

The keys at the top are either reserved or sections (`Config\Catalogue::ReservedKeys`, `CoreSections`). The reserved ones are `use`, the facts of the project (`targets`, `namespaces`, `nameResolution`), the scope (`paths`, `excludePaths`, `fileExtensions`, `skipWhen`), what the project brings in (`rules`, `analyses`), how a run treats what it finds (`fixRisky`, `warnOnly`) and `overrides`; every other key is a section of the decisions, `file`, `indentation`, `spacing`, `qualification` and the rest of the core, a section of a plugin named after it and `project` for the rules of the project. `NeonReader` takes a key one letter off a reserved one for a misspelling rather than a section. The sections stand at the top or under `decisions`, never both, which the reader refuses rather than drop one of them. The style is decisions like any other (`indentation.unit`, `indentation.tabWidth`, `file.lineEnding`, `file.maxLineLength`), which the resolver turns into the `Style` of the engine: where one is `keep` the file has no requirement, but new code must still be written somehow, so the indentation is a tab, the line ending the majority of each file and the line has no limit.

`Profile` holds what decides how a file is processed (`use`, `targets`, `namespaces`, `nameResolution`, `fixRisky`, `warnOnly`, `decisions`), an `Override` is the `paths` it applies to with the profile they get, and `Config` is the profile of the whole project with the rest; a preset is a file of the shape of a profile. They are readonly values checked when they are constructed: a value one of them refuses is an `InvalidArgumentException`, which `NeonReader` and `Loader` turn into a `ConfigurationException` naming the file and the resolver into one naming the preset. The tree of the decisions is not read there but by the resolver, against the catalogue.

What the PHP notation passes as an object or a callable the NEON writes as an entity in three places only, a plugin in `use`, `skipWhen` and the factory of an analysis: `Class(args)` is a new object, `Class::method(args)` what the static method returns, `Class::method(...)` the method itself, and in a chain `Class(args)::method(args)` a link calls the method on what the link before it gave. An entity is evaluated when the file is read, one of `use` only once its class is known to be a plugin, so that a configuration of a repository someone merely checks cannot run other code by naming it. A rule of the project is named by its class in NEON; one built by a factory, a recipe evaluated at every build, is given by `dresscode.php`. The schema keeps only the keys the file gave, so that an absent key keeps the default of the constructor, and it takes a single entry of `use` without a list.

`Loader::find()` walks upwards and takes, in each directory, the local file before the `.dist` template; the two formats side by side are an ambiguity it refuses rather than resolves. A configuration file is the only thing laid over a project, and `--config` names it (its format follows its extension); a wrapper binary that wants a configuration to apply in a project without one hands `Console\Application` a `defaultConfig`, which the loader uses when it finds no file. The command line is no key of a file: it is a profile laid over everything the file says, `--use` naming a preset or a plugin as `use` of a file does, and `--set path=value` a decision (the value is NEON, decoded as the value in a file); `--only` is a parameter of `RunnerFactory::resolve()` and `--strict-rules` one of `RunnerFactory::createRunner()`.

### The catalogue

A rule declares what it decides in `Rule::getDecisions()`, and the decisions of every registered rule, with those of a tree its rules name, are the catalogue (`Config\Catalogue`), which is what a file is read against and what an editor of the configuration loads. A `Decision` has a path, which is the identity of everything a user ever sees about it, the report and the suppression included, a `Domain` of the values it takes, a description and notes saying what it is not about; it is a requirement, which turns its rule on wherever it is not `keep`, a parameter, which only refines a requirement, turns nothing on and has a default instead of `keep` (`controlFlow.trailingIfMinStatements`, `naming.except`), or a fact, a key of the environment the rule guards (below). A rule runs where one of its requirements takes effect, so a rule is never named to be turned on: a project or a preset writes the decisions it wants, and a decision nobody writes requires nothing. A decision of one rule is declared by that rule; one several rules share, or one the engine reads, is declared by a tree, the decisions of the manifest of the plugin bringing the rules (`PluginManifest::$decisions`, the core being `Config\CorePlugin`), and each rule taking it names its path in `RuleInfo::$decisions`, a decision of the core or of its own plugin, never the rule that would otherwise own it, so that a decision over constructs with nothing in common to share is several rules and not one rule of several parts, and its words are written once. It turns on every rule naming it that can run, and it takes effect while one of them can; a rule that only reads a decision of a tree, to leave to it what it governs, names it in `RuleInfo::$reads`, which puts it in the catalogue and in the values of the run without turning the rule on (`Catalogue::getReadersOf()`, the `readers` of `toArray()`); a decision of a tree no registered rule names is not in the catalogue, and a rule declaring a path a tree declares, or two rules declaring one path, is a `ConfigurationException`. Where no catalogue is at hand, a test running one rule, `Catalogue::collectDecisions()` gives the decisions of the rule and `Catalogue::fromRules()` the catalogue of a few rules, the trees taken from the core and from the plugin the package of each rule names in `extra.dresscode.plugin` (`PackageDiscovery::findPluginOf()`), so that a plugin tests its rules as they run.

The domains are the kinds of value a key takes, each normalizing what a layer wrote into a `Value` and merging two of them by its law: `Words` (`forbidden`, `nextLine`, a tolerance of several where the domain takes one), `Shapes`, a word for each shape of the construct with an example of it, which the file may write instead (`spacing.call: compact` or `"foo($a, $b)"`), the example only ever compared with the examples of the domain and never parsed, `Count` (`2`, `1–2`, `1+`, a word where the decision names one, `maxLineLength: none`), `Flag`, `Names` (a list of names, regular expressions or an order), `Text` (a text of the project's own the rule writes as it is given), `GrammarEntry` (a value a grammar of its own reads, an entry of a map of the upgrading data) and `Map` (names to values of another domain). `keep` is the one word for "leave this alone" and every requirement takes it, a map entry by entry (`name: keep`) and never as a whole, so `null`, `false` and a turned-off rule never stand side by side for the one idea. `Value` keeps the layer that said it, and a rule reads the values of its decisions from `Values` in `configure()`, never a raw array.

The core keeps to its sections, a plugin to the one its manifest names after it (`PluginManifest::$section`), and the rules of the project to `project`; the catalogue refuses a path outside them, a path two rules declare and a section of a plugin that is a reserved key or a section of the core. A rule of a plugin names a tree of the core, of its own plugin and of the plugins it builds on (`PluginManifest::$plugins`, transitively), a rule of the core one of the core alone, so that a decision is shared across plugins only where one depends on the other. A rule of the project names a tree of the core or of any plugin the project loads, the project standing on all of them. The order of the registration is the order the rules of a stage run in, the core in the fixed list of `Config\CorePlugin`, the plugins after it in the order `use` names them, each after the plugins it builds on, the rules of the project last, so that no order of the keys of a file, which an editor may rewrite, changes what a run does. A decision of the core has its page on dresscode.run by its path, and a report in a terminal links to it.

### Plugins

A plugin stands in `use` of the configuration beside the presets, by class or as an object, and `Config` takes it out of them, because it is no layer and only makes rules and presets known before the layers are laid; the `use` of an override and of a preset refuses one, what it makes known being the whole project's. A `Plugin` is what a package brings to a project: its `getManifest()` is a `PluginManifest` with the `rules` it registers, the `presets` it makes known by their names, each the path of its file, the `section` its rules decide in, the `decisions` of that section several of its rules share, the `plugins` it builds on, `analyses`, `excludePaths`, `skipWhen` and `ruleUrl`; the manifest has no other key and its `decisions` only declare, so a plugin cannot decide what is the project's, and the fields it shares with `Config` are checked by the same code. A rule of the project itself is named by its class in `rules`, with its factory where it has dependencies (in `dresscode.php`), and decides under `project`. `ruleUrl` is the address of the page of each rule, `{slug}` standing for its class without the suffix `Rule`, the first letter in lower case, given by the manifest for the rules of a plugin and by the configuration for those of the project. A plugin lies below the project, the plugins it builds on below it and every class once, by class or as an object, plugins building on each other in a cycle being an error: the excluded paths add up, a file any of them skips is skipped, and an analysis of the same class the project gives wins. How the code is written is no business of a plugin; that is a preset, which the project uses, so the standard of a project is always read in its own file.

### Presets

A preset is a file of the shape of the configuration under a name, `src/Presets/<name>.neon` for those of the core, a file a plugin names in its manifest, or any file `use` gives by its path. It carries decisions and the presets it uses, nothing else: what is the project's, the facts, the scope, `fixRisky`, `warnOnly`, a plugin and `rules`, `NeonReader::readPreset()` refuses, so a file laid by `use` never gains what the file of the project can do. A name without a vendor is the one of the core. A preset opens with a comment, its title and what it is, and says what a decision does, where its key and value do not, in a short comment after the value.

Without a configuration file nothing applies: DressCode has no style of its own to fall back on, so a run refuses, unless `--use` names what to use, which is then all the run has, so that a run over a foreign project can ask for that alone.

### Resolving the layers

`ConfigResolver::resolve()` lays the profiles that decide for a file one over another: the configuration, the overrides the file matches in the order they are written, and the command line, each above what its `use` names, in the order written, a preset above what it uses in turn. Every preset is laid once, where it is named first, so one named again, by a later layer or by the same one, does nothing, and the run says so; that a preset uses what another already brought is no business of the project and is said by nobody, while a preset that comes back to itself through what it uses is an error. A path in `use` is a file of the same shape, its identity the path; a relative one is taken from the directory of the NEON file that writes it, from the root in a `dresscode.php` and its `Override`, and from the working directory in `--use`. A later layer has the last word on a fact (`nameResolution`, every key of `targets`) and adds to a list (`namespaces`, `fixRisky`, `warnOnly`).

The decisions of the layers meet in `Config\DecisionResolver`, which reads every path of a layer against the catalogue, a path it does not know being an error with the nearest one it does, and merges the values of one path by the law of its domain: a structure merges key by key, a word, a shape, a count and a flag replace, a list replaces the list below it, its default included, and a map of names merges by name, an entry `keep` withdrawing the entry below it and the most specific entry winning over a pattern whatever layer said either; a map whose names PHP reads in any letter case (`Map::$caseInsensitive`) takes a name with or without its leading backslash as one, which a layer may not write twice, and a map whose every entry is withdrawn is `keep`. A word over a map is a map with the entry `*`. `keep` on a section or a structure is a tombstone for every key under it, which a later layer brings back one key at a time, the rest staying `keep`, so that nothing a layer below said comes back from under the tombstone. The result is a `ResolvedDecision` per path of the catalogue: the value, what each layer said with its origin, and why it takes no effect where it does not (`keep`, `php`, `nameResolution`).

A rule takes effect where one of its requirements does, and the resolver says of every other rule why (`ResolvedRule::$inactiveReason`): turned off, too new for the target, turned on only by an override, written by nobody, narrowed to other decisions. A preset may decide what cannot run here, silently; the project deciding it asked for what it cannot get, which is a warning for the target. The run builds its instances from that one `ResolvedConfig`; `RuleBuilder` builds every rule that takes effect, with the factory the configuration gave it, and hands it the `Values` of the run.

An override (`overrides` in NEON, `Override` in PHP) is a profile for a part of the tree: the item of `overrides` writes every key a profile has beside its `paths`, which `NeonReader` takes apart into the two, and the `paths` go through the same matcher as the excluded paths, anchored to the root of the configuration. A file's configuration is therefore the combination of overrides it matches. `RunnerFactory::createRunner()` builds one processor per combination, with an `Analyses\Registry` of its own because an override may add to what the namespaces declare, and `Engine\FileProcessors` keeps them, because a rule carries the values it was configured with and must never be reconfigured under a file already being processed. A part of the tree where a decision must not hold is an override that writes `keep` for it, so a later override may write it again. Every override is resolved on its own when the run is built, not when a file of it comes, so a path no decision has and a value its domain refuses are an error naming the override rather than a line that does nothing until such a file comes.

The excluded paths only ever add up, the default list, those of the plugins and those of the configuration, so no layer can bring back what another left out.

`only` (`--only`, a parameter of the run and no key of a file) narrows a run to the decisions it names, and it changes no value: the tree is resolved whole and `only` lays a mask over it, `Values::isSelected()`, so a requirement outside the mask is neither reported nor fixed, while what the rules write keeps the values the project decided (a run narrowed to a rewrite of a structure in a project with four spaces writes the new block with four spaces, not a tab). A rule reads the value with `Values::get()` and asks whether a requirement is selected separately, and reading a value never enforces what the run did not select. A name of `only`, as of `fixRisky` and `warnOnly`, is a decision, a section or a structure for every decision under it, a preset for every decision it and what it uses write, or the class of a rule for its requirements. A section or a preset narrows the run to those of its rules the rest turns on, never more, since its name is no decision about any one of them; where the project turned some of them off the run says which by their requirements, the first five, and a name that lets nothing in is an error rather than a run that checks nothing, naming `--use <name> --only <name>` where the configuration does not use it. `fix --only` fixes those decisions and leaves the rest, so the next full `fix` changes more, which is the point and not a failure to converge.

### The target version of PHP

The versions of PHP the rules target are a property of the checked project, never of the run: `RunnerFactory::getPhpTarget()` takes them as a Composer constraint from `targets: {php: ...}` of the configuration, which is one version, else from `require.php` of the nearest `composer.json` at or above the root, the whole constraint (one without a lower bound, `<8.4` or `*`, leaves the version to the default rather than to a guess), else from `Config::DefaultPhpVersion`, and an override may give its files another one with `targets: {php: ...}`, which is all an override may say there. A rule runs where every version of the target satisfies its `requires`; what a rule asks with `RuleContext::$phpVersion` is the lowest of them. Whichever it is, a version older than `Config::MinPhpVersion` is raised to it by the resolver with a warning, because no rule asks whether the target has what PHP 8.0 already has, so a fix may write such syntax. Nothing else raises it, a package backfilling a newer construct least of all: a rule writes what the version the project moves to gives its code, while such a package exists so that the project need not move, and taking it for an answer would turn the target from a version into a list of what happens to be in the vendor directory.

The version a rule asks about travels as a plain string compared with `version_compare()`, never with the string operators, under which 8.9 outranks 8.10, and always in the short form `Config\Versions::shortenVersion()` gives, without the zeros a normalized one pads with, because `version_compare()` takes `8.1` for older than `8.1.0`. NEON reads a bare number as a version whose minor is a single digit, which every PHP ever released has had, so `8` and `8.0` both mean 8.0, and `php` in `targets` may carry a patch version, so no rule takes the string apart by position. The running interpreter is never the answer, so that the same file gets the same verdict from any directory under any PHP; only `Lexer` asks about the runtime, to emulate the tokens its own build does not know.

A rule whose construct exists only from some version on says so with `requires: ['php' => '>=8.4']` in its `#[RuleInfo]`, a Composer constraint written as the `require` of `composer.json` writes it, all of it read by `composer/semver` (`Config\Versions`) and never by hand, and a range, a single version being refused because it would turn the rule off for every other release; an upper bound says a rule writes what a later version took away. `ConfigResolver` leaves it out below that version: silently when a preset wrote its decisions, with a warning when the project wrote them. A rule that needs the version more finely than "run me or not" asks `RuleContext::$phpVersion` instead, and never about anything PHP 8.0 already had. The version in `requires` and the one read from `RuleContext::$phpVersion` say since when the fix is right, never since when the code it replaces is a problem: the target is the oldest version the code runs on, not the newest, so a rule about a deprecation whose replacement older versions know too asks no version at all, the code meeting the deprecation wherever it runs on a later one. A fix naming a class of PHP needs the version that declares it, though older ones parse the name and ignore an attribute they do not know, code naming a class the target does not declare being no fix for that target.

### The namespaces of the project

What the namespaces of the project declare is a property of the project too, and no file shows it: an unqualified function or constant in a namespace reaches the namespaced one PHP knows at run time before it falls back to the global one. `namespaces: {functions, constants}` lists such symbols as the items of a use statement write them (`Acme\Text\{format, parse}`, parsed by `Parser` when the profile is constructed), and every layer adds to the lists; `nameResolution: certain` says the lists are all there is, which the configuration or an override says and a preset cannot, knowing a framework and not the project. An override may say `uncertain` for a part of the tree whose declarations nothing outside it reaches, such as the helpers of the tests, so that no fix there rests on the lists.

`ConfigResolver` puts both into `ResolvedConfig`, and `Analyses\Registry` builds `NameResolver` with them as `NamespacedSymbols`, which is also the analysis a rule asks for the lists themselves.

## Writing a rule

### Messages

A violation message describes the code, never the reader: no imperative (`Use…`, `Add…`, `Remove…`), because a rule that only reports has nothing to command. It is a sentence and ends with a period, which `PassLoop` checks as a part of the contract of the rule. It takes one of three shapes, and which one is decided by the rule, not by taste: the required state after `Expected` where the rule wants one short thing in one place (`Expected a single space after the comma`), the word saying that it is what should be there and not what was found, `<subject> must <requirement>` where that needs a sentence (`The opening brace must be on its own line`), and the defect where the thing is wrong in itself or the rule guards several places at once (``Function `foo()` is deprecated``, `Wrong whitespace in a type declaration`).

A family shares one pattern: every `…SpacingRule` says `Expected no whitespace <where>`, `Expected a single space <where>` or `Expected at least one space <where>` with the token the claim is on as `<where>` (`before the closing parenthesis`, ``after the `return` keyword``), composed by the engine, `IndentationRule` the measured `Expected <what> indented by <width>, <found> found` (`without indentation` where it wants none) with the width in tabs and spaces, every claim on a line break `Expected a line break <where>` or `Expected no line break <where>` with the bracket at the edge of the gap or the node the claim was made for as `<where>`, and the reason after `because` when the claim follows from a measure or a property of the code (`Claim::$because`: `Expected a line break before the parameter, because the line is 135 characters long`), every `…BlankLinesRule` the measured `Expected <count> <place>, <found> found`, a count of zero written `no blank line`, composed by the engine from the node or token the claim was made for (`before the method`, `after the opening brace`).

What follows the message after a comma says why: `, because <why>` where it explains the finding itself (`…, because the line is 135 characters long, more than 120`), `, but <why>` where the occurrence is reported and left as it is (`…, but a comment stands among its arguments`), while why a fix is risky is not the message but the `because` of the report beside it (`the replacement evaluates the arguments in another order`, ``the namespace may declare `<function>()` ``). A message stays within 104 characters counted with every name as one word, so that a project with long namespaces does not break it.

The subject is the thing at the reported position, with a definite article and its name where it has one (``The property `$value` must be promoted…``, ``The method `run()` must have…``), and an operator or a call in that role carries its kind (``The `<>` operator must be written `!=` ``, ``The `is_null()` call must be…``); `written X` names a literal replacement, `written as X` a form. Everything the message shows that is code stands in backticks, as in an exception (Exceptions and warnings below): a spelling to type or found (``must be written `Exception` ``, ``The keyword `YIELD FROM` ``, ``must start with `//`, not `#` ``), a call the message names (`` `is_null()` ``), an expression built from the code at hand (`` `$obj::class` ``), the name of a declared class, function, constant or member (``Function `foo()` is deprecated``, ``Global constant `PHP_EOL` must be imported``), and a token the engine names by its spelling (``after the `as` keyword``, ``before the `.` operator``). A token named by a word is prose (`the closing parenthesis`, `the comma`), and so is a word that is not a spelling (`camelCase`, `the short syntax`). A name cannot hold a backtick, so the message writes it in backticks directly; code that can, an expression, a string, a comment or a text of the configuration or of the data, goes through `Violation::formatCode()`, which writes a code span of Markdown in a longer run of backticks where the code holds some. Names and measured values belong in the message, the path of the decision and the standard do not. In prose a `/** */` block is a `doc comment` and a tag in it an `annotation`, whatever the path calls them; `whitespace` is what a rule forbids, `a single space` what it requires.

### Exceptions and warnings

An exception or a warning is read by someone who has to act, so it says where, what and what to do, in that order. Where is a prefix naming what the reader edits (`Configuration file X: `, `Preset X: `, `The override for src/: `, `The command line: `), left out only when nothing but the command itself can be meant; what is a sentence about that thing, with the value the reader wrote or has to write; what to do follows after a semicolon, or as a second sentence when the first has one, and it is the only place an imperative may stand. A message the reader cannot act on, a broken rule, says whose fault it is instead. Every message is a capitalized sentence ending with a period, warnings included, `must` and never `has to`; a message wrapping another one puts it after a colon and adds nothing behind it, and what it wraps is left as its author wrote it.

Everything in such a message that is code stands in backticks, as in Markdown: a file and a path, a command and an option, a key of the configuration and a value (`` `x` given `` for a value refused), a decision, a preset, a package and the class of a rule, a class, a function, a member and an annotation (``Configuration file `dresscode.neon`: ``). A word that only speaks about code is not code (`the configuration`, `a preset`). The console draws what the backticks enclose in color and drops them; every other output, a pipe, a log of CI, the formats `json` and `github`, the reader of the PHP API, prints them as they are, which reads well to a human and to an agent alike. Where a page of the manual says more than the message, the exception carries the path of that page (`ConfigurationException::$docs`), and the console prints it under the message as a link to `https://dresscode.run/`. What the author of a plugin reads (`RuleInfo`, the claims, `RuleTester`) states the contract that was broken; what the user of a configuration reads never names an internal class, node or slot.

### Testing

`Testing\RuleTester` runs a rule over `*.code` fixtures (`.expected` output beside them, `.violations` as `line: message` with the risk of a risky one on an indented line below it, `risky <Risk>` with `: <because>` where the rule gives one, the values of its decisions in a `// {"json"}` comment, a key without its section taking the one section of the rule, over those of a `values.neon` beside the fixtures, a run that allows risky fixes in a `// risky` one, the targeted version in a `// php 8.4` one, the widest line in a `// lineLength 80` one (120 without it; `check()` takes a whole `Style` instead, whose line ending stays that of the code) and what the namespaces declare outside the fixture in `// namespacedFunctions`, `// namespacedConstants` and `// nameResolution certain`, all in the comments that open the fixture; without a version the rule is tested at the version of PHP it requires, else at `Config::DefaultPhpVersion`, never at the version of the interpreter running the tests) and, given `analyses:` in the shape of `Config::$analyses`, registers those of a plugin for the rule, then checks the contract: parent invariant, idempotence over the output, comments preserved unless `modifiesComments`, `dresscode:ignoreFile` honored, no silent mutation.
