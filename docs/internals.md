# DressCode internals

How DressCode works: the facts an agent or a contributor needs before touching the engine, a rule or the configuration. The catalog of rules is not here; it lives in the rules themselves.

## Layers

- `phpsyntax/phpsyntax` (namespace `PhpSyntax`, a repository of its own): lexer, parser, tree, printer, navigation, mutation. Its internals are documented there; what a rule of DressCode uses from it is below.
- `DressCode` (`src/`): engine, rules API, rules, configuration, CLI. Rules use only the public API of `PhpSyntax`; whatever a built-in rule needs from it is public API for plugins too.

The public, semver-stable surface of `DressCode` is what the first list names, and the second names what is `@internal`. Every class of `src/` is in one of them, the more specific name deciding (a class before a namespace, a longer namespace before a shorter one). An item names its classes, namespaces or files first, the explanation follows a colon.

Public:

- `Config`, `Profile`, `Override`, `Plugin`, `PluginManifest`: the configuration
- `Rule`, `NodeRule`, `GapRule`, `ConfigurableRule`, `RuleInfo`, `RuleContext`, `Claim`, `Space`, `Line`, `Gap`, `Style`, `Violation`: the API of a rule
- `Stage`, `Severity`, `RuleGroup`, `Tristate`, `Risk`: the enums
- `exceptions.php`, `Testing\exceptions.php`: the exceptions
- `Preset`, `PresetInfo`: the presets
- `FileResult`: the result of a file
- `Console\Application`, `Console\UsageException`: a program embedding a run goes through them
- `Analyses\*`, `Rules\*`: the analyses and the rules
- `Testing\RuleTester`: the tester of a rule

Internal:

- `Engine\*`, `Config\*`, `Console\*`: the engine, the configuration and the console
- `Reporter`, `Reporters\*`: the formats of the output, whose contract is the output itself, and the interface they implement next to them; they print the `Engine\RunResult` of a run
- `Rules\NodeHelpers`, `Rules\Compiler`, `Rules\NativeType`, `Rules\BlankLines`, `Rules\Namespaces\NameReferences`, `Rules\PhpDoc\AnnotationToAttribute`: what the rules share among themselves
- `Analyses\Registry`, `Analyses\PhpSymbolsData`, `Analyses\PhpSignaturesData`: the machinery of the analyses

Of the public classes, the constructors of `Gap` and `RuleContext` and the methods marked `@internal` (`RuleContext::reportGap()`, `hasReports()`, `takeReports()`, `Config::MinPhpVersion`, `Config::checkPlugins()`, `checkRuleUrl()`, `normalizeAnalyses()`, `FileResult::markWritten()`) are the engine's alone. For a rule the name and the namespace of its class are public, so that a configuration and `RuleContext::findRule()` can name it by class, while its methods are not: a method by which one rule asks another is `@internal`.

## The tree a rule works with

Printing the tree reproduces the input byte for byte, so a rule changes what it means to change: formatting rules change trivia, structural rules change nodes.

- Whitespace, comments and open tags are `Trivia` attached to tokens. **Trailing trivia** of a token is everything after it up to and including the first end of line, **leading trivia** of the next token is everything else (blank lines, indentation, comments on their own lines, doc comments). An `OpenTag` trivia (`<?php` with its mandatory whitespace) is always leading trivia of the following token; the final `EndOfFile` token has only leading trivia.
- `<?php` is not a token. `?>` is a token of kind `CloseTag` that keeps the newline PHP swallows after it, and the parser sees it as `;`; after a terminated statement it forms an `EmptyStatementNode`. `<?=` is a token of kind `OpenTagWithEcho` seen as `echo`. `Token::isSemicolon()` and `isOpenTagWithEcho()` cover these cases.
- Whitespace that PHP counts as part of a token stays in its text: inline HTML, `T_ENCAPSED_AND_WHITESPACE`, heredoc delimiters (the closing one keeps its indentation), casts like `( int )`. A BOM or a hashbang line is inline HTML, as PHP sees it. A single-line comment never contains its newline, but it does contain trailing spaces before it.
- Trivia inside string interpolation (`"{$a /* c */ }"`) carry `inInterpolation = true`; the token helpers refuse to change them because that whitespace is part of the string value.
- Slots are named by role (`ifKeyword`, `openParen`, `semicolon`, `condition`, `body`), paired delimiters are always `open*`/`close*`, lists are plural. A slot says what stands in it rather than what the class suggests, so the left of an assignment is `target` and not a variable, and what a `switch` and a `match` compare against is `subject` and not a condition. Every token of the source has a slot or a place in a list, so the order and number of children are not part of the API, only the slot names. Whoever names a slot instead of reaching for it writes the name as a string (`'openParen'`, `'statements:item'`), which is what a gap rule declares its claims with.
- The body of a control structure is a `StatementNode`, not necessarily a block; `else if` is an `ElseNode` whose body is an `IfNode`. The alternative syntax uses the same classes with `colon`, `statements`, `endKeyword` and `semicolon` slots instead of `body`. Class-like declarations implement `ClassLikeNode`, because an anonymous class is not a statement.
- A new node comes from `Parser::parseExpression()`, `parseStatement()`, `parseType()` or `parseName()`, which return it detached, with empty trivia on its edges and without original positions, or, where it is put together from nodes already at hand, from the `of()` factory of its class (`FunctionCallNode`, `MethodCallNode`, `StaticMethodCallNode`, `NewNode`, `ArgumentListNode`, `ParenthesizedNode`), so that a rule does not parse a template with a `0` in it to hunt the placeholder down afterwards; a constructor is public but its parameters follow the slots of the grammar, which a minor release may add to, so a call spells them as named arguments.

## Analyses

An analysis is information derived from a file, and any class the engine can build is one: `NameResolver` (namespace, imports, resolution of class, function and constant names with the runtime fallback of unqualified functions and constants to the global namespace, `isGlobalFunctionCall()`, and the way back: `shortenName()` gives the shortest way to write a fully qualified name where a node stands, through an alias, a prefix import or the namespace, and `isAliasFree()` says whether a name is still free there, which is what a rule adding an import asks), `Scope` (enclosing function-like construct and class, availability of `$this`, captured variables) and, in `DressCode`, `PhpDoc` (doc comments as phpstan/phpdoc-parser trees printed back with the original formatting) and `PhpSymbols` (what PHP declares: its functions with the version each is deprecated since, its classes, interfaces and enums in their declared case, its constants and the functions PHP 8.4 calls without a frame with their parameters, over PHP 8.0 to 8.5 and the extensions shipped with it, from the generated `PhpSymbolsData`; a PECL extension is not PHP and is not there).

Analyses are lazy and computed once per file. `Analyses\Registry`, reached through `RuleContext::getAnalysis()`, one for every combination of overrides, with the factories the `analyses` of the configuration and of its plugins give (given the `FileNode` and the path of the file), creates them on demand, with the `FileNode` when the constructor takes one, and throws them away as soon as `FileNode::$revision` changes, so any mutation invalidates every analysis of the file.

## Mutation from a rule

### Writing the tree

- A node or token belongs to exactly one tree: inserting one that already has a parent throws; `clone` gives a deep copy without a parent.
- A slot is written by assignment (`$node->condition = $expression`, `replaceChild()`, or `setSlot()` given the name of the slot), which adopts the value, releases the current one and tells the index. Lists mutate through `append()`, `insert()`, `removeItem()`, `replaceChild()`; `SeparatedNodeList::insert()` derives a missing separator from the existing ones (or `", "` in a one-line list) and gives the item the indentation of its neighbor in a multi-line list, `removeItem()` takes the separator after the item, or before the last one.
- `Node::remove()` removes a list item: a node alone on its lines takes the lines with it, otherwise the whitespace around stays; its comments, those on its edges included, each with the line ending after it, go to the next token, the previous token, or away, as the `CommentPolicy` says, so that no rule loses a comment by removing a node. The doc comment of a removed declaration therefore lands above the next one, and a rule removing a declaration that may carry one refuses it (`promotedPropertyForAssignment`) or drops it with `CommentPolicy::Drop` under `modifiesComments`. `Node::replaceWith()` keeps the trivia around the old node around the new one by joining them with the new node's own edge trivia; a replacement cloned from nearby source still carries its original leading trivia, so that an `OpenTag` gets doubled; `Node::withoutEdgeTrivia()` is the copy without them, which is what a rule takes of whatever it writes into another place.
- What a rule reads is a property (`value`, `base`, `quote`, `label`, `indentation`, `kind`, `parts`, `role`, `text`), and it writes one where the write takes a single value with a single consequence: a slot, and `NameNode::$text`, whose hook tokenizes the name anew. It writes through a method where the write takes more values or two things change together (`StringNode::setValue($value, ?$quote)`, the delimiter deciding how the value is written), and for a token always, because `?->` cannot stand on the left of an assignment: `Token::setText()`, `setLeadingTrivia()`, `setTrailingTrivia()`, and `Node::setEdgeTrivia()` for the outer edges of a node, where the first or the last token may be missing.
- What has no hook the language guards: the text and the trivia of a token are `private(set)`, the items of a list its own storage, written by its methods alone, and `parent` is written by the nodes when they adopt or release a child. Such a property takes no indirect modification from outside, and neither does the hooked `leadingTrivia` or `trailingTrivia` of a node, so `end($token->trailingTrivia)`, which takes its argument by reference, needs a copy.
- Every mutation increments `FileNode::$revision`, which the engine reads to detect mutations; it is a version of the tree, not a count, because a compound mutation raises it several times. `Token::$line` and `$pos`, inherited from `PhpToken`, never change and are the source of positions in reports; `$currentLine`, `$currentColumn` and `$currentOffset` follow mutations.

### Comments and doc comments

- A single trivia (typically a comment) is removed by `Token::removeTrivia()`, which tidies the whitespace around it: one alone on its line takes the line with it, an inline one takes an adjacent space; `Token::replaceTrivia()` swaps one in place.
- A rule that must not destroy a comment asks `Token::hasComment()` (in the trivia of the token), `Token::hasCommentUpTo()` (anywhere between the texts of two tokens) or `Node::hasInnerComment()` (inside the node, its outer edges excluded); `Token::getComments()` and `Node::getInnerComments()` give what those count, and a `Trivia` says of itself whether it `isDocComment()`, `isLineComment()` or `isMultiLineComment()` and hands over its text without the delimiters as `getCommentText()`.
- A doc comment is read with `Node::getDocComment()` (above the node, or after the previous token) and, after editing through `Analyses\PhpDoc`, written back with `Node::replaceDocComment()` or dropped with `Node::removeDocComment()`. The tree is the phpstan/phpdoc-parser AST itself, which is therefore part of the public API (its major version is ours), and it is edited the way its format-preserving printer expects: replace `children` or return a new node from a visitor, never mutate a list such as `UnionTypeNode::$types` in place (it prints wrongly); a text node whose text changed loses its ` * ` line prefixes, so rewrite whole lines; a tree with nothing but blank text (`PhpDoc::isEmpty()`) is removed, not printed, or it prints `/**  */`. `Rules\NativeType` (annotation to native type) is the helper the rules share above the AST and `PhpDoc::findTemplates()` names the template types in scope, which a native type cannot use; there is no tag-editing layer of DressCode's own.

### What the rules share

- `Node::matches()` compares two nodes by their token texts and `ExpressionNode::isRepeatableRead()` tells whether reading an expression again is free of side effects; together they answer "does this assignment repeat its target". `ExpressionNode::isDereferenced()` tells whether the parent accesses a member or element of the expression, which is what decides whether parentheses around it can go.
- `Rules\NodeHelpers` holds the questions and constructions several rules need: the negation of an expression as a detached node, the constructs that reach a variable by a name they do not spell out, the width a node takes on one line (`measureNode()`), and splitting a declaration of several items. What the tree alone answers is asked of the tree: whether an expression is a boolean by its form (`ExpressionNode::isBoolean()`), an operator one a condition is chained with (`BinaryOpNode::isLogical()`), the code goes on after a statement or a block (`StatementNode::interruptsFlow()`), something writes an expression (`ExpressionNode::isWritten()`) and a single line ending follows a token (`Token::isFollowedByLineEnding()`). `Rules\GlobalCalls` is public and answers which global function a call calls (`findFunction()`, given the names as the keys of a map whose values it does not read, so that a rule passes the map of its data) and why that may be another one (`findUncertainty()`), which a rule of a package asks as one of the core. `Rules\Compiler` says what the compiler of PHP knows of the code: whether it optimizes a call (`isOptimizedCall()`) and whether it knows the value of an expression (`isConstantExpression()`). `Rules\CodeWriter` is public and writes code in the shape of the file for a rule of a package as for one of the core: a class written the way the file reaches it (`writeClass()`), another global function written in place of the name of a call (`spellFunction()`), an import added where `canAddImport()` finds the scope a line for one (`addImport()`), a member removed so that one gap stays of the two around it (`removeBetweenGaps()`). A rule asks them rather than reimplementing them, and some of them carry what the name does not say: `negate()` flips an equality but never an ordering, which NAN makes false both ways; a rule reasoning about the variables of a scope must respect `findDynamicVariableAccesses()` (`$$name`, `compact()`, `extract()`, `get_defined_vars()`, `eval`, `include`); `NodeHelpers::hasCommentUpToLineEnding()` also counts the comment ending the last line of the node, which `Node::hasInnerComment()` leaves out; and `CodeWriter::writeClass()` may add an import, so it is called only after `report()` returned true, never to compose the message.
- Whether an expression a rule writes into a place needs parentheses there is not the rule's to decide: `ExpressionNode::replaceWithExpression()` puts it in and keeps the parentheses `ParenthesizedNode::isRedundant()` does not call needless, by the precedence of both sides and by what follows the place, and `ParenthesizedNode::of()` writes the ones a rule wants for the reader alone (`explicitOperatorPrecedence`). A rule with a list of operators of its own for that is a rule with an answer of its own.
- A rule that writes a call or a node of its own clones the arguments and the operands it keeps, and a clone brings the trivia of its edges along: the trailing trivia of the closing parenthesis belongs to what follows the call, which `replaceWith()` keeps on the node it replaces, so the clone must lose it or the space or the line ending comes twice. A fixture ending every call with a semicolon never shows it.
- PHP binds a function or a class declared at the top level of a file or of a namespace before the code runs, and one inside a function, a loop or a branch only when the code reaches it. A rule that moves statements out of a branch therefore keeps a branch declaring one where it stands at the top level (`earlyExit`, `uselessElse`), because the move would bind the declaration whatever the condition says.
- `Rules\Upgrading` holds the rules whose subject is a catalogue and not a construct, which is why they live together although they fire on nodes of every kind: `forbiddenFunctions`, which a map the project gives fills. A rule reading the catalogue PHP carries of itself is about its construct still and lives with it (`noDeprecatedFunctions`, `noDeprecatedArguments`).
- A rule adding code writes it in the shape the other rules ask for, so that they find nothing to add. `CodeWriter::addImport()` writes an import in the shape `dresscode/importNotation` gives its kind, asked through `RuleContext::findRule()`, which hands a rule another rule as configured for the file, or where that rule gives none the way the scope writes its imports, and puts it where the default order of orderedImports does; a group use standing under the namespace of the name takes it as an item where importNotation keeps groups, orderedImports placing a group by the first name it imports and sorting its items under its prefix, which it can do without disturbing the shape because it keeps the whitespace of a group place by place; a group writing a type per item holds several kinds, so it keeps the order it has and only takes its place. How wide a group may be before its names fill several lines is `dresscode/multilineImport`, the comma that ends them `dresscode/trailingComma`, and from how many imports of one namespace a group is made `dresscode/groupImport`, whose count holds both ways, a group of fewer names becoming imports of their own through `NodeHelpers::expandGroup()`, and which says nothing at all while importNotation expands group uses, and nothing of a kind it writes combined.
- `Rules\BlankLines` holds the schema of a count of blank lines in the options of a rule: a number, a range `[min, max]` (a `tuple`, with `null` for an open end) or `keep` to leave the place alone; the count is what a rule claims as the `blankLines` of a `Gap`, and the engine moves a count outside the range to its nearest bound.

### Names of global functions and constants

- `dresscode/nameNotation` and `dresscode/nameFallback` split the writing of names by the transition, so that they never pull at one token: nameNotation moves a qualified name between the import and the leading backslash and is never risky, nameFallback moves a global function or constant between bare and qualified, risky unless the resolution of names is certain. nameFallback writes a qualified name in the shape nameNotation gives it (`findShape()`), and nameNotation leaves a name nameFallback writes bare (`isWrittenBare()`) and adds no import a bare name would be taken over by; what both read of a namespace is `Rules\Namespaces\NameReferences`.
- The keys of nameFallback go from the general to the particular and the most particular that answers decides: `function` and `constant` speak of every global function and constant, `optimizedFunction` of a function PHP optimizes where a call of it is optimized with its arguments (`Compiler::isOptimizedCall()`), and `optimizedConstant` of a constant of PHP where the compiler computes with it, which takes only `qualified` or `keep`. The compiler optimizes a call or puts a constant in place only for a name it knows to be global while compiling: qualified, imported, or in a file without a namespace.
- `dresscode/optimizedCallNotation` writes a call PHP optimizes in the form the optimization takes: a named argument of a function PHP 8.4 calls without a frame positionally where it stands at the position of its parameter (`PhpSymbols::findFramelessParameterNames()`), and an unpacked argument is reported with no fix. The rules that write calls in the form PHP optimizes carry the group `optimizedCalls`; `nameFallback` is not among them, because its decision needs an option a group does not carry, so a project names it itself.

### Whitespace and indentation

- Horizontal whitespace between two tokens on a line is the trailing trivia of the first one, never the leading trivia of the second (a rule joining two lines writes the space there, or the next rule reading the gap sees none), and it is read and written through `Token::getTrailingSpace()` and `setTrailingSpace()`, which answer `null` and refuse where no such whitespace is there to write. `Token::is()` given a text never matches the content of a string, only operators and punctuation. `Indentation::measureLineWidth()` measures a line visually, tabs by the tab width of the style.
- The style a rule gets from `RuleContext::$style` and `Gap::$style` is `DressCode\Style`: the indentation, the line ending, the tab width and `lineLength`, the widest line that passes (null for none), which every rule that breaks or reports a long line reads instead of a threshold of its own. A rule that breaks a line by its width decides only once the line has the indentation `dresscode/indentation` gives it (`NodeHelpers::isLineInPlace()`, the rule reached through `Gap::findRule()`), a pass later where the indentation is wrong, because the width of a line indented by chance would make the break a fixpoint of its own. What PhpSyntax measures and writes whitespace with (`Indentation`, `Indentation::measureLineWidth()`, `Token::getVisualColumn()`) takes `PhpSyntax\Style`, which has no line length, and gets it from `toPhpSyntax()`.
- `Token::removeTrailingWhitespace()` also trims the end of a `//` or `#` comment, because the tokenizer counts the spaces before the line break as part of the comment text; a rule that calls it therefore changes a comment. Where the line goes on it takes the space before the next token as well, joining the two, so it is for a token that ends its line.
- Indentation is changed through `Indentation` and `Token::getLineIndentation()`; `Token::setIndentation()` alone moves one line and leaves the rest of the statement where it was. `Indentation::opensLine()` says whether the line ending above a token is trivia, which is the only case its indentation is whitespace a rule may write: `Token::startsLine()` also answers yes after inline HTML, a heredoc body or a close tag, and there the leading whitespace is text.

The indentation of every line is decided by one rule, `dresscode/indentation`, and it is a function of the tree alone: a line-opening token belongs to the lowest ancestor it does not begin (`Indentation::findOwner()`), the slot it stands in has a `LayoutRole` (`LayoutData`, which the syntax layer generates for every slot), and the line is placed by that role at a level counted from the level the rule gave the line the ancestor begins on, never read from the text. A line no rule governs (the first token of a file, the code after inline HTML, an operator the options leave alone) is a fact the lines below count from.

The rules that break a construct over lines (`bracesPosition`, `multilineCall`, `multilineSignature`, `multilineCondition`, `multilineArray`, `multilineChain`, `multilineTernary`, `singleStatementPerLine`, `singleMemberPerLine`, `attributePosition`) are claims on the line breaks, and where the lines then stand is not their business; the engine gives an opened line the conventional indentation (`Indentation::infer()`), so that the shape is acceptable even when no rule about indentation runs. A rule that reads the indentation of a line to place another one reintroduces what this design removed: a wrong line that carries its neighbours with it and is a fixpoint afterwards.

Code between pieces of inline HTML (a template with `<?php if ($a) { ?>` around markup) begins on lines the markup opens, and what those lines have is text the rule counts from as it is: such a file is not laid out by the tree, and PER exempts templates as well.

### Gaps

The gap between two tokens (the whitespace when they share a line, the line break, the blank lines when there is one) is decided by claims rather than by procedures. A `GapRule` declares, per node class (or `*`) and slot (`'body'`, or `'statements:item'` for every item of a list, `'arguments:separator'` for its separators), the `Claim` it makes before and after the value of the slot: `space`, `line`, `blankLines`, `blankLinesBelowComment`, each null when not claimed. The factories `Claim::singleSpace()`, `Claim::nextLine()`, `Claim::blankLines(1)` are the claims on one component, shared instances, and a rule with an option builds its claim once in `configure()`. Where the claim depends on the code (`?:`, `.` against the other operators, a keyword followed by `;`, the kind of the statement above) it is a closure given the `Gap`: the token at its edge, the value or item the claim was made for and its index in the list, the `Style`.

A claim of `*` applies to every class that has the slot, so it is right only where the slot means the same thing in all of them (the `openBrace` of a block is not the one of `$o->{$m}`, the `body` of a statement is not the one of a `match` arm), and elsewhere it names the classes. A claim must also be right on its own: the stricter claim wins only among the rules that are on, and a fixture runs its rule alone, so a claim right only thanks to another rule passes its fixture and breaks under a preset.

A claim that depends on the shape of the text (a list already broken, a line too long) must give every gap of the construct the same answer whatever the engine did to the gaps before it: the closure decides once per pass, from the shape the construct has when its first gap is reached (`Gap::once()`, which the engine remembers by rule and node until the pass ends), and a list counts as broken once any item or its closing delimiter begins a line, so that a decision to break it holds for the rest of the list.

`Engine\Gaps\Resolver` applies every gap rule along the traversal of the formatting stage: entering a node hands the claims to the first and last tokens of its slot values and to each item of a list, and reaching a token decides the gap before it component by component. The claim of a class goes before one of `*`, an inner slot before an ancestor's, the stricter space before the looser (`return;`), and of blank lines the count both sides allow or the narrower of two counts that exclude each other. When the two sides disagree about the line, `Line::Next` wins over `Line::Same`. What was decided goes to a `Gaps\Sink`: `Gaps\Fixer` reports under the name of the rule whose claim won and fixes; the messages of all three components are composed by `Gaps\Messages`. The claims are checked and indexed by class and slot once for a configuration, by `Gaps\Claims`, which `Engine\RulePlan` holds together with the node rules of each stage and the classes each of them is dispatched to; `FileProcessor` makes the plan at the first file and the runner of every file reads it, keeping only what belongs to the file and the pass.

Blank lines are counted above the comment that stands on lines of its own above a token, because the comment goes with the code below it, except above a token that closes a construct (`LayoutRole::Closer`) or the file, where the comment belongs to what is above and the blank lines below it are what is counted. The blank lines between the last comment in the gap and the token are a component of their own, `blankLinesBelowComment`, which the rule about declarations claims for a doc comment, so that no rule reaches into the trivia of a token for them.

The open tag is trivia too, and the gap it stands in is decided like any other where the tag opens the code of the file (after nothing or a hashbang): a `Line::Next` there means the tag ends its line, which `blankLines` claims; inside markup the tag's line is the template's and no rule breaks it. A gap inside a string (an interpolation, a heredoc, backticks) or next to a close tag, inline HTML or the data after `__halt_compiler()` is printed text, and the resolver decides nothing there whatever is claimed.

A claim of no whitespace is a claim of a single space between two tokens the lexer would read as something else once they touch (`Lexer::canAdjoin()`): `- -$a` is not `--$a`, whatever a rule says about the space after an operator.

A required line break goes in first and the blank lines wait for the next pass, and a doc comment standing in front of the token on its line goes below with it, because it documents the token. A forbidden line break is taken out only when nothing but whitespace stands in the gap; where a comment stands there the claim is reported and left unfixed, and the settled round reports it again, so it is among what the fix leaves.

Two plain claims on the same component of the same side of the same slot are a `ConfigurationException` when the rules are put together, so a gap has one owner; closures may share a slot because each abstains where the other decides, a plain claim shares it only with a plain claim on other components. Put together is also where a claim is checked against the slots the tree has (`LayoutData::Roles`, the same table the resolver hands the claims out by): a claim on a slot no node has, or `:item` and `:separator` on a slot holding no such list, is a `ConfigurationException`, because a slot renamed in the tree would otherwise leave the rule claiming gaps that never reach it, and neither a type nor a fixture would say a word.

Two closures deciding one component on one side of one slot at the same gap are refused there, so rules whose closures share a slot abstain by a predicate they both read, not by two that happen to agree: `binaryOperatorSpacing` leaves the line around a boolean operator chaining a condition to `multilineCondition`, both asking `NodeHelpers::findConditionStatement()`. Where no predicate can say which rule decides, a rule claims the break from the other side of the gap: `ternaryOperatorSpacing` claims the break in front of `?` and `:` after the operand before them, because the claim before the operator is `multilineTernary`'s. An empty pair of braces has one gap and not two, and it belongs to the closing brace, so a claim after the opening one abstains there; the braces of a `BlockNode` are claimed through the block, whose parent says whether it is a body.

A gap rule is made of claims alone: `GapRule` and `NodeRule` are the two shapes of `Rule`, a class is one or the other, and a rule that also has to change tokens is two rules (`attributeSpacing` and `uselessAttributeParentheses`). `RulePlan` refuses with a `ConfigurationException` what would never run: a rule of neither shape, a gap rule whose `RuleInfo` names another stage than `Formatting`, where the engine settles every claim, and a visited type that is no class of a node or a token, nor an interface. A gap nobody claims is left alone.

### Traversal

`Node::getChildren()` is the children in source order, empty slots left out, and the only way to the children: a node is not iterable, except a list (`NodeList`, plain or separated), which is read as a collection of its items, and `ModifiersNode` over its tokens, so that there is one way and it is an array, which the printer, the index and the traverser read directly. `Node::find()` takes a node class, optionally narrowed by a predicate, and gives the descendants it accepts as a snapshot safe to iterate while mutating; `Node::findFirst()` stops at the first one. The `Traverser` walks in pre-order; it does not descend into a node a callback replaced, skips siblings detached meanwhile and leaves inserted ones for the next walk.

## Rules and the engine

### Identity

A rule is one instance per run and stateless across files; the state of a pass over a file lives in `RuleContext::$storage`, which every pass begins empty, so that the last pass reports all it finds. Its identity is the `#[RuleInfo]` name (`vendor/slug`); `RuleRegistry` maps names and classes and refuses a name owned by two classes.

### Report before mutation

Every mutation must follow a `RuleContext::report()` that returned `true`. `PassRunner` pairs the two through `FileNode::$revision`: a callback that raised the revision without a report ("silent mutation") or after a report that returned `false` (silenced by a `dresscode:ignore` comment) breaks the contract; `strict` mode (RuleTester, `--strict-rules`) throws, otherwise it is a warning of the file. A denied report, by a comment or because the run refuses a risky fix, is judged by the window between it and the next report of the same rule, not by the whole callback, because a callback that reports many times may be denied one occurrence and allowed the next. Along the gap traversal the revision covers every rule of the stage, so the silent-mutation check is left out there: the whitespace of a gap is written by the engine and always after a report of its own.

What a fix leaves is not read from the reports at all: a rule may report every occurrence first and write its fixes afterwards, the whitespace of a gap is written for the whole traversal, and a rule may rewrite what another one reported, so no window of revisions says which report a mutation was for. `FileResult::$remaining` is what the rules report over the settled text instead, see below.

### Risk and consent

Risk is a property of the occurrence, not of the rule: `report(risk: Risk::TypeUnknown)` says that fixing this one may change what the code does, and names what would decide that it does not: the type of a value (`TypeUnknown`), whether an unqualified name reaches a function of the namespace (`NameUncertain`), or a human (`BehaviorChanges`), where changing what the code does is the point of the fix or depends on code the run does not see. `because` says what may go wrong at this occurrence where the risk alone does not say it; it stands beside the message and never in it, the message being part of the fingerprint and bound to stay the same whether the run can decide the risk or not. The violation is recorded either way, and `false` comes back until the run is allowed to make such a fix (the configuration names the rule in `fixRisky`, or `--fix-risky` on the command line allows every such fix). The rule then leaves the code alone, and the violation says `risk` and `refused` and stays among what the fix leaves. A `dresscode:ignore` comment silences it like any other violation.

An occurrence the rule has no fix for is reported with `fixable: false`, which is never risky, never lets the rule mutate and is therefore never offered to the consent (`strictCall` on an explicit `false`, `typeHintRequired` on a parameter with neither a type nor an annotation), and a pass that changed nothing while a rule reported an occurrence without it, neither refused as risky nor a gap the engine fixes, is a broken contract (`PassRunner::checkUnfixed()`), so a forgotten `fixable: false` is a failing fixture rather than a false offer.

A comment inside the code a rule would rewrite silences the rule, which then neither fixes nor reports: the comment says the code is written so for a reason, and the rewrite would lose it or carry it where it no longer says that. A rule that reports such an occurrence anyway (`noCallUserFunc`, `optimizedCallNotation`) reports it with `fixable: false`, best with the reason after the message (`, but a comment stands among its arguments`), and says so in its docblock, where silence needs no word.

**A risky fix may change what the code does; it may never write code that does not compile.** What only a file the project need not know of could decide is therefore not risky but undecidable, and there the rule says nothing at all, because the consent of `fixRisky` cannot be asked for it: `readonlyClassForReadonlyMembers` marks a final class alone, since the children of any other would have to turn readonly with it, `readonlyForUnwrittenProperty` and `readonlyForAnnotation` a private property or any property of a final class, since a child may redeclare a protected one, and `neverForThrowingFunction` a method nothing can declare again, `never` having no subtype. Each is a fatal error in another file, not a change of behaviour in this one. A class marked `@internal` is where the project does know: only its own package may extend it, so the project giving the consent is the one place such a child may live, and `finalInternalClass` is risky rather than silent.

An unqualified call of a global function in a namespace is a risky occurrence wherever `NameResolver::getUnqualifiedResolution()` says `UnqualifiedResolution::Uncertain`, which `nameResolution: certain` of the project takes away, and the rule that rewrites it reports it with `Risk::NameUncertain` and the reason `GlobalCalls::findUncertainty()` gives; a name the rule writes anew follows the name it replaces, or `NameResolver::shortenName()` where there is none.

A rule whose every fix may change what the code does says so at every report, the risk having no other channel: `staticClosure` cannot see a later `bindTo()`, and `strictTypesRequired` turns a coerced argument into a TypeError. Turning such a rule on, by name or by a preset, is not consent to the change: the project gives it by naming the rule in `fixRisky`, for the whole tree or in an override for a part of it, which a preset cannot (the resolver refuses it), and `--fix-risky` gives it to every rule for one run. A hook therefore needs no switch of its own: it fixes what the project accepted and reports the rest.

### Severity

Every violation is an error until the configuration softens it: the `warnOnly` of a profile names the rules whose violations only warn, `PassRunner` stamps the severity when it makes the violation, and `RunResult::getExitCode()` counts the errors and syntax errors alone, with `--max-warnings` as the only threshold the warnings can cross. `keep` on a rule says what `false` says.

### Passes

A pass is one pre-order traversal per stage (`Structure`, `Formatting`, `Finishing`); node rules are dispatched by `instanceof` on the node class, in configuration order within a stage, `enter()` and `leave()` apart and only for the rules that override them, and the gap rules ride along the traversal of the formatting stage. When a rule replaces or removes the node it was given, the rest of the chain for that node is skipped. Passes repeat until one changes nothing; the printed text of every mutating pass is hashed and a repeated state is a cycle, reported at once with the rules that mutated and a diff of the two states. Rules must therefore be idempotent and must not depend on the pass number, which the context does not expose.

### Positions and derived violations

Violations carry positions from the original file (`Token::$line`; for a synthetic token the first original one after it within its statement or member, which is what a fix moved or left in place of the code it replaced, so that a report of a later pass on a rewritten call lands on the line of the call, and failing that the nearest original token before it; `Trivia::$line` when the report names a trivia, so that whitespace and comment problems land on their own line for suppression).

A violation that the fix of another violation brought about is **derived** from it: `Violation::$derivedFrom` names the fingerprint of the first violation of the chain, so that a report is true about the file on disk or says which violation made it true. The fixer remembers, per token, the violation it opened or closed the line before that token for, and a report about the gap before such a token (its blank lines, which wait for the next pass, the whitespace of a joined line, the indentation the engine inferred for an opened one) follows from it. A rule that places a line by what another line was given says so with `report(follows: $token)`, the token opening that line, and the report follows from whatever opened, closed or moved that line; `dresscode/indentation` names the line its construct begins on, so a block indented consistently wrong is one violation and the lines placed by it follow it, and a condition written again carries its continuation lines with it. A rule that reports the shape of the line a token stands on says `report(byLine: true)` instead, which asks the same of that line but claims nothing about its whitespace, so nothing is placed by such a report: the comma `dresscode/trailingComma` asks for is there because the closing bracket takes a line of its own, so it follows whatever put the bracket there.

Nothing else is derived: not a report on a tree another rule has changed, by that alone, and not even one on a token a fix wrote anew, which is often the user's code rebuilt (a group import expanded into statements, a gap moved in front of an inserted modifier), and a rule adding code writes it instead in the shape the other rules ask for; not a report about a comment, which is the user's whatever line it stands on, and not the sibling claims of one decision, each about a break the user did not write. Those are not derived but one: the claims whose closure decided something about a construct through `Gap::once()`, a decision other than null, false or an empty array, are about its shape, so every gap of that construct is reported in the pass as a single violation, placed at its first report, silenced by a comment on that line and given one fingerprint (`Fingerprints::createFor()`, placed by `placeConstruct()`), and a rule of a shape is reported once per construct, which is what counting the places it decides needs.

A derived violation is a violation like any other, in the JSON, under `dresscode:ignore` and in the exit code, because `fix` changes what `check` reports and the derived ones are changed too; only the console format folds them under an ancestor of the same severity, and the bare one folds nothing.

`RuleContext` keeps the reports of a callback as `Engine\Report`, with the gap and the line a report is about, and `PassRunner::account()` turns them into violations. The fingerprint (rule, normalized line content, and the place of the violation among those of the rule on that line, in the order they first come while the file is processed) is made by `Engine\Fingerprints` at the moment of the report, so that the position is the one the reported code still had; repeated reports of one violation across passes collapse on it. The message tells the violations of a rule on a line apart and is not part of the fingerprint, so that a message worded otherwise by a newer version keeps the fingerprint; two violations of one rule on one line are told apart by their order alone, and once the first is fixed, the second takes its fingerprint.

### Suppression

Suppression is read once from the original comments before any mutation: `dresscode:ignore [names]` on a line silences that line, on its own line the nearest node starting on the next line, `disable`/`enable` a range, `ignoreFile` everything; what follows ` -- ` says why, as in ESLint and phpcs, and names no rule.

### Processing a file

`FileProcessor` is a pure function of path and text: parse, passes, print. A mutated tree is not the tree the parser would build from the printed text, so a rule can miss what another one has just written; a strict run (`--strict-rules`) therefore does the same again over the printed text until it settles, at most five rounds: a text the rounds come back to, or one still changing in the fifth, is a `ConvergenceException` and fails the file like a cycle of passes, because only a broken rule gets there. Any other run takes the last pass of the tree, which changed nothing, for the round over the printed text, which spares a pass of every fixed file and keeps only its parse, so that a broken rule never writes code PHP refuses: what that pass reported, identified by the lines of the printed text as a run over it identifies it (`PassRunner::collectRemaining()`: the line of a token where it stands now, of a trivia counted back from its token, the fingerprints counted again in the order of the pass, the violations it follows from found again), is what that round reports. `RuleTester` holds the two equal on every fixture, and a run over the corpora found them equal on every file; the price is that a rule missing in the tree what the text shows is seen only by a strict run.

The violations reported are those of the first round, whose positions belong to the file as it was. What the last round reports, or the last pass standing for it, is `FileResult::$remaining`, positioned in the fixed text: it is a full check of the text a fix writes, so it says exactly what the next check of that text reports, and the exit code of a fix and every listing of what a fix left read it, while a check says how many a fix would leave. A text that no longer parses is a failure of the fixer rather than a syntax error of the file. What a run reports therefore depends on which other rules are on: a rule that fixes a shape first takes away the report of a rule that would have met it later. A syntax error is a result, not an exception, and the `Style` follows the prevailing line ending of the file unless the configuration fixes one.

### Running

`Runner::findFiles()` finds the files (patterns with a slash are anchored to the root, without one they match a segment at any depth, both also match directories on the way; a file named on the command line is taken as it is, and only `--skip-excluded`, which a hook or an editor naming every file it touches passes, lets the excluded paths leave it out like a found one) and `Runner::run()` takes that list, reads and writes the files and hands results to a `Reporter`. The caller expands the paths so that it knows the scope before the run starts. A path named on the command line is relative to the working directory, and `Runner::narrowPaths()` narrows a named directory that holds some of the configured `paths` to those, so that `fix .` in the root never reaches beyond them, while a path outside them is taken as named.

The format is the whole contract of the output, never a switch modifying another one: `console` unless `--format` says otherwise, `github` when `GITHUB_ACTIONS` says the run is a step of a workflow, `json` and `checkstyle` for tools (the JSON document says its `version`, the `mode` and the `root` of the run, its keys are camelCase and the values from the code stand as they are, a change of its shape being a new version), and `bare` for a hook, which prints the violations left to the user and a `rewritten` note for every file the fixer touched, so a clean run prints nothing while a silent rewrite never happens. The header naming the configuration file and the scope belongs to `Console\Application` and is written, together with the warning that Xdebug makes the run many times slower, only for the console and github formats; the progress bar only for the console format on a terminal, where it is a status of the very console the report goes to, so that writing the report erases it. A fix run lists every file it touched exactly once, with a `rewritten` note and under it what the fixed text still violates; which violation a fix removed cannot be told from the text, so the verdict counts what was found and what remains, and `--diff` shows what changed.

A rule exception or a cycle fails that one file (nothing is written, the run goes on, exit code 2, also for a runtime error of the tool), and so does a file whose text on the disk is no longer the one processed when the fix is about to write it, so that what an editor saved meanwhile is never overwritten; a syntax error is exit code 1 like a violation, while a mistake of the command line or of the configuration, and a program run without a command, is exit code 3, which is no result of a run at all.

A process working through files keeps the cycle collector of PHP off and collects between two files once the memory has doubled since what the last collection left, never above three quarters of `memory_limit` (`Engine\CycleCollector`). The collector PHP runs by itself scans again and again what stays alive, the tree being processed above all, and frees little.

The run keeps of the result of a file what it needs without the code and the output (`Engine\FileSummary`), so that only the file in progress is held as text.

## Configuration

### The file

A configuration is written as `dresscode.neon` or `dresscode.php`, and the two are the same thing said twice: every key of the NEON is a named argument of the constructor of `Config`, so `NeonReader` is a schema that accepts no key it does not know, the evaluation of entities and a spread into the constructor.

The shape is shared: `Profile` holds what decides how a file is processed (`presets`, `rules`, `indent`, `lineEnding`, `lineLength`, `targets`, `namespaces`, `nameResolution`, `fixRisky`, `warnOnly`), a preset is a profile under a name, an `Override` is a profile with the `paths` it applies to, and `Config` is the profile of the whole project with the scope of a run (`paths`, `excludePaths`, `fileExtensions`, `skipWhen`), its `overrides` and what it brings in (`plugins`, `analyses`). They are readonly values checked when they are constructed: a value one of them refuses is an `InvalidArgumentException`, which `NeonReader` and `Loader` turn into a `ConfigurationException` naming the file and the resolver into one naming the preset.

What the PHP notation passes as an object or a callable (a plugin, `skipWhen`, the factory of a rule or of an analysis) the NEON writes as an entity: `Class(args)` is a new object, `Class::method(args)` what the static method returns, `Class::method(...)` the method itself, and in a chain `Class(args)::method(args)` a link calls the method on what the link before it gave. An entity is evaluated when the file is read, except the one of a rule: a rule is built anew for every combination of overrides, so its entity is a recipe evaluated at every build, and only the class or method it starts from is looked up when the file is read, so that a misspelled one is still an error of the file. The schema keeps only the keys the file gave, so that an absent key keeps the default of the constructor.

`Loader::find()` walks upwards and takes, in each directory, the local file before the `.dist` template; the two formats side by side are an ambiguity it refuses rather than resolves. A configuration file is the only thing laid over a project, and `--config` names it (its format follows its extension); a wrapper binary that wants a configuration to apply in a project without one hands `Console\Application` a `defaultConfig`, which the loader uses when it finds no file. The command line is no key of a file: `--preset` and `--rule` are a `Profile` laid over everything the file says (the value of `--rule name=value` is NEON, decoded as the value of the rule in a file, a bare `name` meaning `true`), and `--only`, `--fix-risky` and `--strict-rules` are parameters of `RunnerFactory::createRunner()`.

### Plugins

`plugins` names plugins alone, by class or as an object, and a class that is none is refused with the message of `Config`. A `Plugin` is what a package brings to a project: its `getManifest()` is a `PluginManifest` with the `rules` and the `presets` it makes known by their names, the `plugins` it builds on, `analyses`, `excludePaths`, `skipWhen` and `ruleUrl`; the manifest has no other key, so a plugin cannot decide what is the project's, and the fields it shares with `Config` are checked by the same code. A rule of the project itself is named by its class in `rules`, a preset in `presets`, and `RunnerFactory` makes either known by its name, the rule with the `ruleUrl` of the configuration. `ruleUrl` is the address of the page of each rule, `{slug}` standing for the name without the vendor, given by the manifest for the rules of a plugin and by the configuration for those it names by class; the name of the rule in the report of a terminal links to it, and a built-in rule has its page on dresscode.run. A plugin lies below the project, the plugins it builds on below it and every class once: the excluded paths add up, a file any of them skips is skipped, and an analysis of the same class the project gives wins. How the code is written is no business of a plugin; that is a preset, which the project names, so the standard of a project is always read in its own file.

### Presets

A preset is a `Profile` under a name (`Preset::getProfile()`), whose `presets` are the ones it builds on; it may carry the style it needs, and it may not make a decision of the project, `targets`, `nameResolution`, `fixRisky` or `warnOnly`, which the resolver refuses. A rule or preset is named either by class or by name, and a name without a vendor is the built-in one. Any preset may set the style, `indent`, `lineEnding` and `lineLength`, the later layer deciding as it does for the options of a rule; that two presets of a project fit together is for their authors and the project to see to.

Without a configuration file nothing applies: DressCode has no style of its own to fall back on, so a run refuses, unless `--preset` names a preset, which is then all the run has, so that a run over a foreign project can ask for that alone.

### Resolving the layers

`ConfigResolver::resolve()` lays the profiles that decide for a file one over another: the configuration, the overrides the file matches in the order they are written, and the command line, each above the presets it names with their parents, parents first and every preset once, where it is named first. A later layer has the last word on a value (`indent`, `lineEnding`, `lineLength`, `nameResolution`, and every key of `targets`), adds to a list (`namespaces`, `fixRisky`, `warnOnly`) and merges the options it gives a rule with those of the layers below; the order of the rules is that of their first mention. Every mention of a rule is a layer, and the resolver turns the layers into a `ResolvedConfig`: what each rule ends up with, the layers that said it, the style, the target version of PHP, and for a rule that does not run the reason it does not. The run builds its instances from that one result.

**A map of options merges with the layer below it key by key; a list and a scalar replace it, and a list also replaces its default.** Turning a rule off drops what was said before it, so a map written after that starts from the defaults of the schema again. A preset that writes `true` over a parent that set options therefore keeps them, and a preset that wants something else says so. The merging is `Processor::processMultiple()` over the schema of the rule, which knows a map from a tuple, in `Config\RuleBuilder`, which also makes the instance of the rule from what the layers come to; the policy that a list replaces is one line there, the `Helpers::PreventMerging` marker every `merge()` of `nette/schema` honours.

A rule that is one decision says so with `RuleInfo::$decision`, the option a bare value written for the rule fills (`dresscode/yoda: forbidden`), which `RuleBuilder` turns into that one-key layer before the layers meet, so the long and the short notation resolve to the same thing; a rule that declares none refuses a bare value and says which options it has.

`keep` is the only word for "leave this alone" and it means the same at every level: on a rule it drops the rule from the run, in an option it takes that one place out of what the rule governs, so `null`, `false` and a turned-off rule never stand side by side for the one idea. The schema of such an option names `keep` among its values, and the rule turns it into whatever its own code calls "nothing to claim" in `configure()`.

An option whose value is one of an enumeration may also take a list of them, and that list is a tolerance, not a set: every shape in it passes, and what is in none of them is written in the first. The rule turns the list into the shapes that pass and the target once, in `configure()`, decides per unit which it is (`Gap::once()` for a gap rule) and then claims the target alone; a rule that held one claim per tolerated shape would claim the same gap twice. What the predicate of a shape measures and how far the claims reach must be the same set of nodes, or the rule reports what it cannot fix, or fixes what it did not report.

What the schema warns about the options it completed, through `Context::addWarning()` in a `transform()` (that they leave the rule nothing to do), or what `nette/schema` warns itself (a deprecated option), reaches the user as `Rule <name>: <message>`, once however many overrides are resolved, so a message is a sentence of its own, and the resolver knows no rule by name.

An override (`overrides` in NEON, `Override` in PHP) is a profile for a part of the tree, with every key a profile has: its `paths` go through the same matcher as the excluded paths, anchored to the root of the configuration. A file's configuration is therefore the combination of overrides it matches. `RunnerFactory::createRunner()` builds one processor per combination, with an `Analyses\Registry` of its own because an override may add to what the namespaces declare, and `Config\FileProcessors` keeps them, because a rule carries the options it was configured with and must never be reconfigured under a file already being processed. A part of the tree where a rule must not run is an override that turns it off, so a later override may turn it on again. Every override is resolved on its own when the run is built, not when a file of it comes, so a name no rule or preset owns and an option no rule takes are an error naming the override rather than a line that does nothing until such a file comes.

The style is the last one a layer says, else a tab, the majority line ending of each file and no line length (`false` in a layer says none over a length below it); `platform` is answered by the resolver, so what reaches the engine is a line ending or `majority`. The excluded paths only ever add up, the default list, those of the extensions and those of the configuration, so no layer can bring back what another left out.

`only` (`--only`, a parameter of the run and no key of a file) narrows a run to the rules it names, a preset standing for every rule it and its parents mention, and it is one more reason of that resolution, applied to what the rest came to after `--preset` and `--rule`: it takes a rule away and never enables one, and a name that lets nothing in is an error rather than a run that checks nothing. `fix --only` fixes that one rule and leaves the rest, so the next full `fix` changes more, which is the point and not a failure to converge.

### The target version of PHP

The versions of PHP the rules target are a property of the checked project, never of the run: `RunnerFactory::resolvePhpTarget()` takes them as a Composer constraint from `targets: {php: ...}` of the configuration, which is one version, else from `require.php` of the nearest `composer.json` at or above the root, the whole constraint (one without a lower bound, `<8.4` or `*`, leaves the version to the default rather than to a guess), else from `Config::DefaultPhpVersion`, and an override may give its files another one with `targets: {php: ...}`, which is all an override may say there. A rule runs where every version of the target satisfies its `requires`; what a rule asks with `RuleContext::$phpVersion` is the lowest of them. Whichever it is, a version older than `Config::MinPhpVersion` is raised to it by the resolver with a warning, because no rule asks whether the target has what PHP 8.0 already has, so a fix may write such syntax. Nothing else raises it, a package backfilling a newer construct least of all: a rule writes what the version the project moves to gives its code, while such a package exists so that the project need not move, and taking it for an answer would turn the target from a version into a list of what happens to be in the vendor directory.

The version a rule asks about travels as a plain string compared with `version_compare()`, never with the string operators, under which 8.9 outranks 8.10, and always in the short form `Config\Versions::shortenVersion()` gives, without the zeros a normalized one pads with, because `version_compare()` takes `8.1` for older than `8.1.0`. NEON reads a bare number as a version whose minor is a single digit, which every PHP ever released has had, so `8` and `8.0` both mean 8.0, and `php` in `targets` may carry a patch version, so no rule takes the string apart by position. The running interpreter is never the answer, so that the same file gets the same verdict from any directory under any PHP; only `Lexer` asks about the runtime, to emulate the tokens its own build does not know.

What PHP itself declares is the same kind of question, and a rule asks `Analyses\PhpSymbols` about it rather than `function_exists()` or reflection, which would answer with the extensions and the version of the machine: the catalog holds every version from 8.0 on, so what depends on the version, since when a function is deprecated and which versions declare it at all, is compared with the target. The parameters of those functions are a catalog of their own, `Analyses\PhpSignatures`, because they are two thirds the size of the rest and the command line compiles what it loads on every run, so only a rule that asks about them pays for it; it answers with `Parameter`, whose `canReplace()` says whether an argument written for one parameter may stand at another, and it knows nothing of the extensions its source cannot see, where a rule then has no answer rather than a wrong one. A rule whose construct exists only from some version on says so with `requires: ['php' => '>=8.4']` in its `#[RuleInfo]`, a Composer constraint written as the `require` of `composer.json` writes it, all of it read by `composer/semver` (`Config\Versions`) and never by hand, and a range, a single version being refused because it would turn the rule off for every other release; an upper bound says a rule writes what a later version took away. It is metadata and never a directory, so that a rule lives with its topic, and `ConfigResolver` leaves it out below that version: silently when it came from a preset, with a warning when the configuration asked for it by name. A rule that needs the version more finely than "run me or not" asks `RuleContext::$phpVersion` instead, and never about anything PHP 8.0 already had. So does a rule about a deprecation whose replacement older versions know too (`noNullArrayKeys`, `noSleepAndWakeup`, `noDeprecatedArguments`): `requires` names the version that brought what a rule writes, which such a rule does not need, and the rule asks whether the target deprecates what it replaces.

### The namespaces of the project

What the namespaces of the project declare is a property of the project too, and no file shows it: an unqualified function or constant in a namespace reaches the namespaced one PHP knows at run time before it falls back to the global one. `namespaces: {functions, constants}` lists such symbols as the items of a use statement write them (`App\Utils\{format, parse}`, parsed by `Parser` when the profile is constructed), and every layer adds to the lists; `nameResolution: certain` says the lists are all there is, which the configuration or an override says and a preset cannot, knowing a framework and not the project. An override may say `uncertain` for a part of the tree whose declarations nothing outside it reaches, such as the helpers of the tests, so that no fix there rests on the lists and nothing there is guarded.

`ConfigResolver` puts both into `ResolvedConfig`, and `Analyses\Registry` builds `NameResolver` with them as `NamespacedSymbols`, which is also the analysis a rule asks for the lists themselves.

A certain resolution rests on lists that must stay complete, so the key turns on their guard, `noUnlistedNamespacedDeclarations`, as a layer of its own below the rules of the same profile, which may turn it off, and a file whose resolution ends up uncertain has no guard; a declaration the lists do not name is decidable in its file, a declaration inside a condition and a `define()` with its name written as a string among them (`NameResolver::findNamespacedDeclarations()`), and the lists can then go stale only through a path left out of the run or a package of the same namespace.

## Writing a rule

### Messages

A violation message describes the code, never the reader: no imperative (`Use…`, `Add…`, `Remove…`), because a rule that only reports has nothing to command. It takes one of three shapes, and which one is decided by the rule, not by taste: the required state as a noun phrase where the rule wants one short thing in one place (`A single space after a comma`), `<subject> must <requirement>` where that needs a sentence (`The opening brace must be on its own line`), and the defect where the thing is wrong in itself or the rule guards several places at once (``Function `foo()` is deprecated``, `Wrong whitespace in a type declaration`).

A family shares one pattern: every `…Spacing` rule says `No whitespace <where>`, `A single space <where>` or `At least one space <where>` with the token the claim is on as `<where>` (`before the closing parenthesis`, ``after the `return` keyword``), composed by the engine, every `…Indentation` rule `Wrong indentation of <what>`, every claim on a line break `A line break <where>` or `No line break <where>` with the bracket at the edge of the gap or the node the claim was made for as `<where>`, and the reason after a comma when the claim follows from a measure or a property of the code (`Claim::$because`: `A line break before the parameter, the line is 135 characters long`), every `…BlankLines` rule the measured `Expected <count> <place>, <found> found` composed by the engine from the node or token the claim was made for (`before the method`, `after the opening brace`), every `useless…` rule `Useless <what>` with the reason after a comma.

What follows the message after a comma says why the occurrence is treated otherwise: `, but <why>` where it is reported and left as it is (`…, but a comment stands among its arguments`), while why a fix is risky is not the message but the `because` of the report beside it (`the replacement evaluates the arguments in another order`, ``the namespace may declare `<function>()` ``). What follows a colon is the sentence of a map (``Function `X()` is forbidden: <sentence>``), and may command; the rule only trims its period and folds its whitespace. The sentence of a map writes its code in backticks as the rest of the message does. A message stays within 104 characters counted with every name as one word, so that a project with long namespaces does not break it.

The subject is the thing at the reported position, with a definite article, and an operator or a call in that role carries its kind (``The `<>` operator must be written `!=` ``, ``The `is_null()` call must be…``); `written X` names a literal replacement, `written as X` a form. Everything the message shows that is code stands in backticks, as in an exception (Exceptions and warnings below): a spelling to type or found (``must be written `Exception` ``, ``The keyword `YIELD FROM` ``, ``must start with `//`, not `#` ``), a call the message names (`` `is_null()` ``), an expression built from the code at hand (`` `$obj::class` ``), the name of a declared class, function, constant or member (``Global constant `PHP_EOL` must be imported``), and a token the engine names by its spelling (``after the `as` keyword``, ``before the `.` operator``). A token named by a word is prose (`the closing parenthesis`, `the comma`), and so is a word that is not a spelling (`camelCase`, `the short syntax`). A name cannot hold a backtick, so the message writes it in backticks directly; code that can, an expression, a string, a comment or a text of the configuration or of the data, goes through `Violation::formatCode()`, which writes a code span of Markdown in a longer run of backticks where the code holds some. Names and measured values belong in the message, the rule name and the standard do not. In prose a `/** */` block is a `doc comment` and a tag in it an `annotation`, whatever the rule name calls them; `whitespace` is what a rule forbids, `a single space` what it requires.

### Options

An option is named after the place or the shape it governs, and the bare name is that: `emptyBody`, `onObjects`, `leadingLinks`, `betweenMembers`. The prefix `allow` is reserved for the permission of an exception the rule would otherwise report (`allowMultiline`, `allowMultilineExpression`), so it never stands in front of a choice of shape. One idea carries one name across the catalogue, whichever rule has it: `ignorePatterns` is the list of regular expressions whose match is never reported, wherever a rule takes one.

Where a rule chooses a shape for each of several places, the key of the option is the place and its value the shape, `keep` among them (`bracesPosition.class: nextLine`, `nameCasing.method: camelCase`); a rule with a single shape takes the list of the places where it holds (`singleMemberPerDeclaration.members: [constant, property]`). A place is singular, in a key as in a value, and one place has one word across the catalogue: `class`, `anonymousClass`, `function`, `anonymousFunction`, `arrowFunction`, `method`, `constant`, `property`, `variable`, `enumCase`, `parameter`, `argument`, `array`, `list`, `matchArm`, `closureUse`, `import`, `trait`, `controlStructure`, `switchCase`, `catch`, `return`, `body`, a qualifier standing in front of the word (`globalFunction`, `optimizedConstant`, `emptyBody`, `promotedProperty`). A key relating places keeps the plural English asks for (`betweenMethods`, `afterTraitUses`), and so does a list of names the project brings (`sensitiveParameterRequired.parameters`).

An option deciding **when** a construct is split takes `always` and `keep`, with a width where the length decides (`maxWidth`), and one deciding **how** a split construct looks takes its shapes, `perLine` and `compact` for the items, `ownLine` and `sameLine` for where a token stands, so that a new rule speaks of the two in the words the catalogue already has.

An option carries a `description()` only where its name, type and default do not say everything: a hidden scope (`class` also covers interfaces, traits and enums), a hidden condition (`beforeFirstMember` does not apply when the first member is a method), an inclusive threshold (`minIntegerDigits`), a value whose meaning is not its name (`nextLineAfterReturnType`); a description that restates the name is noise. Its form follows `RuleInfo::$description`: English, one sentence, capitalized unless it begins with a value of the option, no trailing period, and its code in backticks as in a message (``Replaces `dirname(__FILE__)` with `__DIR__` ``); the same holds for the texts of the help of the command line. A count says where it applies ("Before the first member, unless…"), a boolean states what holds when true ("A class name referenced in a doc comment counts as used"), a choice names its values and what they do ("`atLeastOne` keeps…, `single` collapses…"). Another rule is referred to by its full name (`afterOpeningTag of dresscode/blankLines`). The text is checked against the code, not against the docblock of the rule.

### Exceptions and warnings

An exception or a warning is read by someone who has to act, so it says where, what and what to do, in that order. Where is a prefix naming what the reader edits (`Configuration file X: `, `Preset X: `, `The override for src/: `, `The command line: `), left out only when nothing but the command itself can be meant; what is a sentence about that thing, with the value the reader wrote or has to write; what to do follows after a semicolon, or as a second sentence when the first has one, and it is the only place an imperative may stand. A message the reader cannot act on, a broken rule, says whose fault it is instead. Every message is a capitalized sentence ending with a period, warnings included, `must` and never `has to`; a message wrapping another one puts it after a colon and adds nothing behind it, and what it wraps is left as its author wrote it.

Everything in such a message that is code stands in backticks, as in Markdown: a file and a path, a command and an option, a key of the configuration and a value (`` `x` given `` for a value refused), the name of a rule, a preset, a group or a package, a class, a function, a member and an annotation (``Configuration file `dresscode.neon`: ``). A word that only speaks about code is not code (`the configuration`, `a preset`). The console draws what the backticks enclose in color and drops them; every other output, a pipe, a log of CI, the formats `json` and `github`, the reader of the PHP API, prints them as they are, which reads well to a human and to an agent alike. Where a page of the manual says more than the message, the exception carries the path of that page (`ConfigurationException::$docs`), and the console prints it under the message as a link to `https://dresscode.run/`. What the author of a plugin reads (`RuleInfo`, the claims, `RuleTester`) states the contract that was broken; what the user of a configuration reads never names an internal class, node or slot.

### Testing

`Testing\RuleTester` runs a rule over `*.code` fixtures (`.expected` output beside them, `.violations` as `line: message` with the risk of a risky one on an indented line below it, `risky <Risk>` with `: <because>` where the rule gives one, options in a `// {"json"}` comment, a run that allows risky fixes in a `// risky` one, the targeted version in a `// php 8.4` one, the widest line in a `// lineLength 80` one (120 without it; `check()` takes a whole `Style` instead, whose line ending stays that of the code) and what the namespaces declare outside the fixture in `// namespacedFunctions`, `// namespacedConstants` and `// nameResolution certain`, all in the comments that open the fixture; without a version the rule is tested at the version of PHP it requires, else at `Config::DefaultPhpVersion`, never at the version of the interpreter running the tests) and, given `analyses:` in the shape of `Config::$analyses`, registers those of a plugin for the rule, then checks the contract: parent invariant, idempotence over the output, comments preserved unless `modifiesComments`, `dresscode:ignoreFile` honored, no silent mutation.

What no fixture catches, the runs over the corpus do: `name-meaning.phpt` runs the rules that write names and imports over the corpus and requires every name outside the imports to resolve to what it resolved to before, because an import moved into a statement writing its items differently, or dropped while something still uses it, leaves code that parses and round-trips and says nothing else.
