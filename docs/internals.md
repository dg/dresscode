# DressCode internals

How DressCode works: the facts an agent or a contributor needs before touching the engine, a rule or the configuration. The catalog of rules is not here; it is generated from the rules themselves.

## Layers

- `phpsyntax/phpsyntax` (namespace `PhpSyntax`, a repository of its own): lexer, parser, tree, printer, navigation, mutation. Its internals are documented there; what a rule of DressCode uses from it is below.
- `DressCode` (`src/`): engine, rules API, rules, configuration, CLI. Rules use only the public API of `PhpSyntax`; whatever a built-in rule needs from it is public API for plugins too.

## The tree a rule works with

Printing the tree reproduces the input byte for byte, so a rule changes what it means to change: formatting rules change trivia, structural rules change nodes.

- Whitespace, comments and open tags are `Trivia` attached to tokens. **Trailing trivia** of a token is everything after it up to and including the first end of line, **leading trivia** of the next token is everything else (blank lines, indentation, comments on their own lines, doc comments). An `OpenTag` trivia (`<?php` with its mandatory whitespace) is always leading trivia of the following token; the final `EndOfFile` token has only leading trivia.
- `<?php` is not a token. `?>` is a token of kind `CloseTag` that keeps the newline PHP swallows after it, and the parser sees it as `;`; after a terminated statement it forms an `EmptyStatementNode`. `<?=` is a token of kind `OpenTagWithEcho` seen as `echo`. `Token::isSemicolon()` and `isOpenTagWithEcho()` cover these cases.
- Whitespace that PHP counts as part of a token stays in its text: inline HTML, `T_ENCAPSED_AND_WHITESPACE`, heredoc delimiters (the closing one keeps its indentation), casts like `( int )`. A BOM or a hashbang line is inline HTML, as PHP sees it. A single-line comment never contains its newline, but it does contain trailing spaces before it.
- Trivia inside string interpolation (`"{$a /* c */ }"`) carry `inInterpolation = true`; the token helpers refuse to change them because that whitespace is part of the string value.
- Slots are named by role (`ifKeyword`, `openParen`, `semicolon`, `condition`, `body`), paired delimiters are always `open*`/`close*`, lists are plural. A slot says what stands in it rather than what the class suggests, so the left of an assignment is `target` and not a variable, and what a `switch` and a `match` compare against is `subject` and not a condition. Every token of the source has a slot or a place in a list, so the order and number of children are not part of the API, only the slot names. Whoever names a slot instead of reaching for it writes the name as a string (`'openParen'`, `'statements:item'`), which is what a gap rule declares its claims with.
- The body of a control structure is a `StatementNode`, not necessarily a block; `else if` is an `ElseNode` whose body is an `IfNode`. The alternative syntax uses the same classes with `colon`, `statements`, `endKeyword` and `semicolon` slots instead of `body`. Class-like declarations implement `ClassLikeNode`, because an anonymous class is not a statement.
- A new node comes from `Parser::parseExpression()`, `parseStatement()`, `parseType()` or `parseName()`, which return it detached, with empty trivia on its edges and without original positions; a constructor is public but its parameters follow the slots of the grammar, which a minor release may add to, so a call spells them as named arguments.

## Analyses

An analysis is information derived from a file, and any class the engine can build is one: `NameResolver` (namespace, imports, resolution of class, function and constant names with the runtime fallback of unqualified functions and constants to the global namespace, `isGlobalFunctionCall()`, and the way back: `getShortName()` gives the shortest way to write a fully qualified name where a node stands, through an alias, a prefix import or the namespace, and `isAliasFree()` says whether a name is still free there, which is what a rule adding an import asks), `Scope` (enclosing function-like construct and class, availability of `$this`, captured variables) and, in `DressCode`, `PhpDoc` (doc comments as phpstan/phpdoc-parser trees printed back with the original formatting). Analyses are lazy and computed once per file; `Analyses\Registry` (internal, reached through `RuleContext::getAnalysis()` and `Config::analysis()`) creates them on demand, with the `FileNode` when the constructor takes one, and throws them away as soon as `FileNode::$revision` changes, so any mutation invalidates every analysis of the file.

## Mutation from a rule

- A node or token belongs to exactly one tree: inserting one that already has a parent throws; `clone` gives a deep copy without a parent.
- A slot is written by assignment (`$node->condition = $expression`, `replaceChild()`, or `setSlot()` given the name of the slot), which adopts the value, releases the current one and tells the index. Lists mutate through `append()`, `insert()`, `removeItem()`, `replaceChild()`; `SeparatedNodeList::insert()` derives a missing separator from the existing ones (or `", "` in a one-line list) and gives the item the indentation of its neighbor in a multi-line list, `removeItem()` takes the separator after the item, or before the last one.
- `Node::remove()` removes a list item: a node alone on its lines takes the lines with it, otherwise the whitespace around stays; comments inside, each with the line ending after it, go to the next token, the previous token, or away, as the `CommentPolicy` says. `Node::replaceWith()` keeps the trivia around the old node around the new one by joining them with the new node's own edge trivia; a replacement cloned from nearby source still carries its original leading trivia, so clear the clone's edges first or an `OpenTag` gets doubled.
- What a rule reads is a property (`value`, `base`, `quote`, `label`, `indentation`, `kind`, `parts`, `role`, `text`), and it writes one where the write takes a single value with a single consequence: a slot, and `NameNode::$text`, whose hook tokenizes the name anew. It writes through a method where the write takes more values or two things change together (`StringNode::setValue($value, ?$quote)`, the delimiter deciding how the value is written), and for a token always, because `?->` cannot stand on the left of an assignment: `Token::setText()`, `setLeadingTrivia()`, `setTrailingTrivia()`, and `Node::setEdgeTrivia()` for the outer edges of a node, where the first or the last token may be missing. What has no hook the language guards: the text and the trivia of a token are `private(set)`, the items of a list `protected(set)`, `parent` is written by `attachTo()`. A hooked property takes no indirect change, so `end($token->trailingTrivia)` needs a copy.
- Every mutation increments `FileNode::$revision`, which the engine reads to detect mutations; it is a version of the tree, not a count, because a compound mutation raises it several times. `Token::$originalLine` and `$originalOffset` never change and are the source of positions in reports; `getLine()` and `getColumn()` follow mutations.
- A single trivia (typically a comment) is removed by `Token::removeTrivia()`, which tidies the whitespace around it: one alone on its line takes the line with it, an inline one takes an adjacent space; `Token::replaceTrivia()` swaps one in place. A doc comment is read with `Node::getDocComment()` (above the node, or after the previous token) and, after editing through `Analyses\PhpDoc`, written back with `Node::replaceDocComment()` or dropped with `Node::removeDocComment()`. The tree is the phpstan/phpdoc-parser AST itself, which is therefore part of the public API (its major version is ours), and it is edited the way its format-preserving printer expects: replace `children` or return a new node from a visitor, never mutate a list such as `UnionTypeNode::$types` in place (it prints wrongly); a text node whose text changed loses its ` * ` line prefixes, so rewrite whole lines; a tree with nothing but blank text (`PhpDoc::isEmpty()`) is removed, not printed, or it prints `/**  */`. `NativeType` (annotation to native type) is the shared helper above the AST and `PhpDoc::findTemplates()` names the template types in scope, which a native type cannot use; there is no tag-editing layer of DressCode's own. `Rules\Whitespace\BlankLines` holds the schema of a count of blank lines in the options of a rule: a number, a range `[min, max]` (a `tuple`, with `null` for an open end) or `null` to leave the place alone; the count is what a rule claims as the `blank` of a `Gap`, and the engine moves a count outside the range to its nearest bound.
- Comment queries for rules that must not destroy a comment: `Token::hasComment()` (in the trivia of the token), `Token::hasCommentUpTo()` (anywhere between the texts of two tokens) and `Node::hasComment()` (inside the node, its outer edges excluded); `Token::getComments()` and `Node::getComments()` give what those count, and a `Trivia` says of itself whether it `isDocComment()`, `isLineComment()` or `isMultiLine()` and hands over its text without the delimiters as `getCommentText()`. `Node::matches()` compares two nodes by their token texts, `ExpressionNode::isRepeatableRead()` tells whether reading an expression again is free of side effects; together they answer "does this assignment repeat its target". `NodeHelpers::isBoolean()` tells whether an expression is a boolean by its form, `NodeHelpers::negate()` builds its negation as a detached node, `NodeHelpers::bindsTighterThanPrefix()` whether a prefix operator or a cast written in front of it applies to the whole of it without parentheses, which it reads from the precedence of the expression and not from a list of classes, `NodeHelpers::leaves()` whether a block ends by leaving (return, break, continue, goto, throw, exit) and `NodeHelpers::splitItems()` turns a declaration of several items into one per item; `ExpressionNode::isDereferenced()` tells whether the parent accesses a member or element of the expression, which is what decides whether parentheses around it can go.
- Horizontal whitespace between two tokens on a line is the trailing trivia of the first one, never the leading trivia of the second (a rule joining two lines writes the space there, or the next rule reading the gap sees none), and it is read and written through `Token::getTrailingSpace()` and `setTrailingSpace()`, which return or refuse `null` when a line ending, a comment or string content is in the way, or when the first token ends its line by its own text (a close tag, a heredoc start); `Token::is()` given a text never matches the content of a string, only operators and punctuation. `Token::getLineWidth()` measures the line of a token visually (tabs by the tab width of the style), which is how rules about line length decide. `Token::removeTrailingWhitespace()` also trims the end of a `//` or `#` comment, because the tokenizer counts the spaces before the line break as part of the comment text; a rule that calls it therefore changes a comment.
- Indentation is changed through `Indentation` (`set()` a line and the comments above it, `normalize()` into the characters of the style) and `Token::getLineIndentation()`; `Token::setIndentation()` alone moves one line and leaves the rest of the statement where it was. `Indentation::findOwner()` and `findRole()` tell which construct a line-opening token continues and in what role, and `Indentation::infer()` gives the indentation such a line conventionally has, counted from the line its construct begins on: what the engine gives a line it has just opened for a required break, before the rule about indentation places it. `Indentation::opensLine()` says whether the line ending above a token is trivia, which is the only case its indentation is whitespace a rule may write: `Token::startsLine()` also answers yes after inline HTML, a heredoc body or a close tag, and there the leading whitespace is text.
- The indentation of every line is decided by one rule, `dresscode/indentation`, and it is a function of the tree alone: a line-opening token belongs to the lowest ancestor it does not begin, the slot it stands in has a `LayoutRole` (`LayoutData`, which the syntax layer generates for every slot), and the line is placed by that role at a level counted from the level the rule gave the line the ancestor begins on, never read from the text. A line no rule governs (the first token of a file, the code after inline HTML, an operator the options leave alone) is a fact the lines below count from. The rules that break a construct over lines (`braces-position`, `multi-line-call`, `multi-line-signature`, `multi-line-condition`, `multi-line-array`, `multi-line-chain`, `multi-line-ternary`, `single-statement-per-line`, `single-member-per-line`, `continuation-position`, `attribute-position`) are claims on the line breaks, and where the lines then stand is not their business; the engine gives an opened line the conventional indentation so that the shape is acceptable even when no rule about indentation runs. A claim that depends on the shape of the text (a list already broken, a line too long) must give every gap of the construct the same answer whatever the engine did to the gaps before it: the closure decides once per pass, from the shape the construct has when its first gap is reached (`Gap::once()`, which the engine remembers by rule and node until the pass ends, unlike `RuleContext::$storage`, which lives for the file), and a list counts as broken once any item or its closing delimiter begins a line, so that a decision to break it holds for the rest of the list. A rule that reads the indentation of a line to place another one reintroduces what this design removed: a wrong line that carries its neighbours with it and is a fixpoint afterwards. Code between pieces of inline HTML (a template with `<?php if ($a) { ?>` around markup) begins on lines the markup opens, and what those lines have is text the rule counts from as it is: such a file is not laid out by the tree, and PER exempts templates as well.
- The gap between two tokens (the whitespace when they share a line, the line break, the blank lines when there is one) is decided the same way, by claims rather than by procedures: a `GapRule` declares, per node class (or `*`) and slot (`'body'`, or `'stmts:item'` for every item of a list, `'args:separator'` for its separators), the `Claim` it makes before and after the value of the slot (`space`, `line`, `blank`, `blankBelowComment`, each null when not claimed; the factories `Claim::single()`, `Claim::nextLine()`, `Claim::blank(1)` are the claims on one component, shared instances, and a rule with an option builds its claim once in `configure()`), a closure given the `Gap` (the token at its edge, the value or item the claim was made for and its index in the list, the `Style`) where that depends on the code (`?:`, `.` against the other operators, a keyword followed by `;`, the kind of the statement above), and `Engine\Gaps\Resolver` applies every such rule along the traversal of the formatting stage: entering a node hands the claims to the first and last tokens of its slot values and to each item of a list, reaching a token decides the gap before it component by component, the claim of a class before one of `*`, an inner slot before an ancestor's, the stricter space before the looser (`return;`), the blank lines both sides allow or the narrower of two counts that exclude each other, and hands what it decided to a `Gaps\Sink`: `Gaps\Fixer` reports under the name of the rule whose claim won and fixes, `Testing\GapSurvey` records what the rules govern for the whitespace fuzz; the messages of all three components are composed by `Gaps\Messages`. Blank lines are counted above the comment that stands on lines of its own above a token, because the comment goes with the code below it, except above a token that closes a construct (`LayoutRole::Closes`) or the file, where the comment belongs to what is above and the blank lines below it are what is counted; the blank lines between the last comment in the gap and the token are a component of their own, `blankBelowComment`, which the rule about declarations claims for a doc comment, so that no rule reaches into the trivia of a token for them. The open tag is trivia too, and the gap it stands in is decided like any other where the tag opens the code of the file (after nothing or a hashbang): a `Line::Next` there means the tag ends its line, which `header-blank-lines` claims; inside markup the tag's line is the template's and no rule breaks it. When the two sides disagree about the line, `Line::Next` wins over `Line::Same`. A required line break goes in first and the blank lines wait for the next pass; a forbidden one is taken out only when nothing but whitespace stands in the gap. Two plain claims on the same component of the same side of the same slot are a `ConfigurationException` when the rules are put together, so a gap has one owner; closures may share a slot because each abstains where the other decides, a plain claim shares it only with a plain claim on other components. A gap rule is made of claims alone: `GapRule` and `NodeRule` are the two shapes of `Rule`, a class is one or the other, and a rule that also has to change tokens is two rules (`attribute-spacing` and `useless-attribute-parentheses`). A gap nobody claims is left alone: the whitespace fuzz runs with every spacing rule on and exact to find such gaps.
- `Node::getChildren()` is the children in source order, empty slots left out, and the only way to the children: a node is not iterable, so that there is one way and it is an array, which the printer, the index and the traverser read directly. `Node::find()` takes a node class or a predicate and gives the descendants it accepts as a snapshot safe to iterate while mutating, `Node::findFirst()` stops at the first one; the `Traverser` walks in pre-order with `traverse($root, $enter, $leave)`, a callback steering it with `DontTraverseChildren` or `StopTraversal`, and it does not descend into a replaced node, skips siblings detached meanwhile and leaves inserted ones for the next walk.

## Rules and the engine

- A rule is one instance per run and stateless across files; per-file state lives in `RuleContext::getStorage()`. Its identity is the `#[RuleInfo]` name (`vendor/slug`); `RuleRegistry` maps names, aliases and classes and refuses a name owned by two classes.
- Every mutation must follow a `RuleContext::report()` that returned `true`. `PassRunner` pairs the two through `FileNode::$revision`: a callback that raised the revision without a report ("silent mutation") or after a report that returned `false` (suppressed by a `dresscode:ignore` comment) breaks the contract; `strict` mode (RuleTester, `--strict`) throws, otherwise it is a warning of the file.
- A pass is one pre-order traversal per stage (`Structure`, `Formatting`, `Cleanup`); rules are dispatched by `instanceof` on the node class, in configuration order within a stage, `enter()` and `leave()` apart and only for the rules that override them. When a rule replaces or removes the node it was given, the rest of the chain for that node is skipped. Passes repeat until one changes nothing; the printed text of every mutating pass is hashed and a repeated state is a cycle, reported at once with the rules that mutated and a diff of the two states. Rules must therefore be idempotent and must not depend on the pass number, which the context does not expose.
- Violations carry positions from the original file (`Token::$originalLine`, the nearest original token before a synthetic one); a violation reported on a tree already changed by another rule is `followUp`. `fixable` means the rule mutated after the report. The fingerprint (rule, message, normalized line content, occurrence) is stable across runs for baselines; repeated reports of one violation across passes collapse on it.
- Suppression is read once from the original comments before any mutation: `dresscode:ignore [names]` on a line silences that line, on its own line the nearest node starting on the next line, `disable`/`enable` a range, `ignore-file` everything; `phpcs:*` forms work through rule aliases.
- `FileProcessor` is a pure function of path and text: parse, passes, print, and the same again over the printed text until it settles, at most five rounds and a warning of the file when it does not. A mutated tree is not the tree the parser would build from the printed text, so a rule can miss what another one has just written; the text is what has to settle, not the tree. The violations reported are those of the first round, whose positions belong to the file as it was, and a text that no longer parses is a failure of the fixer rather than a syntax error of the file. What a run reports therefore depends on which other rules are on: a rule that fixes a shape first takes away the report of a rule that would have met it later. A syntax error is a result, not an exception, and the `Style` follows the prevailing line ending of the file unless the configuration fixes one. `Engine` finds the files (patterns with a slash are anchored to the root, without one they match a segment at any depth, both also match directories on the way), reads and writes them and hands results to a `Reporter`. A rule exception or a cycle fails that one file (nothing is written, the run goes on, exit code 2); a syntax error is exit code 1 like a violation.
- Configuration composes presets parents first; a later mention overrides the whole entry (options are never deep-merged, a list option replaces its default) and the order of rules is that of the first mention. Options are validated by the rule's `nette/schema` and passed to `configure()` as an array. Without a configuration file the `dresscode/per` preset applies.
- A violation message describes the code, never the reader: no imperative (`Use…`, `Add…`, `Remove…`), because a rule that only reports has nothing to command. It takes one of three shapes, and which one is decided by the rule, not by taste: the required state as a noun phrase where the rule wants one short thing in one place (`A single space after a comma`), `<subject> must <requirement>` where that needs a sentence (`The opening brace must be on its own line`), and the defect where the thing is wrong in itself or the rule guards several places at once (`Function foo() is deprecated`, `Wrong whitespace in a type declaration`). A family shares one pattern: every `-spacing` rule says `No whitespace <where>` or `A single space <where>`, every `-indentation` rule `Wrong indentation of <what>`, every `-blank-lines` rule the measured `Expected <count> <place>, <found> found` of `BlankLines::describe()`, every `useless-` rule `Useless <what>` with the reason after a comma. The subject is the thing at the reported position, with a definite article, and an operator or a call in that role carries its kind (`The <> operator must be written !=`, `The is_null() call must be…`); `written X` names a literal replacement, `written as X` a form. A spelling the message shows — the one to type, and the one found when it holds a space — goes in single quotes (`must be written 'Exception'`, `The keyword 'YIELD FROM'`, `must start with '//', not '#'`), because a bare token at the end of a sentence has no visible end; what carries its own delimiter stays bare: a call the message only names (`is_null()`), an expression built from the code at hand (`$obj::class`), and a word that is not a spelling (`camelCase`, `the short syntax`). Names and measured values belong in the message, the rule name and the standard do not. In prose a `/** */` block is a `doc comment` and a tag in it an `annotation`, whatever the rule name calls them; `whitespace` is what a rule forbids, `a single space` what it requires.
- An option carries a `description()` only where its name, type and default do not say everything: a hidden scope (`classes` also covers interfaces, traits and enums), a hidden condition (`afterOpeningBrace` does not apply when the first member is a method), an inclusive threshold, a value whose meaning is not its name (`nextLineAfterReturnType`); a description that restates the name is noise. Its form follows `RuleInfo::$description`: English, one sentence, capitalized, no trailing period. A count says where it applies ("Before the first member, unless…"), a boolean states what holds when true ("A class name referenced in a doc comment counts as used"), a choice names its values and what they do ("atLeastSingle keeps…, single collapses…"). Another rule is referred to by its full name (`beforeFirst of dresscode/function-spacing`). The text is checked against the code, not against the docblock of the rule.
- `Testing\RuleTester` runs a rule over `*.code` fixtures (`.expected` output beside them, `.violations` as `line: message`, options in a `// {"json"}` comment on the first lines) and checks the contract: parent invariant, idempotence over the output, comments preserved unless `modifiesComments`, `dresscode:ignore-file` honored, no silent mutation.
