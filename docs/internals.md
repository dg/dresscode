# DressCode internals

How DressCode works: the facts an agent or a contributor needs before touching the engine, a rule or the configuration. The catalog of rules is not here; it is generated from the rules themselves.

## Layers

- `phpsyntax/phpsyntax` (namespace `PhpSyntax`, a repository of its own): lexer, parser, tree, printer, navigation, mutation. Its internals are documented there; what a rule of DressCode uses from it is below.
- `DressCode` (`src/`): engine, rules API, rules, configuration, CLI. Rules use only the public API of `PhpSyntax`; whatever a rule of the core needs from it is public API for plugins too.

The public, semver-stable surface of `DressCode` is what the first list names, and the second names what is `@internal`. Every class of `src/` is in one of them, the more specific name deciding (a class before a namespace, a longer namespace before a shorter one), and `tests/DressCode/api.phpt` checks both lists against the code. An item names its classes, namespaces or files first, the explanation follows a colon.

Public:

- `Config`, `Profile`, `Override`, `Plugin`, `PluginManifest`: the configuration
- `Decision`, `Domain`, `Domains\*`, `Value`, `Values`, `Config\Layer`, `Config\LayerKind`, `Config\Catalogue`: the decisions a rule declares, the values they take, the values decided for a file with the layer that said each, and the catalogue of them all
- `Rule`, `NodeRule`, `GapRule`, `RuleInfo`, `RuleContext`, `Claim`, `Space`, `Line`, `Gap`, `Style`, `ImportStyle`, `LineSplits`, `Violation`: the API of a rule
- `CodeWriter`, `GlobalCalls`, `QualifiedNames`: the helpers a rule of a package writes and reads names with, as one of the core does
- `Upgrading\*`: the grammar of the maps of members and the keys of functions, which a rule of a package is fed by as one of the core is
- `Stage`, `Severity`, `Tristate`, `Risk`, `DecisionKind`: the enums
- `exceptions.php`, `Testing\exceptions.php`: the exceptions
- `FileResult`: the result of a file, which `Testing\UpgradingTester::runSample()` gives
- `Console\Application`: a program embedding a run goes through it
- `Analyses\*`, `Rules\*`: the analyses and the rules
- `Testing\RuleTester`, `Testing\UpgradingTester`: the testers

Internal:

- `Engine\*`, `Config\*`, `Measuring\*`, `Console\*`: the engine, the configuration, the measuring of `init` and the console
- `Reporter`, `Reporters\*`: the formats of the output, whose contract is the output itself, and the interface they implement next to them; they print the `Engine\RunResult` of a run
- `Rules\NodeHelpers`, `Rules\ListLayout`, `Rules\Compiler`, `Rules\NativeType`, `Rules\Classes\PropertyWrites`, `Rules\Classes\MemberModifiers`, `Rules\Functions\ForwardingClosure`, `Rules\Namespaces\NameReferences`, `Rules\Namespaces\QualificationPolicy`, `Rules\PhpDoc\AnnotationReplacement`, `Rules\PhpDoc\PhpdocTypeNotationVisitor`, `Rules\Whitespace\BlankLineClaims`, `Rules\Whitespace\Padding`: what the rules share among themselves or a rule does in a class of its own
- `Rules\Upgrading\AnnotationArguments`, `Rules\Upgrading\CallableLiteral`, `Rules\Upgrading\CallTemplate`, `Rules\Upgrading\ClassReplacement`, `Rules\Upgrading\MagicCall`, `Rules\Upgrading\MemberTarget`, `Rules\Upgrading\AttributeTarget`, `Rules\Upgrading\Rewrite`, `Rules\Upgrading\AttributeForMemberEntry`, `Rules\Upgrading\AnnotationMap`, `Rules\Upgrading\enums.php`: the helpers of the rules fed by maps that are not the grammar of the maps
- `Analyses\Registry`, `Analyses\PhpStan`, `Analyses\Declarations`, `Analyses\PhpSymbolsData`, `Analyses\PhpSignaturesData`: the machinery of the analyses
- `Testing\GapSurvey`: what the gap rules govern, recorded for the whitespace fuzz

Of the public classes, the constructors of `Gap`, `RuleContext`, `FileResult`, `ImportStyle`, `LineSplits`, `ArgumentPatternItem`, `ArgumentBindings`, `MemberMapEntry`, `MemberMapMatch`, `Catalogue`, `IndentationPlan` and `IndentationSnapshot`, which only the engine, a factory or a parser makes, and the methods marked `@internal` (`Value::__construct()`, `Value::keep()`, `Values::__construct()`, `reportGap()`, `hasReports()`, `takeReports()`, `Types::__construct()`, `Types::findTraitParameterNames()`, `Config::MinPhpVersion`, `Catalogue::QuestionGroups`, `PlaceKinds`, `ReservedKeys`, `findLexiconProblems()`, `Deprecation::fromDescription()`, `findReplacementCode()`, `FileResult::markWritten()`, `IndentationPlan::register()`, `RuleContext::dropPassAnalysis()`, `recordRemovedImport()`, `takeRemovedImports()`, `ArgumentBindings::$unseenKeys`, `$takenApart`) are the engine's alone. For a rule the name and the namespace of its class are public, so that a configuration can name it by class, while its methods are not. A rule never asks another one: what two rules share is a decision of a tree, which a rule that only reads it names in `RuleInfo::$reads` and reads from its values, the style of the run (`Style`, its imports among it), or an analysis of the file (`Analyses\IndentationPlan`).

## The tree a rule works with

Printing the tree reproduces the input byte for byte, so a rule changes what it means to change: formatting rules change trivia, structural rules change nodes.

- Whitespace, comments and open tags are `Trivia` attached to tokens. **Trailing trivia** of a token is everything after it up to and including the first end of line, **leading trivia** of the next token is everything else (blank lines, indentation, comments on their own lines, doc comments). An `OpenTag` trivia (`<?php` with its mandatory whitespace) is always leading trivia of the following token; the final `EndOfFile` token has only leading trivia.
- `<?php` is not a token. `?>` is a token of kind `CloseTag` that keeps the newline PHP swallows after it, and the parser sees it as `;`; after a terminated statement it forms an `EmptyStatementNode`. `<?=` is a token of kind `OpenTagWithEcho` seen as `echo`. A rule tells them by their kind, `$semicolon->is(Token::CloseTag)`.
- Whitespace that PHP counts as part of a token stays in its text: inline HTML, `T_ENCAPSED_AND_WHITESPACE`, heredoc delimiters (the closing one keeps its indentation), casts like `( int )`. A BOM or a hashbang line is inline HTML, as PHP sees it. A single-line comment never contains its newline, but it does contain trailing spaces before it.
- Trivia inside string interpolation (`"{$a /* c */ }"`) carry `inInterpolation = true`; the token helpers refuse to change them because that whitespace is part of the string value.
- Slots are named by role (`ifKeyword`, `openParen`, `semicolon`, `condition`, `body`), paired delimiters are always `open*`/`close*`, lists are plural. A slot says what stands in it rather than what the class suggests, so the left of an assignment is `target` and not a variable, and what a `switch` and a `match` compare against is `subject` and not a condition. Every token of the source has a slot or a place in a list, so the order and number of children are not part of the API, only the slot names. Whoever names a slot instead of reaching for it writes the name as a string (`'openParen'`, `'statements:item'`), which is what a gap rule declares its claims with.
- The body of a control structure is a `StatementNode`, not necessarily a block; `else if` is an `ElseNode` whose body is an `IfNode`. The alternative syntax uses the same classes with `colon`, `statements`, `endKeyword` and `semicolon` slots instead of `body`. Class-like declarations implement `ClassLikeNode`, because an anonymous class is not a statement.
- A new node comes from `Builder`: `expression()`, `statement()`, `type()`, `name()` and `fragment()` (a node of the class given) parse a piece of code and return it detached, with empty trivia on its edges and without original positions. Where it is put together from nodes already at hand, the template names them as placeholders (`$builder->expression('count($x) > 0', x: $array)`), each put in by `replaceWithExpression()`, and what data decide (a name from a variable, an operator as a string, a varying number of arguments) is a method of the builder (`call()`, `methodCall()`, `staticMethodCall()`, `new()`, `arguments()`, the fetches, `binary()`, `unary()`, `cast()`, `ternary()`, `assign()`, `parenthesize()`, `value()` for a literal), so that a rule neither glues code from the text of nodes nor hunts a placeholder down afterwards. A name, an identifier and a string literal are also made from their text or value (`NameNode::fromText()`, `IdentifierNode::fromText()`, `StringNode::fromValue()`), a `Token` and a `Trivia` by `Token::fromText()` and `Trivia::fromText()`, which give the kind PHP gives the text. A node constructor is `@internal`, its parameters following the slots of a grammar the next version of PHP may extend.

## Analyses

An analysis is information derived from a file, and any class the engine can build is one: `NameResolver` (namespace, imports, resolution of class, function and constant names with the runtime fallback of unqualified functions and constants to the global namespace, `isGlobalFunctionCall()`, and the way back: `shortenName()` gives the shortest way to write a fully qualified name where a node stands, through an alias, a prefix import or the namespace, and `isAliasFree()` says whether a name is still free there, which is what a rule adding an import asks), `Scope` (availability of `$this`; the enclosing function-like construct and class are `findAncestor(FunctionLikeNode::class)` and `findAncestor(ClassLikeNode::class)` of the node, no analysis) and, in `DressCode`, `PhpDoc` (doc comments as phpstan/phpdoc-parser trees printed back with the original formatting) and `PhpSymbols` (what PHP declares: its functions with the version each is deprecated since, its classes, interfaces and enums in their declared case, its constants and the functions PHP 8.4 calls without a frame with their parameters, over PHP 8.0 to 8.6 and the extensions shipped with it, from the generated `PhpSymbolsData`; a PECL extension is not PHP and is not there).

Analyses are lazy and computed once per file. `Analyses\Registry`, reached through `RuleContext::getAnalysis()`, one for every combination of overrides, with the factories the `analyses` of the configuration and of its plugins give (given the `FileNode` and the path of the file), creates them on demand, with the `FileNode` when the constructor takes one, and throws them away as soon as `FileNode::$revision` changes, so any mutation invalidates every analysis of the file, and all of them once the passes over the file are over (`Registry::endFile()`). The instance a rule holds is not invalidated with it and answers about the tree as it was, so a rule asks for an analysis again after it mutates the tree, `getAnalysis()` then giving a new one, and gathers what it needs from an analysis before its first mutation rather than keep the analysis across it. An analysis is identified by its class, the one the engine builds or a factory gives: a rule asks for that class, never for an interface another one would implement, and `Types` is final. A rule names in `RuleInfo::$analyses` every analysis it asks for, through `RuleContext`, through `Gap` or through a helper it calls, and a strict run refuses one it does not name, so that what a rule depends on stands in its attribute; `typesRequired` says more, that the rule does not run without the types at all. An analysis implementing `Analyses\PassAnalysis` is the exception: computed at the first question in a pass, over the tree as the rules before it have changed it, and kept over the mutations after it, because computing it anew after every mutation would cost more than the staleness, and dropped when `PassLoop` begins the next pass (`Registry::beginPass()`); a node inserted after the first question has no answer in it, and a rule asking for one asks with `?->`. `Analyses\Types` is one: the types of the code from the `phpstan/phpstan` installed beside DressCode, in the vendor the process runs from, which `RunnerFactory` wires when the configuration says `typeAnalysis: phpstan` and which is otherwise not there at all. That is the PHPStan of the project where both are installed in it; a global DressCode asks a global PHPStan, which reads the classes of the project and of its packages from their source by the `composer.json` and `installed.json` of the root, never loading them. Where none is installed beside DressCode, `RunnerFactory` resolves the configuration as if it set no types, with a warning, and a rule needing them that the project names is a `ConfigurationException`. The analysis prints the tree, has PHPStan's `currentPhpVersionRichParser` parse the text (`defaultAnalysisParser` routes a string to the simple parser, which drops the bodies of functions), records where the text of every expression and method declaration stands, as `FileNode::findNode()` does (whose parity with php-parser PhpSyntax tests), and runs `NodeScopeResolver::processNodes()` only at the first question that needs the scopes, most files asking about classes alone; it maps every expression of PHPStan to the tree by those offsets, so the map holds on the identity of the nodes and a mutation of the pass before that question moves nothing; only what PHPStan marks `@api` is used, besides the newest version of PHP it accepts and handing its static state back (below), through `Analyses\PhpStan`, which builds the container once per process from the `phpstan.neon` of the project and the extensions `phpstan/extension-installer` registered (where the target, the newest one an override sets included, is newer than the running PHP, a configuration giving PHPStan that `phpVersion`, capped at the newest it accepts, comes between the two, so that its lexer reads the newer syntax and a version the project sets wins), and runs the `bootstrapFiles` they name, as `phpstan analyse` does (the container of PHPStan runs none itself, and an extension such as Larastan dies without them). Starting it registers the Composer loader inside the phar, after which `Composer\InstalledVersions` answers with the packages, the versions and the root of the phar as well; `RunnerFactory` therefore reads `InstalledVersions`, for the identity of a result and to tell the files no package of the process holds, with the roots inside a phar left out. A rule asks questions (`findMember()`, the member an access or a call reaches, decided by the class that declares it and not by the text, so that `$order::STATUS_PAID`, `MyOrder::STATUS_PAID` and `self::STATUS_PAID` are one `Member`; `findDeprecation()`, what its declaration says; `findOverridden()`, the method of a parent class or of an interface a method declaration overrides, declared in the code and not by a `@method` annotation, which `#[\Override]` does not take, and found from the class the declaration stands in by its name, the scopes being asked only for an anonymous class; `matchesParentSignature()`, whether the parent class declares the method as the declaration does, so that no caller tells them apart; `findClassName()`, the declared spelling of a class the project, its packages or PHP declare, or null; `hasMember()`, a bool and not a `Tristate`, a class nothing declares having no member, because what the maps of members ask is whether the code still reaches a declaration); the types themselves, in the words of PHPStan, stay inside the analysis, a rule asking `isOfType()` where no other question covers what it needs. PHPStan reads the declarations of a file from the disk, so the path the analysis gets must be a file holding them: the file of the run, or in `RuleTester` a file the text the run began with is written to, named by it. The disk keeps that text over all the passes, while the reflection of PHPStan, kept in its container, answers every question about the hierarchy (`isSubtype()`, `findMemberAccess()`, a member inherited). Where the text of a pass declares other classes, or gives one of them another parent, interface or trait, or other members by name, than the disk (a parent renamed, a constructor a rule added, the code of stdin), `PhpStan::deriveFor()` hands the analysis a container that reads the declarations of the file from a copy of that text, as the editor mode of PHPStan does (`singleReflectionFile`), one at a time and built in a fraction of the first one; a text declaring what the disk declares keeps the shared container, since the signatures of methods, which a pass changes in many files, are read from the text of the pass cheaply, and only their ancestors from the reflection (`findOverriddenSignature()`). What `Types` asks of a class by its name alone (`isSubtype()`, `hasMember()`, `findClassName()` and their kin) it asks `Analyses\Declarations`, one for each `PhpStan`, so that the answers and their caches hold for every pass of every file that PHPStan reads, a derived one having its own. A class whose parent another file of the same run renamed still gets the hierarchy of the disk, and the second run completes it. PHPStan keeps the reflection in static state that the container created last takes over, so `PhpStan` hands it back to its own container before every use. The path of a run is relative to the root, while PHPStan resolves a relative path against the working directory, which is another; `Analyses\PhpStan` therefore makes it absolute against the root before handing it over. PHPStan may fail on a file whose syntax its version does not support yet, as a partial application of PHP 8.6, which its parser reads and its analysis does not: what `processNodes()` throws, and a warning raised inside its phar, which printed would spoil the output, is `TypesUnavailableException`, told apart from what the callback of `Types` throws, which is a bug of DressCode and passes through. The nodes PHPStan did not reach have no types, as those inside a class whose ancestors run in a circle; the file goes on with the rules that need none, and `PassLoop` gives it a warning saying why (`Types::$failure`), which also keeps it out of the cache.

## Mutation from a rule

### Writing the tree

- A node or token belongs to exactly one tree: inserting one that already has a parent throws; `clone` gives a deep copy without a parent.
- A slot is written by assignment (`$node->condition = $expression`, or `replaceChild()`), which adopts the value, releases the current one and tells the index. Lists mutate through `append()`, `insert()` and its `insertAfter()` and `insertBefore()` an item already there, `removeItem()`, `replaceChild()`; `SeparatedNodeList::insert()` derives a missing separator from the existing ones (or `", "` in a one-line list) and gives the item the indentation of its neighbor in a multi-line list, `removeItem()` takes the separator after the item, or before the last one. `Node::getNextSibling()` and `getPreviousSibling()` are the neighboring items of the list, null at its ends. `BlockNode::unwrap()` moves the statements of a block standing among statements into its place and removes the braces, their comments going before the first statement and after the last one; the statements keep their indentation, which `Indentation::shift()` moves a level up.
- `Node::remove()` removes a list item: a node alone on its lines takes the lines with it, otherwise the whitespace around stays; the comments it owns (inside it, on its line, its doc comment and those right above it), each with the line ending after it, go to the next token, the previous token, or out of the tree with the node, as the `CommentPolicy` says, so that no rule loses a comment by removing a node; a comment above it set apart by a blank line, the header of a section, stays where it is. The doc comment of a removed declaration therefore lands above the next one, and a rule removing a declaration that may carry one refuses it (`PromotedPropertyForAssignmentRule`) or takes it out with `CommentPolicy::StayWithNode` under `modifiesComments`. The blank lines around the node stay, both gaps joined into one; `remove(mergeBlankLines: true)` leaves the narrower of the two instead, so that removing a member leaves the spacing of the class as it was. `Node::replaceWith()` keeps the trivia around the old node around the new one by joining them with the new node's own edge trivia; a replacement cloned from nearby source still carries its original leading trivia, so that an `OpenTag` gets doubled. A node standing in the tree that a rule hands to the builder comes in as a copy without the trivia on its edges, as many times as it is given; one written into another place by assignment or `replaceWith()` is taken with `Node::withoutEdgeTrivia()`, the copy without them, never with `clone`.
- What a rule reads is a property (`value`, `base`, `quote`, `label`, `indentation`, `kind`, `parts`, `role`, `text`), and it writes one where the write takes a single value with a single consequence: a slot, and `NameNode::$text`, whose hook tokenizes the name anew. It writes through a method where the write takes more values or two things change together (`StringNode::setValue($value, ?$quote)`, the delimiter deciding how the value is written), and for a token always, because `?->` cannot stand on the left of an assignment: `Token::setText()`, `setLeadingTrivia()`, `setTrailingTrivia()`, and `Node::setEdgeTrivia()` for the outer edges of a node, where the first or the last token may be missing.
- What has no hook the language guards: the text and the trivia of a token are `private(set)`, the items of a list its own storage, written by its methods alone, and `parent` is written by the nodes when they adopt or release a child. Such a property takes no indirect modification from outside, and neither does the hooked `leadingTrivia` or `trailingTrivia` of a node, so `end($token->trailingTrivia)`, which takes its argument by reference, needs a copy.
- Every mutation increments `FileNode::$revision`, which the engine reads to detect mutations; it is a version of the tree, not a count, because a compound mutation raises it several times. `Token::$line` and `$pos`, inherited from `PhpToken`, never change and are the source of positions in reports; `getCurrentLine()`, `getCurrentColumn()` and `getCurrentOffset()` follow mutations.

### Comments and doc comments

- A single trivia (typically a comment) is removed by `Token::removeTrivia()`, which tidies the whitespace around it: one alone on its line takes the line with it, an inline one takes an adjacent space; `Token::replaceTrivia()` swaps one in place.
- A rule that must not destroy a comment asks `Token::hasComment()` (in the trivia of the token), `Token::hasCommentUpTo()` (anywhere between the texts of two tokens) or `Node::hasInnerComment()` (inside the node, its outer edges excluded, walking the whole subtree, so it is asked of a candidate only), and by place `hasLeadingComment()` and `hasTrailingComment()` of a node (on its outer edges) and of a token (on either side of its text, which `hasComment()` asks of both at once); `Token::getComments()`, `Node::getInnerComments()` and the `getLeadingComments()` and `getTrailingComments()` of both give what those count, and a `Trivia` says of itself whether it `isComment()`, `isLineComment()` or `isMultiLineComment()`, a doc comment being `is(Trivia::DocComment)`, and hands over its text without the delimiters as `getCommentText()`.
- A doc comment is read with `Node::getDocComment()` (above the node, or after the previous token) and, after editing through `Analyses\PhpDoc`, written back by `PhpDoc::writeBack()`, which replaces it, or drops it where the tree is left empty, on the node or on the token it stands at. The tree is the phpstan/phpdoc-parser AST itself, which is therefore part of the public API (its major version is ours), and it is edited the way its format-preserving printer expects: replace `children` or return a new node from a visitor, never mutate a list such as `UnionTypeNode::$types` in place (it prints wrongly); a text node whose text changed loses its ` * ` line prefixes, so rewrite whole lines; a tree with nothing but blank text (`PhpDoc::isEmpty()`) is removed, not printed, or it prints `/**  */`. `Rules\NativeType` (annotation to native type) is the helper the rules share above the AST and `PhpDoc::findLocalTypes()` names the templates and type aliases in scope, which a native type cannot use; there is no tag-editing layer of DressCode's own. A rule that removes annotations leaves the rest with `PhpDoc::keepChildren()`, which takes with each removed annotation the blank line that separated it where that line would then stand at an edge or beside another one; children removed by hand leave a dangling ` *`.

### What the rules share

- `Node::matches()` compares two nodes by their token texts and `ExpressionNode::isRepeatableRead()` tells whether reading an expression again is free of side effects; together they answer "does this assignment repeat its target". `ExpressionNode::isDereferenced()` tells whether the parent accesses a member or element of the expression, which is what decides whether parentheses around it can go.
- `Rules\NodeHelpers` holds the questions and constructions several rules need: the negation of an expression as a detached node, the constructs that reach a variable by a name they do not spell out, the width a node takes on one line (`measureNode()`), and splitting a declaration of several items. `Rules\ListLayout` holds the two axes of a list spread over lines, how its items stand and where its edges do, which the rules of the lists share: the shapes a list stands in (`findShapes()`) and the claims that write them (`claim()`). What the tree alone answers is asked of the tree: whether an expression evaluates to a boolean by its form (`ExpressionNode::evaluatesToBoolean()`), an operator one a condition is chained with (`BinaryOpNode::isLogical()`), the code goes on after a statement or a block (`StatementNode::interruptsFlow()`, `alwaysLeaves()`), a member may be declared again by a descendant (`MethodNode::isOverridable()`), the class scope a node stands in (`Node::findClassScope()`), the plain values of the arguments of a call (`ArgumentListNode::getPlainValues()`), something writes an expression (`ExpressionNode::isWritten()`) and a single line ending follows a token (`Token::isFollowedByLineEnding()`). `GlobalCalls` is public and answers which global function a call calls (`findFunction()`, given the names as the keys of a map whose values it does not read, so that a rule passes the map of its data) and why that may be another one (`findUncertainty()`), which a rule of a package asks as one of the core. `Rules\Compiler` says what the compiler of PHP knows of the code: whether it optimizes a call (`isOptimizedCall()`) and whether it knows the value of an expression (`isKnownAtCompileTime()`). `CodeWriter` is public and writes code in the shape of the file for a rule of a package as for one of the core: a class written the way the file reaches it (`writeClass()`), another global function written in place of the name of a call (`spellFunction()`), an import added where `canAddImport()` finds the scope a line for one (`addImport()`). Whether an expression may be written in place of another, in a string where its interpolation may not take it or braces would read as `${`, is asked of the tree: `ExpressionNode::checkReplaceWithExpression()` throws what `replaceWithExpression()` would, and a rule reports the reason with the occurrence it leaves. A rule asks them rather than reimplementing them, and some of them carry what the name does not say: `negate()` flips an equality but never an ordering, which NAN makes false both ways; a rule reasoning about the variables of a scope must respect `findDynamicVariableAccesses()` (`$$name`, `compact()`, `extract()`, `get_defined_vars()`, `eval`, `include`); and `CodeWriter::writeClass()` may add an import, so it is called only after `report()` returned true, never to compose the message.
- Whether an expression a rule writes into a place needs parentheses there is not the rule's to decide: `ExpressionNode::replaceWithExpression()` puts it in and keeps the parentheses `ParenthesizedNode::isRedundant()` does not call needless, by the precedence of both sides and by what follows the place, and `Builder::parenthesize()` writes the ones a rule wants for the reader alone (`ExplicitPrecedenceRequiredRule`). A rule with a list of operators of its own for that is a rule with an answer of its own.
- A rule that writes a call or a node of its own gives the builder the arguments and the operands it keeps as they stand, and the builder copies them without the trivia of their edges: the trailing trivia of the closing parenthesis belongs to what follows the call, which `replaceWith()` keeps on the node it replaces, so a copy that brought it along would write the space or the line ending twice. A rule that writes such a node into a slot itself takes it with `withoutEdgeTrivia()` for the same reason. A fixture ending every call with a semicolon never shows it.
- PHP binds a function or a class declared at the top level of a file or of a namespace before the code runs, and one inside a function, a loop or a branch only when the code reaches it. A rule that moves statements out of a branch therefore keeps a branch declaring one where it stands at the top level (`EarlyExitForTrailingIfRule`, `UselessElseRule`), because the move would bind the declaration whatever the condition says.
- `Rules\Upgrading` holds the rules whose subject is a catalogue and not a construct, which is why they live together although they fire on nodes of every kind: those the maps of `upgrading.api` fill, a rule for each map (`Replaced…Rule`, `Forbidden…Rule`, `AttributeFor…Rule`), the ones reporting what a declaration deprecates, except what those maps rewrite (`NoDeprecatedClassesRule`, `NoDeprecatedMembersRule`, `NoDeprecatedFunctionsRule`), the values of arguments PHP deprecated, which no map can name (`NoDeprecatedPhpArgumentsRule`), and the grammar of the maps they share; the upgrading data of PHP, `src/Rules/Upgrading/php.neon`, feed the rules of the maps as those of any package do. A rule asking what PHP declares about its own construct is about the construct still and lives with it (`RedundantArgumentsRule`).
- The maps `replacedFunctions`, `replacedClasses`, `replacedMembers` and `replacedCalls` of `upgrading.api` are tools the project, or a package it stands on, fills with what it wants written instead, not policies with a list of their own, so their fix is not risky: what changes is what the project asked for, and only a call in a namespace that may reach a function of that namespace, where the code decides the target, is. A call is rewritten only where the replacement takes every argument of it, compared by the type at the position and by the name of a named argument (`Parameter::canReplace()`, not the name at the position, which `substr()` and `mb_substr()` spell differently for the same thing), no parameter the replacement needs is left out and the target version declares it; any other call is reported with `fixable: false`. Where either function is not PHP's own its parameters are unknown and the map is taken at its word. The rewrite of a class, its imports among the references, is `Rules\Upgrading\ClassReplacement`, which `NoDeprecatedClassesRule` shares; `ReplacedClassesRule` asks it for the doc comments too, and `NoDeprecatedClassesRule` for a class whose deprecation names the replacement, a mention of one without it being no finding worth the noise; the names there are rewritten token by token (`PhpDoc::getTokens()`), the printer of phpdoc-parser writing a changed tag anew with one space where the comment had its own; a file that declares no namespace is a scope of imports of its own (`CodeWriter::findImportScope()`), where `CodeWriter::writeClass()` imports a class of a namespace rather than write it qualified. A key of the two maps of members is `Upgrading\MemberPattern`, which takes an access for its member by the type of the receiver (`Types::findMemberAccess()`), so that a member a library has removed and one a child overrides are found alike, and the rules of replacedMembers, replacedCalls and forbiddenMembers therefore require the types (`typesRequired`); ### Whitespace and indentation

- Horizontal whitespace between two tokens on a line is the trailing trivia of the first one, never the leading trivia of the second (a rule joining two lines writes the space there, or the next rule reading the gap sees none), and it is read and written through `Token::getTrailingSpace()` and `setTrailingSpace()`, which answer `null` and refuse where no such whitespace is there to write. `Token::is()` given a text never matches the content of a string, only operators and punctuation. `Indentation::measureLineWidth()` measures a line visually, tabs by the tab width of the style.
- The style a rule gets from `RuleContext::$style` and `Gap::$style` is `DressCode\Style`: the indentation, the line ending, the tab width and `maxLineLength`, the widest line that passes (null for none), which every rule that breaks or reports a long line reads instead of a threshold of its own, and `$imports`, the `ImportStyle` an import a rule adds is written in (each kind separated or combined, whether a group use stays, null for a kind the file decides). A construct on a line too wide is spread from the outside in: `NodeHelpers::measureOverflow()` measures the code of the line, a comment after it left out, and answers null while an outer construct on the line stands at a place the run spreads for its width (`Style::$lineSplits`, the places whose `multiline.items` is not `keep`, which the run selects and `file.lineLengthExcept` does not name) and not spread yet, or is a message, a call whose sole argument is a string, which leaves the line whole; a call hugging its sole or last argument (`multiline.spreadItem`, `LineSplits::$spreadItem`, `NodeHelpers::findHuggedFrame()`) neither spreads nor waits, its argument spreading in its parentheses, and so does a chain spread `attached` whose split would leave its first method call too wide on the first line all the same, where the links after the call, on one line, fit after its closing parenthesis (`NodeHelpers::findHuggedCall()`, `LineSplits::$chainAttached`), the arguments of that call spreading and `)->fetchField();` closing them; a list whose items are narrower all together than a tenth of the line length neither spreads nor makes a construct before it wait (`NodeHelpers::isTooNarrowToSpread()`), the line being too wide for what stands around it, `->fetch(` above `true,` no better than the line it came from; a condition that is a comparison splits before it, where a comparison opens its line (`LineSplits::$comparisonLineStart`) and each side then fits on a line of its own (`NodeHelpers::findConditionComparison()`), what the sides hold waiting for it as for any outer construct; a `match` arm wholly on one line too wide splits before its `=>` where the conditions fit up to it, at least as wide as two levels of indentation, and `=>` with the result fits on the line below (`NodeHelpers::isArmSplitBeforeArrow()`, `LineSplits::$armArrow`, the break `BinaryOperatorSpacingRule`'s), before anything the arm holds is spread, the right sibling first holding only where that does not fit; the inner one is measured on the line the outer one leaves it on, up to the first token a spread outer frame puts at the start of a line (the next argument, section, operator or link, the closing parenthesis), which its rule moves away later in the pass, so that a cascade of breaks after an opening parenthesis takes one pass; a break after a left operand (a chain, a ternary) comes after the inner constructs it holds, which wait a pass for it. A line opened by text, the end of a heredoc or markup, is spread nowhere, having no indentation the lines spread from it could count from, and neither is a line with a comment after its code, which would stay on the last line of what is spread, away from the code it speaks of or silences. What holds a construct may keep it whole, the offset of an array access, a message and an interpolated string, and so may what precedes it on the line, which stays on its first line, or what follows it, which stays on its last line, where that alone is too wide. Of two constructs on a line with no common one to spread, a `match` arm, an assignment to an offset, the last is spread first, as the last argument or the body of an arm is, unless what precedes it is too wide by itself, and the other one is measured again in the next pass (`NodeHelpers::measureOverflow()` says all of it). What none of them could break `LineLengthRule` reports, measured the same way, so a comment after the code never makes a line too wide while a line of a comment alone is measured whole; with `strings` in `file.lineLengthExcept` it leaves a line that would fit were each of its string literals an empty pair of quotes, a string being split by no rule. A rule that breaks a line by its width decides only once the line has the indentation the run gives it (`NodeHelpers::isLineInPlace()`, the plan reached through `Gap::findAnalysis()`), a pass later where the indentation is wrong, because the width of a line indented by chance would make the break a fixpoint of its own. ### Gaps

The gap between two tokens (the whitespace when they share a line, the line break, the blank lines when there is one) is decided by claims rather than by procedures. A `GapRule` declares, per node class (or `*`) and slot (`'body'`, or `'statements:item'` for every item of a list, `'arguments:separator'` for its separators), the `Claim` it makes before and after the value of the slot: `space`, `line`, `blankLines`, `blankLinesBelowComment`, each null when not claimed. The factories `Claim::singleSpace()`, `Claim::nextLine()`, `Claim::blankLines(1)` are the claims on one component, shared instances, and a rule with an option builds its claim once in `configure()`. Where the claim depends on the code (`?:`, `.` against the other operators, a keyword followed by `;`, the kind of the statement above) it is a closure given the `Gap`: the token at its edge, the value or item the claim was made for and its index in the list, the `Style`.

A claim of `*` applies to every class that has the slot, so it is right only where the slot means the same thing in all of them (the `openBrace` of a block is not the one of `$o->{$m}`, the `body` of a statement is not the one of a `match` arm), and elsewhere it names the classes. A claim must also be right on its own: the stricter claim wins only among the rules that are on, and a fixture runs its rule alone, so a claim right only thanks to another rule passes its fixture and breaks under a preset.

A claim that depends on the shape of the text (a list already broken, a line too long) must give every gap of the construct the same answer whatever the engine did to the gaps before it: the closure decides once per pass, from the shape the construct has when its first gap is reached (`Gap::once()`, which the engine remembers by rule and node until the pass ends), and a list counts as broken once any item or its closing delimiter begins a line, so that a decision to break it holds for the rest of the list.

`Engine\Gaps\Resolver` applies every gap rule along the traversal of the formatting stage: entering a node hands the claims to the first and last tokens of its slot values and to each item of a list, and reaching a token decides the gap before it component by component. The claim of a class goes before one of `*`, an inner slot before an ancestor's, the stricter space before the looser (`return;`), and of blank lines the count both sides allow or the narrower of two counts that exclude each other. When the two sides disagree about the line, `Line::Next` wins over `Line::Same`. What was decided goes to a `Gaps\Sink`: `Gaps\Fixer` reports under the decision of the claim that won and fixes, `Testing\GapSurvey` records what the rules govern for the whitespace fuzz; the messages of all three components are composed by `Gaps\Messages`. The claims are checked and indexed by class and slot once for a configuration, by `Gaps\Claims`, which `Engine\RulePlan` holds together with the node rules of each stage, the classes each of them is dispatched to and the gate of the reports of every rule; `PhpFileProcessor` makes the plan when it is made itself and the runner of every file reads it, keeping only what belongs to the file and the pass, and `Runner::run()` makes the processor of every file it will process before the first one, so that rules the configuration does not fit are a mistake of the configuration (exit code 3), never a failure inside a file or a worker.

Blank lines are counted above the comment that stands on lines of its own above a token, because the comment goes with the code below it, except above a token that closes a construct (`LayoutRole::Closer`) or the file, where the comment belongs to what is above and the blank lines below it are what is counted. The blank lines between the last comment in the gap and the token are a component of their own, `blankLinesBelowComment`, which the rule about declarations claims for a doc comment, so that no rule reaches into the trivia of a token for them.

Every gap the blank lines are decided in belongs to one decision of `blankLines`, chosen by the structure of the code and never by a value, and `keep` leaves the gap as it is rather than handing it to another decision. The one composition is narrowing: a count by the kind of the statement (`beforeStatement`, `afterStatement`) narrows `betweenStatementsInFunction`, the kinds before and after one gap intersect, and two entries whose counts exclude each other are a mistake of the configuration. A key names the position and the place: `between<X>` the gap between two neighbours, `around<X>` the gap between X and a sibling and never the edge of a body, `before<X>` and `after<X>` one side, `bodyStart.<place>` and `bodyEnd.<place>` the edges of a body. A count of blank lines makes no line break, except `blankLines.afterOpeningTag`, which ends the line of `<?php` where no declaration of strict types follows, whose line `file.strictTypes.position` decides.

The open tag is trivia too, and the gap it stands in is decided like any other where the tag opens the code of the file (after nothing or a hashbang): a `Line::Next` there means the tag ends its line, which `blankLines` claims; inside markup the tag's line is the template's and no rule breaks it. A gap inside a string (an interpolation, a heredoc, backticks) or next to a close tag, inline HTML or the data after `__halt_compiler()` is printed text, and the resolver decides nothing there whatever is claimed.

A claim of no whitespace is a claim of a single space between two tokens the lexer would read as something else once they touch (`Lexer::canAdjoin()`): `- -$a` is not `--$a`, whatever a rule says about the space after an operator.

A required line break goes in first and the blank lines wait for the next pass, and a doc comment standing in front of the token on its line goes below with it, because it documents the token. A forbidden line break is taken out only when nothing but whitespace stands in the gap; where a comment stands there the claim is reported and left unfixed, and the settled round reports it again, so it is among what the fix leaves.

Two plain claims on the same component of the same side of the same slot are a `ConfigurationException` when the rules are put together, so a gap has one owner; closures may share a slot because each abstains where the other decides, a plain claim shares it only with a plain claim on other components. Put together is also where a claim is checked against the slots the tree has (`LayoutData::Roles`, the same table the resolver hands the claims out by): a claim on a slot no node has, `:item` and `:separator` on a slot holding no such list, or `*` for the slot anywhere but in `*.*:item` and `*.*:separator`, the items and separators of every list, is a `ConfigurationException`, because a slot renamed in the tree would otherwise leave the rule claiming gaps that never reach it, and neither a type nor a fixture would say a word.

Two closures deciding one component on one side of one slot at the same gap are refused there, so rules whose closures share a slot abstain by a predicate they both read, not by two that happen to agree: the line around a boolean operator chaining a condition is `MultilineConditionRule`'s, which `MultilineBinaryOperatorRule` and `BinaryOperatorSpacingRule` tell by `NodeHelpers::findConditionStatement()`, the line around an operator of a family `MultilineBinaryOperatorRule`'s, for its spreading and for where the operator stands at a break alike, and the line around a comparison `BinaryOperatorSpacingRule`'s, all three telling the place of an operator by `NodeHelpers::findOperatorPlace()`; the rules of the spacing decide only the space. A rule deciding two things about one node asks `Gap::once()` with a question for each. Where no predicate can say which rule decides, a rule claims the break from the other side of the gap: `TernaryOperatorSpacingRule` claims the break in front of `?` and `:` after the operand before them, because the claim before the operator is `MultilineTernaryRule`'s. An empty pair of braces has one gap and not two, and it belongs to the closing brace, so a claim after the opening one abstains there; the braces of a `BlockNode` are claimed through the block, whose parent says whether it is a body. A space a rule of the spacing claims is exact: wider whitespace passes only where a parameter of alignment lets it (`spacing.alignment.binaryOperator`), and alignment is never made; and such a rule holds two tokens on one line only where no other decision owns the break there (`braces.position`, `multiline`, `file.statementsPerLine`).

A claim without a decision is reported under the only requirement of its rule, so a gap rule with several requirements gives every claim its decision (`Claim::withDecision()`) and makes none where that decision is `keep`.

A gap rule is made of claims alone: `GapRule` and `NodeRule` are the two shapes of `Rule`, a class is one or the other, and a rule that also has to change tokens is two rules (`AttributeSpacingRule` and `EmptyArgumentParenthesesRule`). `RulePlan` refuses with a `ConfigurationException` what would never run: a rule of neither shape, a gap rule whose `RuleInfo` names another stage than `Formatting`, where the engine settles every claim, and a visited class that is no class of a node or a token, nor an interface. A gap nobody claims is left alone: the whitespace fuzz runs with every spacing rule on and exact to find such gaps.

### Traversal

`Node::getChildren()` is the children in source order, empty slots left out, and the only way to the children: a node is not iterable, except a list (`NodeList`, plain or separated), which is read as a collection of its items, and `ModifiersNode` over its tokens, so that there is one way and it is an array, which the printer, the index and the traverser read directly. `Node::find()` takes a node class, optionally narrowed by a predicate, and gives the descendants it accepts as a snapshot safe to iterate while mutating; `Node::findFirst()` stops at the first one. The `Traverser` walks in pre-order; it does not descend into a node a callback replaced, skips siblings detached meanwhile and leaves inserted ones for the next walk.

## Rules and the engine

### Identity

A rule is one instance per run and stateless across files; the state of a pass over a file lives in `RuleContext::$passStorage`, which every pass begins empty, so that the last pass reports all it finds. It has no name: what a user writes, reads in a report, silences and accepts is a decision, and the rule is known by its class, in the profile, in a fixture and in the message of a broken contract. Every rule declares or names a decision at least, and one that has none is a mistake of the configuration, refused by the catalogue and by the plan. It reports an occurrence under the path of the decision it violates (the `decision` of `report()`, `Claim::$decision`), which only a rule of one requirement leaves out; a report under a decision the rule does not declare or under a parameter is a broken contract, and one under a requirement that is `keep` or narrowed away records nothing and returns false. What decides it is the `Engine\Gate` of the rule, which the plan holds for every rule, made from the values of the run (`ResolvedConfig::getGates()`) or open, every requirement reported, for a rule run without a resolution; the requirements it admits are also those among which a narrowed run counts the entries of the baseline nothing matched. `PluginRegistry` keeps the classes in the order of their registration and the presets by name.

### Report before mutation

Every mutation must follow a `RuleContext::report()` that returned `true`. `PassLoop` pairs the two through `FileNode::$revision`: a callback that raised the revision without a report ("silent mutation") or after a report that returned `false` (silenced by a `dresscode:ignore` comment) breaks the contract; `strict` mode (RuleTester, `--strict-rules`) throws, otherwise it is a warning of the file. A denied report, by a comment or because the run refuses a risky fix, is judged by the window between it and the next report of the same rule, not by the whole callback, because a callback that reports many times may be denied one occurrence and allowed the next. Along the gap traversal the revision covers every rule of the stage, so the silent-mutation check is left out there: the whitespace of a gap is written by the engine and always after a report of its own.

What a fix leaves is not read from the reports at all: a rule may report every occurrence first and write its fixes afterwards, the whitespace of a gap is written for the whole traversal, and a rule may rewrite what another one reported, so no window of revisions says which report a mutation was for. `FileResult::$remaining` is what the rules report over the settled text instead, see below.

### Risk and consent

Risk is a property of the occurrence, not of the rule: `report(risk: Risk::TypeUnknown)` says that fixing this one may change what the code does, and names what would decide that it does not: the type of a value (`TypeUnknown`), whether an unqualified name reaches a function of the namespace (`NameUncertain`), or a human (`BehaviorChanges`), where changing what the code does is the point of the fix or depends on code the run does not see. `because` says what may go wrong at this occurrence where the risk alone does not say it; it stands beside the message and never in it, the message being part of the fingerprint and bound to stay the same whether the run has the types or a certain resolution. The violation is recorded either way, and `false` comes back until the run is allowed to make such a fix (the configuration names the decision in `fixRisky`, or `--fix-risky` on the command line allows every such fix). The rule then leaves the code alone, and the violation says `risk` and `refused` and stays among what the fix leaves, so the summary can offer the refused ones, grouped by the risk, each with the sentence and the page of the manual that say how the risk is taken away. The severity of a refused occurrence follows its risk: where what the project can tell the tool would decide it, the types or a certain resolution (`Risk::isResolvable()`), it is a warning, because pressing it through the exit code leads to a blind consent; where a human decides it, it is an error like any other until it is fixed or in the baseline, or a rule turned on would quietly become advice. A `dresscode:ignore` comment silences either like any other.

What a fix does to the evaluation of the code is risky where it skips, repeats or reorders an expression that computes: a call or anything else with an effect (`ExpressionNode::hasEffect()`), and a callback no longer called for the later elements of an array, which a division by zero or a property read may fail on there (`ArraySearchForFilterRule`). A read `isRepeatableRead()` takes, a variable, a property, an offset, is free to merge with another read of it or to drop, though a magic getter, `offsetGet()`, a hook or an uninitialized property behind it then runs fewer times or not at all; it keeps its order only against an argument doing something, which may change the value it reads (`CallTemplate`).

An occurrence the rule has no fix for is reported with `fixable: false`, which the violation carries on (`Violation::$fixable`, the key `fixable` of the JSON, a refused risky fix being fixable and a decision of `reportOnly` not), which is never risky, never lets the rule mutate and is therefore never offered to the consent (`StrictComparisonArgumentRequiredRule` on an explicit `false`, `NativeTypeRequiredRule` on a parameter with neither a type nor an annotation), and a pass that changed nothing while a rule reported an occurrence without it, neither refused as risky nor a gap the engine fixes, is a broken contract (`PassLoop::checkUnfixed()`), so a forgotten `fixable: false` is a failing fixture rather than a false offer.

A comment inside the code a rule would rewrite silences the rule, which then neither fixes nor reports: the comment says the code is written so for a reason, and the rewrite would lose it or carry it where it no longer says that. A rule that reports such an occurrence anyway (`NoCallUserFuncRule`, `GlobalNameQualificationRule`, `ReplacedCallsRule`) reports it with `fixable: false`, best with the reason after the message (`, but a comment stands among its arguments`), and says so in its docblock, where silence needs no word.

**A risky fix may change what the code does; it may never write code that does not compile.** What only a file the project need not know of could decide is therefore not risky but undecidable, and there the rule says nothing at all, because the consent of `fixRisky` cannot be asked for it: `ReadonlyClassForReadonlyPropertiesRule` marks a final class alone, since the children of any other would have to turn readonly with it, `ReadonlyForUnwrittenPropertyRule` and `ReadonlyForAnnotationRule` a private property or any property of a final class, since a child may redeclare a protected one, and `NeverForThrowingFunctionRule` a method nothing can declare again, `never` having no subtype. Each is a fatal error in another file, not a change of behaviour in this one. `NativeTypeRequiredRule` stands apart by decision: the native type it writes from an annotation, and `void`, on a member a child may declare again is offered as risky rather than left alone, the annotation being the contract the children already keep and a project asking for native types moving its classes to them together; a function, a closure and a method nothing can declare again (`MethodNode::isOverridable()`) have no such child, so `void` costs them nothing. `ConstantTypeRequiredRule` follows the same decision: the type of a class constant a child may declare again is offered as risky, and a constant nothing can declare again, private, final or of a final class, an anonymous class or an enum, gets its type without risk. The other direction is a fatal error here and not in a child, so it gets no such exception: a parent, an interface or a trait declaring the member without a type refuses the native type of its redeclaration, and without the types, which would tell, the rule writes none on a property or a parameter of a method in a class that has one. A class marked `@internal` is where the project does know: only its own package may extend it, so the project giving the consent is the one place such a child may live, and `FinalForInternalClassRule` is risky rather than silent.

The behaviour a fix keeps is that of working code. A fix that only spares an error or a warning the original code would raise past the point where it knows its answer, its evaluation cut short (`array_any()` instead of `count(array_filter())`), is not risky. Nor is code protected that relies on what PHP deprecates in every version of the target: `ReadonlyClassForReadonlyPropertiesRule` makes a final class readonly although code elsewhere may create a dynamic property on it, deprecated from 8.2, the version the rule requires, and the Error that code then meets is no risk of the fix.

An unqualified call of a global function in a namespace is a risky occurrence wherever `NameResolver::getUnqualifiedResolution()` says `UnqualifiedResolution::Uncertain`, which `nameResolution: certain` of the project takes away, and the rule that rewrites it reports it with `Risk::NameUncertain` and the reason `GlobalCalls::findUncertainty()` gives; a name the rule writes anew follows the name it replaces, or `NameResolver::shortenName()` where there is none.

A rule whose every fix may change what the code does says so at every report, the risk having no other channel: `StaticForClosureWithoutThisRule` cannot see a later `bindTo()`, and `StrictTypesRequiredRule` turns a coerced argument into a TypeError. Writing such a decision, in the project or by a preset, is not consent to the change: the project gives it by naming the decision in `fixRisky`, for the whole tree or in an override for a part of it, which a preset cannot (the resolver refuses it), and `--fix-risky` gives it to every decision for one run, or with `--fix-risky=<name>` to the decisions a name stands for; a name of `fixRisky` or of the option is read as `only` reads one, a decision, a section or a structure for every decision under it, a preset for every decision it writes. `fix --ask-risky` gives it occurrence by occurrence: after the fix it asks about every risky fix left, with the diff of that one fix, and makes the one accepted by running the file again with its fingerprint allowed (`Runner::processCode()` with the accepted risks, down to `RuleContext`); the occurrence is taken on the text the fix wrote, which is the text the fingerprints of what a fix leaves are counted on, so the consent reaches that occurrence and no other. It asks in an interactive terminal only (`Console\RiskReview`). A hook therefore needs no switch of its own: it fixes what the project accepted and reports the rest. The other way round, `reportOnly` of a profile, read with the names `fixRisky` takes, has the decisions under it reported and never fixed, as when the project brings the tool in or makes such a fix by hand: `RuleContext` records their violations as it records one the rule has no fix for (`fixable: false`), so `report()` answers `false`, no risk of theirs waits for a consent, and a fixture or `--strict-rules` sees no broken contract. The reference marks a decision with such a fix from a fixture of its rule whose header says `// risky`, so no hand-kept list can go stale.

### Severity

Every violation is an error until a layer softens it: `severity` of a profile maps the names `fixRisky` takes, a decision, a group, a section, a preset or the class of a rule, to `warning` or `error`, and a preset may write it, the soft limit of a line being a property of a standard and no consent of the project. A severity is no value and changes no fix. It holds for a requirement whose value the layer saying it or one below it said, so a layer that writes the value anew without a severity makes it an error again, and within one layer the most specific name wins: a decision, a deeper group, a shallower one, a section, the class of a rule, a preset; two names of one rank saying two severities of one decision and a name covering parameters alone are errors (`ConfigResolver::collectSeverity()`). `PassLoop` stamps the severity when it makes the violation, and `RunResult::getExitCode()` counts the errors and syntax errors alone, with `--max-warnings` as the only threshold the warnings can cross. A refused risky fix a project could decide by telling the tool more warns whatever the profile says (Risk and consent above).

### Passes

A pass is one pre-order traversal per stage (`Structure`, `Formatting`, `Finishing`); node rules are dispatched by `instanceof` on the node class, in configuration order within a stage, `enter()` and `leave()` apart and only for the rules that override them, and the gap rules ride along the traversal of the formatting stage. When a rule replaces or removes the node it was given, the rest of the chain for that node is skipped. Passes repeat until one changes nothing; the printed text of every mutating pass is hashed and a repeated state is a cycle, reported at once with the rules that mutated and a diff of the two states. Rules must therefore be idempotent and must not depend on the pass number, which the context does not expose.

### Positions and derived violations

Violations carry positions from the original file (`Token::$line`; for a synthetic token the first original one after it within its statement or member, which is what a fix moved or left in place of the code it replaced, so that a report of a later pass on a rewritten call lands on the line of the call, and failing that the nearest original token before it; `Trivia::$line` when the report names a trivia, so that whitespace and comment problems land on their own line for suppression and baselines, and the line `lineInTrivia` counts from it for a problem on an inner line of a comment spanning several).

A violation that the fix of another violation brought about is **derived** from it: `Violation::$derivedFrom` names the fingerprint of the first violation of the chain, so that a report is true about the file on disk or says which violation made it true. The fixer remembers, per token, the violation it opened or closed the line before that token for, and a report about the gap before such a token (its blank lines, which wait for the next pass, the whitespace of a joined line, the indentation the engine inferred for an opened one) follows from it. A rule that places a line by what another line was given says so with `report(follows: $token)`, the token opening that line, and the report follows from whatever opened, closed or moved that line; `IndentationRule` names the line its construct begins on, so a block indented consistently wrong is one violation and the lines placed by it follow it, and a condition written again carries its continuation lines with it. A rule that reports the shape of the line a token stands on says `report(byLine: true)` instead, which asks the same of that line but claims nothing about its whitespace, so nothing is placed by such a report: the comma `TrailingCommaRule` asks for is there because the closing bracket takes a line of its own, so it follows whatever put the bracket there. A structural fix that writes a statement anew, moving the lines it holds, says so with `RuleContext::markRewritten()`, and a report placing such a line follows from it as from a line the fixer moved (`TernaryForIfRule`, whose operands come a level out of the branches).

Nothing else is derived: not a report on a tree another rule has changed, by that alone, and not even one on a token a fix wrote anew, which is often the user's code rebuilt (a group import expanded into statements, a gap moved in front of an inserted modifier), and a rule adding code writes it instead in the shape the other rules ask for; not a report about a comment, which is the user's whatever line it stands on, and not the sibling claims of one decision, each about a break the user did not write. Those are not derived but one: the claims whose closure decided something about a construct through `Gap::once()`, a decision other than null, false or an empty array, are about its shape, so every gap of that construct is reported in the pass as a single violation, placed at its first report, silenced by a comment on that line and known to the baseline under one fingerprint (`Fingerprints::createFor()`, placed by `placeConstruct()`), and a rule of a shape is reported once per construct, which is what counting the places it decides needs.

A derived violation is a violation like any other, in the JSON, in the baseline, under `dresscode:ignore` and in the exit code, because `fix` changes what `check` reports and the derived ones are changed too; only the console format folds them under an ancestor of the same state (error, warning, or a risky fix the run did not make), a `Then also` line with its message and rule, and the format for an agent into a sentence of its item.

`RuleContext` keeps the reports of a callback as `Engine\Report`, with the gap and the line a report is about, and `PassLoop::account()` turns them into violations. The fingerprint (rule, normalized line content, and the place of the violation among those of the rule on that line, in the order they first come while the file is processed) is made by `Engine\Fingerprints` at the moment of the report, so that the position is the one the reported code still had; repeated reports of one violation across passes collapse on it. The message tells the violations of a rule on a line apart and is not part of the fingerprint, so that a message worded otherwise by a newer version keeps what a baseline holds; two violations of one rule on one line are told apart by their order alone, and once the first is fixed, the second takes its fingerprint and the entry of the baseline the first had.

A violation also carries the span of what it is about, `Violation::$offset` and `$length` in bytes of the text it was found in, which an editor underlines: the node or token reported, the trivia of a report about whitespace or a comment, the one line of it `lineInTrivia` names, and the whitespace of the gap a gap report is about, an empty span where whitespace is missing. `Engine\Spans` measures it at `report()`, by the positions the lexer gave, so that it is the place in the file as read, not what the fixes made of it; a token a fix wrote or rewrote at either end has no such place, and the span is then null. What the fix leaves is measured in the fixed text instead. The span is no part of the fingerprint. `Violation::$originalLines` keeps the lines of the file as read the span covers, the line of the report where it has none, so code a fix wrote takes the line of the code beside it; of what a fix leaves too, because the last pass reports on the tree parsed from the file as read, unless a later round read the fixed text anew, as a strict run and one with a baseline do, and then it is null.

`--lines` narrows what a run reports to those lines of the file as read (`Engine\LineRanges`, over the result of the file before the reporter and the summary see it): a violation is listed where its original lines reach into a range or where it has none, the rest is counted in `FileResult::$unlisted` and decides no exit code. The rules, the suppressions and the cache see the whole file, so a fix still fixes all of it. It takes one file, the `agent` format and no `--strict-rules`.

`--before <file>` gives the text the file had before the edit, and then what the file did not follow is its own style rather than the edit's mistake: the decisions that text violates, found by processing it first (`CheckCommand::findBrokenDecisions()`), are left as the file writes them (`ReportPolicy::$leftAsWritten`: `report()` answers false and the pass loop holds it like a refused fix), and every other decision is fixed in the whole file, because a violation of a decision the file kept is one the edit made, wherever it stands: an import whose last use it removed, the lines it put into a new block. The listing follows (`LineRanges` with the decisions left): a violation of a kept decision is listed wherever it is, one of a decision left only where it waits for a judgement, a risky fix or none, on the lines of `--lines`, and the agent is told the decisions left whose violations have a plain fix, which are the style of the file to write in. A file whose old text breaks a decision anywhere thus has it left everywhere, which keeps the file consistent: an edit of a file indented by spaces stays indented by spaces.

### Baseline

A `Baseline` (per file and fingerprint, written by `dresscode baseline` into the file the key `baseline` names, or into `dresscode-baseline.*` beside the configuration, which the user then has to name for it to apply) is asked at `report()` beside the `dresscode:ignore` comment, and it is no suppression: a violation the baseline holds is not recorded, but `report()` does not deny it, so a rule that can fix it by now fixes it and the entry turns stale; outside the baseline **`fix` changes exactly what `check` reports**.

A baseline is the way to enforce a rule the code does not meet yet, and it holds only what a fix leaves: `dresscode baseline`, a command taking the options of `check` that make sense for it (not `--only`, `--fix-risky`, `--stdin`, `--diff` or `--max-warnings`, which it does not know), writes nothing while a fix would still change a file or a file fails or does not parse (exit code 1), so its entries are the violations the rules have no fix for and the risky fixes the project does not accept that change what the code does, the others being warnings that wait for the types or a certain resolution; a style the rules can fix is reached by a fix, not recorded. A later round of `PhpFileProcessor` computes the fingerprints from its own text, so a baselined violation on a line another fix rewrote is not recognized there: it is recorded in `remaining`, which is what the next check reports.

Its format follows the extension of its file, so it is written in whichever of the two the configuration is written in and there is no third format, and any other extension is refused instead of guessed at, whether the file exists yet or not. The file carries the `version` of the way the fingerprints are made, and one of another version is refused with the advice to generate it again, its entries matching nothing any more. The fingerprints a file silenced travel back in `FileResult::$baselined`, because a worker has a baseline of its own; the run marks them used, counts them for the summary and warns about stale entries: the unmatched entries of the files it processed and, in a run narrowed by `only`, of the rules that ran there, because an entry of a file outside the scope or of a rule narrowed away is not stale, only not asked about. The identity of the result cache holds the baseline for the same reason, a file clean under one baseline is not clean under another, and a cached content keeps the fingerprints the baseline matched in it, so that a run served by the cache counts and marks what a processing run would.

### Suppression

Suppression is read once from the original comments before any mutation: `dresscode:ignore [paths]` on a line silences that line, a section or a structure standing for every decision under it, on its own line the nearest node starting on the next line, `disable`/`enable` a range, `ignoreFile` everything; what follows ` -- ` says why, as in ESLint and phpcs, and names no rule. A name no decision stands for is a warning of the run. A project that already marks its intended exceptions with a comment of its own says so in `suppressionComments`, a map of a pattern to the decisions it silences (`'~\bintentionally\s+[!=]=~': expressions.comparison.loose`, which the `nette` preset carries): a comment the pattern matches silences those decisions as `dresscode:ignore` would at its place, on its line or, alone on a line, on the next node; an entry written as `{decisions: …, example: '// @ <why>'}` carries the example of such a comment too, which must match the pattern with a word put for `<why>`, and a layer saying the pattern again replaces the entry, the example with it (`ResolvedConfig::$suppressionExamples`, what the output for an agent offers); a pattern is matched against the text of one comment, so `^` stands at its start (`'~^//\s*@\s+\S~'`), and where a configuration has any, every file has its comments walked.

### Processing a file

A file is processed by the `Engine\FileProcessor` of its kind, which its extension tells: `Engine\FileProcessors` keeps a builder for every extension with a processor of its own and one for every other extension, which is the processor of PHP, so that every extension `fileExtensions` names is processed by something: `fileExtensions` says what is found, the builders say what processes it. The core knows the kind PHP alone. `PhpFileProcessor` is a pure function of path and text: parse, passes, print. What a run decides about the reports, the same for every file of one configuration (the severity, `fixRisky`, `reportOnly`, `suppressionComments`, the baseline, `--strict-rules`), reaches it, the passes and the `RuleContext` of every rule as one `Engine\ReportPolicy`, which `RunnerFactory` builds from the configuration and the options of the run. A mutated tree is not the tree the parser would build from the printed text, so a rule can miss what another one has just written; a strict run (`--strict-rules`) and a run with a baseline therefore do the same again over the printed text until it settles, at most five rounds: a text the rounds come back to, or one still changing in the fifth, is a `ConvergenceException` and fails the file like a cycle of passes, because only a broken rule gets there. Any other run takes the last pass of the tree, which changed nothing, for the round over the printed text, which spares a pass of every fixed file and keeps only its parse with the check of two imports under one name, which PHP refuses and the parser does not, so that a broken rule never writes code PHP refuses: what that pass reported, identified by the lines of the printed text as a run over it identifies it (`PassLoop::collectRemaining()`: the line of a token where it stands now, of a trivia counted back from its token, the fingerprints counted again in the order of the pass, the violations it follows from found again), is what that round reports. `RuleTester` holds the two equal on every fixture, and a run over the corpora found them equal on every file; the price is that a rule missing in the tree what the text shows is seen only by a strict run.

The violations reported are those of the first round, whose positions belong to the file as it was. What the last round reports, or the last pass standing for it, is `FileResult::$remaining`, positioned in the fixed text: it is a full check of the text a fix writes, the baseline included, so it says exactly what the next check of that text reports, and the exit code of a fix, the result cache and every listing of what a fix left read it, while a check says how many a fix would leave. A fix that removed an import nothing used says so in `FileResult::$removedImports`, its kind, name, alias and namespace, because the code a fix is run on may be unfinished, an import added before the code that needs it, and an agent that wrote it has to learn that it is gone. A text that no longer parses is a failure of the fixer rather than a syntax error of the file. What a run reports therefore depends on which other rules are on: a rule that fixes a shape first takes away the report of a rule that would have met it later. A syntax error is a result, not an exception, and the `Style` follows the prevailing line ending of the file unless the configuration fixes one.

### Running

`Runner::findFiles()` finds the files (patterns with a slash are anchored to the root, without one they match a segment at any depth, both also match directories on the way, and `**/` is no directory or any number of them, as in gitignore, a pattern that is no valid glob being refused when the configuration is read; a file named on the command line is taken as it is, and only `--skip-excluded`, which a hook or an editor naming every file it touches passes, lets the excluded paths leave it out like a found one, and the configured `paths` leave out what they do not hold; the excluded paths are those of the configuration and its plugins over `Config::DefaultExcludePaths`, and a `.gitignore` is not read, what it ignores, a build or a cache, being left out by `excludePaths` where the defaults miss it) and `Runner::run()` takes that list, reads and writes the files and hands results to a `Reporter`. The caller expands the paths so that it knows the scope before the run starts. A path named on the command line is relative to the working directory, and `Runner::narrowPaths()` narrows a named directory that holds some of the configured `paths` to those, so that `fix .` in the root never reaches beyond them, while a path outside them is taken as named, unless `--skip-excluded` says the caller names every file it touches.

The format is the whole contract of the output, never a switch modifying another one: `console` unless `--format` says otherwise, `github` when `GITHUB_ACTIONS` says the run is a step of a workflow, `json` and `checkstyle` for tools (the JSON document says its `version`, the `mode` and the `root` of the run, its keys are camelCase and the values from the code stand as they are, the `severity` of a violation being `error` or `warning` and its `risk` `typeUnknown`, `nameUncertain` or `behaviorChanges`, the backing values of `Severity` and `Risk`, the span of a violation as `offset` and `length` and where it ends as `endLine` and `endColumn`, null where it has none, a key removed, renamed or meaning another thing being a new version and a key added none), `lines` for a hook of git and the linters of an editor, one line for every event in the shape a compiler writes (`path:line:column: severity: message [decision; risk=…]`, the column where the span starts when it starts on that line, the path relative to the working directory or absolute and with forward slashes, a message on one line, a clean or merely rewritten file printing nothing), `agent` for an AI agent that has just edited the files (`Reporters\AgentReporter`: sentences on stdout naming the file as the command line named it, what a fix wrote as the hunks of a fenced diff with their standard headers, the imports it removed by name from `FileResult::$removedImports`, and every violation left with what to do about it, the reason of a risky fix it did not make and the comment the configuration of the file accepts from `suppressionComments`, never `dresscode:ignore`; a clean file says nothing, a rewrite is claimed only where the file was written, the warnings of the configuration are left out by the command, and the whole message keeps to a budget of lines and bytes, a diff that does not fit giving way to a summary naming the decisions of the rules that changed the file, `FileResult::$mutatedRules`, and a listing that does not fit saying how many it left out). The header naming the configuration file and the scope belongs to the command (`Console\Commands\CheckCommand`) and is written, together with the warning that Xdebug makes the run many times slower, only for the console and github formats; the progress bar only for the console format on a terminal, where it is a status of the very console the report goes to, so that writing the report erases it. A fix run lists every file it touched exactly once, with a `rewritten` note and under it what the fixed text still violates; which violation a fix removed cannot be told from the text, so the verdict counts what was found and what remains, and `--diff` shows what changed.

`fix --stdin` is the formatter of an editor, which reads the text and the exit code alone: the whole fixed text goes to stdout and nothing to stderr, with exit code 0 whatever the text still violates, an empty input being valid; a syntax error gives the text back as it came with one line on stderr and exit code 1, a failure the same with exit code 2, and a path `--skip-excluded` leaves out the text as it came without a word. It writes nothing to the disk and refuses the options of a report, `--format`, `--diff`, `--max-warnings` and `--ask-risky`, with the advice of `check --stdin`, which reports on the code in any format, and nothing at all of a path `--skip-excluded` leaves out; the warnings of the configuration are not printed.

A rule exception or a cycle fails that one file (nothing is written, the run goes on, exit code 2, also for a runtime error of the tool), and so does a file that cannot be read or written, and a file whose text on the disk is no longer the one processed when the fix is about to write it, so that what an editor saved meanwhile is never overwritten; a syntax error is exit code 1 like a violation, and so is a baseline refused, while a mistake of the command line or of the configuration, and a program run without a command, is exit code 3, which is no result of a run at all. The fix writes a file through a temporary one renamed over it, so that an interrupted run never leaves it cut short, and in place where no temporary file can be made beside it or renamed over it (a directory that is not writable, a file mounted on its own, on Windows a file another process holds).

A `ResultCache` (one JSON file per project root in `cacheDir` or the system temp) remembers every content that came out clean under the effective configuration: the rules and the values of the decisions, the selection of `only`, style, PHP version, the same of every override resolved on its own, so that a preset only an override uses counts too, the installed version of each package of the project with the reference of the source it came from (`ProjectPackages::getIdentity()`), the same of each package of the running process, which is where the tool, its PHPStan and the extensions of it come from wherever they are not installed in the project, its root and the roots inside a phar left out (`RunnerFactory::getProcessIdentity()`), the times and sizes of the files of the rule, preset and analysis classes neither a package of the process nor a phar holds, which a rule of the project itself changes under the same version (a process without Composer knows no package, so every file outside a phar counts), and so of every PHP and NEON file of the source trees of DressCode and PhpSyntax, whose helpers and data the rules stand on, where they are a working tree rather than a package, and the text of the configuration file, hashed by `RunnerFactory::hashConfiguration()`. That text is all that describes a rule or an analysis a closure builds, so such a closure must build from nothing but what the text says, and a run with a closure and no file is not cached. A content is remembered by its path together with its text, because an override or a rule reading the path gives the same text in two files two verdicts; `Runner::run()` skips such a file with a `cached` result, its text read again when it is reported and processed after all where it is no longer the text the cache knew, and, after a fix whose text has nothing remaining, remembers the written content too, unless there is a baseline, whose entries no run has yet held against the fixed lines. With the types a result also depends on what other files of the project declare and on the `phpstan.neon` of the project, so the identity then holds the time and size of every file under the analysed paths, the configuration of PHPStan and `installed.json` (`RunnerFactory::fingerprintProject()`): a change anywhere throws the cache away, which is the price of a clean verdict that stays true after a pull or a rebase. What that configuration includes, its stubs and bootstrap files outside those paths, only the container of PHPStan knows, and a run served whole by the cache builds none, so the run that builds one records them with their stamps in the cache (`PhpStan::getConfigurationFiles()`, a worker sending them with its first result after it knows them, `ResultCache::recordDependencies()`), and the next run drops the cache where any of them changed; those of PHPStan itself and those in its temporary directory are left out. A file modified in the second before the run began or later, where a change in the same second would leave its time and size as they were, adds the hash of its text, as git does with the files it calls racy, which holds for the files of the rules too; a file restored with an older time and the same size is the one limit left. `--no-cache` serves no file from it but remembers what the run finds, forgetting a content it found not clean; `processCode()` (stdin) never uses it.

With `--jobs` above 1 (by default the processor count, capped at one worker per four files, because a worker costs about that much to start; an explicit `--jobs` is taken as given) the files not served by the cache go to a `WorkerPool`. Worker processes are started with the same command line plus a hidden `--worker <address>`, under the `php.ini` of the parent (`-c`, or `-n` where it loaded none) and with the settings the parent has beyond it, those of `-d` among them, which PHP tells no process, so the parent asks the same PHP for its settings and passes on the difference as `-d`, and connect to a TCP server on the loopback: `stream_select()` handles no pipes on Windows before PHP 8.5, and where it does, a message over a pipe costs there hundreds of times what it costs over the loopback, so the server stays whatever the minimum version. With the types, a worker fills the cache of PHPStan before it connects (`PhpStan::warmUp()`), and the pool starts the others only once the first has connected: workers started together would all write the same cold cache, which on Windows makes every write slow and fails the renames over a file another worker holds. A worker that has not connected within the connect timeout of the pool fails the run, which with the types bounds that warm-up. A worker receives one path at a time and answers with the `FileResult` as a line of JSON (`Engine\WorkerCodec`), the path both ways and the output base64-encoded, since neither need be UTF-8. The parent reads the connections without blocking and puts a line together from its parts, because waiting for the rest of one would stop it from hearing the other workers and from noticing a stuck one; it takes an answer only about the path it gave that worker, and a worker spending longer than the timeout of the pool on one file fails the run, since a rule has most likely looped. The listening socket is closed as soon as the last worker is in, because on Windows closing it later costs every run a wait, and it comes from ext/sockets where there is one, because closing one of the stream layer there waits half a second.

A process working through files, the parent without workers and every worker, keeps the cycle collector of PHP off and collects between two files once the memory has doubled since what the last collection left, never above three quarters of `memory_limit` (`Engine\CycleCollector`). The collector PHP runs by itself scans again and again what stays alive, the tree being processed and above all the reflection of PHPStan, and frees little: with the types it took a third of the run.

A worker only processes and, when fixing, writes; the parent keeps the cache and the baseline, reads a file again when it hands it out, reports every file in the order of the input as soon as the files before it are done and keeps of its result what the run needs without the code and the output (`Engine\FileSummary`), so that only the files in progress and those waiting for an earlier one are held as text, and turns a worker that dies or exits with an error into a failure of the run.

## Configuration

### The file

A configuration says how the code of a project is written, decision by decision, and what surrounds that: the facts of the project, the scope of a run and how a run treats what it finds. It is written as `dresscode.neon` or `dresscode.php`, and the two are the same thing said twice: every key of the NEON is a named argument of the constructor of `Config`, the sections of the decisions together under `decisions`, so `NeonReader` is a schema of the reserved keys that accepts none it does not know, the evaluation of entities and a spread into the constructor, and a test asserts that the two files of the fixture build an equal `Config`.

The keys at the top are either reserved or sections (`Config\Catalogue::ReservedKeys`, `CoreSections`). The reserved ones are `use`, the facts of the project (`targets`, `typeAnalysis`, `namespaces`, `nameResolution`), the scope (`paths`, `excludePaths`, `fileExtensions`, `skipWhen`, `baseline`, `cacheDir`), what the project brings in (`rules`, `analyses`), how a run treats what it finds (`fixRisky`, `reportOnly`, `severity`, `suppressionComments`) and `overrides`; every other key is a section of the decisions, `file`, `indentation`, `spacing`, `qualification` and the rest of the core, a section of a plugin named after it and `project` for the rules of the project. `NeonReader` takes a key one letter off a reserved one for a misspelling rather than a section. The sections stand at the top or under `decisions`, never both, which the reader refuses rather than drop one of them. The style is decisions like any other (`indentation.unit`, `indentation.tabWidth`, `file.lineEnding`, `file.lineLength`), which the resolver turns into the `Style` of the engine: where one is `keep` the file has no requirement, but new code must still be written somehow, so the indentation is a tab, the line ending the majority of each file and the line has no limit.

`Profile` holds what decides how a file is processed (`use`, `targets`, `namespaces`, `nameResolution`, `fixRisky`, `reportOnly`, `severity`, `suppressionComments`, `decisions`), an `Override` is the `paths` it applies to with the profile they get, and `Config` is the profile of the whole project with the rest, the one class extending `Profile`, which is not to be extended elsewhere, and one an override refuses, what it adds having no meaning for a part of the tree; a preset is a file of the shape of a profile. They are readonly values checked when they are constructed: a value one of them refuses is an `InvalidArgumentException`, which `NeonReader` and `Loader` turn into a `ConfigurationException` naming the file and the resolver into one naming the preset. The tree of the decisions is not read there but by the resolver, against the catalogue.

What the PHP notation passes as an object or a callable the NEON writes as an entity in three places only, a plugin in `use`, `skipWhen` and the factory of an analysis: `Class(args)` is a new object, `Class::method(args)` what the static method returns, `Class::method(...)` the method itself, and in a chain `Class(args)::method(args)` a link calls the method on what the link before it gave. An entity is evaluated when the file is read, one of `use` only once its class is known to be a plugin, so that a configuration of a repository someone merely checks cannot run other code by naming it. A rule of the project is named by its class in NEON; one built by a factory, a recipe evaluated at every build, is given by `dresscode.php`. In the decisions an entity stands only in the maps of the upgrading data, whose grammar takes one (`isMethod(POST)`). The schema keeps only the keys the file gave, so that an absent key keeps the default of the constructor, and it takes a single entry of `use` without a list (`use: nette`).

`Loader::find()` walks upwards and takes, in each directory, the local file before the `.dist` template; the two formats side by side are an ambiguity it refuses rather than resolves. A configuration file is the only thing laid over a project, and `--config` names it (its format follows its extension); a wrapper binary that wants a configuration to apply in a project without one hands `Console\Application` a `defaultConfig`, which the loader uses when it finds no file, and the workers get it because they are started with the same script. Without a file the root is the directory of the nearest `composer.json`, else the working directory, as for the target version, so that a run from a subdirectory shares the cache, the relative paths and the patterns of a `defaultConfig` with a run from the root. The command line is no key of a file: it is a profile laid over everything the file says, `--use` naming a preset or a plugin as `use` of a file does, `--set path=value` a decision (the value is NEON, decoded as the value in a file) and `--fix-risky=<name>` what it accepts; `--only` is a parameter of `RunnerFactory::resolve()` and `--strict-rules` one of `RunnerFactory::createRunner()`.

### The catalogue

A rule declares what it decides in `Rule::getDecisions()`, and the decisions of every registered rule, with those of a tree its rules name, are the catalogue (`Config\Catalogue`), which is what a file is read against, what `explain` and the reference print and what an editor of the configuration loads. A `Decision` has a path, which is the identity of everything a user ever sees about it, the report and the suppression included, a `Domain` of the values it takes, a description and notes saying what it is not about; it is a requirement, which turns its rule on wherever it is not `keep`, a parameter, which only refines a requirement, turns nothing on and has a default instead of `keep` (`controlFlow.trailingIfMinStatements`, `naming.except`; the flag `upgrading.packages` turns nothing on either, but what it lets in is a layer of requirements, the maps of `upgrading.api` and of plugins and the requirements of the rules of the plugin of a package its upgrading files turn on, which then take effect with nothing of the project), or a fact, a key of the environment the rule guards (below). A rule runs where one of its requirements takes effect, so a rule is never named to be turned on: a project or a preset writes the decisions it wants, and a decision nobody writes requires nothing. A decision of one rule is declared by that rule; one several rules share, or one the engine reads, is declared by a tree, the decisions of the manifest of the plugin bringing the rules (`PluginManifest::$decisions`, the core being `Config\CorePlugin`), and each rule taking it names its path in `RuleInfo::$decisions`, a decision of the core or of its own plugin, never the rule that would otherwise own it, so that a decision over constructs with nothing in common to share is several rules and not one rule of several parts, and its words are written once. The other way round, rules that would repeat the same mechanism over different constructs (a table of claims, a call written another way) are one rule with a decision for each construct, every part reporting under its own and doing nothing where it is `keep`; a part that comes to need logic of its own is split off again. It turns on every rule naming it that can run, and it takes effect while one of them can; a rule that only reads a decision of a tree, to leave to it what it governs, names it in `RuleInfo::$reads`, which puts it in the catalogue and in the values of the run without turning the rule on (`Catalogue::getReadersOf()`, the `readers` of `toArray()`); where two decisions reach one occurrence, the rule of the broader one leaves it to the narrower one whatever its value, `keep` included, knowing what to leave from what the other rule makes public (`StrictComparisonArgumentRequiredRule::StrictArguments`, `NoUnreachableCatchesRule::isUnreachable()`) and never from the values of the run, and where two rules could both take it the order of their registration decides; a decision of a tree no registered rule names is not in the catalogue, and a rule declaring a path a tree declares, or two rules declaring one path, is a `ConfigurationException`. Where no catalogue is at hand, a test running one rule, `Catalogue::collectDecisions()` gives the decisions of the rule and `Catalogue::fromRules()` the catalogue of a few rules, the trees taken from the core and from the plugin the package of each rule names in `extra.dresscode.plugin` (`PackageDiscovery::findPluginOf()`), so that a plugin tests its rules as they run.

The domains are the kinds of value a key takes, each normalizing what a layer wrote into a `Value` and merging two of them by its law: `Words` (`forbidden`, `nextLine`, a tolerance of several where the domain takes one, the first of them the one written: `[perLine, fill]`), `Shapes`, the shapes of a construct each written by its example (`spacing.call: 'foo($a, $b)'`), which shows the whitespace its decision governs and every other whitespace in it as all the standards write it, so that it is read as that one space and nothing else, a shape no such example shows alone being a word, a tolerance of several where the decision declares one, every example in it passing and the first written where none matches (`spacing.logicalNot: ['!$x', '! $x']`), which the tool writes in single quotes and a configuration has to quote, NEON reading `foo($a, $b)` as an entity, the example only ever compared with the examples of the domain and never parsed, and the word naming the shape the rules read never written by a layer, `Count` (`2`, `1-2`, `1+`, a word where the decision names one, `file.lineLength: none`), `Flag`, `Names` (a list of names, regular expressions or an order, an empty set having no item and an empty order or a set a requirement acts on being refused, as is `keep` among the items), `Text` (a text of the project's own the rule writes as it is given), `GrammarEntry` (a value a grammar of its own reads, an entry of a map of the upgrading data) and `Map` (names to values of another domain, the maps of the upgrading data among them). The eight are the whole set: a plugin declares its decisions with them, never with a domain of its own, so `Domain::normalize()` and the constructor of `Value` are `@internal`. `keep` is the one word for "leave this alone" and every requirement takes it, a map entry by entry (`name: keep`) and as a whole, which withdraws what the layers below said, the data of the packages included, an entry a later layer writes standing alone, so `null`, `false` and a turned-off rule never stand side by side for the one idea. `Value` keeps the layer that said it, and a rule reads the values of its decisions from `Values` in `configure()`, never a raw array. A value is written one way in every output, by `Value::toWrittenText()` (`config`, `explain`, the reference, `init`, the catalogue): a word bare, an example in single quotes, `1-2` and `1+`, `yes` and `no`; `Value::toData()`, the normalized content, stays the identity of the value the result cache keys on, so a change of the writing invalidates nothing. A map whose entries a grammar reads as a whole, a map of the upgrading data, is a `Map` carrying that grammar (`Map::$grammar`, a schema of `nette/schema` over the merged entries), and its rule reads it with `Values::readMap()`, which hands over what the grammar makes of the entries no layer withdrew, while the grammar takes `keep` still, for a section of an upgrading file read alone; a wrong entry is an error of the configuration naming the path.

The core keeps to its sections, a plugin to the one its manifest names after it (`PluginManifest::$section`), and the rules of the project to `project`; the catalogue refuses a path outside them, a path two rules declare and a section of a plugin that is a reserved key or a section of the core. A rule of a plugin names a tree of the core, of its own plugin and of the plugins it builds on (`PluginManifest::$plugins`, transitively), a rule of the core one of the core alone, so that a decision is shared across plugins only where one depends on the other. A rule of the project names a tree of the core or of any plugin the project loads, the project standing on all of them. The order of the registration is the order the rules of a stage run in, the core in the fixed list of `Config\CorePlugin`, the plugins after it in the order `use` names them, each after the plugins it builds on, the rules of the project last, so that no order of the keys of a file, which an editor may rewrite, changes what a run does. A decision of the core has its page on dresscode.run by its path, and a report in a terminal links to it.

### Plugins

A plugin stands in `use` of the configuration beside the presets, by class or as an object, and `Config` takes it out of them, because it is no layer and only makes rules and presets known before the layers are laid; the `use` of an override and of a preset refuses one, what it makes known being the whole project's. A `Plugin` is what a package brings to a project: its `getManifest()` is a `PluginManifest` with the `rules` it registers, each by its class or with the factory of a rule with dependencies as `rules` of the configuration takes them (a factory is called for every combination of overrides, which must not share an instance, a rule carrying the values it was configured with, and a worker calls it in a manifest of its own, the closure never leaving the process), the `presets` it makes known by their names, each the path of its file, the `section` its rules decide in, the `decisions` of that section several of its rules share, the `plugins` it builds on, `analyses`, `excludePaths`, `skipWhen` and `ruleUrl`; the manifest has no other key and its `decisions` only declare, so a plugin cannot decide what is the project's, and the fields it shares with `Config` are checked by the same code. A rule of the project itself is named by its class in `rules`, with its factory where it has dependencies (in `dresscode.php`), and decides under `project`. `ruleUrl` is the address of the page of each rule, `{slug}` standing for its class without the suffix `Rule`, the first letter in lower case, given by the manifest for the rules of a plugin and by the configuration for those of the project. A plugin lies below the project, the plugins it builds on below it and every class once, by class or as an object, plugins building on each other in a cycle being an error: the excluded paths add up, a file any of them skips is skipped, and an analysis of the same class the project gives wins. How the code is written is no business of a plugin; that is a preset, which the project uses, so the standard of a project is always read in its own file.

### What the packages bring

A package installed with the project speaks without being named: `Config\PackageDiscovery` reads `vendor/composer/installed.json` of the nearest `composer.json`, the root package included, and takes from every package what its `composer.json` says under `extra.dresscode`: `plugin`, a class loaded where `use` of the configuration names the package or the plugin, the root package needing no name, a plugin bringing code that runs in every check and therefore let in by the project as Composer lets in its own plugins, the others being a warning (a package of the vendor `dresscode` is named with the vendor or without it, as a preset of the core is, a package named so makes its name no preset, and a package and a preset of the same name are an error; a key of `extra.dresscode` that DressCode does not know, `PackageDiscovery::Keys` being the ones it does, is a warning of the run and a problem for `Testing\UpgradingTester`, the package possibly being newer than the tool), and `upgrading-dir`, the directory of the upgrading files, every NEON file in it, `upgrading/<library>.neon` by convention (`PackageDiscovery::findUpgradingFiles()`). Such a file says what the versions of a library retired and what to write instead: `package` names the package whose versions the sections are of (the carrier itself, or the library a package of rules carries the file for), and every section `since <version>` holds the maps that version brought, the renames it made as `replacedClasses` and `replacedMembers`, a map of a rule of a plugin by the path of its decision, and a rule of the plugin the package ships itself turned on by the path of its requirement and a word (`acme.statusEnum: required` from the version that made the rewrite right), which a section above the lowest version leaves off without reporting anything. A map the project writes under `upgrading.api` itself turns its rule on, and `upgrading.packages: yes` lays the maps and the requirements of every file under it; a file names no intent, because the same entry is an offer of a newer form when a version brings it and a retirement once a later one drops the old, which the section `since <version>` already says. The sections the lowest version the code must work with reaches are merged in the order of their versions whatever order the file writes them in (newest first, as a guide to upgrading is written), a later one having the last word on an entry, every one where any version does, none where the versions have no lower bound, a package the project does not require among them, none for a package the project does not have, while a section above the lowest version that a version the constraint allows reaches is reported without a fix, the code meeting it wherever it runs on that version: what it forbids stays forbidden and what it replaces, a class, a function, a member or a call by the shape of its arguments, becomes the entry of the forbidden map with the replacement in its sentence, unless a section reached already writes the key, while an annotation forbids nothing by itself and says nothing (`UpgradingData::$reported`); an entry whose fix is right before the version that retired what it replaces says from which one, `{write: …, from: '8.0'}`, and is rewritten wherever the lowest version reaches that one, the map getting the entry without it, and the versions of the sections holding what is not rewritten stay with the data (`UpgradingData::$unreached`). The file is read and checked by `Config\UpgradingFile::fromFile()` and laid out for a constraint by `selectFor()`; the data keep the words of the file, and the version that retired an entry of a forbidden map (`UpgradingData::$retirements`) ends its sentence only where the data are laid (`UpgradingData::buildDecisions()`, ``Class `Acme\Old` is deprecated: replaced by `Acme\New`, since acme/lib 4.0``), so that `Testing\UpgradingTester` checks the sentence its author wrote; the key is spelled `since 3.10` because NEON reads a bare `3.10` as the number 3.1. A value is handed over as NEON reads it, so what it reads as an entity (`isPaid()`) is for the domain of the map to take. A member is spelled the way PHP reads it, `Class::name` for a constant or a method, whichever the code reaches, `Class::name(...$args)` for a method alone where a constant of that name exists too (parentheses make a key of replacedMembers a method whatever they hold, while replacedCalls reads them as the shape of the arguments, empty ones as none, and a placeholder with a type in front of it, `array $options` or `list $values`, as one only for an argument the types say is of it; the template unpacking such an argument, `...$options`, is risky where its keys are not seen, it being neither an array literal nor a list), `Class::$name` for a property and `Class::$name::get` or `Class::$name::set` for one of its two uses, a read (`isset()` among them) or a write (any assignment, `unset()`), as the hooks of PHP divide them, which is how `replacedCalls` gives the expression of each and `forbiddenMembers` forbids a write alone, and the replacement is the name alone for the same class, `Class::name` for another, or `\function` for the global function a method becomes. What a version took back, a later section withdraws with the value `keep` in place of the replacement, and so does any layer of the project, in the map of `replacedClasses` and of `replacedFunctions` as well; the entry never reaches the rule (`Upgrading\MemberMapGrammar`, the grammar such maps share, which also takes a value NEON reads as an entity, `isMethod(POST)`, and reads its arguments the way NEON gives them: a placeholder, a number, `Class::NAME` and a nested call as written, any other string as a string, quoted or not; what that cannot say is a string holding the whole code).

Such a file sets maps, the requirements of the rules of the plugin of its own package and, under `namespaces` as the configuration writes them, what the namespaces of the package declare for the files a project writes into them, and nothing else: no package may decide how the code of the project is written, so a requirement of the core or of another plugin is a `ConfigurationException` (`PluginRegistry::findPackageSection()`). `ConfigResolver` lays them under every layer of the project, where `upgrading.packages` is `yes`; a map this DressCode does not know is a warning, because the package may be newer than the tool. PHP is a library like any other: what its versions retired is `src/Rules/Upgrading/php.neon` in the same grammar, the data of the platform package `php` (`PackageDiscovery::readPhpData()`), cut by the target of PHP as a package is by its constraint and laid where the requirement `upgrading.php.deprecatedApi` is `forbidden`, which the standard `nette` says without the data of the libraries, and what they say is reported under that requirement, not under the map (`Values::getEntryDecision()`, `MemberMapEntry::$decision`), so that `only`, `severity` and a suppression name it as any other; a fix right before the version that deprecated the function says so with `from`, `curl_close()` doing nothing since PHP 8.0 though deprecated in 8.5, and the values of arguments PHP deprecated, which no map can name, are `NoDeprecatedPhpArgumentsRule` under `upgrading.php.deprecatedArgument`. The result cache needs nothing new, the values a rule ends up with being in its identity, and so are the versions of the installed packages.

### Presets

A preset is a file of the shape of the configuration under a name, `src/Presets/<name>.neon` for those of the core, a file a plugin names in its manifest, or any file `use` gives by its path. It carries decisions, the presets it uses, `suppressionComments` and `severity`, nothing else: what is the project's, the facts, the scope, `fixRisky`, `reportOnly`, a plugin and `rules`, `NeonReader::readPreset()` refuses, so a file laid by `use` never gains what the file of the project can do. A name without a vendor is the one of the core, so `perCs` and `dresscode/perCs` are the same preset. A preset opens with a comment, its title and what it is, and says what a decision does, where its key and value do not, in a short comment after the value.

The presets of the core are the five standards, "standard" being the word for a preset that carries a style and says how the code looks: `psr12`, `perCs` on top of it, `nette` on `perCs` and the sets `cleanup`, `types` and `correctness`, with tabs and the layout of the Nette libraries, `symfony` on `perCs` and `laravel` on `perCs`, the preset laravel of Laravel Pint. What a project wants beyond the looks of its code is a set, a preset of one intent used beside the standard (`use: [nette, modernizations]`): `modernizations`, `deprecations`, `cleanup`, `correctness`, `types` and `compilerOptimizations`. A set decides nothing about the layout, so it never fights the standard, and a decision the core gains goes into its set, so it reaches every project using the set without a change of its configuration. A standard may use a set and keep some of its decisions, as `nette` keeps the native types and an else after a return; a project naming that set beside the standard gets none of them back, the set being laid once, below the standard, and the run says so; the project writes those decisions itself. `tests/DressCode/Presets/sets.phpt` holds that every construct and function newer PHP brought or retired is in a set and lists, with the reason, the decisions a project writes itself. A decision of a rule of a plugin reaches a project when a preset it uses or the project writes it. `psr12` and `perCs` follow their specifications section by section and add no style of their own, so a rule whose fixed behaviour contradicts a specification gets a value rather than a preset-side workaround. Without a configuration file nothing applies: DressCode has no style of its own to fall back on, so a run refuses, unless `--use` names what to use, which is then all the run has, so that a run over a foreign project can ask for that alone.

`multiline.trailingComma` removes the comma of a list written on one line wherever its place is not `keep`, so `perCs`, `nette` and `symfony` also fix `function f($a,)`, `use ($a,)` and a `match` on one line whose last arm is followed by a comma. For `symfony` that is a deliberate departure from `no_trailing_comma_in_singleline` of PHP CS Fixer, and so is the comma `optional` removes where the closing bracket follows it on the line of the last item, which `trailing_comma_in_multiline` leaves.

### Resolving the layers

`ConfigResolver::resolve()` lays the profiles that decide for a file one over another: the configuration, the overrides the file matches in the order they are written, and the command line, each above what its `use` names, in the order written, a preset above what it uses in turn. Every preset is laid once, where it is named first, so one named again, by a later layer or by the same one, does nothing, and the run says so; that a preset uses what another already brought is no business of the project and is said by nobody, while a preset that comes back to itself through what it uses is an error. A path in `use` is a file of the same shape, its identity the path; a relative one is taken from the directory of the NEON file that writes it, from the root in a `dresscode.php` and its `Override`, and from the working directory in `--use`. A later layer has the last word on a fact (`nameResolution`, `targets.php`; the package keys of `targets` are read from the configuration alone) and adds to a list (`namespaces`, `fixRisky`), a name of `severity` holding for the values it covers (Severity above) and a pattern of `suppressionComments` being a key whose decisions the last layer naming it decides.

The decisions of the layers meet in `Config\DecisionResolver`, which reads every path of a layer against the catalogue, a path it does not know being an error with the nearest one it does, and merges the values of one path by the law of its domain: a structure merges key by key, a word, a shape, a count and a flag replace, a list replaces the list below it, its default included, unless it holds `...`, once and anywhere, which stands for that list in its place (an item both give merging in a set and refused in an order or a tolerance, and `...` refused in a list on a structure, every decision under it reading another list), and a map of names merges by name, unless its key is written with `!` (`replacedClasses!:`), which replaces the maps below it, the data of the packages included, with its entries, an entry `keep` withdrawing the entry below it and the most specific entry winning over a pattern whatever layer said either; a map whose names PHP reads in any letter case (`Map::$caseInsensitive`) takes a name with or without its leading backslash as one, which a layer may not write twice, a map of members reads its keys as its lookup does (`Upgrading\MemberPattern::canonicalizeKey()`), so that `keep` and a layer above find an entry in any writing of it, and a map whose every entry is withdrawn is `keep`. `keep` on a section or a structure is a tombstone for every key under it, which a later layer brings back one key at a time, the rest staying `keep`, so that nothing a layer below said comes back from under the tombstone. The result is a `ResolvedDecision` per path of the catalogue: the value, what each layer said with its origin, and why it takes no effect where it does not (`keep`, `php`, `package`, `types`, `nameResolution`).

A rule takes effect where one of its requirements does, and the resolver says of every other rule why (`ResolvedRule::$inactiveReason`): turned off, too new for the target, needing a package the project does not have or the types it does not ask for, turned on only by an override, written by nobody, narrowed to other decisions. A preset may decide what cannot run here, silently; the project deciding it asked for what it cannot get, which is an error for the types and a warning for the target and for a package. The run builds its instances from that one `ResolvedConfig`, the result cache keys on it and whoever prints the configuration reads it, so none of them can say something the others do not; `RuleBuilder` builds every rule that takes effect, with the factory the configuration gave it, and hands it the `Values` of the run.

An override (`overrides` in NEON, `Override` in PHP) is a profile for a part of the tree: the item of `overrides` writes every key a profile has beside its `paths`, which `NeonReader` takes apart into the two, and the `paths` go through the same matcher as the excluded paths, anchored to the root of the configuration. A file's configuration is therefore the combination of overrides it matches. `RunnerFactory::createRunner()` builds one processor per combination and kind of file, with an `Analyses\Registry` of its own because an override may add to what the namespaces declare, and `Engine\FileProcessors` keeps them, because a rule carries the values it was configured with and must never be reconfigured under a file already being processed; the identity of a cached result carries the path, which decides that combination, because the same text is clean under one and not under another. A part of the tree where a decision must not hold is an override that writes `keep` for it, so a later override may write it again. Every override is resolved on its own when the run is built, not when a file of it comes, so a path no decision has and a value its domain refuses are an error naming the override rather than a line that does nothing until such a file comes; what each of them comes to is part of the identity of a cached result.

The excluded paths only ever add up, the default list, those of the plugins and those of the configuration, so no layer can bring back what another left out.

`only` (`--only`, a parameter of the run and no key of a file) narrows a run to the decisions it names, and it changes no value: the tree is resolved whole and `only` lays a mask over it, `Values::isSelected()`, so a requirement outside the mask is neither reported nor fixed, while what the rules write keeps the values the project decided (a run narrowed to a rewrite of a structure in a project with four spaces writes the new block with four spaces, not a tab). A rule reads the value with `Values::get()` and asks whether a requirement is selected separately, and reading a value never enforces what the run did not select. A name of `only`, as of `fixRisky` and `severity`, is a decision, a section or a structure for every decision under it, a package of upgrading data, one of the vendor `dresscode` written without it too, for the maps and the requirements its files set, so the rules reading them, core and plugin alike, and only its maps where no other name covers a map (`ConfigResolver::collectPackageMaps()`), a library the same way for the files about it, whichever package ships them (`php` for the data of PHP), a name that is both a package shipping files and a library the files of another package are about standing for both, a preset for every decision it and what it uses write, or the class of a rule for its requirements. A section that shares its name with a preset (`types`) is written `types.*`, the bare name being refused as one that says both. A section or a preset narrows the run to those of its rules the rest turns on, never more, since its name is no decision about any one of them; where the project turned some of them off the run says which by their requirements, the first five, and a name that lets nothing in is an error rather than a run that checks nothing, naming `--use <name> --only <name>` where the configuration does not use it. A name whose rules the target or the packages of the project leave out is skipped with a warning instead, so that one command serves projects of several targets, and is an error only where no other name of `only` runs. The result cache keys on the selection, and the workers get it on their command line. `fix --only` fixes those decisions and leaves the rest, so the next full `fix` changes more, which is the point and not a failure to converge.

### What the commands print

`dresscode explain <path>` says what one decision is for: its description, the values it takes with what each means, its notes, the value here with the layer that said it, the values of the five standards and the rule that owns it with what it requires. With a section it explains every decision under it; without an argument it explains the configuration as one document, by sections, drawn on the console, and with `--format markdown` it writes that document to the standard output as Markdown instead of drawing it. Both are written in Markdown by one `Console\ExplainPrinter` and the console draws that Markdown (`Markup::formatMarkdown()`), so that a fact is written once and the two never part; there are no tables.

`dresscode config` prints that resolution in the shape of the file, every decision a layer said with the layer in a comment (`# dresscode/perCs`, `# the override for tests/`), why it takes no effect where it does not, whether it lies outside `--only` and whether its risky fixes are accepted, and `--preset <name>` prints one preset alone, what it uses included. `--file` narrows it to what the run uses for one file and `--format json` gives it as data: its `version`, the facts in the words of the configuration, the decisions by path, each with `value`, `layer`, `inactive`, `selected` and `severity` (`error` or `warning`), and the rules by class with the reason a rule does not run as a word (`turnedOff`, `php`, `package`, `types`, `narrowed`, `onlyOverride` or `notMentioned`) beside the sentence. A name in `fixRisky` whose rules run nowhere, not even in an override, is a warning of every run.

`dresscode catalogue` prints the catalogue of the installed set and `--format json` gives it as data, versioned (`Catalogue::Version`): every decision with its kind, its domain as data, its description and notes, the rules declaring it with what each requires and the values of the five standards as a configuration writes them. It is the interface an editor of the configuration is built on, and `composer reference` writes `docs/reference/decisions.md` from the same data.

### The target version of PHP

The versions of PHP the rules target are a property of the checked project, never of the run: `RunnerFactory::getPhpTarget()` takes them as a Composer constraint from `targets: {php: ...}` of the configuration, which is one version, else from `require.php` of the nearest `composer.json` at or above the root from the version `config.platform.php` names on, the one Composer resolves the packages for and the project usually runs on (`^8.1` with `8.3` being `^8.1, >=8.3`; Composer itself refuses a platform below the constraint, but never narrows it), the whole constraint (one without a lower bound, `<8.4` or `*`, leaves the version to the default rather than to a guess), else from `Config::DefaultPhpVersion`, and an override may give its files another one with `targets: {php: ...}`, which is all an override may say there. A rule runs where every version of the target satisfies its `requires`; what a rule asks with `RuleContext::$phpVersion` is the lowest of them. Whichever it is, a version older than `Config::MinPhpVersion` is raised to it by the resolver with a warning, because no rule asks whether the target has what PHP 8.0 already has, so a fix may write such syntax. Nothing else raises it, a package backfilling a newer construct least of all: a rule writes what the version the project moves to gives its code, while such a package exists so that the project need not move, and taking it for an answer would turn the target from a version into a list of what happens to be in the vendor directory.

The version a rule asks about travels as a plain string compared with `version_compare()`, never with the string operators, under which 8.9 outranks 8.10, and always in the short form `Config\Versions::shortenVersion()` gives, without the zeros a normalized one pads with, because `version_compare()` takes `8.1` for older than `8.1.0`. NEON reads a bare number as a version whose minor is a single digit, which every PHP ever released has had, so `8` and `8.0` both mean 8.0, and `php` in `targets` may carry a patch version, so no rule takes the string apart by position. The running interpreter is never the answer, so that the same file gets the same verdict from any directory under any PHP; only `Lexer` asks about the runtime, to emulate the tokens its own build does not know.

What PHP itself declares is the same kind of question, and a rule asks `Analyses\PhpSymbols` about it rather than `function_exists()` or reflection, which would answer with the extensions and the version of the machine: the catalog holds every version from 8.0 on, so what depends on the version, which versions declare a function at all, is compared with the target, and what PHP retired is in its upgrading data, `src/Rules/Upgrading/php.neon`. The parameters of those functions are a catalog of their own, `Analyses\PhpSignatures`, because they are two thirds the size of the rest and the command line compiles what it loads on every run, so only a rule that asks about them pays for it; it answers with `Parameter`, whose `canReplace()` says whether an argument written for one parameter may stand at another and whose `default` is known where every version from 8.0 on declares the same scalar, and it knows nothing of the extensions its source cannot see, where a rule then has no answer rather than a wrong one. A rule whose construct exists only from some version on says so with `requires: ['php' => '>=8.4']` in its `#[RuleInfo]`, a Composer constraint written as the `require` of `composer.json` writes it, all of it read by `composer/semver` (`Config\Versions`) and never by hand, and a range, a single version being refused because it would turn the rule off for every other release; an upper bound says a rule writes what a later version took away. It is metadata and never a directory, so that a rule lives with its topic and the reference can index the catalogue by the version a rule needs, and `ConfigResolver` leaves it out below that version: silently when a preset wrote its decisions, with a warning when the project wrote them. A rule that needs the version more finely than "run me or not" asks `RuleContext::$phpVersion` instead, and never about anything PHP 8.0 already had. The version in `requires` and the one read from `RuleContext::$phpVersion` say since when the fix is right, never since when the code it replaces is a problem: the target is the oldest version the code runs on, not the newest, so the upgrading data of PHP remove `curl_close()` only where every version of the target has made it a no-op, while a rule about a deprecation whose replacement older versions know too (`NoNullArrayKeysRule`, `NoSleepAndWakeupRule`, `RedundantArgumentsRule`) asks no version at all, the code meeting the deprecation wherever it runs on a later one, and neither does `OptimizedCallNotationRule` writing the arguments of an optimized call, an argument written by position being right everywhere and optimized wherever the code runs on 8.4 or later. A fix naming a class of PHP needs the version that declares it, though older ones parse the name and ignore an attribute they do not know: `OverrideAttributeRequiredRule`, `SensitiveParameterRequiredRule` and `DeprecatedAttributeForAnnotationRule` require the version of their attribute, code naming a class the target does not declare being no fix for that target. A package in `requires` is the same question asked of `Config\ProjectPackages`, which answers from the `composer.json` of the project and the `installed.json` beside it, never from the Composer of the running process: for a package the project requires itself the versions are those its constraint allows, because code written for a newer one breaks wherever the constraint lets an older one in, so a constraint without a lower bound allows every version, for a package that only comes with another, which the project promises nothing about, it is every version too, the installed one never answering, the alias of a development branch the project requires standing for the newest of its line, a package an installed one replaces with its own version, a part of a monorepo installed as the whole, is had in the version of the one replacing it, and any version does for the project itself and for a branch without an alias. The packages in `targets` of the configuration (`targets: {acme/mailer: '3.3'}`) say the version of an installed package outright and come before all of that (`ProjectPackages::withTargets()`), so that code is fixed for a version while the one before it is still installed and its members still have a declaration to read; the version is quoted, because NEON reads a bare `3.10` as the number 3.1. The resolver leaves a rule whose package the project does not have, or has in a version its requirement does not allow, out as it does a rule too new for the target, and the sections `since` of a package's deprecations are cut by the lowest of those versions. A rule that makes no sense without the types of the code says so with `typesRequired`, and the resolver leaves it out where the configuration sets no `typeAnalysis` (a fact of the project, which a preset may not state): silently when a preset or the data of a package wrote its decisions, so that a preset may write them whatever the project has, and as a `ConfigurationException` when the configuration or the command line wrote them, because the project then asked for what it cannot get and a run without the rule would lie. The registry builds `Analyses\Types` only where the configuration asked for the types, so `getAnalysis()` of them throws elsewhere. A rule that would only do better with them asks `RuleContext::findAnalysis()`, which answers `null` where the run has none (`ReplacedClassesRule` then writes a class without asking whether the project has it), or does without them altogether, and says in its docblock what it then cannot see, in one shape: `Without the types, <this> is not told from <that>.` Its correctness never rests on them: without the types the rule breaks nothing, what it cannot tell apart being risky or left alone, and the types only narrow that. Such a rule answers in three states (`Tristate`): for certain yes, the fix is safe; for certain no, the rule says nothing, never offering a fix it knows is wrong; maybe, the fix is risky with `Risk::TypeUnknown`. The declarations in sight give the answer first (a parameter, a property, a method of `$this`, whose types a child may not turn into another), and the types narrow what they leave as maybe, through a question `Types` already answers (`isSubtype()` in `StaticForMethodWithoutThisRule`, `findParameters()` in `PipeForNestedCallsRule`). A question of `Types` about a fact whose no a caller may act on answers in `Tristate` too (`isOfType()`, `isSubtype()`, `isInterface()`, `isFinalClass()`, `isAttributeClass()`, `isStaticMethod()`, `isPlainProperty()`, `isComparedAlike()`), maybe for a class nothing declares and for one whose hierarchy is not seen whole, a parent, an interface or a trait of it or of an ancestor being one nothing declares; a question asking whether something may be done answers `bool`, `true` only where it certainly may (`canReplace()`, `matchesParentSignature()`). `hasMember()` answers `bool` although it asks about a fact, a class nothing declares having no member: what the maps of members ask with it is whether the code still reaches a declaration, and a member a library removed together with its class is as undeclared as one removed from the class alone.

### The namespaces of the project

What the namespaces of the project declare is a property of the project too, and no file shows it: an unqualified function or constant in a namespace reaches the namespaced one PHP knows at run time before it falls back to the global one. `namespaces: {functions, constants}` lists such symbols as the items of a use statement write them (`Acme\Text\{format, parse}`, parsed by `Parser` when the profile is constructed), and every layer adds to the lists; `nameResolution: certain` says the lists are all there is, which the configuration or an override says and a preset cannot, knowing a framework and not the project. An override may say `uncertain` for a part of the tree whose declarations nothing outside it reaches, such as the helpers of the tests, so that no fix there rests on the lists and nothing there is guarded.

`ConfigResolver` puts both into `ResolvedConfig`, so they are in the identity of the result cache and in `dresscode config` with the layer that named each symbol, and `Analyses\Registry` builds `NameResolver` with them as `NamespacedSymbols`, which is also the analysis a rule asks for the lists themselves.

A certain resolution rests on lists that must stay complete, so the key turns on their guard, `NoUnlistedNamespacedDeclarationsRule`, whose decisions are the facts `namespaces.functions` and `namespaces.constants`: it reports a declaration missing from them under the path of the list, `--only` never narrows it away, since a fix resting on the lists must not lose what keeps them true, and a file whose resolution ends up uncertain has no guard; a declaration the lists do not name is decidable in its file, a declaration inside a condition and a `define()` with its name written as a string among them (`NameResolver::findNamespacedDeclarations()`), and the lists can then go stale only through a path left out of the run or a package of the same namespace. What a package declares for the files a project writes into its namespace is said by the data of the package (`namespaces` of its upgrading file), which lies under the lists of every layer; `dresscode config` names the source of each.

## Writing a rule

### Messages

A violation message describes the code, never the reader: no imperative (`Use…`, `Add…`, `Remove…`), because a rule that only reports has nothing to command. It is a sentence and ends with a period, which `PassLoop` checks as a part of the contract of the rule. It takes one of three shapes, and which one is decided by the rule, not by taste: the required state after `Expected` where the rule wants one short thing in one place (`Expected a single space after the comma`), the word saying that it is what should be there and not what was found, `<subject> must <requirement>` where that needs a sentence (`The opening brace must be on its own line`), and the defect where the thing is wrong in itself or the rule guards several places at once (``Function `foo()` is deprecated``, `Wrong whitespace in a type declaration`).

A family shares one pattern: every `…SpacingRule` says `Expected no whitespace <where>`, `Expected a single space <where>` or `Expected at least one space <where>` with the token the claim is on as `<where>` (`before the closing parenthesis`, ``after the `return` keyword``), composed by the engine, `IndentationRule` the measured `Expected <what> indented by <width>, <found> found` (`without indentation` where it wants none) with the width in tabs and spaces, every claim on a line break `Expected a line break <where>` or `Expected no line break <where>` with the bracket at the edge of the gap or the node the claim was made for as `<where>`, and the reason after `because` when the claim follows from a measure or a property of the code (`Claim::$because`: `Expected a line break before the parameter, because the line is 135 characters long`), every `…BlankLinesRule` the measured `Expected <count> <place>, <found> found`, a count of zero written `no blank line`, composed by the engine from the node or token the claim was made for (`before the method`, `after the opening brace`), every `Useless…Rule` `Useless <what>` with the reason after `because` (`Useless else, because the branches before it always leave`).

What follows the message after a comma says why: `, because <why>` where it explains the finding itself (`…, because the line is 135 characters long, more than 120`), `, but <why>` where the occurrence is reported and left as it is (`…, but a comment stands among its arguments`), while why a fix is risky is not the message but the `because` of the report beside it (`the replacement evaluates the arguments in another order`, ``the namespace may declare `<function>()` ``). What follows a colon is the word of a library or a package, the description of a deprecation or the sentence of a map (``Class `X` is deprecated: <description>``, ``Method `X()` is forbidden: <sentence>``), and may command; the rule only trims its period and folds its whitespace. The sentence of a map writes its code in backticks as the rest of the message does; the description of a deprecation is the library's and stays as it is. A message stays within 104 characters counted with every name as one word, so that a project with long namespaces does not break it, while the sentence of a map has a limit of its own (`Testing\UpgradingTester`).

The subject is the thing at the reported position, with a definite article and its name where it has one (``The property `$value` must be promoted…``, ``The method `run()` must have…``), and an operator or a call in that role carries its kind (``The `<>` operator must be written `!=` ``, ``The `is_null()` call must be…``); `written X` names a literal replacement, `written as X` a form. Everything the message shows that is code stands in backticks, as in an exception (Exceptions and warnings below): a spelling to type or found (``must be written `Exception` ``, ``The keyword `YIELD FROM` ``, ``must start with `//`, not `#` ``), a call the message names (`` `is_null()` ``), an expression built from the code at hand (`` `$obj::class` ``), the name of a declared class, function, constant or member (``Class `Acme\Mail\Sender` is replaced by `Acme\Mail\Mailer` ``, ``Global constant `PHP_EOL` must be imported``), and a token the engine names by its spelling (``after the `as` keyword``, ``before the `.` operator``). A token named by a word is prose (`the closing parenthesis`, `the comma`), and so is a word that is not a spelling (`camelCase`, `the short syntax`). A name cannot hold a backtick, so the message writes it in backticks directly; code that can, an expression, a string, a comment or a text of the configuration or of the data, goes through `Violation::formatCode()`, which writes a code span of Markdown in a longer run of backticks where the code holds some. Names and measured values belong in the message, the path of the decision and the standard do not. In prose a `/** */` block is a `doc comment` and a tag in it an `annotation`, whatever the path calls them; `whitespace` is what a rule forbids, `a single space` what it requires.

### Decisions

A path names a thing in the code, by the name PHP gives it where it has one (`hygiene.is_null`, `mistakes.__serialize`) and by the name of the family where several things share the key (`upgrading.functions.arrayFirstLast`), under the section a reader looks for it in; nothing of how a decision behaves follows from its section. Its value says how the thing is written. In the sections of the style a decision with several shapes is a preference and names them (`sameLine`, `nextLine`), while one with `forbidden` or `required` has no second shape to choose: either the other one adds nothing or the project decides it as a policy. Under `upgrading` stands what a version of PHP above the floor decided, `required` writing a construct a newer PHP gave where the older way is found and `forbidden` writing the replacement of what PHP deprecated; under `mistakes` stands what is wrong or dangerous whatever the style. A decision that only refines another one is a parameter (`controlFlow.trailingIfMinStatements`), so that a list a project writes never turns a rule on by itself.

A path reads as a sentence: the section names the area, a group the question or the thing, the last link the place. A group stands only where it says what the section does not, in one of two ways: one question several places answer in one domain, the group naming the question or the thing the places belong to and its keys the places (`braces.position.class`, `multiline.trailingComma.array`, `qualification.function.global`), or one thing several questions are asked of, the group naming the thing and its keys the questions (`classes.modifiers.order`, `file.strictTypes.position`). A requirement whose only name is that of the thing stands flat, its parameters beside it carrying its name and saying what they refine (`controlFlow.trailingIf` and `controlFlow.trailingIfMinStatements`): a group named after the thing would leave the requirement a word that says nothing (`max`, `level`). A group holds a parameter beside requirements with names of their own, or parameters alone where they are one question asked of several places (`spacing.alignment.comma`, `multiline.fillMinItems.array`). A section asking one question of many places has no group (`naming`, `casing`), and a path has four links at most. What a key means is read at first sight, which comes before every other rule of the path: a group is named by a noun, the thing or the question (`strictTypes`, `position`, `trailingComma`), never by an adjective, a participle or a phrase with a preposition, and where no noun reads well the keys stand flat however long (`braces.emptyBody`, `controlFlow.elseAfterReturn`). `keep` on a group keeps every key of it, and a word, a count, a flag or a list on a group is the value of each of its keys of a closed vocabulary (words, counts, flags) that takes it (`multiline.operatorPosition: lineStart`, `qualification.function: imported`), a list giving each key the words of it the key takes, never a text, a list of names, a map or an example; a word no key takes, one that among requirements only a parameter takes, a word of presence (`required`, `forbidden`, `optional`) that a requirement of the group does not take or that is given to a group naming one thing several decisions ask about (`Catalogue::QuestionGroups`, where it would read as one about the thing itself), `[]` and `{}`, a list leaving a requirement none of its words, `keep` or `...` in a list and any value but `keep` on a section are refused. A value a group gives a decision whose rule the target or the packages of the project leave out is skipped silently, as one of a preset (`ResolvedDecision::$cascaded`), while the decision written by its path warns. Where the keys of a group are places, a kind of places stands for all of its places at once (`lists`, `operators`, `blocks`, `Config\Catalogue::PlaceKinds`), a place the same map names winning over its kind, while a later layer replaces whatever its value covers. A key of a configuration is one link of the path, the links nested a key under the other, and `DecisionResolver` refuses a key holding a dot, so that a decision has one way to be written; the dotted path only names a decision (`fixRisky`, `--only`, `dresscode:ignore`, the messages, the name of a map in an upgrading file), and what is given as paths (the header of a fixture, `RuleBuilder::resolveValues()`) is placed into the tree by `Engine\Helpers::placeValue()`.

Where a thing has a shape for each of several places, each place is a key of its own (`braces.position.class: nextLine`, `naming.method: camelCase`), and a list of places stands where one shape holds for all of them. A place is singular, in a key as in a value, and one place has one word across the catalogue: `class`, `anonymousClass`, `function`, `anonymousFunction`, `arrowFunction`, `method`, `constant`, `property`, `propertyHook`, `variable`, `enumCase`, `parameter`, `argument`, `instantiation`, `array`, `list`, `matchArm`, `closureUse`, `import`, `trait`, `traitUse`, `controlStructure`, `branch`, `switchCase`, `catch`, `return`, `body`, and for what spreads over lines `attribute`, `matchCondition`, `for`, `implements`, `condition`, `chain`, `ternary` and the operators by their family (`logical`, `concatenation`, `arithmetic`, `bitwise`, `coalesce`, `comparison`, `pipe`), a qualifier standing in front of the word where no group names it (`anonymousClass`, `promotedProperty`). The places of one group do not overlap: a narrower place takes its members from the wider one (`interfaceMethod` the methods of an interface from `method`, `anonymousClass` the instantiation of an anonymous class from `instantiation`), so that every occurrence is decided by one key; the places of a group fall into the kinds of `Config\Catalogue::PlaceKinds`, `lists`, `operators` and `blocks`. A key relating places keeps the plural English asks for (`blankLines.aroundMethods`), and so does a list of names the project brings (`mistakes.debugOutputFunctions`). A construct spread over lines takes its shape on two axes, `multiline.items` (`perLine`, `fill`) and `multiline.edges` (`apart`, `attached`, `closingApart`), a value being one shape or a list of the shapes accepted, the first of which is written where DressCode spreads the construct and on the axis whose shape the author's construct does not pass; a construct on one line always passes and a spread one is never joined. Where a token stands is `sameLine` or `nextLine`, an operator at a break `lineStart` or `lineEnd`, so that a new rule speaks in the words a reader knows.

A decision has a description, the sentence `explain` and the reference print first: English, capitalized, no trailing period, and its code in backticks as in a message, which `explain` draws in color and the reference leaves to Markdown. It says what the thing is and what the rule does where the value is not `keep`, a hidden scope (`naming.class` also covers interfaces, traits and enums) and a hidden condition included; every word and shape of its domain says what it means, and a note says what the decision is not about, never an action the reader would learn only from it. The description names what the key names, in its polarity: of a presence the thing itself, never its absence (`A byte order mark at the start of the file`), what the fix makes of it following after a comma, and it begins with `Whether` exactly where the decision is a flag. A word several decisions share comes from `Catalogue::Lexicon`, and where the lexicon fixes its meaning (`required` is always there, `forbidden` never there) every gloss of it begins with that meaning, the decision adding a scope or an example; `catalogue.phpt` checks the core and `RuleTester` the rule of a plugin. Another decision is referred to by its path (`blankLines.afterOpeningTag`). The texts of the help of the command line take the form command-line tools write theirs in, capitalized and imperative and without a trailing period (`Report the violations`, `Fix what the rules can and report the rest`, `Treat a rule breaking its contract as an error, not a warning`), an option taking a value may begin with what the value is (`Configuration file; the nearest …`), and their code stands in backticks as in a description. The text is checked against the code, not against the docblock of the rule.

### Exceptions and warnings

An exception or a warning is read by someone who has to act, so it says where, what and what to do, in that order. Where is a prefix naming what the reader edits (`Configuration file X: `, `Upgrading file X: `, `Preset X: `, `The override for src/: `, `The command line: `), left out only when nothing but the command itself can be meant; what is a sentence about that thing, with the value the reader wrote or has to write; what to do follows after a semicolon, or as a second sentence when the first has one, and it is the only place an imperative may stand. A message the reader cannot act on, a broken rule or a failing worker, says whose fault it is instead. Every message is a capitalized sentence ending with a period, warnings included, `must` and never `has to`; a message wrapping another one puts it after a colon and adds nothing behind it, and what it wraps is left as its author wrote it.

Everything in such a message that is code stands in backticks, as in Markdown: a file and a path, a command and an option, a key of the configuration and a value (`` `x` given `` for a value refused), a decision, a preset, a package and the class of a rule, a class, a function, a member and an annotation (``Configuration file `dresscode.neon`: ``, ``set `typeAnalysis: phpstan` ``). A word that only speaks about code is not code (`the configuration`, `a preset`). The console draws what the backticks enclose in color and drops them; every other output, a pipe, a log of CI, the formats `json` and `github`, the reader of the PHP API, prints them as they are, which reads well to a human and to an agent alike. Where a page of the manual says more than the message, the exception carries the path of that page (`ConfigurationException::$docs`), and the console prints it under the message as a link to `https://dresscode.run/`. What the author of a plugin reads (`RuleInfo`, the claims, `RuleTester`) states the contract that was broken; what the user of a configuration reads never names an internal class, node or slot.

### Testing

`Testing\RuleTester` runs a rule over `*.code` fixtures (`.expected` output beside them, `.violations` as `line: message` with the risk of a risky one on an indented line below it, `risky <Risk>` with `: <because>` where the rule gives one, the values of its decisions in a `// {"json"}` comment, a key without its section taking the one section of the rule, over those of a `values.neon` beside the fixtures, a run that allows risky fixes in a `// risky` one, the code and the fixed code run under the CLI of PHP in a `// run` one, which must print the same and exit alike, the targeted version in a `// php 8.4` one, the types turned off in a `// types off` one, the widest line in a `// lineLength 80` one (120 without it; `check()` takes a whole `Style` instead, whose line ending stays that of the code) and what the namespaces declare outside the fixture in `// namespacedFunctions`, `// namespacedConstants` and `// nameResolution certain`, all in the comments that open the fixture; without a version the rule is tested at the version of PHP it requires, else at `Config::DefaultPhpVersion`, never at the version of the interpreter running the tests) and, given `analyses:` in the shape of `Config::$analyses`, registers those of a plugin for the rule, then checks the contract: parent invariant, idempotence over the output, comments preserved unless `modifiesComments`, `dresscode:ignoreFile` honored, no silent mutation.

`Testing\UpgradingTester` is for a package that ships upgrading files: `collectProblems($file, $root, $packageRules)` reads a file the way a run would, in the project whose vendor holds the library, the rules the package ships itself known besides those of DressCode, and gives back sentences. A key under `extra.dresscode` of the nearest `composer.json` at or above the file that `PackageDiscovery` does not read is a problem too (a run only warns of it, the package may be newer than the tool). Every section, reached or not, has to be what the grammars of its maps accept, and what the sections come to at the installed version has to replace, in `replacedClasses` and `replacedMembers` and by a static method in `replacedFunctions`, by classes, members and methods that exist, asked of the loaded code (a function of a library is declared by a file loaded with its first use, so it is not looked up); the other maps are held to their grammar alone. A replacement the file replaces in its turn (`REALPATH`, then `Realpath`, then `RealPath`) is followed to its end, the way the passes of a run follow it, and one that leads back to where it started is a problem; an entry withdrawn with `keep` is thereby not checked, and one whose withdrawal was forgotten shows as a replacement that does not exist. What is replaced is not looked up, a library having usually removed it. The sentence of a `forbidden…` map is read as the end of the message it completes: in lower case unless it begins with a name, with its code in backticks, with no period, double quote or "should", and at most 160 characters, the backticks not counted; an entry of a `forbidden…` map that gives none (a project may leave it out) is a problem in the data of a package. `runSample($code, $root, $decisions)` is the other half: code written for the old API as the decisions given fix and report it, every section the installed version reaches applying, whatever the constraint of the project allows, the types taken from the PHPStan of the project, which reads the code from `temp/` of the root, and no result cache; it gives the `FileResult`, so that a package tests its data without reaching for the `@internal` factory of the run.

The fixtures of every rule run again under each standard with the sets beside it (`robustness.phpt`), which no fixture of one rule tries: the run must not fail, write code that does not parse or fail to settle, whatever the other rules make of the code. What no fixture catches, the runs over the corpus do: the whitespace fuzz damages the whitespace of a fixed file and requires the fixer to come back to it, and `name-meaning.phpt` runs the rules that write names and imports over the corpus and requires every name outside the imports to resolve to what it resolved to before, because an import moved into a statement writing its items differently, or dropped while something still uses it, leaves code that parses and round-trips and says nothing else.
