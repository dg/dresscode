# DressCode internals

How the syntax layer works: the facts an agent or a contributor needs before touching the lexer, the grammar, the nodes or the mutation API. Catalogs of nodes and rules are not here; they are generated from `grammar/nodes.php` and from the rules themselves.

## Layers

- `PhpSyntax` (`src/PhpSyntax/`): lexer, parser, tree, printer, navigation, mutation. It has no dependencies and never imports `DressCode\`, Nette, php-parser or anything from `vendor/`; a PHPStan rule (`LayerBoundaryRule`) enforces it.
- `DressCode` (`src/DressCode/`): engine, rules API, rules, configuration, CLI. Rules use only the public API of `PhpSyntax`; whatever a built-in rule needs from it is public API for plugins too.

## Tokens and trivia

The lexer (`PhpSyntax\Lexer\Lexer`) turns `PhpToken::tokenize()` output into significant tokens; whitespace, comments and open tags become `Trivia` attached to tokens:

- **Trailing trivia** of a token is everything after it up to and including the first end of line. **Leading trivia** of the next token is everything else (blank lines, indentation, comments on their own lines, doc comments). Whitespace is split into `Whitespace` runs and single `EndOfLine` pieces (`"\n"`, `"\r\n"` or a lone `"\r"`), so the leading trivia of a token starting a line looks like `[..., EndOfLine, Whitespace]`.
- Exceptions: an `OpenTag` trivia (`<?php` with its mandatory whitespace) is always leading trivia of the following token, and everything after it too; the final `EndOfFile` token has only leading trivia, never trailing; a token whose text ends with a newline (`CloseTag`, a heredoc start) ends its line the same way an `EndOfLine` does.
- `<?php` is not a token. `?>` is a token of kind `CloseTag` that keeps the newline PHP swallows after it, and the parser sees it as `;`; after a terminated statement it forms an `EmptyStatementNode`. `<?=` is a token of kind `OpenTagWithEcho` seen as `echo`. `Token::isSemicolon()` and `isOpenTagWithEcho()` cover these cases.
- Whitespace that PHP counts as part of a token stays in its text: inline HTML, `T_ENCAPSED_AND_WHITESPACE`, heredoc delimiters (the closing one keeps its indentation), casts like `( int )`.
- Trivia inside string interpolation (`"{$a /* c */ }"`) carry `inInterpolation = true`; the token helpers refuse to change them because that whitespace is part of the string value.
- A BOM or a hashbang line is inline HTML, as PHP sees it. A single-line comment never contains its newline, but it does contain trailing spaces before it.
- Token ids differ between PHP builds; `TokenKind::HostConstants` maps them by constant name. Syntax of PHP 8.4 and 8.5 on an older runtime is emulated by rewriting the raw token stream (`Lexer\Emulators`).

## Round trip

`Printer::print(parse($code)) === $code` byte for byte for any input PHP accepts, including BOM, hashbang, CR/CRLF, close tags, inline HTML and `__halt_compiler()` data. It is the invariant every change to the lexer, the grammar, the nodes or the printer must keep; the tests run it over the committed corpus (`tests/PhpSyntax/Parser/corpus/`) and, with `DRESSCODE_CORPUS` set, over an external tree. Formatting rules change trivia, structural rules change nodes; the printer is a concatenation and has no logic of its own.

## Parser and generated files

The parser is an LALR(1) driver over tables generated by phpyacc from `grammar/php.y`, a fork of the nikic/php-parser grammar with the PHP 7 branch and the error-recovery productions removed. Productions are never changed, only their semantic actions. `composer build` regenerates `src/PhpSyntax/Parser/ParserData.php`, `src/PhpSyntax/TokenKind.php` and the node classes in `src/PhpSyntax/Nodes/**` from `grammar/php.y` and `grammar/nodes.php`; the output is committed and CI checks that it is up to date. Every generated file says so with `@generated` in its header, which is how the node generator tells its own stale output from the handwritten classes it leaves alone, and how the check of this project leaves generated code out (`tools/SkipGenerated`); handwritten classes therefore live in `Nodes/` next to the generated ones without any path having to name them.

- Every grammar alternative with two or more symbols must have an action that uses every symbol, otherwise tokens would drop out of the tree; the build fails on such an alternative. A single symbol passes through, an empty alternative yields `null`.
- Actions may put plain arrays of slot values on the value stack (tails of alternative syntax, optional pairs such as `: type`); they are spread into the node constructor and never leave the parser.
- After parsing, statements following `namespace A;` are nested into that `NamespaceNode`, so every namespace has its statements as children; only `__halt_compiler()` stays outside.
- The data after `__halt_compiler();` is a token in `HaltCompilerNode::$data`.
- `Parser::parseExpression()`, `parseStatement()`, `parseType()` and `parseName()` parse a fragment inside a helper file and return the node detached, with empty trivia on its edges and without original positions. Plugins build new nodes this way; node constructors are `@internal`.

## Tree

- Every node class ends with `Node`; slots are named by role (`ifKeyword`, `openParen`, `semicolon`, `cond`, `body`), paired delimiters are always `open*`/`close*`. Every token of the source has a slot or a place in a list, so the order and number of children are not part of the API, only the slot names.
- Lists: `NodeList<T>` (statements, members, attribute groups) and `SeparatedNodeList<T>` (parameters, arguments, items, imports) with separator tokens between items and an optional trailing separator; `EmptyArrayItemNode` stands for nothing between two commas of a destructuring list. `ModifiersNode` holds modifier tokens in source order.
- The body of a control structure is a `StatementNode`, not necessarily a block; `else if` is an `ElseNode` whose body is an `IfNode`. The alternative syntax uses the same classes with `colon`, `stmts`, `endKeyword` and `semicolon` slots instead of `body`.
- Scalars keep their raw text (`IntegerNode::$token->text` is `0x1F`). Operators are one `BinaryNode`, `UnaryNode`, `PostfixNode`, `AssignNode` or `CastNode` with the operator token; names are one `NameNode` with a token of any kind, including keywords the grammar accepts as names.
- Class-like declarations (`ClassNode`, `InterfaceNode`, `TraitNode`, `EnumNode`, `AnonymousClassNode`) implement the `ClassLikeNode` interface, because an anonymous class is not a statement.

## Parents, mutation and the index

- A node or token belongs to exactly one tree: `$parent` is set by the parser and by the mutation API, and inserting a node that already has a parent throws; `clone` gives a deep copy without a parent.
- Slots are public but written only through the generated setters (`setCond()`, `replaceChild()`), which move parents and invalidate the index; `NodeSlotWriteRule` forbids direct writes outside the tree implementation. Lists mutate through `append()`, `insert()`, `removeItem()`, `replaceChild()`; `SeparatedNodeList::insert()` derives a missing separator from the existing ones (or `", "` in a one-line list) and gives the item the indentation of its neighbor in a multi-line list, `removeItem()` takes the separator after the item, or before the last one.
- `Node::remove()` removes a list item: a node alone on its lines takes the lines with it, otherwise the whitespace around stays; comments inside, each with the line ending after it, go to the next token, the previous token, or away, as the `CommentPolicy` says. `Node::replaceWith()` keeps the trivia around the old node around the new one by joining them with the new node's own edge trivia; a replacement cloned from nearby source still carries its original leading trivia, so clear the clone's edges first or an `OpenTag` gets doubled.
- The text and trivia of a token are written only through `setText()`, `setLeadingTrivia()` and `setTrailingTrivia()`, the same way slots are written through the setters of nodes; `TreeWriteRule` enforces both outside the tree implementation; the lexer and the parser go through the setters too, on tokens that are not in a file yet, which costs nothing. The setters are what keeps the index right: `FileNode` owns the `TokenIndex` (order, previous/next token, offset, line, column, visual column) built lazily and kept up to date rather than rebuilt. A structural change reports the children it adopted and released and, once complete, `structureChanged()`, and the index moves their tokens; a token setter reports `tokenChanged()` with the line endings the token gained or lost, and the lines before the token stay as they are; only offsets and columns are recomputed from scratch. The numbering and the lines of the tokens after a change are brought up to date lazily, as far as the queries reach, so the cost of a mutation followed by a query nearby is proportional to the distance, not to the file. A tree changed behind the back of the index is a `LogicException` at the next mutation, not a slow path. Every mutation increments `FileNode::$revision`, which the engine reads to detect mutations. A token carries its index and the index that numbered it (`Token::$index`, `Token::$indexedBy`, both `@internal`), which is how navigation finds the file without walking the parents; the shortcut is verified against the index before use, so a token moved to another tree falls back to the parents. Navigation from a detached subtree returns `null`.
- `Token::$originalLine` and `$originalOffset` never change and are the source of positions in reports; `getLine()` and `getColumn()` follow mutations.
- `Node::getChildren()` is the generated list of the children in source order, empty slots left out, and the only way to the children: a node is not iterable, so that there is one way and it is an array, which the printer, the index, the traverser and `attach()` read directly. `Node::getDescendants()` is a snapshot safe to iterate while mutating; the `Traverser` walks in pre-order, does not descend into a replaced node, skips siblings detached meanwhile and leaves inserted ones for the next walk.
