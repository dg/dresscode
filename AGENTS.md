# To My Agents!

It is my fervent wish that this file guide every AI coding agent working with code in this repository.


## Documentation

`docs/internals.md` is the source of truth for how DressCode works: the tree as a rule sees it, the mutation API, the engine of gaps, the rules and the interop. Read it before any non-trivial change.

## Project overview

DressCode is a PHP code style checker and fixer built on a **lossless concrete syntax tree**: every token of the source is in the tree, whitespace and comments are trivia attached to tokens, and printing the tree reproduces the input byte for byte.

The tree itself is the `phpsyntax/phpsyntax` library (namespace `PhpSyntax`), developed in a repository of its own. This one holds `DressCode` (`src/`): engine, rules API, the library of generic rules, configuration, CLI. The names of other tools live only in `Interop/`, never in a rule.

Rules use only the public API of `PhpSyntax`; whatever a rule in DressCode needs from it is public API for plugins too. What the rules only share among themselves (`Rules\NodeHelpers`, `Rules\Compiler` and the helpers beside the rules that carry `@internal`) is `@internal`; the grammar of a map of members (`Rules\Upgrading\MemberMapGrammar`, the map itself `MemberMap` with `findAccess()` and its `MapMatch`, `MemberPattern`, `ArgumentPattern`, `FunctionPattern`) is not, a rule shipped by a package being fed the same way, and neither is `Rules\GlobalCalls`, which answers which global function a call calls and why that may be another one, nor `Rules\CodeWriter`, which writes code in the shape of the file (a class written the way the file reaches it, an import added the way the file writes its imports) for a rule of a package as for one of the core. Presets define style; DressCode has no style of its own. The four standards carry one: `dresscode/perCs` (PER Coding Style 3.1), `dresscode/psr12`, `dresscode/nette` (the Nette Coding Standard, PER with tabs, the layout of the Nette libraries and their departures, which the repository itself is checked with) and `dresscode/symfony`. What a project wants beyond the looks of its code comes in a set, a preset of one intent that decides nothing about the layout and is used beside the standard (`modernizations`, `deprecations`, `cleanup`, `correctness`, `types`, `compilerOptimizations`); a decision the core gains goes into its set, one that writes a newer construct and the replacement of what PHP deprecated alike into every set whose intent it meets (`upgrading.syntax.firstClassCallables` in `modernizations` and `deprecations`), and what no set holds the project decides itself.

## Essential commands

- `composer tester`: Nette Tester over `tests/`.
- `composer phpstan`: PHPStan level 8, no baseline; `ignoreErrors` only with a reason.
- `composer reference`: regenerates `docs/reference/decisions.md` (every decision with its values, the values of the standards and the rules declaring it) from the catalogue. Commit the output; CI diffs it.
- `composer api`: regenerates `docs/reference/api.md`, the public classes and members as reflection sees them. Commit the output and read its diff, which is what a change does to the public surface; CI diffs it.
- `php bin/dresscode check`: DressCode over its own sources with `dresscode.neon`; CI runs it too.
- `php bin/dresscode init` in the root of another project: writes the `dresscode.neon` measured from its code, or prints it when a configuration exists; how it measures is in `docs/internals.md`.

## Conventions

- Nette coding standard: tabs, `declare(strict_types=1)`, single quotes, types everywhere, two blank lines between methods.
- Modern PHP: `match` instead of `switch`, enums, `readonly`, promoted properties, named arguments, `never`.
- Naming:
  - methods are actions and start with a verb (`getFirstToken()`, `replaceChild()`, `report()`); a bare noun is not a method name, except a static factory named after the value it makes (`Claim::nextLine()`, `Domain::state()`, `ArgumentPattern::any()`) and the established idiom `Gap::once()`;
  - `get*` returns something that belongs to the object (may be `null`), `find*` searches and `null` means not found;
  - of the methods that give code to write, `write*` may change the file on the way, adding the import the code needs (`CodeWriter::writeClass()`), and `spell*` only answers (`CodeWriter::spellFunction()`);
  - a setter, a method whose only job is to write one value, returns `static` so that writes chain, as the setters of PhpSyntax do (`$token->setText('+=')->setTrailingSpace(' ')`); a method that decides what to change, such as `ensureStartsLine()` or `removeTrailingWhitespace()`, returns `void`;
  - boolean queries `is*`/`has*`/`can*`, or a verb in the third person where the question is what the subject does (`matches()`, `startsLine()`, `takesRest()`), and `is*` also where the code may not settle the answer and the query returns a `Tristate`, as PHPStan names those returning its `TrinaryLogic` (such an answer is compared with `=== Tristate::Yes` or taken apart by `match`, an enum being always true); never `check*`, which is the name of a method that answers nothing and raises the problem itself, by throwing or by reporting; a boolean property is named by the state itself (`$active`), never `$isActive`, and one read from a decision may carry the name of the decision where it says that the decision holds (`$parameter` of `types.declaration.parameter`), never where it says the opposite or another thing of the same name stands beside it (`$singlelineClosureKept`, `$fixesSignature`);
  - rule classes end with `Rule`, analyses carry bare names in `Analyses/`;
  - a gap rule names the slots it claims as strings (`'openParen'`, `'statements:item'`), which no type checks, so a claim on a slot that is gone shows up only in the fixture of the rule; the names are in the node reference of PhpSyntax;
  - no `Abstract`, `Interface`, `I` prefixes/suffixes; an interface or base class sits next to the directory of its implementations (`Rule.php` next to `Rules/`);
  - enums of a namespace live in `enums.php`, exceptions in `exceptions.php`;
  - names of the API are written in full, the slots of PhpSyntax a claim names among them (`expression`, `condition`, `statements`, `arguments`, `parameters`, `variable`); the abbreviations left there are `paren` in `openParen`/`closeParen`, the delimiter having no one-word English name, and `Op` in `BinaryOpNode` and its kin, which names the family across PHP tooling. A local variable may be abbreviated and often reads better for it (`$stmts`, `$args`, `$params`).
- A rule is known by its class, which no user writes, and the name of the class, read without `Rule` and with its first letter in lower case (`BracesPositionRule` is `bracesPosition`), says the state the rule enforces, never the step the fixer takes, and follows one vocabulary; `tests/DressCode/Rules/naming.phpt` enforces it. A name is built in the shape of its kind: a **decision** is the noun of the construct and the rule gives it a value (`bracesPosition`, `lineLength`, `trailingComma`), **hygiene** is a sentence of state and the rule has nothing to choose (`uselessElse`, `parenthesesSpacing`), a **policy** is the area it governs and the project brings the list, `forbidden…` for what may not be there and `replaced…` for what is written instead (`forbiddenFunctions`, `replacedClasses`). A bare noun therefore belongs only to a rule with a value to give. Its words are those of camelCase, `phpdoc`, `eof`, `inheritdoc`, `elseif`, `multiline` and `singleline` being one word each and the name of a function of PHP the words it has (`mbConvertEncoding` is three); three words are fine, more than five never:
  - `no…` is a construct that must not appear at all (`noGlobalStatements`), `useless…` one that is legal and right elsewhere but adds nothing here (`uselessElse`); an empty instance is always `no…`; `noManual<Thing>` is the shape for code doing by hand what one call does (`noManualSubstringTests`, `noManualListTests`), where the several forms it reads have nothing else in common to name;
  - `no…` is plural where what it forbids can be counted (`noEmptyComments`, `noHashComments`), singular where it cannot or is the name of a function or a keyword (`noBom`, `noIsNull`), and `noClosingTag` stays singular because a file has at most one closing `?>` the rule is about;
  - `<construct>For<Situation>` is the construct written where an older one said the same (`matchForSwitch`, `selfForCurrentClass`), the shape of most modernizations; the construct comes first because it is what the rule writes, and the situation names the old construct by its shortest established name, leaving out the conditions that only guard when the rule may act, as long as the name stays clear (`ternaryForIf`, not `ternaryForSimpleBranch`);
  - horizontal space is `<construct>Spacing`, vertical blank lines `<construct>BlankLines`, indentation `<construct>Indentation`;
  - `Multiline<Construct>` is where the construct breaks over lines, the section `multiline` (`multilineCall`, `multilineArray`); `<construct>Position` is where a thing stands (`bracesPosition`), `<construct>Alignment` how it is aligned (`phpdocAlignment`);
  - `multiline` and `singleline` are one word, in the names of rules, paths and values as in code (`MultilineCallRule`, `braces.position.multilineSignature`, `$singleline`), except where a library spells them otherwise (`Node::isMultiLine()` of PhpSyntax, the sniffs of other tools);
  - `phpdoc` is the whole block, `annotation` a single tag; `parameter` is declared, `argument` is passed; a backslash is `backslash`;
  - canonical spelling is `…Notation` or `…Canonical…`, canonical case `…Casing`; `…Notation` also names the one form a whole family is written in, where the rule reads several inputs and writes one construct (`callableNotation`, `roundingModeNotation`); something that must be present is `…Required`.
- What a user writes is the path of a decision, `section.key`, deeper through a group (`multiline.trailingComma.array`), which stands where several places answer one question or several questions are asked of one thing, a requirement with its parameters among them (`file.lineLength.max`, `file.lineLength.except`), four links at most and the rule in `docs/internals.md`, every link camelCase or the name PHP gives the thing (`cleanup.is_null`, `correctness.__set_state`). The sections of the core are the closed list of `Config\Catalogue::CoreSections`, a plugin decides under the section of its manifest, named after it, and a rule of the project under `project`; a section is for the reader to find the key and nothing of how a decision behaves follows from it. A key names the thing in the code, by the name of the family where several share it (`upgrading.functions.arrayFirstLast`), and its value says how the thing is written: a word, a shape with its word and an example (`spacing.call: compact` or `"foo($a, $b)"`, the code and the data writing the word), a count, a list, a map, or `keep`, which every requirement takes, a map for each of its entries and never as a whole. In the sections of the style a key with several shapes names them (`sameLine`, `nextLine`), a key with `forbidden` or `required` has no second shape to choose; under `upgrading` `adopted` writes a construct a newer PHP gave and `forbidden` the replacement of what PHP deprecated. A key that only refines another one is a parameter, with a default and no `keep`, so that it never turns a rule on by itself (`controlFlow.trailingIfMinStatements`). A place is singular and has one word across the catalogue (`class`, `method`, `parameter`, `argument`, `arrowFunction`, `matchArm`, the full list in `docs/internals.md`). A decision has a description, every word and shape of it says what it means, and a note says what it is not about, never an action of its own; `tests/DressCode/Rules/catalogue.phpt` checks the catalogue.
- A decision of one rule is declared by that rule in `getDecisions()`; one several rules share, or one the engine reads, is declared by the decisions of the manifest, `CorePlugin` for the core, and each rule taking it names its path in `RuleInfo::$decisions`. A rule is cut by its logic: one carrying constructs with nothing in common to share is several rules, which a decision of the tree turns on together.
- The version a rule needs is metadata, never a directory: a rule lives with the topic it is about and says with the `php` it requires which version gave it its construct, which is what the index by version of `docs/reference/decisions.md` reads.
- The directory of a rule is the most encompassing of the topics it could belong to, not a criterion: none exists that would hold for the whole catalogue, and a reader finds a decision by its section, never by the directory of its rule. What each one holds: `Arrays` the array and its brackets, `Classes` the shape and the design of a class-like declaration, `Comments` the syntax of a comment, `ControlFlow` the statements that branch and loop, `Expressions` the operators, `Files` the file as a text, `Functions` a function and a call of one, `Literals` a string, a number and a keyword as they are written, `Namespaces` the imports and the writing of names, `PhpDoc` the doc comment, `Types` a native type declaration, `Upgrading` a rule whose subject is a catalogue, `Variables` `isset`, `unset`, `global` and the assignment to a variable, `Whitespace` the layout of lines and the punctuation belonging to no single construct.
- `Upgrading` is the one directory named after no construct, because its rules are about none: what they look for is decided by a map the project or a package gives them (`Replaced…Rule`, `Forbidden…Rule`, `AttributeForAnnotationRule`, `AttributeForMemberRule`, whose helpers are the grammar of those maps), by what a declaration of the code deprecates, except what those maps rewrite (`NoDeprecatedClassesRule`, `NoDeprecatedMembersRule`) or by the upgrading data of PHP, written in the same grammar (`NoDeprecatedPhpCallsRule`, `src/Rules/Upgrading/php.neon`). A rule asking what PHP declares about its own construct is not one of them and stays with the construct (`RedundantArgumentsRule`).
- A preset is a file of the shape of a configuration in `src/Presets/`, named in the manifest of the plugin that brings it (`dresscode/nette` is `nette.neon`). It opens with a comment, its title on the first line and what it is under it, then `use`, `suppressionComments` where it has them, and the sections of its decisions in the order of the sections of the core, leaving out a value its parents already give. What a decision does, where its key and value do not say it, is said briefly after the value, an example rather than words (`is_null: forbidden   # `$x === null``), three spaces from the value and aligned within its block; a key and a value that say it all get no comment, and a comment above the keys is for what covers several of them or does not fit the line. The rules run in the order of their registration, whatever order a preset writes the decisions in.
- A rule is never left out of the catalogue because another tool already does it. What leaves one out is a reason about the rule itself: there is no canonical form to write because the choice belongs to the project (then it may still be a value of a rule, or a policy whose list the project brings), there is nothing in the run to decide it from (then it waits for the analysis that would decide it), or it would repeat, less precisely, what the analyzer of the project already reports.
- Comments only where the code itself is not enough; never restate what the code shows; density follows the surrounding file. No phpDoc for what the types already say.
- Code in a doc comment is written in backticks: a call, a variable or a property, an operator, a keyword, a literal, the case of an enum (`report()`, `$this`, `?->`, `static`, `'*'`, `Severity::Warning`). Doc comments are read as Markdown in an IDE, and what stands bare there is typeset as text: `->` becomes an arrow, `...` an ellipsis. Backticks mark the code itself, so what only resembles code stays bare, whatever the IDE makes of it: a keyword used as a word (a static method, a readonly class, but a `match` expression), `null`, `true` and `false` in "null when …", and the `=>` describing a map (path => its size).
- A framework or library is named in the core only where it is the subject of the code (its preset, its interop, a dependency, a file or key another tool defines). An example of a general mechanism uses invented names under the vendor `Acme`, in a domain of their own that mirrors no real API (`Acme\Shop\Order::STATUS_PAID`, `Acme\Mail\SmtpTransport`).
- Code, comments, identifiers and messages in English.
- A string a `.neon` file has to quote is written in single quotes (`call: 'foo($a, $b)'`), double quotes only where it needs an escape or holds a single quote.

## Working rules

- Every unit of work (class, rule) ends with tests, PHPStan and a critical review of correctness, clarity, elegance and names. Fix findings immediately, not in a later commit.
- One commit per unit, message lowercase, past tense, `subject: description` when it clarifies the area. Linear history.
- Committed files, commit messages and code comments never refer to documents outside the repository, nor to transient states of the work (milestones, phases, "until X exists"). Describe the current state; the history is in git.

## Traps

- `<?php` is not a token but `OpenTag` trivia carrying its whole text including the mandatory whitespace; it is always leading trivia of the following token.
- `?>` is a `CloseTag` token that keeps the newline PHP swallows after it; after a terminated statement it forms its own `EmptyStatementNode`.
- Trivia inside string interpolation (`"{$a /* c */}"`) carry `inInterpolation` and must never be reformatted.
- Whitespace that is part of a token stays in its text: inline HTML, heredoc delimiters, `( int )` casts, `T_ENCAPSED_AND_WHITESPACE`.
- A rule mutates only after `$context->report()` returned `true`; a mutation without a report or after a suppressed one is a broken contract that `RuleTester` and `--strict-rules` turn into an error. The other way round does not hold: a rule that cannot fix what it found reports and leaves the code alone, and the last round of the fix reports it again, which is how the run knows it remains. An occurrence the rule has no fix for is reported with `fixable: false`: such a report is never risky, so it is never offered to the consent, and a report without it that the last pass, which changed nothing, makes again breaks the contract, so the fixture in which it remains fails. An occurrence whose fix may change what the code does is reported with `risk:` and the `Risk` that would decide it (`TypeUnknown`, `NameUncertain`, `BehaviorChanges`), with `because:` where the risk alone does not say what may go wrong there, never glued to the message, and such a fix is made only for a decision the project names in `fixRisky` or with `--fix-risky`; a rule that knows its fix would be wrong, a loop over a `\Generator` declared in sight, says nothing at all; risky covers a changed behaviour and never a fix that may produce code PHP refuses to compile, which is what a fix decided by a file the project need not know of does: there the rule says nothing at all (`ReadonlyClassForReadonlyPropertiesRule` marks only a final class, a child of a non-final one being a fatal error and not a behaviour), while a child of an `@internal` class lives in the project itself, so `FinalForInternalClassRule` is risky; a fixture with `// risky` in its header is a run that allows it, and it is what the reference reads to say a decision has such a fix. Every rule ships with fixtures under `tests/DressCode/Rules/fixtures/<slug>/`; `tests/DressCode/Rules/rules.phpt` picks the directory up by itself, a rule needs no test file of its own.
- A rule for a construct PHP gained in some version says so with `requires: ['php' => '>=8.4']` in its `#[RuleInfo]`, the key and the operator being those of the `require` of `composer.json`, the true version even at or below the floor of 8.0 (`str_contains()` is 8.0, an arrow function 7.4), and nothing older than 7.0, where no reader asks any more whether the code knows the construct (`[]` for `array()`, `?:`); the resolver leaves the rule out below that version, so a preset never has to guard it and `--only` cannot break the code, and a target never falls under the floor, so a version there never turns anything off. PHP 8.0 is the floor: never ask whether the target has something 8.0 already had. A rule whose version decides what it may write, not whether it runs at all, reads `RuleContext::$phpVersion` and compares the string with `version_compare()`, never with the string operators. The version in `requires` and the one read from `RuleContext::$phpVersion` say since when the fix is right, never since when the code it replaces is a problem: the target is the oldest version the code runs on, not the newest, so the upgrading data of PHP remove `curl_close()` only where every version of the target has made it a no-op, while a rule about a deprecation whose replacement older versions know too asks no version at all, the code meeting the deprecation wherever it runs on a later one. A fix naming a class of PHP needs the version that declares it, though older ones parse the name: `OverrideAttributeRequiredRule` writes `#[\Override]` from 8.3 on. A package goes into `requires` the same way (`'acme/mailer' => '>=3.3'`, `'>=3.3 <5.0'` for what a later version took away, or `'*'` for being there at all), a Composer constraint and never a single version, and the rule runs where every version the constraint of the project allows satisfies it, not the installed one alone, for the same reason the target of PHP is. A fixture is tested at the version of PHP its rule requires unless it says otherwise with `// php 8.2` next to the values in its header. A rule that makes no sense without the types of the code says so with `typesRequired` and the resolver leaves it out where the configuration sets no `typeAnalysis: phpstan` (silently from a preset or the data of a package, a `ConfigurationException` when the project wrote its decisions); a rule that would only do better with them asks `RuleContext::findAnalysis()`, which answers null where the run has none, or does without, and says in its docblock what it then cannot see. Every analysis a rule asks for, through a helper it calls too, is named in `analyses` of its `#[RuleInfo]`, `Analyses\Types` among them where it requires the types, and the strict run of the fixtures refuses one it does not name. The types come from the `phpstan/phpstan` of the project and hold for the text of the pass at its first question (`Analyses\PassAnalysis`); a rule asks `findMember()`, `findDeprecation()` and, for what no other question covers, `isOfType()`, the types in the words of PHPStan staying inside the analysis. The fixtures of such a rule get their declarations from a `stubs` directory beside them.
- A violation is positioned at the token it was reported on; a problem in whitespace or a comment is reported with the trivia (`report($token, $message, trivia: $trivia)`), whose `line` the lexer stamped, otherwise it lands on the token's line and `dresscode:ignore` on the real line would not match it.
- A value is checked and normalized by the `Domain` of its decision when the layers are resolved, and a rule reads the values in `configure()` from `Values`, never from an array of its own; a list given replaces the one below it, its default included. The maps of `upgrading.libraries` (`replacedClasses`, `replacedFunctions`, `replacedMembers`, `replacedCalls`, `forbiddenClasses`, `forbiddenMembers`, `forbiddenFunctions`, `attributeForAnnotation`, `attributeForMember`) and the map of a rule a package ships that reads the same grammar are also fed by the upgrading data of the installed packages (`Config\PackageDiscovery`, the `upgrading.neon` a package ships under `extra.dresscode.upgrading`), which lie under every layer and never turn a rule on themselves, `upgrading.libraries.packages: adopted`, which both sets `deprecations` and `modernizations` say, lays them under the maps of the project; the maps of members share their keys (`Rules\Upgrading\MemberPattern`, `MemberMapGrammar`), and `Testing\UpgradingTester` checks such a file against the installed library.
- Nodes are matched by `instanceof`: `StatementNode::class` in `getVisitedNodes()` catches every statement. A `match` over node classes in a rule needs a `default` arm, because new node classes may appear in a minor release; `composer phpstan` reports a missing one as `match.unhandled`.
- A slot of a node is written by assignment (`$node->condition = $expression`): its set hook moves the parents and tells the index. The text and the trivia of a token are written by `setText()`, `setLeadingTrivia()` and `setTrailingTrivia()`, because `?->` cannot stand on the left of an assignment. A property is written where the write takes one value and has one consequence, a method where it takes more or where two things change together (`StringNode::setValue($value, ?$quote)`). What has no hook the language guards instead: the items of a list are its own storage and change only through the methods of the list, and `parent` is written by the nodes when they adopt or release a child.
- `Node::getChildren()` is the only way to the children and `Node::find()` (a class, optionally narrowed by a predicate) to the descendants; a node is not iterable, except a list (`NodeList`, plain or separated), which is read as a collection of its items, and `ModifiersNode` over its tokens, and a child is never replaced by assigning to it: `replaceWith()` or the setter of the parent, which the `Traverser` notices and skips the replaced node.
- What a rule may write depends on where the expression stands, which the shape of the expression does not say: a call gives a value and never the place `unset()` and an assignment need, `self`, `parent` and `static` are resolved where a first-class callable is made and not where a closure is called, and PHP refuses a first-class callable made anywhere in a nullsafe chain; a partial application of PHP 8.6 evaluates its arguments and its object once, when it is made, where the closure it replaces evaluated them at every call. A fixture shows the shape; the context is what the corpus run finds.
- A rule replaces the node it was given, or something inside it, never an ancestor of it. The walk notices a replaced node by its parent, and an ancestor taken out leaves that parent as it was: the rest of the chain and the whole subtree go on being visited outside the file, where `getAnalysis()` throws. `!is_null($x)` is rewritten where the negation stands, not where the call does.
- `FileNode::$revision` is a version of the tree, not a count of mutations: a compound mutation such as `remove()` moves trivia in several steps and increments it several times. Compare it, never count on it.
- What a rule gathers from the whole file before it rewrites (the names the imports reach, the occurrences a loop goes through) is gathered before the first mutation; gathered lazily, it reads a tree the loop has already changed.
- A mutation must keep the trivia canonical: the line ending that ends the line of a token belongs to that token's trailing trivia, never to the leading trivia of the next one. A misplaced one makes `getTrailingSpace()` and the whitespace rules blind to the line break; `ensureStartsLine()` and `setBlankLinesBefore()` place it correctly, so build on them.
- The whitespace between two tokens is nobody's to write: a `GapRule` claims what the gap must be (`Claim`: the `Space` of a line, the `Line` the second token stands on, the blank lines above and below a comment in the gap), the engine decides, fixes and reports under the decision of the claim, and two plain claims on one component of one side of a slot are a `ConfigurationException`. So is a claim on a slot no node has: the gaps of a slot renamed in the tree would otherwise never reach the rule and turn it off in silence, so a claim names the class that really has the slot, and `:item` or `:separator` only a slot holding a list. A rule builds its claims from its values once in `configure()`, not at every gap. A closure gets the `Gap` and must give every gap of a construct the same answer whatever the engine did to the gaps before it: a decision read from the shape of the code (a list already broken, a line too long) goes through `Gap::once()`, which keeps it for the pass.
- A rule that must not destroy a comment asks `Token::hasComment()`, `Token::hasCommentUpTo()` or removes one with `Token::removeTrivia()`; `Node::matches()` and `ExpressionNode::isRepeatableRead()` answer "does this expression repeat that one safely". Do not reimplement these locally.
- PHPStan analyzes all the tests at once, so a global function or constant in a `.phpt` collides with one of the same name in another test; name them after the test. And the file system of Windows ignores the case of letters: `Config/catalogue.phpt` overwrites `Config/Catalogue.phpt`, so check a new file beside an existing one by its name in any case.
